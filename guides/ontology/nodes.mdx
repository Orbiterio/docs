Node types of the Orbiter Universe graph, organized by logical group. Each section states what the **Universe Go writers** in `orbiter-universe/internal/platform/graph` write today: the MERGE pattern and key, the labels as they appear in the pattern or are added with `SET`, and the properties set explicitly or fanned out from the node's property envelope.

<Note>
  **Synchronized with the orbiter-universe checkout on 2026-09-13** (branch `ORBIT-1879/video-game-waterfall`). Every label, key and property below is what the Go writers produce. Game and theatre contract tables are kept as locked design references with their implementation status marked.
</Note>

<Info>
  Each section opens with a <Icon icon="play" /> writer card naming the Go file and the MERGE pattern. Envelope properties pass through `propertyFanOut` (`graph.go:148-202`), which drops empty values and any key in the reserved set `uuid`, `name`, `name_embedding`, `embeddings`, `description`, `created_at`, `updated_at`, `flag`, `entity_type`, `entity_id`; those are only ever set explicitly by the builder. Every vector-bearing node also carries `embedding_model` and `embedding_dimensions`. All timestamps are Cypher `timestamp()` epoch milliseconds: `created_at` ON CREATE, `updated_at` on every write.
</Info>

</Card>

## Video game nodes — Go contract

<Info>
**Synchronized September 9, 2026.** This is the node reference for the [Go/GCP video-game build plan](/guides/open-work/video-game-waterfall), including the [locked Game_Platform properties](#game-platform-properties). Game runtime registration and writers remain proposed. The [real-data simulation](/guides/open-work/video-game-waterfall-examples) contains **29 nodes and 30 edges**, with real names/source IDs and simulated internal UUIDs and processing state. It is not a production graph snapshot.
</Info>

<Card icon="play">

```
internal/platform/graph/game.go · game_support.go · game_series.go · game_platform.go · game_engine.go · game_release.go · game_award.go
```

**Universe writers, as implemented (audited 2026-09-13).** `Video_Game` MERGEs on `(g:Entity {entity_id})` and adds `:Video_Game` with `SET` on every write, so an existing `Film_TV:Video_Game` node with the same `entity_id` is updated in place (`game.go:128-131`). The five support kinds MERGE on `(n:<Label>:Entity {entity_id})` through one shared builder (`game_support.go:74-78`). Venue associations belong in a dated SQL association list and the proposed `STAGED_AT` relationship, so a production can move without overwriting its history. Budgets, capitalization, recoupment and alleged investor amounts are outside this credit waterfall.

**Labels:** `Entity:Work:Theatrical_Work`, optionally `:Play` or `:Musical`.

**Canonical Go type:** proposed `theatrical_work`.

| `original_title` | string · O | Official programme/work evidence explicitly distinguishes an original title; never reverse-translate |
| `language_codes` | string[] · O | Explicit work-language evidence, normalized to the agreed language vocabulary; a production's location or page language is insufficient |

**Source IDs:** Wikidata QIDs can supply typed work identity after review; P1219 supplies an IBDB **show/work** ID. Neither an external alias nor a production programme is a universal work-identity guarantee. Do not invent `ibdb_work_id`, reuse `ibdb_production_id`, or attach a score/recording MBID to the whole stage work. Preserve statement IDs, ranks, qualifiers, references and item revision in SQL, and hold disputed mappings for review.

### Relationships and release boundary

The [closed build output manifest](/guides/open-work/roadmap/broadway-co-producers#theatre-graph-output-manifest) links every owned/reused node and all ten relationship families to these examples. Only the production hub and direct `PRODUCED` edges are mandatory in v1.

| Proposed connection | Ownership and limit |
| --- | --- |
| `Person/Company → PRODUCED → Stage_Production` | First-release direct-credit backbone, using the plan's agreed role weights and evidence envelope |
| `Stage_Production → PRODUCTION_OF → Theatrical_Work` | Optional resolved work context; proposed weight 50, excluded from scoring |
| `Stage_Production → STAGED_AT → Place:Venue:Theatre` | Dated support-place association; proposed weight 50, excluded; shared-place ownership required |
| `Theatrical_Work → ADAPTED_FROM → resolved source work` | Later explicit adaptation evidence; proposed weight 55, excluded; no `SAME_AS` shortcut |
| `Person/Music_Group → WROTE/COMPOSED/WROTE_LYRICS → Theatrical_Work` | Explicit work-level roles; proposed 10/8/12 using music precedents, excluded initially |
| `Stage_Production → HAS_AWARD → Stage_Award` | Production/associated-recipient context; proposed weight 40, excluded initially |
| `Explicit Person/Company → WON_AWARD/NOMINATED_FOR → Stage_Award` | Only named recipients; proposed 30/35, excluded initially; a production result is not copied to its producers |

A shared work or venue must not create the same relationship strength as co-producing **the same production**. The [theatre edge contracts and property examples](/guides/ontology/edges#theatre-edges), [proposed weights](/guides/ontology/edge-weights#theatre-weights) and [Go build plan](/guides/open-work/roadmap/broadway-co-producers#proposed-theatre-node-types) are aligned documentation. The direct-credit SQL tables exist; runtime type registration, endpoint dispatch, scoring filters and API registration remain unbuilt. Optional work/venue/award storage still belongs to its respective build slice; context graph writes stay disabled until their reader exclusions are verified.

Individual showings are deferred. A future `Entity:Event:Theatre_Performance` could represent a dated performance if attendance/ticketing requires it, but it is **not added to the reserved label inventory or v1 work**. People and producing companies retain their existing canonical types.

Before implementation, freeze the property/identifier enums and minimum fixture coverage; register both canonical types through admission, queues, facts, distill, graph sync, publish, merge and repair; define support-place/result ownership; and test cross-feature replay and corrections. These are development requirements, not changes performed by this documentation pass.

### MediaAppearance

<Card icon="play">

```
internal/platform/graph/appearances.go
```

**Universe writer, as implemented.** `MERGE (m:MediaAppearance {media_key})` — **no `Entity` label**, on purpose: an episode is not an entity and must not be found by entity-wide reads or the shared vector index (`appearances.go:19-21`, `:147-151`). </Card>

One source-identified episode or session, independent of the sites/assets distributing it. A publisher podcast episode and an explicitly equivalent video share one canonical identity. A show, channel, conference edition, clip and news article are different things. Do not key this node by title/date/host set or use a show-level URL as an episode ID.

**Proposed upsert identity:** canonical `entity_id`; `uuid` remains the stable graph UUID. Typed source aliases are resolved through `entity_identifiers` and the media source-association owner. Review these keys before implementing the writer. YouTube video IDs are case-sensitive; RSS GUIDs are exact and feed-scoped; conference session IDs are organizer/edition-scoped. Compilation assets map to scoped segments in SQL and are not single-appearance strong aliases. Source identity and retention rules are in the [build contract](/guides/open-work/roadmap/media-co-occurrence#identity-node-types-and-cross-source-deduplication).

The key is lowercased and computed by the caller: a certification is **shared** (`"AWS Solutions Architect"` is one node for everyone), while an honor, project or publication is **personal** and keyed per person with the node uuid pinned to the owning row. The whole property set, including the envelope and `description`, is written **ON CREATE only**; ON MATCH touches `updated_at` alone, so a later thinner sighting never blanks a richer one.

## Timestamps

Every Go writer stamps `created_at` ON CREATE and `updated_at` on every write with Cypher `timestamp()` (epoch milliseconds). Edge writers share one identity helper (`person_edges.go:44-48`) that keeps the first `created_at` across re-merges.
