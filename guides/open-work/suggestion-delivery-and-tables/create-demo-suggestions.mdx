Demo suggestions are hand-written. Mark writes the content — who is suggested, the WHY, the outreach drafts — as one JSON package, and hands it to Claude. Claude resolves every person, company, user, and organization to a real ID, converts the package to the format the backend loads, stores it, and reads it back. Nothing is generated by Universe and nothing is sent to anyone.

<Warning>
**The `POST /v1/ingest/suggestions` receiver described in [Suggestion Delivery and Tables](/guides/open-work/suggestion-delivery-and-tables) was not built.** Packages are loaded with a backend CLI, `cmd/ingestpackage`, which writes straight to the database behind `DB_DSN`. The JSON Mark writes is still the documented v2 envelope; the file the CLI accepts is slightly different, and [Claude does that conversion](#marks-json-vs-the-loaded-file).
</Warning>

<Info>
Checked against `orbiter-backend` `main` at `fd32f8e` (2026-09-17) and `orbiter-frontend` `dev` at `24564350` (2026-09-17). Recheck `cmd/ingestpackage/main.go` if the flags below stop working.
</Info>

## Who does what

| Step | Mark | Claude |
| --- | --- | --- |
| Pick the type and the people | Decides | — |
| Identity links for every person and company | Supplies LinkedIn or website URLs | Resolves each to a row ID; asks when ambiguous or missing |
| WHY, trajectories, sequencing, drafts, contact options | Writes | Validates shape only; never rewrites copy |
| Whose account the demo is for | Names the user | Finds that user's ID and personal organization ID |
| Request ID, batch ID, timestamp | Leaves the placeholders | Mints and fills |
| Loading and read-back | — | Runs the CLI, checks counts, reports the IDs |
| Review | Opens the app and checks the cards | Fixes and reloads as a new batch |

## Part 1: Mark writes the package

<Steps>
  <Step title="Choose the type">
    One package holds one type. Write two packages if the demo needs both.

    | | Leverage Loop | Outcome |
    | --- | --- | --- |
    | `suggestion_type` | `leverage_loop` | `outcome` |
    | Beneficiary | Required — the person being helped (Katelyn) | None; `beneficiary_contact_id` is `null` |
    | Card header | Suggested person + beneficiary | Target + its `target_org`, or a company on its own |
    | `badge` | `LEVERAGE LOOP` | `MOONSHOT` |
    | `trajectories`, `suggested_sequencing`, `key_people` | Must be empty, empty, `null` | One trajectory per connector, ordered steps, key people |
    | Introduction action (`make_intro`) | Yes — suggested person to beneficiary | Not possible; it needs a beneficiary |
    | Typical actions | Introduction, then email and SMS to each side | Email and SMS per connector, one action group per route |
    | Where it shows in the app | Inside the loop for that beneficiary | One entry per batch in the Outcomes sidebar |
  </Step>

  <Step title="List every person and company with an identity link">
    A name does not identify a record. For each entity the package references — suggested people, the beneficiary, connectors, key people, and any `target_org` — give a LinkedIn URL for a person or a website or LinkedIn URL for a company. This is the same preparation list as [Add Required Entities](/guides/open-work/suggestion-delivery-and-tables/add-required-entities).

    Placeholder suggestions need this too. An empty bar still names a real person or company.
  </Step>

  <Step title="Say whose account it is for">
    Name the user who should see the demo, and the environment. The app reads suggestions from that user's **personal organization**, so that is where Claude loads them unless you say otherwise.
  </Step>

  <Step title="Copy a template and edit only the content">
    Start from the full [Leverage Loop](/guides/open-work/suggestion-delivery-and-tables/sample-suggestion-data#leverage-loop) or [Outcome](/guides/open-work/suggestion-delivery-and-tables/sample-suggestion-data#outcome) sample. The Leverage Loop sample is reproduced [below](#leverage-loop-example).

    | You write | Leave exactly as it is |
    | --- | --- |
    | `why.headline` and `why.body[]` — one array item per paragraph | Every `{entity ID for …}` placeholder — use the same wording everywhere the same person appears |
    | `badge` | `batch_id`, `request_suggestion_id`, `org_id`, `requested_by`, `generated_at` placeholders |
    | `trajectories[].body[]` and `suggested_sequencing[]` headline and body (Outcome) | `schema_version`, `origin`, `trigger_source`, `status`, `suggestion_mode` |
    | Action `label`, and every `draft.subject` and `draft.message` | `score: {}`, `paths: []`, `evidence: []`, `hooks: null` |
    | `emails[]` and `mobile_phones[]`, in the order you want them offered | The key names and nesting — an extra or misspelled key rejects the whole package |
    | `source_ref` and the `ref` values, if you add or rename candidates, groups, or actions | |

    Do not invent UUIDs. A made-up ID loads without error and then renders the wrong card, or none.
  </Step>

  <Step title="Get the contact options right">
    Emails are bare addresses: `kyle@beinghuman.studio`, never `Kyle <kyle@beinghuman.studio>`. Mobile numbers are E.164: a leading `+`, country code, digits only — `+16175922739`. No duplicates within a list. The first item is the default the UI selects; the rest appear in a dropdown.

    Every email action needs at least one address and every SMS action at least one number. An introduction needs email options for both people.
  </Step>

  <Step title="Add named empty bars if you want them">
    A placeholder is a named candidate with no content yet. Set `content_status` to `placeholder` and keep its `source_ref`, `rank`, `entity_id`, `entity_type`, and `entities[]`. Everything else takes the empty shape: `why`, `badge`, `key_people`, and `hooks` are `null`, `score` is `{}`, and every other array is `[]`. Rebekah Jefferis and Bilawal Sidhu in the example below are placeholders.

    Ranks run 1, 2, 3 in the order the cards should appear, ready and placeholder alike.
  </Step>

  <Step title="Hand it to Claude">
    Paste this into a Claude Code session opened in the `orbiter-backend` repo with database access to the target environment, or send it to whoever operates that session.

    ```text Prompt
    Create demo suggestions from the JSON below, following
    guides/open-work/suggestion-delivery-and-tables/create-demo-suggestions.

    Account: <user's login email> — personal organization
    Environment: <dev | staging | production>
    Type: leverage_loop

    Identity links:
    - Katelyn Gallanty — https://www.linkedin.com/in/katelynhgallanty/
    - Ethan Jacks — https://www.linkedin.com/in/ethanjacks/
    - Rebekah Jefferis — <LinkedIn URL>
    - Bilawal Sidhu — <LinkedIn URL>

    Stop and ask me if any person or company is ambiguous or missing.

    <paste the JSON>
    ```
  </Step>

  <Step title="Review it in the app">
    Sign in as that user. A Leverage Loop appears inside the loop for its beneficiary; an Outcome appears as a new entry in the Outcomes sidebar. Check the header names and avatars first — a wrong face means a wrong entity ID, not wrong copy.

    Stored suggestions are immutable. A copy change is a new load, which [appears above the old one](#fix-or-re-run-a-demo) rather than replacing it, so batch your edits.
  </Step>
</Steps>

## Part 2: Claude loads it

<Steps>
  <Step title="Check the package before touching anything">
    Validate Mark's JSON against the [rejection rules](#rules-that-reject-a-package). Report every problem at once with its field path, such as `suggestions[0].actions[2].params.mobile_phones[0]`. Do not fix copy, reorder contacts, or drop a candidate to make the package pass.
  </Step>

  <Step title="Resolve every entity to a row ID">
    An entity ID is the primary key of that entity's own table: `persons.persons.id` for a person, `companies.companies.id` for a company. Resolve through the backend API as a signed-in user:

    | Have | Use |
    | --- | --- |
    | A person's LinkedIn URL | `POST /v1/persons/url-lookup` with `{"profile_url": "…"}` — returns `found`, `created`, or `pending_enrichment`, and the person |
    | A person's name only | `GET /v1/persons?query=…` — confirm the match with Mark when more than one row comes back |
    | A company URL | `POST /v1/companies/url-lookup` |
    | A company name only | `GET /v1/companies?query=…` |

    `persons.persons` no longer has a `linkedin_url` column, so do not look people up by LinkedIn URL in SQL. A `url-lookup` that returns `created` or `pending_enrichment` has made a new row whose card may be bare until enrichment finishes; tell Mark.

    Only the beneficiary is checked at load time (a foreign key to `persons.persons`). Every other entity ID is stored unchecked, so confirm each one resolves to the intended person before loading.
  </Step>

  <Step title="Resolve the user and their personal organization">
    `-requested-by` is the user's `users.users.id`. `-org` is their personal organization, and the user must be an active member of it:

    ```sql Personal organization for a user
    SELECT o.id AS org_id, o.name
    FROM organizations.organization_memberships m
    JOIN organizations.organizations o ON o.id = m.organization_id
    WHERE m.user_id = '<user id>'
      AND m.status = 'active'
      AND o.is_personal;
    ```

    Neither is a WorkOS ID. Loading into a company organization stores fine and then never appears, because the app reads the personal organization.
  </Step>

  <Step title="Convert Mark's JSON to the loadable file">
    Apply the [conversion table](#marks-json-vs-the-loaded-file): move the scope fields out to flags, rename the request ID key, change `person` to `persons` and `company` to `companies`, substitute every placeholder, and set `generated_at` to a real UTC timestamp. Keep Mark's original JSON untouched beside the converted file — it is the portable source for [other users and environments](#replicate-the-demo-for-another-user).
  </Step>

  <Step title="Mint the IDs">
    ```bash From the orbiter-backend repo
    go run ./cmd/ingestpackage -mint
    # request_id=0199…  batch_id=0199…
    ```

    Put the request ID in the file's `suggestion_request_id` and pass both as flags.
  </Step>

  <Step title="Load the package">
    ```bash Leverage Loop
    make ingest-package args="-file leverage-loop.katelyn.json -type leverage_loop \
      -org <personal org id> -requested-by <user id> \
      -beneficiary <person id for Katelyn Gallanty> \
      -request-id <minted request id> -batch-id <minted batch id> \
      -expect <host:port/db>"
    ```

    ```bash Outcome — no beneficiary
    make ingest-package args="-file outcome.maximum-effort.json -type outcome \
      -org <personal org id> -requested-by <user id> \
      -request-id <minted request id> -batch-id <minted batch id> \
      -expect <host:port/db>"
    ```

    Always pass `-expect`. The CLI writes wherever `DB_DSN` points, and `-expect` makes it refuse to run when that is not the database you meant. Add `-paths` only when the demo should show the requester's connection paths; it calls Universe and must run through `make`, which loads `.env`.
  </Step>

  <Step title="Read the report">
    The CLI prints one JSON report and exits non-zero on failure. Check that `result.created` is `true`, that `result.suggestion_count` matches the package, and that `counts` matches what Mark wrote — for the example above: 3 suggestions, 1 action group, 5 actions. On a rejection, `error.fields` lists the field paths; fix the file and rerun with the same IDs.
  </Step>

  <Step title="Report back">
    Give Mark the user, the organization, the type, the request ID, the batch ID, the database, and the list of resolved entities with their IDs. Keep the converted file with those flags; `replay_flags` in the report is ready to paste.
  </Step>
</Steps>

## Mark's JSON vs the loaded file

The CLI decodes strictly, so a scope field left in the file fails the load. Scope never comes from the file; it comes from flags.

| In Mark's JSON | In the loaded file | Where it goes |
| --- | --- | --- |
| `batch_id` | Removed | `-batch-id`, minted |
| `request_suggestion_id` | Renamed `suggestion_request_id` | Also `-request-id`, which overrides the file value |
| `org_id` | Removed | `-org` |
| `requested_by` | Removed | `-requested-by` |
| `suggestion_type` | Removed | `-type` |
| `beneficiary_contact_id` | Removed | `-beneficiary`; omitted entirely for Outcome |
| `origin`, `trigger_source` | Removed | The CLI always stores `user_requested` |
| `entity_type: "person"` | `"persons"` | Everywhere an `entity_type` appears |
| `entity_type: "company"` | `"companies"` | Everywhere an `entity_type` appears |
| `{entity ID for …}` | The resolved row ID | The same ID everywhere that entity appears |
| `generated_at` placeholder | A UTC RFC3339 timestamp | `2026-09-18T14:00:00Z` |
| `schema_version`, `status`, `suggestions[]` and all their content | Unchanged | — |

```json Loaded file — envelope and first entity entry
{
  "schema_version": 2,
  "suggestion_request_id": "<minted request id>",
  "status": "complete",
  "generated_at": "2026-09-18T14:00:00Z",
  "suggestions": [
    {
      "source_ref": "candidate-ethan-jacks",
      "rank": 1,
      "entity_id": "<person id for Ethan Jacks>",
      "entity_type": "persons",
      "content_status": "ready"
    }
  ]
}
```

The entity roles `beneficiary` and `target_org` must be spelled exactly; the UI builds the card header from them. Other roles, such as `target` and `connector`, are free text.

## Rules that reject a package

| Rule | Detail |
| --- | --- |
| No unknown keys | Anywhere in the file, including inside every action's `params` |
| Ranks | Positive and strictly ascending in array order — suggestions, trajectories, sequencing steps, action groups, actions, and introduction steps |
| Refs | `source_ref` unique across the package; trajectory, group, and action `ref` values unique within their suggestion |
| Entity registry | Every ID used anywhere in a suggestion is declared in that suggestion's `entities[]` with the same type. It must include the suggested entity, and the beneficiary for a Leverage Loop |
| One type per entity | The same ID cannot be `persons` in one place and `companies` in another |
| Ready | `why.headline` and `why.body[]` are non-empty, with no empty paragraph |
| Placeholder | `why`, `badge`, `key_people`, `hooks` are `null` — not `[]`; `score` is `{}`; all other arrays are empty |
| Leverage Loop | `trajectories` and `suggested_sequencing` empty; `key_people` `null` |
| Outcome | No beneficiary, therefore no `make_intro` |
| `make_intro` | `workflow` is `double_opt_in`; the target is the beneficiary; exactly two recipients, the suggested person and the beneficiary, each with emails; steps are `ask_beneficiary`, `ask_suggested_person`, `introduce`, in that order, each with a subject and message |
| Action targets | Every email, SMS, and introduction targets a declared person |
| Action groups | Every group has at least one action; every `group_ref` and `trajectory_ref` names something in the same suggestion |
| Emails and phones | Non-empty lists, no duplicates, bare addresses, E.164 numbers |
| `suggestion_mode` | `null` for both types |
| Docs placeholder UUIDs | Any ID starting `019a0000-0000-7000-8000-` aborts the run. The backend test fixtures use this prefix, so a copied fixture will not load until its IDs are replaced |
| Requester | Must be an active member of `-org`, or the load is refused as forbidden |

## Replicate the demo for another user

People and companies are shared rows: every user in one database sees the same `persons.persons` and `companies.companies` IDs, and a user's own contacts are a separate layer on top. So within one environment the converted file is reused as-is, and only the scope changes.

| Value | For the next user |
| --- | --- |
| The converted package file | Same file |
| `-type` | Same |
| `-beneficiary` | Same person — the loop is still for Katelyn |

### Another environment

Entity, user, and organization IDs are row IDs in one database and are not guaranteed to match in another. Moving a demo from dev to staging or production means starting again from **Mark's original JSON and identity links**, not from the converted file: resolve every entity, the user, and the organization in the new environment, convert, mint, and load.

This is the case to be careful with. A stale entity ID from another environment passes every load check except the beneficiary's and then renders the wrong card.

## Fix or re-run a demo

| Situation | What to do |
| --- | --- |
| Rerun the identical file with the same flags | Safe. The report shows `created: false` and nothing changes |
| The load was rejected | Fix the file and rerun with the same request and batch IDs; nothing was stored |
| Copy or contacts need changing after a successful load | New batch ID, same request ID, same scope. The same batch ID with different content is a conflict |
| The old version is still visible | Expected. The feed returns every complete batch in the scope, newest first, so the corrected batch appears above the original. The CLI has no delete; removing a stored batch is a manual database change and needs explicit approval first |
