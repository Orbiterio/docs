## ID preparation

1. Resolve each listed identity against existing entity records. Reuse its canonical UUID; avoid duplicate records for people or companies already present.
2. Record the resolved UUID for every placeholder above. Use the same UUID everywhere that entity appears, including the entity registry, target, beneficiary, connectors, key people, and introduction recipients.
3. Keep `entity_type` beside every explicit `entity_id` object. ID-only references resolve through the typed `entities[]` entries in their owning suggestion.
4. Keep the supplied email and E.164 mobile arrays from [Sample Suggestion Data](/guides/open-work/suggestion-delivery-and-tables/sample-suggestion-data#recipient-options), in their existing order. LinkedIn URLs identify the records to resolve; they do not replace entity IDs or recipient contact options.
5. Before the eventual POST test, replace all six entity placeholders. The sample JSON uses two entities for Leverage Loop and four for Outcome; each entity must be declared in the appropriate suggestion's `entities[]` list.

These LinkedIn links are preparation references, not new fields in the v2 suggestion envelope. No real entity UUIDs have been filled in by this documentation update, and entity existence has not been checked.

## Other IDs in the package

| Field | Preparation |
| --- | --- |
| `org_id` | An existing local `organizations.organizations.id` UUID for the owning personal or company workspace. |
| `requested_by` | An existing local `users.users.id` UUID for a current member of that workspace. This is the requesting user, not one of the graph entities by implication. |
| `request_suggestion_id` | A sender-supplied UUIDv7. The proposed receiver creates its minimal parent attribution row if absent; no separate request setup is required. |
| `batch_id` | A sender-supplied UUIDv7 per package, retained unchanged for retries. |
