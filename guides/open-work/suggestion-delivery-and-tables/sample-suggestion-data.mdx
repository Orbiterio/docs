## Schema revision

**Version 2 is the build target for the Orbiter Backend creation test.** The [parent build guide](/guides/open-work/suggestion-delivery-and-tables#envelope) defines the matching tables and direct POST receiver. These examples include structured trajectories, suggested sequencing, action groups, SMS, and ordered recipient contact arrays. The documentation does not indicate that the backend already accepts them.

Every person or company reference uses a quoted placeholder such as `"{entity ID for Ethan Jacks}"`. Replace placeholders with real IDs before ingestion. `org_id` is the local UUID in `organizations.organizations.id`, linked to WorkOS; `requested_by` is the local user UUID in `users.users.id`. Do not use external WorkOS IDs or graph entity IDs for either field. The timestamp is also a placeholder. Candidate, route, group, and action `ref` values are local references within the payload, not entity IDs.

Fill the existing local org/user and entity UUIDs, mint request/batch UUIDv7 IDs, then POST the complete raw JSON to `POST /v1/ingest/suggestions` using the Universe service identity. The proposed receiver creates the minimal parent request row when absent in the same transaction as the suggestion batch. No separate request setup is required. Follow the [manual creation test](/guides/open-work/suggestion-delivery-and-tables#manual-creation-test); no Universe generation or message sending is required.

| Field | UI behavior |
| --- | --- |
| `entity_id` and `entity_type` | Every entity object pairs its ID with its type, including the suggested entity, `entities[]`, and introduction recipients. These examples use `person` and `company`. |
| `requested_by` | The requesting user's `user_id`. Required for these user-requested samples. It supplies the new parent request’s attribution, or must match the requester on an existing request. |
| `org_id` | The owning organization and access scope. The requesting user must belong to it. |
| `content_status` | `ready` for populated suggestions; `placeholder` for a named suggestion whose supporting content has not been supplied. Separate from batch delivery status and accordion open/closed state. |
| `badge` | Displays LEVERAGE LOOP or MOONSHOT. It is a display label, separate from `suggestion_mode`, which remains null for these types. |
| `why.headline` and `why.body[]` | Headline with a short underline, followed by one paragraph per array item. `why` is null for a placeholder. |
| `trajectories[]` | One route per connector, ordered by rank. Connector names supply the route headings and the closed summary, “Charlie Anderson & Kyle Jackson.” |
| `suggested_sequencing[]` | Ordered steps. The closed accordion shows the first step’s headline, “Start with Charlie.” |
| `action_groups[]` and `actions[].group_ref` | One action bar per group. The lowest-ranked action in that group is always visible; the chevron reveals the remaining actions in rank order. |
| `draft_email.params.emails[]` | Ordered email options for the action’s target. Use the first by default; show a dropdown only when there is more than one. |
| `draft_email.params.sender_name` | Optional. The requester's display name. The AI cold email draft signs off with it; without it the backend falls back to the name the app sends. |
| `draft_sms.params.mobile_phones[]` | Ordered mobile options in E.164 format. Use the first by default; show a dropdown only when there is more than one. |
| `make_intro.params.recipients[]` | Each person has an `entity_id`, `entity_type: "person"`, and their own ordered `emails[]` options. Steps select people using `recipient_entity_ids[]`. |
| `params.draft` | Initial editable draft. Email has `subject` and `message`; SMS has `message` only. |
| `make_intro.params.steps[]` | Ask the beneficiary, ask the suggested person, then introduce both after opt-in. Each step identifies its recipients. |

Suggestion ranks order cards within the batch; group ranks order action bars; action ranks order actions within the suggestion and are filtered by group. The Leverage Loop has one group containing the introduction plus four alternatives. Outcome has one group for Charlie and one for Kyle, each with email first and SMS second.

**User identity:** `requested_by` is the user ID for the request, so there is no second `user_id` field. It identifies the requester, while `org_id` controls ownership and visibility. An agent-generated batch may have `requested_by: null`, as in the parent contract. The suggested person, beneficiary, and connectors are graph entities and are not the requesting user.

Names, profile titles, bios, avatars, and company logos are still resolved from entity IDs. The Leverage Loop header combines the suggested person and beneficiary; the Outcome header combines its target and the entity with role `target_org`, when present. A company-only target such as The Lighthouse or AI LA uses its own display name. Open/closed state, Midnight colors, and chevrons belong to the UI, not the stored recommendation.

Placeholders retain their rank, target, and typed entity registry. They have `why: null`, `score: {}`, null `badge`, `key_people`, and `hooks`, and empty trajectory, sequencing, path, evidence, action-group, and action arrays. Their rows still count toward `suggestion_count`. Opening one shows an empty content area; the UI must not synthesize WHY text or offer outreach actions. A ready suggestion can also be collapsed, so closing a card never changes `content_status`.

Both packages use delivery `status: "complete"` because the supplied package is final, even though some candidates are placeholders. Recommendation rows remain immutable: filling a placeholder later requires a new batch ID. The prototype's **ARCHIVED 1** counter has no supplied archived suggestion behind it and is not a fabricated eighth suggestion in these packages.

In Leverage Loop, email and introduction composers show **Send** on the right; SMS composers show **QRCODE** on the right. Those are composer controls, not separate recommendation action types. Outcome’s current prototype still uses Copy draft. These samples carry draft content, not send status, QR images, opt-in responses, or credentials.

## Recipient options

Contact arrays preserve the order supplied by the user. The UI initially selects index 0. A single option is shown as a fixed recipient field; two or more options are shown in a dropdown. Changing the selection uses exactly one email address or mobile number for that person and channel. Selections remain in the current preview session and reset to the first option on refresh.

For introductions, each step’s `recipient_entity_ids[]` resolves against `params.recipients[]`. Ask Katelyn uses Katelyn’s email options, Ask Ethan uses Ethan’s, and Introduction shows one separately selected address for each person. Alternatives do not add extra recipients.

All mobile values are E.164 strings, including the leading `+` and country code, with no spaces or punctuation. Ethan’s supplied US number is represented as `+16175922739`.

## Validation and implementation notes

- Every object containing `entity_id` must also contain `entity_type`. People use `person`; the four companies/organizations use `company`. Repeated references to the same ID must have the same type. Additional entity types must use the shared entity taxonomy.
- Every suggestion requires `content_status`. `ready` requires a nonempty WHY headline and paragraph array. `placeholder` requires null WHY and the empty content shape described above; entity IDs, types, ranks, and reference validation still apply. Do not reject a placeholder merely because it has no actions or WHY, or relax the WHY requirement for a ready suggestion.
- Every `entity_id`, `beneficiary_contact_id`, `target_entity_id`, and member of an entity ID array must resolve after placeholder substitution. Every referenced person/company is declared with its type in the owning suggestion’s `entities[]` list. ID-only references such as `recipient_entity_ids[]` resolve against these typed entries; introduction recipients also have their type alongside their ID.
- Email option arrays contain unique, nonempty email strings. Mobile option arrays contain unique strings matching `^\+[1-9]\d{1,14}$`. Array order is significant and is preserved by storage and reads.
- Every introduction step’s recipient ID must resolve to exactly one `params.recipients[]` entry. The final introduction step references both the suggested person and beneficiary, each with their own email options. User selections and opt-in responses are execution state, not mutations to these immutable recommendation arrays.
- Every action `group_ref` must resolve to a group in the same suggestion. Every group `trajectory_ref` and sequencing `trajectory_refs[]` entry must resolve to a trajectory in that suggestion. Leverage Loop groups use a null trajectory reference.
- Group, action, trajectory, and sequencing ranks are positive and unique within their respective arrays. The first action in each group is the top action. Local refs must also be unique within their array.
- `trajectories[].path_refs[]` resolves against `paths[].ref` in the same suggestion. These design examples have no verified graph path records, evidence, or scores, so those values are empty; the supplied narratives are retained without fabricated graph edges.
- Version 2 uses `entity_type` instead of the version 1 entity-list field `entity_kind`, mapping `org` to `company`. It also replaces the single `trajectory_text`, aggregate `trajectory_entity_ids`, and `trajectory_path_refs` with per-route `body`, `connector_entity_ids`, and `path_refs`. Existing version 1 consumers need an explicit mapping or migration.
- Backend adoption requires `draft_sms` in the Go action validator and the v2 table designs in the [build guide](/guides/open-work/suggestion-delivery-and-tables#schema). Drafts, ordered email/mobile arrays, per-person introduction recipient options, and introduction steps are stored in `suggestion_action.params` JSONB; handlers validate their required shape. The new request and result tables live in the `suggestions` schema. These documentation changes do not apply a database migration.

The five empty bars are included as placeholder suggestion records. No WHY narratives, contact options, graph paths, or actions have been invented for them.
