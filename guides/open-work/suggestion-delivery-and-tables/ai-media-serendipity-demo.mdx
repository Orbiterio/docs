This is a hand-written **Serendipity** demo package for the events use case: the agent answers "Events and conferences in AI & Media in the next 60 days" with nine October 2026 events. Three are `ready` cards carrying a WHY and actions; six are `placeholder` bars. It follows the same load path as the [Angel Outcome Demo](/guides/open-work/suggestion-delivery-and-tables/angel-outcome-demo): a `suggestion_request` row, then the package through `cmd/ingestpackage` per [Create Demo Suggestions](/guides/open-work/suggestion-delivery-and-tables/create-demo-suggestions).

<Note>
  **Entity IDs are resolved in dev.** All nine events and three organizers exist in dev as of 2026-09-24, and the package below carries their real IDs. The events were seeded into Universe and hand-projected into the backend; see [Resolve the entity IDs](#resolve-the-entity-ids). The IDs are dev-only: another environment needs its own seed and projection.
</Note>

<Warning>
  **Serendipity loads as `agent_generated`, and the cards are events.** [Leverage Outcome & Serendipity](/guides/open-work/suggestion-delivery-and-tables/leverage-outcome-and-serendipity) defines Serendipity as `agent_generated` with null request, requester and beneficiary, and the backend's `validateScope` enforces it: a `user_requested` Serendipity batch is rejected. So the batch names no request and is found through the org's feed; a separate [request record](#suggestion-request-record) points at it (`GET /v1/suggestion-batches?organization_id=…&suggestion_type=serendipity`). Loading it needs the `cmd/ingestpackage` Serendipity mode on `orbiter-backend` `thursday_dev` (commit `443ba4ab`, not yet on `main`). Second, the cards are events, not people: `entity_type` is `live_events`, which is in `nodespub.ValidEntityType`, and `suggestion_mode` is `new_connection` because the taxonomy has no event value. That one is a demo choice, not a contract change.
</Warning>

The v2 envelope has no batch-level narrative field, so the summary lives on the [request record](#suggestion-request-record), which the feed reads through the request whose `batch_id` points at the batch. The six other events are placeholder cards in the grid beside the three ready ones.

## Batch scope

Serendipity has no request, requester or beneficiary on the batch. Scope comes from CLI flags only: the owning organization is the Angel demo's personal org `01a08264-0ef6-744c-b4f5-5f398dc2f98e`, and the batch ID is `01a0d477-58ea-744d-9015-4c9591acdc30`, minted with `go run ./cmd/ingestpackage -mint` on 2026-09-24. Reuse that batch ID to replay; changed content needs a fresh one, since a replay with a different digest is refused. The first load, `01a0d44a-d414-7762-9bc8-e9aac16bc77c`, carried the earlier WHYs and no register actions; its suggestions are dismissed, so it no longer shows in the feed.

## Suggestion request record

The request row still exists, so the request carries its titles and summary: the Serendipity header shows `llm_summary_context` (one paragraph per string) under the title, falling back to `request_context`, then `request_header_title`. The link runs one way: the request's `batch_id` points at the batch, while the batch's `suggestion_request_id` stays `null`, because `validateScope` rejects a Serendipity batch that names a request. Insert it with an idempotent `INSERT … ON CONFLICT (id) DO UPDATE`; order relative to the batch load does not matter, since `batch_id` has no foreign key. The feed joins titles through the batch's `suggestion_request_id`, so the feed itself still shows no title.

## Resolve the entity IDs

Done in dev on 2026-09-24. The steps below record what was run, so another environment can repeat them.

<Steps>
  <Step title="Seed the events into Universe">
    None of the nine editions existed in Universe dev. They were seeded from the [seed records](#seed-records) with `cmd/seed-live-events` in `orbiter-universe`, which writes a `universe.live_events` row and a vectorized `Entity:Event:Live_*` graph node per event, and stamps `graph_node_uuid` only after the graph write returns. Run a `-dry-run` first. The tool's local-host guard treats `localhost` as local, so through the IAP tunnel it writes to dev; pass `-yes` knowingly.

    ```bash
    DB_DSN="postgres://mark%40orbiter.io:$(gcloud auth print-access-token)@localhost:5436/orbiter_universe?sslmode=require" go run ./cmd/seed-live-events -file events.seed.json -yes
    ```

    The canonical `universe.live_event` table and `live_event_display` are not written by this tool and stay empty.
  </Step>
  <Step title="Project the events into the backend">
    The backend has no Universe-to-backend sync for `live_events`: nothing on `main` writes `live_events.live_events`. The nine rows were inserted by hand with an idempotent `INSERT … ON CONFLICT (id) DO UPDATE`, generated from the Universe rows, keeping the Universe ID as the backend `id` and `graph_node_uuid`. `display_label` is the node's `Live_<event_type>` label and `duration_days` is derived from the dates. The card reads `name` and `COALESCE(tagline, short_description)`.
  </Step>
  <Step title="Resolve the three organizers">
    `POST /v1/companies/url-lookup` with each organizer's domain, as a signed-in dev user. Universe company enrichment has a population ceiling (`consumers.environment_variables`, `kill_switch_company` and `kill_switch_person`); dev was at 5,000/5,000 and skipped all three, so both were raised to 10,000. Paley returned `created` (via the backend provider fallback) and NAB returned `created` after the raise. RX returned a logo.dev brand match with no ID, which short-circuits before Universe, so it was created with `POST /v1/companies` (`brand_selected: false`, domain plus LinkedIn URL). That call also adds the company to the caller's contacts. None of the three is in Universe `master_companies` yet; they are bare cards until enrichment finishes.
  </Step>
  <Step title="Load">
    Save the [package](#package) as `package.json` and load it from `orbiter-backend` on `thursday_dev`. Insert the [request record](#suggestion-request-record) too; it is not created by the CLI. Serendipity takes no `-request-id`, `-requested-by`, `-beneficiary` or `-paths`.

    ```bash
    DB_DSN="postgres://mark%40orbiter.io:$(gcloud auth print-access-token)@localhost:5436/orbiter?sslmode=require" go run ./cmd/ingestpackage -file package.json -type serendipity -org 01a08264-0ef6-744c-b4f5-5f398dc2f98e -batch-id 01a0d477-58ea-744d-9015-4c9591acdc30 -expect localhost:5436/orbiter
    ```

    Expected counts: 1 batch, 9 suggestions, 12 entity rows (`suggestion_node`), 3 action groups, 6 actions.
  </Step>
</Steps>
