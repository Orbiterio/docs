## What this delivers

When a user connects X with follower-import consent, capture the followers returned for that connected account into `x_follower`. Keep one durable row per `(user_id, x_user_id, follower_x_user_id)`, including unresolved accounts. These rows describe observed follower state; a completed paginated pass is not a transactionally frozen snapshot of X.

Use **`entity_id` for the follower's person node UUID**, consistent with [Log X DMs](/guides/open-work/x-followers-capture/log-x-dms). Attach it when a bounded lookup finds a verified existing person; otherwise leave it null and let the CRON resolve and enrich missing people. Capture never waits for enrichment. Keep resolved rows so future scans can reconcile changes.

A follower means **that account follows the connected account**. It does not prove that the connected user follows them back or personally knows them. Preserve that direction and source in the user's relationship data; do not automatically turn a follow into reciprocal KNOWS evidence.

## Identity and ownership contract

| Field | Meaning |
| --- | --- |
| `user_id` | Orbiter owner of the connection and private follower rows; proposed BIGINT matching the app user key |
| `x_user_id` | Connected X account being scanned; text, same meaning as in the DM plan |
| `follower_x_user_id` | X id from each returned follower's `id`; text |
| `entity_id` | Follower's resolved person node UUID; nullable UUID, never an owner id or integer contact id |
| `profile_url` | Current normalized X profile URL; a mutable identity hint, not the dedupe key |

The old outline used `entity_id` for the owner and `x_user_id` for the follower. **Replace those meanings in the proposed Go contract.** Do not copy an old owner integer into the new UUID column. Keep connection ownership, X account identity, and person identity distinct at every boundary. A person's UUID is a logical graph reference; do not declare a foreign key to a separate database.

Support account-scoped storage even if the first UI allows only one X account per user. Authenticate user actions in the App backend and derive `user_id` there. Workers must validate the owned connection; an arbitrary handle or a client-supplied owner id must not authorize a scan. Whether one X account can be connected by multiple Orbiter users is a product decision; never transfer an existing owner's connection silently.

## Build plan for Charles

<Steps>
  <Step title="1. Establish the environment and connection contracts">
    Define the owned connection and the identifier mapping above, with separate callback configuration and secrets per environment. Follower capture can be built independently of Universe environment readiness. When enabling Universe lookup and projection, bind each App environment to its matching Universe environment; a DEV job must never resolve or write against LIVE. **Check:** unavailable or misconfigured Universe routing defers resolution while follower capture continues with unresolved rows.
  </Step>
  <Step title="2. Implement OAuth and shared token management in Go">
    Request `users.read`, `tweet.read`, `follows.read`, and `offline.access`; DM access remains a separate opt-in. Use S256 PKCE and random, expiring, single-use `state` bound to the signed-in user and environment. Exchange the code immediately in the callback, confirm the account through `/2/users/me`, verify granted scopes, and durably store the encrypted token pair with its owned connection. Persist capture intent in the same database transaction so a failed queue send can be retried. **Check:** denied consent, duplicate callbacks, mismatched state, and cross-user connection claims are handled explicitly.
  </Step>
  <Step title="3. Build storage and prove the API fixtures">
    Implement the proposed row and capture-run contracts below in AlloyDB. Capture redacted fixtures for a first page, continuation page, empty account, missing fields, HTTP 200 with errors, and a protected account. Confirm endpoint pricing and returned rate-limit headers for this app. **Check:** the same follower under two connected accounts or owners stays independent; missing optional fields stay unknown instead of becoming false or zero.
  </Step>
  <Step title="4. Implement the resumable capture worker">
    Use Cloud Scheduler to dispatch due durable work to a Go worker through the project's queue. Lease one active full pass per owned account, fetch bounded pages, and commit each page with its cursor. A time, page, rate, or dollar limit pauses the pass. Do not keep a callback or goroutine alive to finish a large import. Follow the [worker algorithm](#proposed-function-twitter-api-capture-followers). **Check:** a crash retries one page safely; a resumed pass gets a fresh per-attempt page budget; a stale lease cannot commit.
  </Step>
  <Step title="5. Reconcile follower state after complete passes">
    Use run identity, not wall-clock comparisons, to identify unseen rows. Finalize only after every page has succeeded; make the finalization resumable and idempotent. Use the conservative [absence policy](#reconciling-missing-followers) below so an interrupted pass or temporary visibility problem cannot remove relationships. **Check:** zero followers can complete, while an empty page with errors cannot trigger removals.
  </Step>
  <Step title="6. Resolve people and project relationship evidence">
    Attach existing person UUIDs through a bounded lookup and let a separate CRON own new identity resolution, enrichment, and relationship projection. Retain the follower row after success. Deduplicate resolution across messages and followers for the same X account identity. Follow [Resolving Followers to Edges in User Graph](#resolving-followers-to-edges-in-user-graph). **Check:** known people need no paid identity search; retries do not create duplicate people or duplicate evidence.
  </Step>
  <Step title="7. Add operational controls and pilot">
    Implement budgets, disconnect/deletion, queue recovery, and the release checks before enabling a schedule. Track capture coverage separately from resolution progress. Pilot with capped internal accounts in DEV, then verify LIVE routing and measured spend before expansion. **Check:** users can distinguish an import still running, a budget pause, a reconsent requirement, and unresolved people.
  </Step>
</Steps>

### OAuth and token rules

X's [OAuth reference](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code) documents a 30-second authorization-code lifetime, exact callback matching, and refresh-token issuance with `offline.access`. Exchange during the callback; queue only the import. Derive access-token expiry from `expires_in` rather than hardcoding two hours.

Build one token manager shared by follower and DM workers. Serialize refreshes across processes for the actual OAuth grant, re-read the latest version before refreshing, and atomically save the rotated pair with a token version. An in-memory mutex on one Cloud Run instance is insufficient. Never use the newest arbitrary token row or fall back to app-only authorization when the owned user's token fails. A lost refresh response may require reconsent; do not blindly retry a consumed refresh token.

Keep token material out of queue payloads, responses, logs, and follower `raw`. The connection contract needs owner/account identity, encrypted credentials, granted scopes, expiry, token version, feature enablement, revocation generation, and scheduling metadata. Follower and DM enablement are independent; reconnect and additional-scope flows must preserve the user's selected features only when their required scopes remain granted.

## Proposed table: x_follower

One row per owned connected account and follower, with the latest allowlisted profile fields and durable resolution/state markers. This is retained capture data, not a disposable resolver queue. Use TIMESTAMPTZ in UTC, BIGINT for app row ids and counts, UUID for `entity_id`, and JSONB for structured profile data. Optional API fields are nullable.

<Warning>
  Preserve X ids such as `1367171255879671808` as **strings end to end**: Go decoding, database, queues, and JSON responses. Both `x_user_id` and `follower_x_user_id` are text. Never pass them through a floating-point number.
</Warning>

Indexes:

- Unique on `(user_id, x_user_id, follower_x_user_id)` for idempotent capture.
- Btree on `(user_id, x_user_id, last_seen_run_id, id)` for scoped reconciliation.
- Btree on `(next_resolution_at, id)` for due pending/retry resolution; on `(user_id, entity_id)` for resolved people.
- Btree on `follower_x_user_id` for identity reuse across imports; normalized handles remain non-unique hints.
- Track pending projection versions through the shared durable job/outbox mechanism. A non-null `entity_id` does not prove that relationship projection succeeded.

Use typed Go response structs with nullable optional fields and `json.RawMessage` only for the allowlisted profile snapshot. Field absence must not erase previously captured values; an explicitly returned empty string or zero can. Keep field presence separately from value when applying updates. A missing `protected` field in the current observation still blocks new external enrichment until refreshed. The [current endpoint schema](https://docs.x.com/x-api/users/get-followers) uses `post_count` where the earlier fixture below uses `tweet_count`; cover both in fixtures and record conflicts rather than silently choosing an arbitrary value.

Do not start a second full pass for the same owned account while the first is resumable or finalizing.

Index due nonterminal work by `(next_attempt_at, id)` and enforce one nonterminal pass per `(user_id, x_user_id)`. Include paused and finalizing states in that uniqueness rule. Abandoning an invalid cursor and creating a new pass happens transactionally. The shared connection keeps `next_capture_at` and `last_completed_capture_run_id` so dispatch also discovers new work and reports freshness.

## Proposed function: twitter-api-capture-followers

This name identifies the proposed **Go worker**, not a new Xano function. Port the API mapping from 13389; Xano's nested-call secret masking and `async-shared` runtime are not Go requirements. Suggested boundaries: a shared token manager, a bounded X HTTP client, an AlloyDB capture store, and a separate Universe resolver/projector. Use request contexts, timeouts, response-body limits, and parameterized database writes.

**Inputs**

| Input | Type | Notes |
| --- | --- | --- |
| `capture_run_id` | bigint | Required queue payload; worker derives owner/account from the persisted run and verifies its connection |
| `max_pages_per_attempt` | int | Server configuration, not a provider quota; cap alongside elapsed time and spend |

**Worker algorithm**

1. Claim a due run with a database lease. A terminal run or an unexpired lease held elsewhere is a no-op. Recheck follower consent, ownership, environment, and connection generation. If resuming `finalizing`, continue that phase without fetching page one again.
2. Obtain a valid token through the shared token manager. Load the persisted cursor and initialize a **local** page counter to zero. Reserve request/resource budget before each call. Renew leases for bounded work; do not hold a database transaction open during an X request or enrichment lookup.
3. Fetch the first page without `pagination_token`; continuation requests use the stored token. **Always fetch the first page even though its input cursor is empty.** Continue until a validated response lacks `meta.next_token`, or an attempt budget is reached. Do not stop on a familiar follower, matching follower count, or a short page that still has a cursor.
4. Validate the response envelope and every follower id. HTTP 200 with unresolved `errors`, contradictory counts, an empty page with a continuation token, or a repeated cursor is `partial`. Valid items may be retained, but keep the input cursor for repair and do not enable absence reconciliation. An explicit zero-result response without errors or a cursor is a valid terminal page. Retry network/5xx failures with bounded backoff; on 429 use returned reset timing with jitter. On 401 recheck token version and allow one controlled refresh/retry; access, scope, and account-availability failures become visible pauses, never empty successful scans.
5. Normalize profiles and perform a best-effort cached, batched Universe identity lookup outside the page transaction. In one transaction, verify the lease version and connection generation, upsert follower rows, set `last_seen_run_id`, clear absence markers for observed followers, preserve resolved identity fields, write any semantic-change projection intent, and commit the next cursor and counters. For a terminal page, **set `pagination_exhausted = true` and `status = finalizing` in that same transaction** so a crash cannot mistake its null cursor for an unstarted import. `first_seen_at` changes only on insert. Count a follower once per pass. A crash before commit retries the same page; a crash after commit resumes the next page or finalization.
6. On time/page/dollar exhaustion, persist a resumable pause with `next_attempt_at`. A scheduler must rediscover durable due work even if queue publication failed. A lost/invalid cursor is not safely resumable: abandon that pass, start a new pass from page one, retain captured rows, and forbid the abandoned pass from inferring removals.
7. In `finalizing`, assess coverage and apply bounded reconciliation batches and durable projection work as described below. Mark `complete` and advance the connection's completed-pass pointer only when finalization finishes. A completed pass may still have unresolved people; report those separately.

### Reconciling missing followers

Use `last_seen_run_id` to identify rows not observed in the current clean full pass. Never compare `last_seen_at` with a run's start time to infer removals. Only one pass may fetch or finalize this owned account at a time; every finalization batch checks the same lease and connection generation as capture.

**Proposed pilot policy: require two consecutive qualifying full passes with absence before setting `is_following = false`.** The first absence sets `missing_since`; each clean pass increments `missing_complete_passes` once. `last_reconciled_run_id` makes batch retries idempotent. Reappearance in any valid page sets `is_following = true`, resets missing counters, and clears `unfollowed_at`. A partial or abandoned pass never adds absence evidence.

This is an inference that the account is no longer observed as a follower, not proof of a deliberate unfollow or its exact time. Visibility changes and accounts becoming unavailable can produce absence too. Keep last-observed state and freshness visible. If a pass has unresolved API errors, an unexplained empty result after a populated baseline, or an anomalously large drop, leave `absence_reconciliation_allowed = false`, retain existing presence, and schedule a fresh verification pass. Release an anomaly hold only when the verification pass and current owned-account/access checks explain the change, or after a recorded operator review. Make the drop threshold configurable and verify it against pilot fixtures. A clean empty account with no populated baseline can complete normally.

Finalization compares one run consistently, advances `finalize_after_id` in the same transaction as row changes, and enqueues versioned updates for the user's follower evidence. A retry cannot double-count absence or replay an old removal over a newer reappearance. Removing follower evidence must preserve DM/email evidence, unrelated relationships, and the canonical person.

## Rate limits and access tier

Checked 2026-09-06: X's [rate-limit table](https://docs.x.com/x-api/fundamentals/rate-limits) lists **300 requests per 15 minutes** for follower lookup in both its per-app and per-user columns. The [endpoint reference](https://docs.x.com/x-api/users/get-followers) allows up to **1,000 users per page**. The original 15-request/four-hour sizing is not the current documented limit. Configure limits from the app's actual access and response headers; maintain shared accounting for every applicable account/app bucket and bound worker concurrency.

The [pricing page](https://docs.x.com/x-api/getting-started/pricing) lists follower reads at **\$0.010 per returned resource**, not per page. Illustrative full-pass costs before other lookups or enrichment:

| Followers returned | Full-pass estimate |
| --- | --- |
| 1,000 | \$10 |
| 10,000 | \$100 |
| 250,000 | \$2,500 |

The listed \$0.001 Owned Read discount requires the authenticated target to also own the developer app; do not assume every connected customer qualifies. Daily UTC deduplication is a soft guarantee, not a guarantee that retries are free. Verify actual billing in the console before enabling imports. [Pricing and Owned Reads](https://docs.x.com/x-api/getting-started/pricing).

**Recommended initial cadence:** one budgeted import at connect time; make automatic repeat full passes configurable and off by default until a per-account freshness/cost policy is chosen. Reserve the estimated maximum page charge before dispatch and reconcile actual returned units. If the remaining budget cannot cover a full page, lower page size only before starting a pass, or pause; do not mutate a cursor's request fingerprint mid-pass. Keep capture and paid resolution budgets separate, with user/account/app caps and visible budget pauses.

Follow/unfollow Activity subscriptions are a possible later cost/freshness improvement. Prove app access, owner routing, replay identity, ordering, and observed billing before using them; keep periodic full reconciliation to repair gaps. They are not part of this first capture worker. Any later kill switch must also remove billable subscriptions.

## Open questions

These decisions remain explicit rather than being inferred from the old prototype:

| Decision | Recommendation / implementation dependency |
| --- | --- |
| Universe integration routing | Confirm matching App/Universe routes when enabling resolution and projection; environment readiness does not block the follower capture build |
| Multiple connected accounts and shared X accounts | Storage supports multiple accounts; product chooses UI limits and whether multiple owners may authorize the same X account |
| Import spend and recurring freshness | Mark sets per-account dollar caps and repeat-scan cadence; Charles enforces them before requests |
| Follower-only contacts | Do not assume every follower belongs in contacts. Decide automatic import vs an explicit add action; keep this separate from the agreed DM-to-contact flow |
| Absence policy | Start with two clean full passes and an anomaly guard; select drop thresholds and maximum acceptable staleness using fixtures |
| Protected, ambiguous, empty, and non-person accounts | Retain observed rows; no automatic external enrichment while protected/unknown; no fabricated Person for a brand or bot |
| Following as well as followers | Separate later scope. Preserve direction with a sibling relation or explicit direction field; never silently mix the two |
| Retention | Specify retention for profile snapshots, completed runs, diagnostics, and backups; implement disconnect cleanup before the pilot |

## Disconnect, telemetry, and release checks

Disabling follower import first clears its enablement, advances the relevant revocation generation, and cancels pending capture/resolver/projection work. Recheck that generation inside every private-data write transaction. Delete the user's account-scoped follower/profile rows and retract only their follower-derived evidence through durable cleanup work. Preserve DM access when only followers are disabled, and preserve contacts or relationships supported by other sources. Account-wide disconnect revokes the grant and disables both features. Shared Universe people are not deleted merely because one user disconnects.

Use structured Go logs and run records with owner/account/run ids, status, committed pages, distinct followers, request counts, oldest pending age, estimated spend, resolution outcomes, and projection lag. Keep tokens, raw profiles, and bios out of telemetry. If the Go service still emits to `log_crash`, add the phase enum first and distinguish success telemetry from non-empty errors; failure of a secondary logger must not invalidate a committed page.

| Scenario | Required result |
| --- | --- |
| Fresh run has a null cursor | First page is requested exactly as a first page; no empty-loop false completion |
| More pages than one attempt budget; rate/time/dollar pause | Same logical pass resumes at its stored cursor with a fresh local page budget |
| Queue duplicate; crash before/after page commit; expired worker lease | Idempotent rows/counters; correct cursor; stale worker cannot commit |
| Crash immediately after the terminal page commits | Persisted `finalizing` state resumes reconciliation, never restarts page one |
| Invalid or repeated cursor; changed request fields | No completion/removal claim; restart safely under a new pass when necessary |
| Same follower under two users or two connected accounts | Independent relationship state; no cross-owner overwrite or cleanup |
| Missing optional fields, `false`, zero, empty strings, and large X ids | Unknowns stay distinct; explicit values update correctly; ids remain exact strings |
| `tweet_count` vs `post_count`; unexpected enum value | Tested normalization and visible conflict handling; no decoder panic |
| HTTP 200 with errors; empty-with-cursor; valid empty account | Partial cases never infer absence; valid zero-follower baseline completes |
| Finalization crashes halfway; same pass replays | Absence counters increment at most once; finalization resumes safely |
| Missing in one pass, missing in two, then reappears | Inference follows the chosen policy; reappearance clears absence and supersedes old projection work |
| Lookup outage, ambiguous handle, reassigned handle, protected account | Capture retained; no speculative person merge or external enrichment |
| Existing person; concurrent creation via DM and follower jobs | Same canonical person UUID reused; paid work and projection deduplicated |
| Identity resolves but relationship projection fails | Row retained with separate pending projection; retry never requires a new person |
| Follow-only evidence | Correct follower-to-connected-account direction; no automatic reciprocal KNOWS or DM count |
| Concurrent DM/follower token refresh; missing scopes; revoked grant | One valid token rotation; feature-specific pauses and owner checks |
| DEV routed to LIVE; disconnect during in-flight work | Environment mismatch rejected; no private-data resurrection or cross-environment writes |
| Pilot import | Measured page coverage, absence behavior, and console billing match the reported result before expansion |

## Resolving Followers to Edges in User Graph

The capture writer may attach an existing person UUID through a cached, bounded lookup. The CRON owns everything that can create or enrich a person or write relationship data. Reuse the [DM identity-resolution contract](/guides/open-work/x-followers-capture/log-x-dms#identity-and-contact-resolution), with the follower identity supplied as `follower_x_user_id`.

1. **Reuse known identities.** Batch lookups by numeric X id. Normalize `x.com`/`twitter.com` profile URLs and handles as secondary hints, verify that a handle still belongs to that account, require a Person match, and follow merge redirects. Match the specific identity field, not arbitrary occurrences of the URL anywhere in the graph. Store the canonical person node UUID in `entity_id`. A missing Universe response leaves the captured row pending.
2. **Resolve missing people within budget.** Process distinct eligible accounts, using captured expanded profile URLs before paying for another profile lookup. Feed candidate evidence through the normal identity-resolution path; recheck the Universe before creation to handle concurrent DM/follower imports. Skip external enrichment for protected or unknown-visibility accounts. Persist ambiguous, non-person, unavailable, retry, and budget outcomes with a next-attempt policy; do not repeatedly spend on every follower row. Correctly classify non-person accounts rather than manufacturing a Person.
3. **Create and enrich through the Universe contract.** Deduplicate by verified canonical identity, save its person node UUID, and reuse/enqueue enrichment. Preserve evidence and confidence; do not trust a successful URL lookup alone. Do not send a bare X URL directly into the legacy person-creation path: [the non-LinkedIn scope](/guides/open-work/enrich-via-non-linkedin-scope) documents why that can create unusable placeholders. Profile text is untrusted data, including when an LLM judges identity.
4. **Project the user's follower evidence.** Apply only the latest `relationship_version` under the same owner/account and current connection generation. Record the direction from follower to connected account with source `x_followers`, observed time, and presence state. Use the agreed user-graph projection API; idempotently upsert by the source relation's stable key. Do not invent a new edge schema or equate this with reciprocal KNOWS. Keep capture rows and use `projected_version` to retry projection separately from identity resolution.
5. **Handle contacts under the chosen policy.** If follower contact import is enabled, upsert membership by `(user_id, entity_id)`, including known people who lack that user's contact. Keep the membership step independently retryable. The agreed DM-to-contact flow remains separate; follower capture does not silently opt a user into importing every follower as a contact.

Durably enqueue resolution/projection work or make pending rows rediscoverable; a database commit followed by a failed queue publish cannot strand work. Coordinate paid jobs by canonical X/person identity across sources, and handle each user's membership/evidence separately. A capture replay must preserve `entity_id` and resolver-owned fields. Meaningful profile changes can explicitly requeue skipped or ambiguous identities under policy, rather than resetting all resolution on every scan.

Public person identity/enrichment may be shared in the Universe. Keep the imported account list, consent, and user-specific relationship evidence in the App's owned scope. Resolved follower rows are **never deleted merely because resolution succeeded**; they remain the basis for rescans, absence reconciliation, and source-specific cleanup.
