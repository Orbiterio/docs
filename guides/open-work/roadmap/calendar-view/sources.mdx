## Why the prompts are shaped this way

The following is section 8 of the supplied brief:

- The brief lives in the repo, not in the prompt. Each phase prompt is short because the constraints are already loaded and stable across phases.
- Phase 0 is a read-and-plan gate. Ambiguities surface before code exists, and the agent has to prove it looked at installed types instead of remembering an API.
- Fixture first. Every later phase measures against the same 5,000-event seed, so performance numbers are comparable and the agent cannot make the UI look fast on ten events.
- Budgets are gates with numbers, and the agent reports raw measurements. "Feels fast" is not a deliverable.
- Every visual phase ends with a screenshot and a one-line critique that names a removal. This is the cheapest way to get a design pass out of a code agent.
- Guardrails name the specific temptations (calendar library, Date math, invented fields) instead of general advice. Agents route around vague warnings and respect specific ones.
- Interactions come after static rendering. Drag logic layered on an unstable grid produces a mess; drag logic on a grid that already meets its render budget is usually short.
- Akira tools reuse the mutation layer rather than calling the API directly, so agent actions and human actions are indistinguishable to the rest of the app and to the SSE reconciliation.

## Primary references checked for this plan

- [Nylas all-day event handling](https://developer.nylas.com/docs/v3/calendar/using-the-events-api/#all-day-event-handling): Google and Microsoft use an exclusive `datespan.end_date`. Still verify real grants during the first backfill.
- [Nylas event-list API](https://developer.nylas.com/docs/reference/api/events/get-all-events/): occurrence-window filtering and provider-specific master filtering.
- [Nylas event notifications](https://developer.nylas.com/docs/reference/notifications/events/) and [recurring events](https://developer.nylas.com/docs/v3/calendar/recurring-events/): webhook and series behavior.
- [PostgreSQL sequence functions](https://www.postgresql.org/docs/current/functions-sequence.html): sequence allocation alone does not provide the per-user commit-order guarantee the SSE cursor requires.
- [MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource): browser lifecycle and the constraints of native EventSource error handling.

These references inform the written acceptance gates. No live Google/Microsoft backfill, migration, frontend phase, benchmark or screenshot run is claimed by this documentation update.
