## Identity gates

### Recipient — required for zero-LLM grants too

1. Use `entitiespub` identifier lookups and canonicalize merged IDs. A filed EIN resolves through an existing company-scoped strong key; accept only recipients in the tracked School set. An out-of-scope company does not become a School.
2. Without EIN, normalized names/aliases nominate candidates. Auto-link on a reviewed unambiguous alias/context mapping, or a unique exact legal-name candidate with **two independent corroboration categories**. Name alone, fuzzy substring, `PC` tax status and generic education language are insufficient. City/state form one location category.
3. Truncated/ambiguous names remain evidence. A reviewed fixture mapping can establish Stanford's alias; that is not a general substring rule. Phase 1 deliberately trades recall for a deterministic, zero-LLM path.
4. Separately incorporated university foundations, hospitals and institutes are not automatically collapsed into a university. Approved mapping must state why the gift qualifies for the School and preserve the legal recipient as filed.
5. No new recipient entities in v1. Missing School identity/node stays pending for its owner. Preserve labels; never create another node to work around a label gap.

### Donor

Phase 1's donor is the **filing's canonical grantor**, not a name in the grant row. `990PF` supports foundation classification. Schedule I alone does not classify its filer as a private foundation or corporation. An unsupported donor class stays pending rather than receiving a misleading weight.

Phase 2 uses strong identifiers or evidence-backed matches onto existing people. Soft names nominate; an `ATTENDED` tie is one category, and class year from the same underlying record does not automatically become a second independent source. Several supported candidates mean review.

Auto-link requires **confidence ≥ 0.85 AND two independent corroboration categories**. With at least one category, confidence **≥ 0.60** may enter review. Zero corroborations caps confidence at **0.59** and stays unresolved. Do not put name-only rows into review merely because the model is confident. Store citations and evidence categories independently of the score.

Reuse 990's conservative ladder: identifiers/local corroboration before search; one supported local candidate goes to adjudication without buying a new search; first-name/nickname/initial **and** surname checks on profile results; uniquely corroborated profile preferred over a same-name crowd. Prove those rules on Donors data.

Mint people only with a verified strong key (v1: LinkedIn) passing the gate. Adjudication of a soft-name candidate links an **existing** entity; it does not create a name-only person. Check population caps before creation, use strong-key collision/merge handling, then `fanoutlimit.Bound.Offer` at tier 4, depth 1 with the true seed. No dispatch, promotion or company/team fanout. The 990 leaf-cap omission is unfinished work, not a pattern to copy.

Anonymous/honor-roll mentions never create people. Preserve couple names as filed: no Couple node, shared invented identity, arbitrary half split, or duplicate full amount on two people. Couple attribution is a decision below.

## Proposed AlloyDB storage

All Donors tables are `universe.*`, UUIDv7 IDs, Go-validated state vocabularies. Existing entities/identifiers, payloads, facts, review and enrichment queue remain owned by their current features. Add schema-skill entries and classify every entity reference in merge inventory.

| Table | Key / responsibility |
| --- | --- |
| `donation_job` | Unique typed job key (recipient sweep, grantor request, filing revision, page request); cursor/high-water mark, priority, claim owner/time, attempts, retry and outcome. `FOR UPDATE SKIP LOCKED`; checkpoint with output in one transaction. |
| `donation_recipient_alias` | Reviewed legal-name/context → canonical School, reviewer/evidence/validity. Uniqueness is context-scoped; ambiguous aliases cannot auto-resolve. |
| `donation_mention` | Source identity + original fields, recipient/donor resolution states/IDs. IRS key `(source_kind, object_id, ordinal, input_revision)`; web key `(snapshot_id, source_item_key, extractor_version)`. Retain cash/noncash, dates/period, names, quotes or structured evidence and provenance. |
| `donation_resolution_attempt` | Append-only, singular name matching 990. Mention, recipient/donor subject, method/candidates/corroboration, model/provider/prompt/parameters, usage/cost/error/outcome, review ref. Request/evidence key prevents duplicate replay attempts. |
| `donation_gift` | Accepted economic gift/installment: original donor/recipient, stated amount/currency, date precision, purpose/type, supersession state. Stable IRS source-line identity starts a candidate; a later article can corroborate it instead of creating another gift. |
| `donation_gift_evidence` | Unique `(gift_id, mention_id)`; explicit authoritative mention for conflicting fields. At most one active gift per mention; uncertain duplicates stay pending. |
| `donation_edge` | Unique canonical donor–recipient pair; chosen fact, aggregate, graph UUID, content/revision hash, written revision, eligibility/block reason. Changed aggregates become pending even after an earlier write. |
| `donation_edge_evidence` | Distinct gifts and direct/derived routes supporting a pair. Derived rows retain foundation, governance mention/ledger/fact/graph refs and grant period. Derivations reference the original gift, not a new economic gift. |
| `donation_source_snapshot` **(Phase 2)** | Canonical URL, fetch time/hash/GCS key, provider payload, source class and extractor/version state. Store raw before extraction; unchanged hash + extractor version skips paid extraction. |

Phase 1 uses existing filing payload/XML refs; it needs no snapshot table yet. Owner children cascade; cross-entity references follow merge conventions and repoint/canonicalize into one aggregate. Keep stable source IDs/public DTOs for filings provenance; Donors never changes/deletes filings rows.

**Separate states:** resolution `unresolved | auto_linked | needs_review | rejected | anonymous`; gift eligibility `eligible | parked | superseded`; graph `pending | written | blocked`. Edge success does not replace identity state. Retry unresolved rows on new evidence; never overwrite a human-review outcome automatically.

## Amounts, deduplication and replay

- Keep 990 cash/noncash as distinct nullable integer USD fields. Null is unknown; zero is stated zero. Sum only stated components, checking overflow. Web extraction preserves original currency/amount; do not assume every dollar sign is USD, invent conversions, or turn a band into an exact amount.
- Preserve real date or filing period/date precision; no synthetic day, no index year. Aggregates describe available source coverage, not lifetime giving.
- `gift_count` counts accepted gifts, **not mentions, URLs or trustees**. Same filing/article replay cannot increase it. Separate installments with identical values must not collapse just because donor/recipient/year/amount match.
- Pledge and payment are not automatically additive. Preserve their relationship/accounting basis; unresolved conflicts and uncertain duplicate contributions stay outside totals.
- Recompute from the complete accepted gift set, serialized per pair. Never `total += amount` in an at-least-once worker. Conditional written-revision stamps prevent an old graph attempt from marking a newer aggregate complete.
- Hub count covers **all grants in the selected foundation filing window**, not the accepted School subset or a batch. Crossing 200 or changing source coverage requeues every affected foundation/derived projection.
- Source replay maps a new mention revision back to the stable gift where appropriate and supersedes old evidence. Identity merges/corrections recompute old and new pairs. Removed final gifts require explicit fact/graph withdrawal; an insert-only pending sweep is insufficient.

## Trustee bridge

The prior proposal derives person `DONOR_TO {via_foundation_uuid}` edges from trustees. Preserve that capability as a proposal, while separating it from personal giving: board membership proves affiliation, not that the person funded or selected the grant.

A candidate requires a resolved individual trustee in a **contributing filing period covering the grant**, chosen `board_member_of` fact, written federal `BOARD_MEMBER_OF`, and an eligible foundation gift. An `OFFICER_OF`, current seat for an old grant, former flag, institutional trustee or missing-year assumption does not substitute. Require the foundation's own `DONOR_TO` before projecting a shortcut. Donors never resolves trustees.

Store exact dependencies; governance corrections invalidate the derivation. Closed graph gates leave it pending. Foundation gifts/edges proceed independently of person resolution.

**Unsettled:** one pair edge + one `via_foundation_uuid` cannot encode direct giving plus two foundations. Do not overwrite the foundation, add indirect amounts to direct personal totals, or create parallel edges to evade the contract. Release foundation edges first, retain bridge evidence, and keep bridge projection off until Q1/Q2 settle attribution and multi-route aggregation. Existing ontology fields remain authoritative until a coordinated change is approved.

## Facts and graph projection

1. Persist a source-linked Donors envelope via `enrichmentpub.AgentPayloadWriter`; IRS raw evidence already has a filing payload/GCS key. Preserve provider attempts separately from identity attempts.
2. Add `donor_to` vocabulary and mapping to facts and elect per recipient in **both person and company distill**; these are not built. Donor class and aggregate/provenance live in Donors' ledger.
3. Recompute the ledger; preserve sibling facts and explicitly withdraw retracted claims. Missing targets in an envelope do not remove old claims.
4. Require feature flag, edge flag, allowed School, both graph nodes and the correct elected target via `ElectedRelationFacts`; record fact ID. Auto-linked mentions alone cannot draw edges.
5. Add a narrow graph-feature Donors writer for **Person→Company and Company→Company**. The current person edge seam lacks the full donation aggregate/company-donor path. Parameterized Cypher, stable canonical pair identity, complete envelope; no company writes squeezed through a person-only MATCH.
6. Stamp graph UUID/written revision after success; reconcile partial failure, merge and retraction. Known-to-unknown changes need deliberate clearing: “omit zero fields” must not preserve stale foundation/amount data.

[Edges → DONOR_TO](/guides/ontology/edges#donor_to) owns the graph contract. Required: `donor_type`, `gift_count`, `mention_ref`, `source_urls`, `confidence`, and envelope `uuid, created_at, updated_at, weight, description, description_generated_at`. Known totals/years, purpose/types are optional. Every source stays in the relational evidence set; `mention_ref` is a deterministic representative.
