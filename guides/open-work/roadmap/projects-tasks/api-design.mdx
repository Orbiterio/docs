## Transport and response conventions

All routes are under `/v1`, authenticated at module registration. Use the existing `{data,error,meta}` envelope and typed middleware errors. Return nullable fields as null and arrays as empty arrays. A list's `data` carries `items`, `total`, and `next_cursor`; do not use offset pagination. Create/execute/adopt operations require an idempotency key; edits/transitions require expected versions. A 202 response means queued, not completed.

Use `pmw.RequireWorkOS` and `pmw.OrbiterUserID` for authenticated routes. Wire DTOs and domain types remain separate, with explicit mappers. Use decimal strings for monetary and estimate amounts at the API boundary and exact decimal arithmetic. Date-only fields use validated YYYY-MM-DD values; null explicitly clears an optional field, while omission from PATCH preserves it.

## Personal ToDo and Suggested task contract

### Create and edit a personal task

A user can capture “Buy milk” with no project. The server takes the owner from authentication, inserts a personal task and its sole owner-assignment atomically, records acceptance/creation and returns the canonical task. Reject attempts to set another owner through this create path. `/me/todos` rejects non-null project/deal references; the generic create route dispatches to this command only when project is absent/null. An invalid supplied project is an error, not a fallback to private ToDo.

```http
POST /v1/me/todos
Idempotency-Key: <client-generated-key>
Content-Type: application/json

{"title":"Buy milk"}
```

The resulting task has `project_id: null`, `root_project_id: null`, `personal_user_id` equal to the signed-in user, that user as its sole assignee, `status: "todo"`, and null target/due/estimate fields. It appears once in that user's ToDo table. Empty personal tables return an empty list; there is no fake project to create or authorize.

Task DTOs include nullable project/root/personal-owner keys, ordinary content/status/version, assignees, acceptance/proposal provenance, `target_date`, `due_date` and `estimate`. The estimate wire shape is either null or `{amount: decimal-string, unit: minutes|hours|days|weeks|months}`. These are documented Go-validated values, not OpenAPI enums. For example:

```json
{
  "expected_version": 1,
  "target_date": "2026-09-21",
  "due_date": "2026-09-22",
  "estimate": {"amount": "1.5", "unit": "hours"}
}
```

Apply this body through `PATCH /tasks/{id}`. `estimate: null` clears both storage fields; a supplied estimate must include both valid amount and unit. Reject invalid units, negative/non-finite/out-of-range values and excess decimal precision instead of rounding. Return a warning for target later than due. Changing an estimate never recalculates dates, completes a task or creates a calendar event. Both personal and project tasks use the same fields/validators.

`GET /me/todos` returns only owner-matching project-free records. Active/Completed filters use accepted work; Suggested uses `status=suggested` and the owner's suppression state. Default rows exclude archived items. Counts, search, export and sorting apply the same scope and lifecycle filters before pagination. My Tasks may expose Suggested as a separate explicitly requested section, never count it as committed assigned workload. Clearing an assignee does not turn a project task into a ToDo; only removing project placement through the dedicated command does.

### Accept or delete an AI proposal

Only a validated, authorized AI proposal/import command creates `status=suggested`; ordinary create is accepted, even when an agent performs an exact user instruction. Create the proposed task and its suggestion/provenance atomically. Store at most one live proposed task per scope/intent. A Suggested row can have editable proposed title, dates and estimate, but no execution/progress/completion or commitment notifications. Editing is not acceptance; update the task and linked proposal versions/fingerprint together, and accept the reviewed current task fields rather than replaying the original AI payload.

`POST /tasks/{id}/accept` takes `expected_version` and an idempotency key. The owner of a personal proposal, or an eligible editor of its project, can accept. Lock the proposal and task, validate current ownership/source/versions, set task `status=todo` and acceptance actor/time, mark the suggestion adopted with `adoption_type=accepted_task` and the same result task ID, then commit activity/receipt together. Accept returns the task; normal assignment and project-placement controls are available afterward. No action run or external side effect is implied.

The existing `/project-suggestions/{id}/adopt` endpoint dispatches new-task proposals to this same service command; its historical route name does not require a personal proposal to have a project. Reject generic PATCH of status to bypass Accept, or of accepted work back to Suggested. Editing/suggesting changes to an existing accepted task uses an independent change request.

`DELETE /tasks/{id}` takes an expected version via `If-Match` and an idempotency key and is supported for **personal Suggested tasks owned by the caller**. It archives the task, withdraws the proposal with a user-deleted reason, and records dismissal by stable intent in one transaction. The UI labels this **Delete** and can offer Undo through an explicit versioned restore command; it does not hard-delete provenance/receipts. `POST /tasks/{id}/restore-suggestion` clears that explicit dismissal and restores the same still-valid proposal to Suggested, never directly to accepted. Expired or invalid source context returns an actionable conflict instead. Accepted tasks continue to use the ordinary archive/cancel commands.

For shared project suggestions, **Delete for me** uses personal dismissal (`/project-suggestions/{id}/my-state`); **Withdraw for everyone** requires the existing root-admin permission and closes the unaccepted row for all readers. Do not represent personal dismissal as a shared deletion. Ignore, save and snooze never accept work. Rephrasing the same dismissed intent does not recreate it.

Concurrent Accept/Accept and Accept/Delete/withdraw use one task/suggestion lock order and expected-version rules. The winner commits once; retries with the same key/body return its existing result after reauthorization, while incompatible later decisions conflict. Archived/withdrawn/expired proposals cannot be accepted through a stale row. Accepting a Suggested task with a past proposed due date discloses that date and only then enters normal accepted-task reminder policy.

### Assigning or removing a project

`PUT /tasks/{id}/project` accepts expected task version, an idempotency key, the requested project ID (or null), and explicit destination-assignee choices. The command previews/discloses the resulting audience in the UI; this is the user's placement action, not a model-selected scope change.

- **ToDo → project:** require the personal owner and editor access to the destination. Accept Suggested work first. Preserve ID/title/date/estimate, set project/root and clear personal ownership, validate assignees as destination editors, then remove the row from ToDo. Retaining the current user is the default when eligible; assigning others is explicit.
- **Project → ToDo:** require a source-root admin and an explicitly chosen active recipient who currently has editor access to the source. Set both project/root to null, set that recipient as personal owner/sole assignee, and make the new state private. Do not interpret a generic PATCH null or project deletion as authorization to privatize shared work.
- **Within one project root:** existing access/eligibility rules apply. Direct project-to-project cross-root moves remain outside V1; the explicit personal/project placement commands above are the scoped exception to the earlier project-only rule.

Reject placement with unresolved deal/work-key links, dependencies that would cross scope, or dispatched/unknown actions. Resolve those explicitly first. Cancel undispatched stale jobs/notifications, invalidate prepared commands, and derive any new follow-ups only for accepted work and the new scope. Historical activity/receipts/provenance keep their original audience and cannot leak private source content into the destination. Record a safe placement event in both relevant histories; fetch task details only under its current ACL. Lock source/destination scope and task rows in a globally stable order and commit all current membership changes atomically, so a failed placement leaves the original ToDo/project row intact.

## Authorization and shared-content rules

For a personal ToDo and its history/suggestions/preferences/jobs, only the active `personal_user_id` owner has access; organization/team/root-admin status confers none. An agent uses that owner's explicit authorized scope, never arbitrary supplied user IDs. Personal tasks do not require organization membership.

For project-scoped work, effective access is the union of valid routes, ordered admin, editor, viewer:

- An active root owner who is still an active member of the owning organization is an admin.
- Active owners/admins of the non-deleted owning organization have recovery/admin access. Ordinary members require an explicit grant.
- Accepted linked-team members are editors; accepted team admins are admins, independently of organization membership.
- Active members of explicitly granted non-deleted organizations receive the grant's viewer/editor role.

All routes require an active account. Pending/rejected/inactive membership confers nothing. Within project scope, creator attribution, deal ownership, task assignment, stakeholder links, preferences, and suggestion targeting never grant visibility; the personal-owner boundary is a separate explicit authorization rule. Revoking one route removes it immediately for subsequent authorization checks, while other intentional routes remain valid.

Admins configure pipelines, sharing, hierarchy, root ownership, and archive. Editors create/edit work, attest criteria, assign eligible users, adopt suggestions, and move deals under the same transition rules. Viewers read and manage their own suggestion responses. Explicitly withdrawing a suggestion for everyone is an admin operation.

Apply ACL before filtering, counts, search, pagination, exports, board summaries, agent inputs, and sends. Return 404 for inaccessible resources, 403 for a forbidden operation on a readable resource, 409 for version/idempotency conflicts, and typed validation errors for invalid input.

`nodespub.Hydrate` can contain the caller's personal contact details and paths. Use it for that caller's response; do not persist the entire hydrated object into shared deal content or agent evidence. Use shared-safe entity facts for root-wide reasoning. Private email, attachments, relationship paths, or imported suggestion content require both source access and permission to disclose to the root audience. Personal feedback stays private.

Organization/team deletion removes that route and nullable ownership/configuration references without deleting the work or making it public. If no admin remains, preserve content for explicit administrative recovery. Parent archive suppresses descendants without overwriting their independent archive state. The explicit personal/project placement command is the only supported change between private ToDo and project audience; direct project-to-project cross-root moves are not supported; a deliberate pipeline copy is configuration reuse, not a work transfer.

## Commands, concurrency, and invariants

For a state-changing command:

1. Verify the caller and normalize the typed request. Begin a transaction, resolve idempotency, and acquire the scope lock: the project root row or an owner-scoped transaction advisory lock for personal ToDos. Define one stable lock-key namespace/order; do not serialize unrelated ToDo owners on a global lock.
2. Recheck the live project ACL or personal owner. Hold shared locks on the authorizing user/org/membership rows for the short mutation so a concurrent revocation has a defined ordering.
3. Lock affected project/pipeline/deal/task/suggestion rows in stable ID order. Compare expected resource versions and pipeline configuration version where relevant.
4. Validate hierarchy, dependencies, assignment eligibility, stage criteria, references, and action scope.
5. Write state, activity, command receipt, and any durable run/follow-up intents atomically. Increment domain versions and relevant board/configuration versions.
6. Commit. Optional Pub/Sub publication wakes the worker; the durable sweep also finds the work if publication fails.

V1 serializes domain mutations within one root or personal owner for clear hierarchy, permission, and transition guarantees. Worker claims are separate short transactions; never hold a job lock while waiting for a scope lock or a provider. Contention is measured before introducing narrower lock partitions.

`last_progress_at` moves only on an explicit progress update, actual delivery, or evidenced advancement. Research scans, reminders, drafts, suggestions, priority/deadline changes, sharing, assignment, and rank changes do not reset it. Operational leases/schedules do not increment domain versions or `updated_at`.

### What the schema requires of a command

The tables are built, and a few of their constraints decide the order or shape of the SQL a command can run. The constraint behind each point is tested in the backend, and so is the placement order. The commands themselves are not built, so each point needs its own test when the command lands. See the [as-built record](/guides/open-work/roadmap/projects-tasks/table-design#as-built-record) for the constraints themselves.

- **Set `accepted_at` on every insert unless the status is `suggested`.** No CHECK reads the status value, so a null `accepted_at` is what the database treats as Suggested: such a row cannot hold a work key, a start, a completion, a completion summary or a progress time, and it is left out of the accepted-only due-scan index. A direct create that forgets `accepted_at`, and with it `accepted_by_user_id`, is stored without error, with `status=todo`, and then silently never gets a due reminder and cannot be started. The database rejects the insert only if the row also carries a column that depends on acceptance: `accepted_by_user_id`, a work key, a start, a completion, a completion summary or a progress time. Nothing in the database ties `status` to `accepted_at`, so add a service invariant test. Accept sets `status=todo` and `accepted_at` in the same statement.
- **Placement runs as delete assignees, update the task, insert assignees.** An assignee row is tied to its task's current scope by foreign keys that are checked at the end of each statement, so updating the task's scope in place while assignee rows exist fails. Reject a dependency that would cross scope before the update; the database would reject it too, with a less useful error.
- **Swapping a pipeline's default stage takes two statements**, clear the old default and then set the new one, inside the command's transaction. One live default per pipeline is a unique index, checked per row.
- **Map a unique violation by constraint name.** tasks, agent_runs and agent_suggestions each hold several unique indexes, so a `23505` can mean a duplicate work key, a second open suggestion for the intent, a duplicate import, or a second active run. Do not collapse them into one conflict message.
- **Claim and reclaim queries write the status value as a literal**, not as a parameter: `WHERE status = 'queued'`, `'running'`, `'pending'` or `'processing'`. The ready and expired-lease indexes are partial on those values and the planner uses them only when it can see the value. Every exit from a lease clears `lease_token` and `lease_until` together.
- **Validate decimals in Go, before the write.** Reject a third decimal on an estimate and a fifth on a deal value, which Postgres would silently round. Reject an 11th integer digit on an estimate and a 17th on a deal value, which Postgres would refuse with a numeric overflow. Reject `NaN` and infinity with a typed validation error instead of letting the database answer with a 500: a CHECK rejects `NaN` on estimates, deal values and the agent budget, a CHECK rejects infinity only on the agent budget, and the two typed columns refuse infinity themselves with the same overflow. `1.5` reads back as `1.50`, so the DTO mapper trims the padding.
- **On a personal agent run, suggestion or action run, the requesting, targeted, authorizing and on-behalf-of user is the owner or null.** The database enforces it, which matches the rule that an agent never acts on supplied user IDs.
- **Placement receipts are root-scoped.** A receipt belongs to exactly one of a root or a personal owner, so a command that spans both records the root.

## Account deletion and personal data

**Tracked as APP-107. It must ship before the first command that can write a personal row, and the workflow API flag must not be enabled without it.**

Table Design requires that a personal owner is never set to null and that work history is never cascaded away, so the database refuses to delete a user who still owns private ToDo data. The refusal is not clean today. Account deletion removes the WorkOS account first and the user row second. If the second step is refused, the person can no longer sign in but their data is still here. On the WorkOS `user.deleted` webhook the same refusal returns a 500 and WorkOS retries.

Add an explicit clean-up step owned by the projects feature, exposed through `projectspub` and called by the users feature. The composition root only wires the two together. It runs on all three deletion paths: self-service, operator, and the WorkOS webhook. On the self-service and operator paths it runs **before** the WorkOS account is removed, so a failure leaves the account fully intact. On the webhook path WorkOS has already removed the account before the event arrives. There the clean-up runs before the local user delete, a failure still answers 500 so WorkOS retries, and the step must therefore be safe to run twice.

In one transaction, as ordered statements:

1. **Clear every nullable pointer at the owner's private rows.** That covers pointers held by rows that survive, such as project history, runs, actions and reminders that mention a task which was later placed into the owner's ToDo. It also covers pointers the private rows hold at each other. Tasks, suggestions, agent runs, action runs and history reference one another through blocking foreign keys, so no delete order exists until those are cleared.
2. **Delete the private rows table by table, children first:** follow-ups, action runs, history, suggestions, agent runs, receipts, task dependencies, tasks.

Deleting those rows is also what cancels the owner's pending personal jobs and reminders. One point is left for APP-107 to decide: what to do when a personal action is mid-dispatch to a provider at the moment the account is deleted. Nothing else needs handling: preferences, personal suggestion responses, reminders addressed to the user and task assignments already disappear with the user, and shared project work survives with the person's name removed.

Test it on a real database with a user who owns personal tasks, a Suggested proposal for one of them, an action run, a reminder and history, including a task that was moved from a project into their ToDo. This is the Account deletion [acceptance gate](/guides/open-work/roadmap/projects-tasks#acceptance-gates-and-operational-checks).

## Stage criteria and suggested actions

Each stage has a stable ID, editable display fields, and a semantic category: `backlog`, `unstarted`, `started`, `done`, or `canceled`. Nonterminal categories derive `open`; `done` derives `won`; `canceled` derives `lost`. The category cannot be changed after the stage has been used; create a replacement stage and explicitly move affected deals instead.

Store a bounded, versioned criteria document on the destination stage. V1 supports an `all` list of at most 20 typed checks, each with a stable criterion UUID:

| Check | Deterministic evidence |
|---|---|
| `has_target` | The deal's canonical target resolves. |
| `has_stakeholder` | An active stakeholder with the required role exists. |
| `field_present` | An allowlisted deal field is populated, such as owner or expected close date. |
| `task_done` | The active task matching the criterion's stable `work_key` in this project/deal is done. Pipeline criteria do not embed one deal's task UUID. |
| `action_succeeded` | A matching action run has an acknowledged result for this deal, action type, and target. |
| `user_confirmed` | An authorized user has explicitly attested the criterion, with timestamp and optional permitted evidence. |

No arbitrary code, SQL, model-written predicates, or unrestricted expression language. Criteria evaluate to met/unmet/unknown; unknown blocks advancement. The model explains gaps and prepares work but cannot manufacture evidence or attest on behalf of a user.

A move validates destination criteria, the deal's expected version, and the pipeline's expected configuration version. A manual drag uses the same rules. There is no silent bypass. A user can explicitly attest a configured human-confirmation criterion or an admin can edit criteria; both create history. A move to an unsuccessful terminal stage requires a reason, and reopening requires an explicit command and the destination's criteria.

Stage action guidance is a bounded list of stable rule IDs, titles, rationale templates, registered action types, and validated default parameters. It is guidance, not an executable authorization. Editing criteria or action guidance increments the pipeline configuration version and invalidates stale prepared commands.

## Registered actions

| Action family | Execution rule |
|---|---|
| Resolve people/companies, inspect permitted context, prepare a next-step explanation or draft text | Allowed by bounded root delegation or an owner-requested personal review; may create Suggested proposal rows/artifacts, never accepted work solely from the model output. |
| Create/link a task, edit work, add/remove a stakeholder, attest a criterion, move/archive/reopen a deal | An explicit typed human command or exact authorized action run calls the same projects service methods as the UI. Agents cannot self-attest human-confirmation criteria. |
| Create/update a mailbox draft | Requires the mailbox owner's explicit action and a verified grant; uses the new `emailspub` service contract. Agent-prepared text can exist before mailbox creation. |
| Send email | Exact sender/grant, recipients, subject, body, and related versions are authorized. Provider outcome is persisted; no automatic resend after uncertainty. |
| Introduction | Prepare a double-opt-in sequence. Each person's consent is retained before the final introduction; one approved request is not approval for all later messages. |
| Draft SMS or meeting brief | Produce a user-visible artifact. No SMS send or calendar mutation capability is advertised until an owned, tested adapter exists. |

The action registry lives in reviewed Go code. Pipeline JSON selects from that registry and cannot introduce arbitrary tools, URLs, SQL, or shell commands. Agents may propose multi-step work, but each executable side effect has its own authorized action run and receipt. Model prose never authorizes an action.

## Pagination

Standard lists use creation-time/ID keyset pagination, default 50 and max 200. ToDo cursors bind the authenticated owner, status/search filters and selected sort. For due/target sorting, use a validated date/null-bucket/ID cursor; do not sort only the current browser page. Mixed estimate units remain separate unless the user selects a disclosed conversion policy. Suggested counts are separate from accepted workload counts. Board columns use a projects cursor carrying pipeline/stage, rank/ID, filters, and board order version. A move/reorder/archive invalidates old column cursors with 409; the UI refetches rather than silently skipping or duplicating cards. Counts remain permission-filtered.

Rank storage, rebalance rules, and the board version counter are defined in [Table Design](/guides/open-work/roadmap/projects-tasks/table-design#board-storage-and-ordering).

## Kanban response and interaction contract

The board response includes stage IDs/categories/order, pipeline configuration/board versions, permission-filtered counts, and the first page per requested column. Cards show owner, canonical target, optional value/currency, dates, stage age, meaningful progress, blockers, and a small set of ready next steps. Detailed private artifacts are fetched separately with their owner's permissions.

Drag/drop shows the resulting operation. On unmet criteria, display the gaps and prepared actions; on 409 refetch without overwriting newer work. Reordering never changes stage. A card can remain visible after a failed or unknown action, with its actual state. Every action has clear prepared/queued/running/succeeded/failed/unknown labels; avoid displaying queued work as finished.

## Implementation and verification

Maintain `api/projects.openapi.yaml` and its root OpenAPI references alongside handlers, DTOs, SQL, and tests. The [main build plan](/guides/open-work/roadmap/projects-tasks#implementation-layout-and-build-slices) defines delivery order; its [acceptance gates](/guides/open-work/roadmap/projects-tasks#acceptance-gates-and-operational-checks) cover access, concurrency, agent execution, provider outcomes, and UI behavior.
