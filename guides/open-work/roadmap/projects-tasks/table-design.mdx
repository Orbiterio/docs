## Data model: 17 feature-owned tables

These 17 tables form the complete feature-owned AlloyDB schema. Reused users, organizations, teams, entity records, email records, and notification records remain in their existing AlloyDB feature schemas.

| # | Table | Purpose |
|---|---|---|
| 1 | `projects.projects` | Root projects and nested subprojects. |
| 2 | `projects.project_organization_access` | Root-level viewer/editor grants. |
| 3 | `projects.tasks` | Personal ToDos and project tasks, including unaccepted Suggested rows; project tasks may link to a deal. |
| 4 | `projects.task_assignees` | Personal owner assignment or multiple eligible project assignees. |
| 5 | `projects.task_dependencies` | Finish-to-start prerequisites. |
| 6 | `projects.pipelines` | Root-owned process configuration. |
| 7 | `projects.pipeline_stages` | Ordered stages, criteria, and action guidance. |
| 8 | `projects.deals` | Project-owned opportunities and current stage. |
| 9 | `projects.deal_stakeholders` | Canonical people/companies with supported roles. |
| 10 | `projects.work_activity` | Append-only history within the recorded personal or project audience. |
| 11 | `projects.agent_suggestions` | Optional next steps and exact change proposals. |
| 12 | `projects.suggestion_user_state` | Private save/snooze/dismiss state by stable intent. |
| 13 | `projects.agent_runs` | Durable, bounded research/planning jobs. |
| 14 | `projects.action_runs` | Authorized action execution and receipts. |
| 15 | `projects.followups` | Durable per-recipient notification occurrences. |
| 16 | `projects.command_receipts` | Idempotency for domain commands. |
| 17 | `projects.project_user_preferences` | Per-user reminder controls for project or personal ToDo scope. |

### Shared schema rules

Below, `?` means nullable; unmarked fields are required. All new row IDs are application-minted UUIDv7. Foreign-key IDs are UUIDs; strings crossing HTTP do not become text FKs. Unless overridden, mutable domain rows have `id`, `created_at`, `updated_at`, and `version BIGINT DEFAULT 1`. Timestamps are `TIMESTAMPTZ`; titles and enum-like values are text. JSON fields have typed, versioned, size-bounded schemas and non-null `{}` or `[]` defaults where appropriate.

Project-only rows retain required project/root keys. Task-capable rows use one of two exclusive work scopes:

| Scope | Required keys | Null keys / constraints |
| --- | --- | --- |
| Project | `project_id`, `root_project_id` matching a real project | `personal_user_id` is null. Optional deal must be in this project. |
| Personal ToDo | `personal_user_id` identifying an active owning user | `project_id`, `root_project_id`, `deal_id` and `work_key` are null. No hidden project or organization grant. |

Apply this choice to tasks and their current assignment, suggestion, run and follow-up context. Dependencies, personal-response and preference rows need the root-or-personal-owner key but not a project key. Structural CHECK constraints reject both scopes, neither scope and partially populated project keys. Composite FKs/unique keys enforce current task/scope and project/root/deal membership. Add the required unique keys before dependent FKs; nullable FK behavior alone is not a scope constraint. Enum membership stays in Go validators.

Historical activity/receipts and accepted suggestion provenance retain their **original** audience and use stable task IDs without a composite FK to the task's current location. Moving a personal task into a project does not republish its earlier private history. Current placement-dependent joins are updated transactionally; historical references confer no new access.

Tasks and shared work are archived, not hard-deleted through ordinary product APIs. Delete on a personal Suggested item is a recoverable archive plus intent dismissal. Structural work/history FKs use `RESTRICT`; nullable human attribution/ownership uses `SET NULL`; pure user-assignee/grant/preference joins may cascade. Deleting a user, team, or organization must not delete shared projects or deals. Personal-owner FKs are not nullable attribution: account deletion must explicitly clean up or retain inaccessible personal rows through the owning account lifecycle, never SET NULL them into an unowned/public task. Cancel the owner's pending jobs and reminders. Canonical entity references are typed logical references through the AlloyDB-backed `nodespub` readers. Validate the resolved entity type as well as its ID.

### 1. projects.projects

| Fields | Type/default and rule |
|---|---|
| `parent_project_id?`, `root_project_id` | UUID FKs. Roots reference themselves; children inherit the root. |
| `title`, `description?`, `success_criteria?` | Nonblank title and optional text. |
| `status`, `priority` | `planned` and `normal` defaults. Project statuses: planned, active, on_hold, completed, canceled. Priorities: low, normal, high, urgent. |
| `owner_user_id?` | Accountable lead; required and eligible on creation. Only root ownership grants access. |
| `owning_organization_id?`, `team_id?`, `timezone?` | Root-only settings. Owning org and valid IANA timezone required on root creation; no child overrides. |
| `target_date?`, `due_date?` | DATE. Target after due is surfaced as a warning, not silently changed. |
| `next_action?`, `last_progress_at` | Accepted next step and last meaningful progress. |
| `agent_assistance_enabled`, `agent_review_interval_hours?`, `agent_daily_budget_usd?`, `next_agent_review_at?` | Root-only; false by default. Enabled roots default to a 24-hour review cycle, minimum 1 hour, and a configurable USD 5 daily budget. |
| `agent_review_cursor?`, `agent_review_cycle_started_at?` | Root-only operational cursor and cycle time, persisted independently of domain versions. |
| `created_by_user_id?`, `created_by_agent_key?`, `created_by_agent_run_id?` | Trusted immutable creation provenance. Human attribution survives as null if the account is removed. |
| `completed_at?`, `archived_at?`, `access_version` | Lifecycle and root authorization version. Access changes increment the root access version. |
| Common mutable fields | `id`, `created_at`, `updated_at` and `version`, per the shared rule. `version` is the value a PATCH echoes as its expected version; `access_version` is separate. |

Root-only settings are null on children; `agent_assistance_enabled` is false on children and their unused `access_version` remains 1. Expose resolved root settings in API responses. Serialize hierarchy changes under the root lock, reject cycles and cross-root moves, and cap nesting at 10 levels. Completing a project requires all non-archived descendant projects to be completed/canceled, accepted tasks done/canceled, and deals terminal; Suggested task rows do not block completion; report remaining blockers instead of silently closing them. Archived unfinished work is shown in the confirmation summary. Completion is an explicit command, not a count-derived mutation.

### 2. projects.project_organization_access

Fields: `id`, `root_project_id`, `organization_id`, `role` (viewer/editor), `granted_by_user_id?`, `created_at`, `updated_at`. Unique root/org, plus reverse org/root index. Resolve active members of non-deleted organizations at request time. No grant means private, not public. Do not automatically grant the owning org or a linked team's attributed org. `organization_ids` in responses is derived from these rows.

### 3. projects.tasks

| Fields | Type/default and rule |
| --- | --- |
| `project_id?`, `root_project_id?`, `personal_user_id?`, `deal_id?`, `work_key?` | Exclusive project-or-personal scope above. Project-free means exactly one personal owner, never unassigned work. |
| `title`, `description?`, `acceptance_criteria?` | Nonblank title plus optional editable text. |
| `status DEFAULT todo`, `priority DEFAULT normal` | Statuses: **suggested**, todo, in_progress, blocked, in_review, done, canceled. Priority: low, normal, high, urgent. |
| `target_date?`, `due_date?` | Independent DATE values. Target after due warns, rather than rewriting either date. |
| `estimate_amount?`, `estimate_unit?` | Paired fields: `NUMERIC(12,2)` and text; both null or both present. Nonnegative amount, no NaN/infinity or silent precision rounding. Units: minutes, hours, days, weeks, months. HTTP amount is a decimal string. |
| `source_suggestion_id?`, `accepted_at?`, `accepted_by_user_id?` | Immutable proposal provenance and explicit commitment time/actor. Suggested has no acceptance time. Direct human creation or an exact user-authorized create records acceptance immediately. |
| `next_action?`, `blocked_reason?`, `blocked_at?`, `next_check_in_at?`, `last_progress_at?` | Manual block needs a reason. Unaccepted Suggested work has no meaningful-progress time. Accepted work uses existing progress rules. |
| `completion_summary?`, `started_at?`, `completed_at?`, `archived_at?` | Ordinary work lifecycle. Suggested cannot start, complete or acquire completion timestamps before acceptance. |
| Creator/agent provenance, common mutable fields | Trusted origin, created/updated time and optimistic version. |

**ToDo is a catch-all view**, not another task table: query `project_id IS NULL` with the authenticated `personal_user_id`, then apply status/archive filters. It exists for every user even with zero tasks/projects. All its task rows belong to and are assigned to that user. Project tasks may be unassigned or have multiple eligible assignees. My Tasks combines accepted personal rows and readable project assignments; Suggested counts remain separate.

Preserve estimate amounts/units exactly: 15 minutes, 1.5 hours, 2 days, 3 weeks and 1 month round-trip without canonicalizing to integer minutes. This replaces `estimated_minutes` as the authoritative estimate. An existing in-range integer value migrates losslessly to amount plus `minutes`; a null remains null. Report out-of-range legacy values for explicit resolution rather than truncating them. Remove or version any legacy writable estimate field so two columns cannot disagree. Do not derive dates, workdays or a fixed-minute month from this value. Cross-unit sums require a declared conversion policy; otherwise group totals by unit.

Acceptance changes `suggested` to `todo` on the same task ID and records acceptance in one transaction with its suggestion/receipt. Editing proposed dates/title/estimate alone does not accept it. Suggested rows are excluded from committed workload/due/reminder scans, dependency endpoints, deal `task_done` requirements and project-completion blockers. No normal edit can reset accepted work to Suggested. Reopening accepted work clears current completion fields while preserving acceptance and history.

Project placement is an explicit command, not arbitrary PATCH of scope columns. It keeps the task ID, date values and estimate; validates the destination audience and assignees; cancels obsolete pending work; and updates current scoped joins without changing historical audiences. An unresolved suggestion must be accepted before placement. Dependencies/deal links or in-flight/unknown actions that cannot safely cross scope block placement with a useful reason. See the [placement contract](/guides/open-work/roadmap/projects-tasks/api-design#assigning-or-removing-a-project).

Suggested proposals keep any proposed work key in the typed suggestion payload until acceptance, so they cannot reserve a committed requirement slot. `work_key` is an optional stable pipeline requirement key, such as `diligence_review`, set by an authorized create/link command and meaningful only with a deal. Validate it against that deal's pipeline criteria/guidance. Enforce one non-archived task per deal/work key. A canceled or missing required task does not satisfy `task_done`; replacement is explicit. Copying a pipeline preserves semantic work keys while giving stage/criterion/rule rows fresh IDs, so every new deal can supply its own work.

### 4. projects.task_assignees

Fields: `id`, `task_id`, `project_id?`, `root_project_id?`, `personal_user_id?`, `user_id`, `assigned_by_user_id?`, `assigned_by_agent_key?`, `assigned_at`. Unique task/user, reverse user/task index, and current-scope consistency with the task. A personal ToDo has exactly one assignment, to `personal_user_id`; create/placement commands maintain it atomically, and the API rejects clearing it or assigning another user while project-free. This identifies the owner of a Suggested row without making it accepted or sending an assignment notification.

Project tasks allow zero or multiple assignments; active assignees require editor rights. Suggested project tasks retain proposed assignee IDs only in the suggestion payload until explicit acceptance/assignment validates them. Project assignment never grants visibility. Revoked project assignments remain visibly ineligible, receive no reminders, and can be explicitly reassigned; user deletion removes the pure link while the personal-owner lifecycle remains enforced.

### 5. projects.task_dependencies

Fields: `id`, `root_project_id?`, `personal_user_id?`, `task_id`, `depends_on_task_id`, `created_by_user_id?`, `created_at`. Unique dependent/prerequisite; reverse prerequisite lookup. Both tasks must be accepted; they must share the same project root or both be personal ToDos of the same owner. Project-to-personal and cross-owner dependencies are invalid. No self-link or cycle, including simultaneous inverse inserts. Unfinished or canceled prerequisites block completion. Removing/replacing a prerequisite is explicit and audited.

### 6. projects.pipelines

Fields: common mutable fields; `root_project_id`; `title`, `description?`, `kind DEFAULT custom`, `icon_name?`, `color?`, `default_currency?`; `position`, `configuration_version BIGINT DEFAULT 1`, `board_version BIGINT DEFAULT 1`; `source_template_key?`, `source_template_version?`, `copied_from_pipeline_id?`; `created_by_user_id?`, `archived_at?`.

Kinds are descriptive Go-validated strings such as fundraising, sales, partnerships, hiring, custom. A root may have multiple pipelines. Root admins manage configuration. Copy requires read access to the source and admin access to the destination; copy stages/criteria/guidance with fresh IDs, preserve semantic work keys, and copy no deals, people, history, or permissions. Remove source-specific targets/evidence/default parameters and require valid configuration before admitting deals. Copies do not receive later source edits. A provenance source FK is nullable with `SET NULL`.

### 7. projects.pipeline_stages

Fields: common mutable fields; `pipeline_id`, `root_project_id`; `name`, `category`, `color?`, `position`, `is_default DEFAULT false`; `criteria JSONB`, `action_guidance JSONB`; `stale_after_days?`; `archived_at?`.

Use stable stage IDs. A pipeline has exactly one active, nonterminal default stage and at least one active successful and unsuccessful terminal stage before deals are admitted. At most one default is enforced by a partial unique index; the full configuration rule is transactional service validation. `stale_after_days` is a positive integer when set. Archive referenced stages rather than deleting them; an archive command names a compatible replacement for open deals and records each transition. A configuration edit increments pipeline configuration version even when no deal moves.

### 8. projects.deals

| Fields | Type/default and rule |
|---|---|
| `project_id`, `root_project_id`, `pipeline_id`, `stage_id` | Required UUIDs with composite integrity. Pipeline and project share a root. |
| `title`, `description?`, `owner_user_id?` | Title required; eligible owner required at creation. Ownership alone grants no access. |
| `entity_type`, `node_uuid` | Canonical primary target: persons or companies. Resolve through nodes before admission; target changes are explicit. |
| `value?`, `currency?`, `expected_close_date?` | NUMERIC(20,4), ISO currency text, DATE. Value/currency are both present or both absent; value is nonnegative. No floating-point money; serialization follows the [API conventions](/guides/open-work/roadmap/projects-tasks/api-design#transport-and-response-conventions). |
| `next_action?`, `blocked_reason?`, `last_progress_at`, `stage_entered_at` | Accepted action, explanatory block, actual progress, and current stage age. |
| `criterion_attestations JSONB` | Typed map keyed by criterion ID/version with attesting user/time and permitted evidence references. A model cannot write user attestations. |
| `position`, `won_at?`, `lost_at?`, `lost_reason?`, `archived_at?` | Board rank and lifecycle. Unsuccessful closure requires a reason. |
| `created_by_user_id?`, `created_by_agent_key?`, `created_by_agent_run_id?` | Immutable creation provenance, plus common mutable fields. |

Derive the deal's outcome from stage category; do not add a separately writable outcome column. Stage moves update current terminal timestamps transactionally; reopening clears current closure fields and records the prior values in history. The same target can legitimately have different opportunities; warn about possible duplicates within the project/pipeline, but do not impose a global target uniqueness constraint. A copied default currency does not redenominate existing deals.

### 9. projects.deal_stakeholders

Fields: common mutable fields; `deal_id`, `project_id`, `root_project_id`; `entity_type`, `node_uuid`; `role`, `description?`, `evidence_refs JSONB`; `added_by_user_id?`, `added_by_agent_key?`, `removed_at?`.

Roles: decision_maker, champion, influencer, blocker, other. The role and canonical target must be supported by user input or permitted evidence. Enforce active uniqueness on deal/entity type/node/role. Soft removal preserves the earlier relationship in history. Multiple roles can be explicit separate links; references confer no access and create no graph edges.

### 10. projects.work_activity

Append-only fields: `id`, `project_id?`, `root_project_id?`, `personal_user_id?`, `task_id?`, `deal_id?`; `event_type`; `actor_type` (user/agent/system), `actor_user_id?`, `agent_key?`, `agent_run_id?`; `command_id?`, `action_run_id?`, `entity_version?`; `body?`, `payload JSONB`, `visibility` (personal/root/admin), `created_at`.

Personal activity is owner-only. Its audience never expands automatically when the task moves to a project; record a fresh, safe placement event in the destination. Store typed old/new values, explanations, and evidence references for creation, suggestion acceptance/deletion, estimate/date edits, assignment, meaningful progress, configuration, transition, attestations, adoption, archive, and reopen. Commit with the state change. Pipeline configuration events use the root project as their project context. Sensitive ACL details are admin-visible. Private suggestion responses and mailbox contents never enter the shared timeline. Provider receipt details can be referenced without exposing private payloads. There is no raw model transcript feed.

### 11. projects.agent_suggestions

Fields: common mutable fields; `project_id?`, `root_project_id?`, `personal_user_id?`, `task_id?`, `deal_id?`, `proposed_task_id?`; `kind` (next_step/change_request), `suggestion_type`; `title`, `description?`, `rationale`, `expected_benefit?`; `suggested_for_user_id?`; `action_type?`, typed `action_payload?`; `intent_key`, `context_fingerprint`, `resource_versions JSONB`; `evidence_refs JSONB`; `agent_run_id?`, `agent_key`, `model_key?`, `prompt_version`, `policy_version`, `on_behalf_of_user_id?`; `source_suggestion_id?`, `source_action_ref?`; `status DEFAULT open`, `expires_at?`; `adopted_at?`, `adopted_by_user_id?`, `adoption_type?`, `result_task_id?`, `action_run_id?`, `applied_activity_id?`; `resolved_at?`, `resolved_by_user_id?`, `resolution_reason?`, `resolution_source?`, `supersedes_suggestion_id?`.

Shared states: open, adopted, resolved, expired, superseded, withdrawn. Adoption types: created_task, accepted_task, linked_task, applied_change, queued_action. `accepted_task` promotes the existing Suggested row without minting another task ID. Queuing an action is adoption, not completion; read execution state from its action run. An action failure remains visible and retryable under its own rules rather than reopening a suggestion automatically.

For a new-task proposal, create exactly one `status=suggested` task and one `proposed_task_id` link in the same transaction, with reciprocal immutable source provenance after FK setup. This is distinct from `task_id`, which is an existing task targeted by a change request. A taskless advice card has no proposed task. Accept locks both records, updates the task, marks the suggestion adopted with the same `result_task_id`, records acceptance/activity and returns one canonical result. The shared suggestion-adopt endpoint dispatches to this same command. Linking an existing task instead archives the unused proposal with a reason, so there are not two live work items. Expiry/withdrawal closes its unaccepted row; accepted work is never archived by later suggestion maintenance.

Personal Delete archives the pending task and records the owner's dismissed intent atomically; use withdrawn plus an explicit user-deleted reason for the proposal's shared lifecycle. In project scope, personal dismissal hides that Suggested row for that user, while authorized global withdrawal closes it for everyone. A suggestion with no accepted task has no workload/reminder obligations. A new-task proposal's current scope must match its Suggested task; editing proposed fields updates the canonical task plus the linked proposal version/fingerprint atomically so Accept never replays an old payload; accepted provenance stays in its original scope if the task later moves.

`intent_key` is server-normalized from action/target/business occurrence, not model wording. Enforce one open suggestion per work-scope/intent using separate project-root and personal-owner partial unique indexes and reject duplicate adoption across users with a locked row/version. An explicit source import is unique per work-scope/source suggestion/action. A root owner's delegation cannot inject a private proposal into another user's ToDo. Revalidate source visibility; do not copy private source content into root-shared cards. Use an optional future `suggestionspub` reader, never direct sibling service imports.

Advice may have no executable payload. Exact changes carry relevant task/deal/root-access/pipeline-configuration versions. Shared cards hold only audience-safe material; a mailbox draft is an owner-scoped resource reference, not shared body/recipient content. Ignoring/saving does not change work, deadlines, next_action, or progress. Resolution requires a user report or a verified canonical event; a model inference can only propose it.

### 12. projects.suggestion_user_state

Fields: `id` UUIDv7 PK; `root_project_id?`, `personal_user_id?`, `user_id`, `intent_key`; `last_suggestion_id?`, `first_viewed_at?`; `disposition DEFAULT undecided` (undecided/saved/snoozed/dismissed), `snoozed_until?`; `feedback_reason?`, `feedback_text?`; `created_at`, `updated_at`.

Enforce XOR root/personal scope, unique `(root_project_id,user_id,intent_key)` for project rows and unique `(personal_user_id,user_id,intent_key)` for personal rows using partial indexes; personal `user_id` must equal the owner. Do not rely on nullable-column uniqueness. Keying by intent preserves suppression across equivalent regenerated suggestions. A snoozed disposition requires a future wake time; saving is a bookmark. Dismissal persists until that user clears it; revised phrasing does not reset it. Global adoption, expiry, resolution, or withdrawal overrides personal resurfacing. Only the user can read/change their private state; root admins and generic root agents do not receive personal feedback. Server-side filtering may honor it without revealing it. No row means no response.

### 13. projects.agent_runs

Fields: `id`, `root_project_id?`, `project_id?`, `personal_user_id?`, `task_id?`, `deal_id?`; `requested_by_user_id?`, `on_behalf_of_user_id?`, `trigger_type`; `dedupe_key`, `context_fingerprint`, `resource_versions JSONB`; `status`, `available_at`, `attempts`, `lease_token?`, `lease_until?`, `lease_fence`; `model_key`, `prompt_version`, `policy_version`; `limits JSONB`, `usage JSONB`, bounded `evidence_manifest JSONB`, `result_summary?`, `error_code?`, sanitized `last_error?`; `created_at`, `started_at?`, `finished_at?`, `updated_at`.

States: queued, running, succeeded, partial, failed, canceled, budget_exhausted. A unique dedupe key covers work scope, trigger/target, input fingerprint, and review occurrence. Store explicit budget counters and provider receipts before making work visible. The bounded evidence manifest records source, visibility, observed time, and freshness/unknown status. Personal reviews are owner-requested/explicitly authorized, not a root background-delegation side effect; apply the same per-run limits and a per-user active-run uniqueness gate. Recheck input versions and permissions before materializing suggestions; stale output is discarded or re-evaluated, never committed as current advice.

### 14. projects.action_runs

Fields: `id`, `root_project_id?`, `project_id?`, `personal_user_id?`, `task_id?`, `deal_id?`, `suggestion_id?`; `action_type`, typed `input JSONB`, `input_hash`, `resource_versions JSONB`; `authorized_by_user_id?`, `authorized_at`, `authorization_expires_at`, `authorization_scope JSONB`; `on_behalf_of_user_id?`, `agent_run_id?`; `status`, `dedupe_key`, `available_at`, `attempts`, `lease_token?`, `lease_until?`, `lease_fence`; `provider_idempotency_key?`, `provider_request_id?`, `provider_result_id?`; typed `result_refs JSONB`, `result_summary?`, `visibility` (personal/root/actor), `error_code?`, sanitized `last_error?`; `created_at`, `started_at?`, `finished_at?`, `updated_at`.

States: queued, running, succeeded, failed, unknown, canceled. One logical action has one stable identity across retries. Personal actions use personal visibility and validate the owner and accepted task; Suggested status alone never authorizes execution. Placement cannot retarget an already prepared/dispatched action. Authorization binds the action, target, relevant versions, and exact content hash; edits require a new authorized command. V1 authorizations expire after 24 hours if not started. Missing/deleted principal cancels unstarted work. A running action whose result is uncertain becomes `unknown`; do not silently retry non-idempotent side effects. Result references distinguish `provider_acknowledged`, `domain_committed`, and `user_reported` evidence. A user report alone cannot satisfy an `action_succeeded` provider criterion; use an explicit human-confirmation criterion where appropriate. Actor-only inputs/results stay private even though the shared timeline can say an authorized action occurred.

### 15. projects.followups

Fields: `id`, `root_project_id?`, `project_id?`, `personal_user_id?`, `task_id?`, `deal_id?`, `suggestion_id?`; `recipient_user_id`, `kind`; `scheduled_for`, `available_at`, `basis JSONB`; `dedupe_key UNIQUE`; `status` (pending/processing/sent/failed/unknown/canceled), `attempts`, `lease_token?`, `lease_until?`, `lease_fence`; `provider_idempotency_key?`, `provider_result_id?`, `sent_at?`; sanitized `last_error?`; `created_at`, `updated_at`.

Kinds: assignment, due_soon, overdue, check_in, blocked_too_long, suggestion_digest, suggestion_reminder. One row is one occurrence for one recipient, not a recurring rule. Suggested tasks produce no assignment/due/overdue occurrence; accepted personal task occurrences target only the owner and use the user timezone. Domain commands create event-based occurrences transactionally; bounded scans derive date-based occurrences. A semantic basis identifies the due date/check-in/stage/suggestion intent, so irrelevant version bumps do not create or cancel valid reminders. Sent means acknowledged provider acceptance, not a read receipt.

### 16. projects.command_receipts

Fields: `id`, `actor_key`, `root_project_id?`, `personal_user_id?`, `operation`, `idempotency_key`, `request_hash`, `result_refs JSONB`, `created_at`. Unique actor/operation/key. Actor keys are verified identities with trusted agent attribution, never credentials. The root or personal scope and the complete normalized command belong in the request hash.

Commit the receipt and domain result together. Same key/body returns the existing result after reauthorization; changed body conflicts. Root creation may begin without a root ID, then stores the created root in the receipt. Retain receipts for the advertised retry lifetime, initially the life of archived work; no V1 purge job. Suggestion adoption also locks the shared suggestion, because per-actor keys alone cannot stop two different users adopting it twice.

### 17. projects.project_user_preferences

Fields: `id` UUIDv7 PK; `root_project_id?`, `personal_user_id?`, `user_id`; `reminders_enabled DEFAULT true`, `suggestion_digest_enabled DEFAULT false`, `muted_until?`, `quiet_hours_start?`, `quiet_hours_end?`, `minimum_reminder_interval_hours DEFAULT 24`; `created_at`, `updated_at`.

Enforce XOR root/personal scope, partial uniqueness for root/user or personal-owner/user, and `user_id=personal_user_id` on personal rows. The existing table name remains; no fictitious project is needed for ToDo preferences. Quiet hours are paired TIME values, resolved in the user's current timezone with root fallback, including overnight/DST behavior. Users manage only their own preferences; project preferences additionally require root access, while personal preferences require the matching owner. Assignment/due reminders use the existing in-app channel; suggestions appear as pull-based cards unless a digest or reminder is explicitly enabled. Save/ignore creates no reminder. Snooze controls display only unless the user separately requests a reminder.

## Board storage and ordering

Use 12-character, zero-padded base-36 text ranks with `C` collation. Compute integer midpoints with checked arithmetic; when no gap remains, rebalance the affected ordered set under the root lock. Assign even ranks across the available range and retry the requested placement in the same transaction. IDs break ties. Test endpoint insertion, repeated midpoint exhaustion, simultaneous moves, and rebalance.

Add a pipeline `board_version` counter for card membership/order mutations; keep it separate from `configuration_version`.

The [API pagination contract](/guides/open-work/roadmap/projects-tasks/api-design#pagination) defines cursor contents and invalidation behavior. Stage criteria and action-guidance documents follow the [typed API contract](/guides/open-work/roadmap/projects-tasks/api-design#stage-criteria-and-suggested-actions).

### How the scope rules became constraints

- **One CHECK per task-capable table** (tasks, task_assignees, work_activity, agent_suggestions, agent_runs, action_runs, followups): either `project_id` and `root_project_id` are both set and `personal_user_id` is null, or the reverse. The root-or-personal tables (task_dependencies, suggestion_user_state, command_receipts, project_user_preferences) use a strict either-or of `root_project_id` and `personal_user_id`.
- **Project integrity is a composite FK** from `(project_id, root_project_id)` to a unique key `(id, root_project_id)` on projects, so a row proves its project and its root belong together. Postgres skips a composite FK when any of its columns is null, which the CHECK makes exact. For the same reason the two scope columns never share one FK: one of them is always null, so that FK would never be enforced.
- **Unique keys added only as FK targets:** projects `(id, root_project_id)`; tasks `(id, project_id)`, `(id, root_project_id)` and `(id, personal_user_id)`; pipelines `(id, root_project_id)`; pipeline_stages `(id, pipeline_id)`; deals `(id, project_id)`.
- **A task's current scope is pinned in two places only.** task_assignees carries three composite FKs to tasks and task_dependencies carries four, so an assignee always matches its task's scope and both ends of a dependency share one root or one owner. History, runs, follow-ups and suggestions keep the audience they were written for and reference a task by plain `task_id`, because placement can move a task across scopes.
- **Deals never change project**, so every table that holds a `deal_id` uses a composite FK `(deal_id, project_id)` to deals. Where the scope columns are nullable, a CHECK adds that a personal row carries no deal.
- **Uniqueness over a nullable scope is always a pair of partial unique indexes**, one for the project root and one for the personal owner. `NULLS NOT DISTINCT` is used only on the two source-import indexes, so a second whole-suggestion import with no action reference is rejected.
- **`accepted_at IS NULL` is the structural form of Suggested.** No CHECK names an enum value. A Suggested row cannot hold a work key, a start, a completion, a completion summary or a progress time, and the accepted-only due-scan index keys off `accepted_at`. Every insert must therefore set `accepted_at` unless the status is `suggested`.

### Delete behaviour

| Reference | On delete |
|---|---|
| Structural work and history: project, task, deal, pipeline, stage, run, suggestion, receipt | `RESTRICT` |
| Personal owner, `personal_user_id` to users, on tasks, work_activity, command_receipts, agent_suggestions, agent_runs and action_runs | `RESTRICT` |
| Human attribution and ownership: every `owner_`, `created_by_`, `granted_by_`, `assigned_by_`, `accepted_by_`, `adopted_by_`, `resolved_by_`, `requested_by_`, `on_behalf_of_`, `authorized_by_`, `added_by_`, `actor_` and `suggested_for_` user column | `SET NULL` |
| `owning_organization_id`, `team_id`, `copied_from_pipeline_id`, `suggestion_user_state.last_suggestion_id` | `SET NULL` |
| Pure joins: task_assignees (to its task and its user), `project_organization_access.organization_id`, `suggestion_user_state.user_id`, `project_user_preferences.user_id`, `followups.recipient_user_id` | `CASCADE` |
| Canonical targets `(entity_type, node_uuid)` and the external `agent_suggestions.source_suggestion_id` and `source_action_ref` | No FK |

Users are deleted by a single `DELETE FROM users.users`, so every action above really fires. The personal-owner `RESTRICT` means **a user who still owns private ToDo data cannot be deleted until an explicit clean-up step exists**. That step is APP-107 and must ship before any command can write a personal row. The contract is in [API Design](/guides/open-work/roadmap/projects-tasks/api-design#account-deletion-and-personal-data).

### Where the build differs from the text above

1. **`personal_user_id` has no FK on suggestion_user_state, project_user_preferences and followups.** Each of those rows also holds a `CASCADE` FK to the same user. A `RESTRICT` beside it would pass or fail depending on which trigger Postgres fires first. A CHECK pins `personal_user_id` to the user column (`recipient_user_id` on followups) instead, which also enforces the rule that a personal row belongs to its owner.
2. **`work_activity.deal_id` is a composite FK.** The carve-out for history in the shared rules is about task IDs. A deal never moves, so its history can prove its project.
3. **One task per source suggestion.** `tasks.source_suggestion_id` has a partial unique index. If adoption ever creates several tasks from one suggestion, drop it in a migration.
4. **An inverse dependency pair is rejected by an index**, a unique index over the lesser and greater of the two task IDs, so "a needs b" and "b needs a" cannot both commit even when the inserts race. Longer cycles are still a service check under the scope lock.
5. **Structural CHECKs the text implies but does not spell out:** a root must have a timezone; root-only settings are null, assistance is off and `access_version` is 1 on a child; a project cannot be its own parent; a work key needs a deal; a deal is not both won and lost, and `lost_at` and `lost_reason` are set together; `adopted_at` and `adoption_type` are set together, and a result task, an action run or an applied activity can exist only on an adopted suggestion; `lease_token` and `lease_until` are set together; `authorization_expires_at` is after `authorized_at`. On a personal agent run, suggestion or action run, the requesting, targeted, authorizing and on-behalf-of user can only be the owner. That last one would need a migration before delegated personal assistance could exist.
6. **Non-negative numeric CHECKs also reject `NaN`**, and `Infinity` on the unconstrained `agent_daily_budget_usd`. Postgres accepts `NaN` in any NUMERIC column and `Infinity` in an unconstrained one, and both pass a plain `>= 0`. On `NUMERIC(12,2)` and `NUMERIC(20,4)` the type itself refuses `Infinity` with a numeric overflow.
7. **Pure attribution columns are not indexed.** `created_by_user_id`, `assigned_by_user_id` and the like are `SET NULL` columns no query filters on. A rare user delete pays a scan instead of every write paying for the indexes. Owner, organization and team columns the access query filters on are indexed.
8. **Indexes whose queries do not exist yet are not built:** a due index on `next_agent_review_at`, the check-in and blocked-too-long scans, and the suggestion expiry sweep. Each arrives in the additive migration that ships its query.
9. **The personal owner/created-time index covers archived rows too.** The index list above asks for it on live personal rows. It is partial on the owner only, so the archived and restore views can use it and so can the probe Postgres runs on the personal-owner `RESTRICT` when a user is deleted. The owner/status/date index is limited to live rows as written.

### Types, defaults and pinned values

- **Ranks** are `position TEXT COLLATE "C" NOT NULL` on pipelines, pipeline_stages and deals, with a CHECK for exactly 12 characters of `0-9a-z`. They are not unique; IDs break ties. The explicit collation is what makes byte order equal numeric order whatever the database locale is.
- **Money and estimates:** `deals.value NUMERIC(20,4)`, `tasks.estimate_amount NUMERIC(12,2)`, `agent_daily_budget_usd NUMERIC`. Postgres silently rounds a decimal beyond the scale, and raises an overflow on an 11th integer digit of an estimate or a 17th of a deal value, so the service is the only guard against both. `1.5` reads back as `1.50`; DTO mappers trim the padding.
- **Other types:** `request_hash` and `input_hash` are `BYTEA`; `lease_token UUID`, `lease_until TIMESTAMPTZ`, `lease_fence BIGINT` default 0, `attempts INT` default 0; quiet hours are `TIME`; `source_template_version` is text.
- **JSON shapes are fixed per column name.** Arrays: `evidence_refs`, `result_refs`. Objects: `payload`, `resource_versions`, `limits`, `usage`, `evidence_manifest`, `criteria`, `action_guidance`, `criterion_attestations`, `basis`, `input`, `authorization_scope`. `criteria` and `action_guidance` are versioned document envelopes, so the criterion list and the guidance list live inside the object. Nullable: `action_payload`, `agent_review_cursor`.
- **Defaults kept:** project `planned` and `normal`, task `todo` and `normal`, pipeline kind `custom`, suggestion status `open`, disposition `undecided`. **No default, on purpose:** `work_activity.visibility`, `event_type` and `actor_type`; `pipeline_stages.category`; the grant `role`; the `status` of agent_runs, action_runs and followups; `action_runs.visibility`.
- **Six enum values are pinned by partial-index predicates:** `open`, `queued`, `running`, `background`, `pending` and `processing`. Renaming one needs a migration. A Go test parses the four migrations and fails if a pinned value or a column default is not in its Go set, or if any CHECK names an enum value.

### In the Go package

`internal/features/projects` holds the enum sets with a `ValidX()` function each (`types.go`, `types_pipeline.go`, `types_agent.go`, `types_actions.go`). Only sets the spec closes are defined: the ones listed on this page, the stage categories listed in API Design, and the five pipeline kinds this page names, which Go treats as the whole set until one is added. `event_type`, `suggestion_type`, `action_type` and `trigger_type` stay open, apart from the one pinned trigger, `background`. sqlc maps NUMERIC to `pgtype.Numeric`, DATE to `pgtype.Date`, TIME to `pgtype.Time` and JSONB to bytes. There is no decimal library in the backend, and money or estimates must never pass through a float.

### What was verified

- Real Goose on Postgres 16: every migration up on an empty database, the four projects migrations down (schema gone), then up again.
- A disposable Postgres 17 test with 77 subtests. Each rejection asserts the SQLSTATE and the constraint name, so a row rejected by the wrong rule fails the test. It covers the scope CHECKs, wrong-root and wrong-project references, cross-root and cross-owner dependencies, the inverse pair, estimate and value pairing, `NaN`, infinity, silent rounding and integer-digit overflow, the owner-only checks on personal runs, suggestions and actions, lease pairing on all three job tables, one default stage, one live task per deal and work key, one open suggestion per scope and intent, the second whole-suggestion import, rank format and order, user, organization and team deletion, and an exact `1.5 hours` plus date round-trip through generated code. It also shows that moving a task's scope in place fails while an assignee row exists, and that delete assignees, update the task, insert assignees succeeds.
- Rollback over rows in all 17 tables, which the test asserts before it starts, with every deferred FK column populated: one more migration at a time until the `projects` schema is dropped, and back. CI applies only the Up half of a migration, so this test is the repeatable proof that the Downs work.
- Not measured yet: the [load-test query plans](#indexes-and-query-plans). None of those queries exists; the only two so far are primary-key reads.
