## What the adapter actually does

Short answer to "does it write to the graph?": **yes, edges and a few nodes, but only behind a gate, and never people it cannot identify.** The bulk of Phase 1's output is relational.

| Layer | Written by Phase 1 | Not written by Phase 1 |
| --- | --- | --- |
| **GCS** | The verbatim filing XML (`irs990/xml/<year>/<object_id>_public.xml`) and the batch zips it came from (`irs990/zip/<year>/<batch>.zip`, cached so one download serves every org in that batch). | — |
| **AlloyDB `universe.*` — lane tables** | `filing_990` (one row per fetched filing), `filing_990_governance_mention` (one row per Part VII / officer line), `filing_990_grant` (one row per grant line — the store the [Donors](/guides/open-work/roadmap/donors) lane reads), `filing_990_governance_edge` (the edge ledger), `filing_990_resolution_attempt` (append-only Stage-B audit), `filing_990_org_queue` (the work queue). | Any `DONOR_TO` state. Any FEC / Form D table. |
| **AlloyDB `universe.*` — backbone** | The nonprofit as a **`company` entity** keyed by a new strong identifier kind `ein`; scalar facts on it (`nonprofit`, `foundation`, `ein`, `website`, `formation_year`, `legal_name`, source `irs_990`); one `enrichment_payloads` envelope per filing; `enrichment_attempts` rows per provider call; **relationship facts** `board_member_of` / `officer_of` (person → org) for resolved people only. | New `person` entities from a **bare name**. A person row is minted only through a strong key (a LinkedIn URL Exa surfaced) or an adjudicated match onto an existing entity — see [D4](#decisions-to-record). No writes to `master_companies` / `master_persons` (typed caches are distill-owned). |
| **Universe graph (FalkorDB)** | `Company:Organization:Entity` node for the org (via `graph.MergeCompany`, labels add-only so a `School` stays a School) with `nonprofit`, `foundation`, `ein` properties; `Person:Entity` nodes for newly minted strong-key people (via `graph.MergePerson`); **`BOARD_MEMBER_OF` (weight 8)** and **`(Person)-[OFFICER_OF]->(Company {nonprofit: true})` (14 officer / 20 key employee)** edges via `graph.MergePersonEdge`, each stamped per the [ontology](/guides/ontology/edges#officer_of) with `role` (`OFFICER_OF` only), `title_as_filed`, `compensation_usd` (when reported), `valid_from`, `valid_to`, `filing_refs`, `mention_ref`, `source_urls`, `confidence`, and the deterministic description. | Pair edges (co-board derives at score time). Any edge while `FILINGS_990_EDGE_WRITES_ENABLED=false` (the Stage-1 gate, default off). |
| **Dispatch** | Nothing. No `entity.enrich_requested`, no Deep Bio, no cascade. New strong-key people get an `enrichment_queue` row at **tier 4** (which the person drain never picks — `PickQueueEntry` drains tier ≤ 1), so they exist as leaves until something else promotes them. | Recursive enrichment of any kind. |

Everything above is idempotent: re-running an org with unchanged filings changes no row and no edge.

## Identity in Universe: what a trustee becomes

The parent page says "unresolved trustees become local-only leaves + queue rows". In Universe that sentence has to be mapped onto the identity rules in `CLAUDE.md`, which are stricter:

- **All lookups enter through `entity_identifiers`.** A Part VII name is a **soft** key; soft keys nominate candidates and never decide identity.
- **A person entity needs a strong key or an adjudicated match.** The adapter mints a person only when (a) Exa surfaces a LinkedIn URL for the mention and `ResolveStrong("linkedin", …)` find-or-creates it, or (b) a soft-name candidate passes adjudication at ≥ 0.85 with two independent corroborations. A bare name with neither stays a **name-anchored mention** (`resolution_state = unresolved`), exactly like `funding_round_investors` keeps unresolved investors, and the weekly sweep retries it as the graph grows.
- **The org is easy.** An EIN is government-issued and unique, so `ein` becomes a **strong** identifier kind for `company` (added to `entities.IsStrongIdentity` and `entitiespub.NormalizeKey`: digits only, 9 characters, zero-padded). `ResolveStrong("ein", ein, "company")` find-or-creates the org; a collision with an existing company that already holds the EIN is the merge flow doing its job.

This is [decision D4](#decisions-to-record) and needs Mark's ratification because it deliberately deviates from the parent page's wording. The payoff: nothing this lane writes can wrongly fuse two humans, and the person cap is never consumed by name-only stubs.

<Note>
  **Why the org queue is its own table and not `enrichment_queue`.** `enrichment_queue` is one row per *entity* awaiting enrichment and requires an `entity_id`. An org enters this lane as an EIN before any entity exists, the unit of work is a filing set rather than an entity run, and the row survives across filings. Its mechanics are copied exactly (`locked_at`/`locked_by` + reaper, `attempts` + `last_error` dead-letter, `count` on re-add, `FOR UPDATE SKIP LOCKED` pickup over a partial index).

  **Why the raw XML is not in `enrichment_payloads.raw`.** That column is JSONB and the source is XML. The byte-exact document lives in GCS (`xml_storage_key`, `xml_sha256`), and the payload row stores a JSON envelope: `object_id`, `xml_batch_id`, `xml_storage_key`, `xml_sha256`, `return_type`, `tax_period`, `return_version`, plus the parsed `governance[]` and `grants[]` arrays. Provider name `irs_990`, endpoint = the zip URL. Retries parse from GCS, never re-fetch (parent-page invariant 7).
</Note>

## Pipeline

```text

                                                   │  Cloud Scheduler → filings.queue_drain_requested
```

### Stage B: resolution

**Org (once per queue row).** `ResolveStrong("ein", ein, "company")`. **On a miss, corroborate through the domain before creating** (open Q6, 2026-09-06): take ProPublica's `website` for the EIN (fallback `WebsiteAddressTxt`), reduce it to its registrable domain, and `FindByStrong("domain", …)`; a hit means the nonprofit already exists in the graph under a LinkedIn/Fundable-sourced `domain` key (every `School` node is one) → `AttachIdentifier(ein)` on **that** entity and continue; record `resolution_method = domain_corroboration` on the queue row. No hit → create: `display_name` = filer name, identifier `ein` (strong) **only** — the website is still never attached as a *new* strong `domain` key (open Q2: a wrong 990 website would merge two organizations; the domain step *finds*, it never *mints*). Phase 0 measures the ProPublica `website` field on the fixture set; if it is too dirty, the fallback is hand-seeding `ein` onto the fixture entities (`resolution_method = ein_preseeded`). Facts (source `irs_990`, confidence 0.95): `nonprofit=true`, `foundation=(return_type == 990PF)`, `ein`, `legal_name`, `website`, `formation_year`; from ProPublica: `ntee_code`, `subsection_code`. Node: `graph.MergeCompany` with `ExtraLabel: "Organization"` (add-only, so an existing `School` keeps its label) and properties `nonprofit`, `foundation`, `ein`, `website`; `Registrar.SetGraphNodeUUID`. The org's node is required before any edge — a missing node is a hard error, never a stub (the `MergePersonEdge` rule).

**Person mention, deterministic ladder, stop at the first hit.** Every step appends a `filing_990_resolution_attempt` row.

1. **`prior_filing`** — a mention on an earlier filing of the **same org** with the same `name_normalized` is already `auto_linked` → inherit `person_entity_id` (confidence = prior). This is what makes tenure cheap.
2. **`affiliation`** — `Resolver.MatchIdentifiers("person", [name])` nominates soft candidates; a candidate with an existing chosen relationship fact or edge to this org (`works_at`, `board_member_of`, `officer_of`, `founded`) is corroboration #1, and a title/employer fact agreeing with `title_as_filed` is #2. Two corroborations → `auto_linked` at 0.90. Exactly one candidate with one corroboration → adjudicate (step 4).
3. **`exa_linkedin`** (the step keeps its name; the provider is a seam — `clients/parallel` after the bake-off, `clients/exa` as the alternative) — `"<name>" "<org name>" <title> linkedin`, 5 results, domain filter `linkedin.com`. Keep only `linkedin.com/in/<slug>` results whose slug carries the **surname and the first name, its nickname or initial** (the surname alone let a company page and three near-names through on the fixture set). Prefer the one surviving profile whose title/excerpt names the org (two corroborations); with no org signal, exactly one survivor (one corroboration); several without an org signal → `rejected`. The chosen profile → adjudicate; adjudication ≥ 0.85 → `ResolveStrong("linkedin", url, "person")` (find-or-create), `AttachIdentifier` soft `name`, `auto_linked`, method `linkedin_strong`. A **created** entity here is a leaf: `graph.MergePerson` (name, embedding via the shared embedder), then `fanoutlimit.Bound.Offer` → `enrichment_queue` upsert at **tier 4**, depth 1, `source_function = filings.irs990`, `seed_entity_id` = the org. Counted against `FILINGS_990_MAX_NEW_PERSONS_PER_RUN` and the person cap.
4. **`adjudication`** — `FILINGS_990_ADJUDICATE_MODEL`, temperature 0.1, strict JSON `{"match":"yes|no|none","candidate":"<id>","confidence":0-1,"reasoning":"…","same_name_different_person":bool}` over the full mention context (name, title, org, org city/state, tax year, comp bracket) plus each candidate's profile summary. Auto-link only at `confidence ≥ FILINGS_990_AUTO_LINK_THRESHOLD` **and** two independent corroborations recorded in the attempt; name-only matches are capped at 0.59 regardless of model output (#13168 guard). `[0.60, 0.85)` → `needs_review` with `ReviewFiler.FileReviewItem` (reason `ambiguous_soft_match`, evidence kind `name`, counterpart = the candidate); below → stays `unresolved`.
5. **No candidate, no profile** → `unresolved`. Never an entity, never an edge. The weekly `filings.resolution_sweep_requested` re-runs steps 1–2 only (free) for `unresolved` mentions, and re-runs 3–4 monthly.

### Stage C: facts, ledger, edges

1. **Facts.** For each `auto_linked` mention with roles, upsert relation facts on the **person**: `entity_facts(entity_id = person, field = board_member_of | officer_of, value_entity_id = org, source = irs_990, confidence = resolution_confidence)`. Add both field names to the facts feature's relation vocabulary so distill's per-target election marks them chosen (single source → trivially chosen; the `entity_facts_relation_winner` unique dedupes re-runs). Only a **chosen** fact may become an edge (repo rule).
2. **Ledger + tenure.** Upsert `filing_990_governance_edge` on `(person, org, edge_kind)` and **recompute the span from every mention of that pair** (one writer, full view — Go Developer Notes §4): `valid_from` = earliest `tax_period_begin` where the person appears non-former; `valid_to` = `NULL` if present on the org's **latest fetched** filing, else the `tax_period_end` of the last filing where present. `title_as_filed` and `compensation_usd` come from the most recent filing (`ReportableCompFromOrgAmt`, org-only, never summed). `filing_ids` lists every contributing filing. Shuffled-year arrival must converge to identical spans (fixture-tested).
3. **Edge write** (only when `FILINGS_990_EDGE_WRITES_ENABLED`). `graph.MergePersonEdge` with `Kind`, `Weight` (8 / 14 / 20), `Title` (→ `r.title`, the live `BOARD_MEMBER_OF` property), `Source: "irs_990"`, `ValidFrom`/`ValidTo` as `YYYY-MM-DD`, and the deterministic description (`"{Person} is a board member of {Org} ({title_as_filed}, FY{from}–FY{to})."`; `OFFICER_OF`: `"{Person} is an officer of {Org} ({title_as_filed}, FY{valid_from}–FY{valid_to})."`, `…was an officer of…` once `valid_to` is set — the [ontology template](/guides/ontology/edges#officer_of)). Additive changes to `platform/graph/person_edges.go`: add `OFFICER_OF` to `personEdgeKinds`, and the [ontology's `OFFICER_OF` property set](/guides/ontology/edges#officer_of) as new `PersonEdge` fields — `Role` (`officer` \| `key_employee`, required on `OFFICER_OF`), `TitleAsFiled` (→ `r.title_as_filed`, required; written beside `r.title` so the live `BOARD_MEMBER_OF` readers keep working), `CompensationUSD` (optional), `FilingRefs` (required), `MentionRef`, `SourceURLs`, `Confidence` (required) — each omitted from the SET when zero (the FOREACH-guard rule: a thinner source never blanks a richer one). Filing-sourced `BOARD_MEMBER_OF` edges carry the same provenance set. Stamp `graph_edge_uuid` + `graph_written_at` on the ledger row; the partial index over `graph_written_at IS NULL` is the sweep queue when the gate opens later.

### Search: Parallel vs Exa — **Parallel**
