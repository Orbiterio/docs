## Table access matrix

Seven Xano tables carry all data traffic. Only `query`, `get`, `add`, `edit` are used — no deletes, bulk, or direct SQL.

| Table | Reads | Writes | Used by |
| --- | --- | --- | --- |
| `suggestion_request` | `get` ×5 | `edit` ×5, `add` ×1 | Drafts, context patch, dispatch, submit-metadata — the write hotspot |
| `conversation` | `query` ×3 | `add` ×2 | `threads/ensure`, `threads/{id}/messages` GET+POST |
| `copilot_chat_messages` | `query` ×2 | `add` ×1 | `threads/{id}/messages` GET+POST (meeting_prep surface) |
| `leverage_loop_conversations` | `query` ×2 | `add` ×1 | `threads/{id}/messages` GET+POST (leverage_loops surface) |
| `outcome_conversations` | `query` ×2 | `add` ×1 | `threads/{id}/messages` GET+POST (outcomes surface) |
| `master_person_relationship` | `query` ×2 | `add` + `edit` (upsert) | How-I-Know GET+PUT |
| `contacts` | `query` ×2 | — | Read-only in this group |

## Xano → AlloyDB coverage

Half the tables already exist on `main` — the `suggestions` and `relationships` features landed mid-September. The merged design **keeps the Xano name** `suggestion_request` (not `request_suggestion` as earlier drafts had it).

| Xano table | AlloyDB table | Status |
| --- | --- | --- |
| `contacts` | `persons.contacts` | Exists — redesigned, diff below |
| `user` | `users.users` | Exists — redesigned, diff below |
| `suggestion_request` | `suggestions.suggestion_request` | **Exists on main** (`suggestions_001_init` + `suggestions_002_ingest`, merged 9/10 & 9/14) — Xano name kept; diff below |
| `master_person_relationship` | `relationships.relationships` | **Exists on main** (`relationships_001_init`, merged 9/8) — diff below |
| `conversation` | `copilot.conversations` *(proposed)* | Missing — new feature |
| `copilot_chat_messages` | `copilot.messages` *(proposed)* | Missing — new feature |
| `leverage_loop_conversations` | `copilot.messages` *(proposed)* | Missing — fold in via `surface` discriminator |
| `outcome_conversations` | `copilot.messages` *(proposed)* | Missing — fold in via `surface` discriminator |

The three per-surface transcript tables (`copilot_chat_messages`, `leverage_loop_conversations`, `outcome_conversations`) have identical shapes and the same UI contract — the proposed Go design combines them into one `copilot.messages` table keyed by `conversation_id`, with the surface carried on the conversation row.

The `suggestions` schema also carries the result/ingest pipeline the results endpoints will read: `suggestion_batch`, `suggestion`, `suggestion_node`, `suggestion_trajectory`, `suggestion_action_group`, `suggestion_action`, `ingest_error`, and the leverage-loop children `leverage_loop_suggestion`, `leverage_loop_action`, `leverage_loop_trajectory`, `leverage_loop_trajectory_node`, `leverage_loop_question`, `leverage_loop_question_node`.

## Notes

- **Deprecation guard.** Xano `suggestion_request` is superseded by `suggestions.suggestion_request` — see [Suggestion Delivery and Tables](/guides/open-work/suggestion-delivery-and-tables). Do not delete the Xano table until the TanStack AI endpoints are complete and Mark approves.
- **`contacts` stays read-only here** — writes flow through other API groups.
- **Name collision.** Xano "outcomes" (suggestion requests/results) is a different domain from the existing Go `outcomes` feature (`outcomes.investment_theses`). The chat endpoints belong in a new feature (`copilot` proposed) — do not wire them into `internal/features/outcomes`.
- **Interview endpoints are stateless** — the four `*/interview` endpoints call OpenRouter and return content without persisting; persistence happens only via the draft/dispatch/context endpoints on `suggestion_request`.
