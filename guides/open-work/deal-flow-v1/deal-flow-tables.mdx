## Summary

The Projects backend already covers most of Deal Flow v1. Decision numbers on this page refer to the [Decided](/guides/open-work/deal-flow-v1/deal-flow-ui-design#decided) table on Deal Flow UI Design; T numbers refer to this page. What the backend lacks falls into four groups:

- **Flows, stages and templates:** stage descriptions, requirements stored on the stage a deal leaves, saved templates and a stage library. The Projects spec ruled out template storage; decision 38 brings it back.
- **Deal fields:** source, tier, a dated next step, soft interest, pass details and contact dates.
- **Access:** confidential deals, which reverse the spec's rule that nothing inside a project is independently private.
- **AI:** private suggestions built from each person's own email, calendar and relationships, and proposed stage moves.

## Where things stand

The Projects feature is on `orbiter-backend` `main`, built September 21 to 23. The [Projects & Tasks Table Design](/guides/open-work/roadmap/projects-tasks/table-design) documents its 17 tables in the `projects` schema, created by four Goose migrations, `projects_001_work` to `projects_004_actions_followups`; no later migration touches them. The 77 endpoints are in the API Reference tab under Orbiter Backend, Projects group, and the [Projects & Tasks API Design](/guides/open-work/roadmap/projects-tasks/api-design) describes their rules.

Every change on this page follows the conventions the Projects spec already sets:

- **Migrations are additive.** New Goose migrations only; the four built migrations are never edited.
- **Identifiers and values:** application-minted UUIDv7 IDs; enum-like values stored as text and validated in Go, with no database or OpenAPI enums; money and amounts as `NUMERIC`, sent as decimal strings.
- **JSON columns** hold typed, versioned, size-bounded documents.
- **Commands** take an expected version and an idempotency key, and write their activity row and command receipt in the same transaction as the change.
- **Access** is applied before any filter, count, page, export or agent input.
- **Other features are reached through their `*pub` contracts**, read from AlloyDB. No Xano, FalkorDB or Universe graph traversal.

## Stage requirements

### Where they are stored

Today a stage's `criteria` document is an entry checklist. A move reads the destination stage's checklist; the code describes the check as answering whether a deal may enter a stage.

The decisions point the other way. A stage owns the requirements to move to the next stage (decision 2). They appear on the current stage (decision 12). They accumulate when a deal jumps ahead (decision 13). And a stage from the stage library carries its own requirements into any flow (decision 37). A stage's requirements must also stay with it when stages are reordered.

**Decided (T1): store the requirements on the stage a deal leaves.**

- Add `pipeline_stages.advance_requirements`, a version 2 requirements document, described below.
- A forward move checks the current stage's requirements and those of every stage it skips, in order. A move back checks nothing but needs a reason (FL-20). A move to a lost stage checks nothing but needs its reasons (FL-08).
- A won stage has no next stage, so what it takes to enter it lives on the stage before it. For example, Wired's "bank confirms the full amount" is stored with Signed's requirements.
- Existing flows are converted once: each stage takes the next stage's `criteria` as its own requirements. `criteria` is retired in a later migration once nothing reads it.

### Requirements document version 2

Version 1 is a single `all` list of up to 20 items and six checks: `has_target`, `has_stakeholder`, `field_present`, `task_done`, `action_succeeded` and `user_confirmed`. It has no either-or. The two shipped templates need more:

| Need | Example from a template | Proposal |
| --- | --- | --- |
| Either-or groups | Committed: a signed term sheet, a confirmed SAFE, or a confirmed follow-on allocation | `any` groups inside the `all` list |
| Not applicable | "For a priced round, the charter is filed"; "A purchase order, if one is required" | A person can mark an item not applicable with a reason, recorded like a confirmation |
| A minimum number of people | "Several people at the buyer are engaged" | `has_stakeholder` gains `min_count` |
| Email and calendar evidence | "The investor has replied"; "A meeting is on the calendar"; "The meeting happened with a partner" | New checks `reply_received`, `meeting_scheduled` and `meeting_held`, read from the interaction log. Until capture feeds them, a person can confirm instead, recorded as a confirmation (T2) |
| New deal fields | A dated next step; a tier | The `field_present` allowlist adds `next_action_on`, `tier` and `source` |

Unknown still blocks, as today: a check whose evidence cannot be read never passes.

## New tables

| Table | For | What it holds |
| --- | --- | --- |
| `projects.deal_stage_visits` | FL-17, FL-18, FL-20, DP-02, RP-01 | One row each time a deal enters a stage: entered and exited times, how it left (forward, back, won, lost or archived), the reason for a move back, and the stage summary with its status (none, drafted or edited), the agent run that drafted it, and who edited it. One open visit per deal. The move command writes it in the same transaction. Summaries are drafted from the stage's shared activity only, so every project reader can see them. |
| `projects.flow_templates` | TP-05 to TP-08, T8 | Saved templates: owner, optional organization, visibility (private or organization), name, outcome, kind, the source flow, a version, and a typed definition with every stage's name, meaning, description, requirements, suggested actions, stale threshold and key, plus role labels, reasons and default currency. Shipped templates stay as files in `assets/pipelines` and are listed alongside. |
| `projects.library_stages` | TP-10, T8 | Saved custom stages: owner, optional organization, visibility, and one stage's name, meaning, description, requirements, suggested actions and stale threshold. Adding one to a flow copies it into `pipeline_stages` with `library_stage_id` set; later library edits do not reach existing flows (decision 42). |
| `projects.deal_members` | CO-06 | The named people who can see a restricted deal. Unique per deal and person. |
| `projects.deal_notes` | DP-05, T4 | Notes on a deal, readable by the project's audience, or by the deal's members when it is restricted: author, body, archive time and version. |
| `projects.capture_exclusions` | AC-07 | Per person: the domains, people and threads never linked to deals. |

**Confidential deals reach every read.** A restricted deal is readable only by its members and its owner. Project admins see the masked card and can manage membership, and every membership change is recorded (T3). Everything that reads deals must apply that rule: the board, lists, search, counts, value totals, linked tasks, activity, notes, stage visits, suggestions, agent evidence, action runs, follow-ups and exports. Other readers see a masked card that keeps the stage count right. Column value totals leave the masked deal out and say how many are hidden, because including its value would reveal it.

## Behaviour changes

These change code in the Projects feature, not tables.

| Change | For | Detail |
| --- | --- | --- |
| Cumulative move check | FL-16, FL-19, FL-20 | Forward moves check the current and skipped stages' requirements. Moves back need a reason and record it in the stage visit. |
| New checks | FL-16 | `reply_received`, `meeting_scheduled` and `meeting_held` read the interaction log. `any` groups, not-applicable items and `min_count` evaluate as described above. |
| Review sees stage context | FL-17 | The review input adds each deal's stage description, next stage and missing requirements, and the summaries of earlier stages. |
| Review proposes stage moves | AI-06 | When the gate reports the next stage's requirements as met, the review may write a change request that moves the deal. A person confirms it through the existing adopt route (decision 10). Today's prompt forbids this. |
| Private reviews | AI-16 | A person can run a review over their own context: interaction log, stored relationship paths and enrichment facts. It writes suggestions only that person sees (decision 9). |
| Stage summaries | FL-18 | When a deal leaves a stage, a bounded review drafts the summary from that stage's shared activity; the person can edit it (decision 14). |
| Contact date rollup | AC-03, AC-06 | A job copies contact dates from project members' interaction logs onto deals. The interaction log's own refresh interval sets how current stale flags are. |
| Stale and at-risk flags on read | AC-06, AI-20 | Stale compares `last_inbound_at` or `last_meeting_at` with the stage's threshold, falling back to `last_progress_at`. At-risk reasons in v1: single-threaded, close date pushed back, no next step and past the close date. Falling activity uses the interaction log's momentum. A changed job waits for signals (AI-25, Later). |
| Nudge limits | AI-23 | Reviews apply the daily cap and muted types before writing suggestions. |
| Shipped templates | TP-01 | `assets/pipelines/investors.v1.json` and `sales.v1.json` are replaced by `funding-round-raise.v1.json` and `enterprise-sale.v1.json` (decision 39). The `starter` field on flow creation takes the new keys. |
