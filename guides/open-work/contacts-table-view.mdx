## Start here

**Contacts View** is a new full-screen route, `/contacts`, reached from the ⌘K palette next to **Activity View** and **Network View**. It renders every contact the signed-in user owns as a row in a virtualized TanStack Table, lets the user add typed custom columns, save named views, and drives the whole table from the same query composer that sits at the bottom of Discover and Collections. The composer is not a chat surface: it is an LLM call with tools whose only job is to change the table (filter, sort, group, columns, fields, values) or hand the current rows to an existing feature (collections, outreach).

| Repository / runtime | Owns |
| --- | --- |
| `orbiter-backend` — Go | `GET /v1/contacts/table` row projection, custom-field definitions and values, saved views, query log. All database access. |
| `orbiter-frontend` — TanStack Start server, TypeScript | `POST /api/contacts-view-query`: the `chat()` loop, system prompt, tool definitions, streaming, verified authentication, model-run telemetry. No Go, no business writes. |
| `orbiter-frontend` — browser, React | `/contacts` route, `contacts-view` feature, TanStack Table v9 + TanStack Virtual, client tools that mutate table state and call Go with the user's own session, confirm cards, person sheet reuse. |

Go runs only in orbiter-backend. The LLM loop runs only in the TanStack Start server. Business writes to Go originate in the browser with the user's session. The BFF verifies that session before spending model tokens and records model-run telemetry; browser receipts record actual tool outcomes. Neither runtime holds a privileged business-write credential.

## Decisions

Each answer was chosen from options with a stated recommendation; the recommended option was taken in every case except 4 and 10, where more scope was selected, and 9, which Mark refined after the first pass.

| # | Question | Decision | Why |
| --- | --- | --- | --- |
| 1 | Which endpoint feeds the rows? | **New Go endpoint `GET /v1/contacts/table`.** | The frontend already reads Go `GET /v1/contacts` on `dev` (`src/features/contacts`), but that list item is shared by search and widgets and stays narrow. The table needs a wider, flatter projection plus custom-field values. |
| 2 | Where do filter/sort/group run? | **Client-side full dataset, virtualized.** | Hydrate all rows once; TanStack Table does the work in the browser; TanStack Virtual keeps the DOM small. AI tools become pure state deltas instead of API calls. Comfortable to roughly 20k rows. |
| 3 | Custom-field storage | **`persons.contact_field_defs` + a `custom_fields` JSONB column on `persons.contacts`, GIN-indexed.** | AlloyDB is Postgres, so JSONB and GIN are available (the archived Deal Flow typed-EAV design existed only because Xano has no GIN). Adding a field is a row insert, not a migration. |
| 4 | What may the AI tools do? | **All four tiers:** view state; create field definitions; bulk-set values on matching rows; hand rows to collections and outreach. | Writes are gated by decision 11. |
| 5 | Where does the LLM loop run? | **TanStack Start server with `@tanstack/ai` tools.** | The Go OpenRouter client (`internal/clients/openrouter`) supports `response_format` structured output only: no `tools`, no streaming. The TanStack AI BFF already has tool calling, and `@tanstack/ai` 0.38 (installed) has `.client()`, `needsApproval`, and `createChatClientOptions`. |
| 6 | Conversation state | **Multi-turn, in memory per view session.** | Each turn carries the last turns plus a compact table snapshot, so "now also sort by last activity" works. Nothing persisted; Go logs each query for telemetry only. |
| 7 | Saved views | **Named views in Go + `?view=` URL param + localStorage last-state.** | `persons.contact_views` with a versioned state JSON. |
| 8 | Custom-field ownership | **Per user in v1, `scope_type` + `scope_id` in the schema for org-shared later.** | No migration when org sharing arrives. |
| 9 | Which contacts are rows? | **All of my contacts, with an All / Personal / Shared scope switch when I belong to at least one org.** | Every row is `user_id = caller` and `merged_into_contact_id IS NULL`, the same predicates as `ListContactsByUser`. Org membership does not change ownership: a contact added while an org was active is still mine. What differs is sharing. `visibility = 'private'` keeps a contact off every org surface (the org graph, teammates); `'visible'` shares it with the orgs I belong to; `organization_id` records which org was active when the contact was created (nullable, attribution only, per `organizations_002`). The switch is a filter on those two columns, not a different query. |
| 10 | Row interaction | **Name opens the existing PersonSheet; inline edit for custom cells, note and nickname; row checkboxes feed the global node-selection store.** | Reuses `PersonSheet` (mounted in `_authed.tsx`, driven by the `person` search param) and `useNodeSelectionStore`, so Email Outreach Composer and add-to-collection work unchanged. |
| 11 | Bulk write policy | **Always preview and confirm.** Field creation is the one exception: additive, applied immediately; removing an unused field is a separate field-manager action. | Every many-row or cross-feature write shows affected count, sample rows and the exact change; nothing writes without the Apply click. |
| 12 | Rollout | **`VITE_CONTACTS_VIEW` flag hides the palette command and redirects the route.** | Same shape as the `VITE_TANSTACK_AI_CHAT_*` flags. Ships dark, enabled per environment. |

### Assumed defaults

Chosen by the author; override in place without reopening the workshop.

- **Route** `/contacts`. Palette command id `contacts-view`, label "Contacts View", category Navigation, lucide `TableIcon`. No hotkey in v1.
- **Default columns, in order:** select, Name (pinned start), Title, Company, Location, Email, Last activity, Kind, Momentum, Emails, Meetings, Connected, Note, Nickname, Added. Visibility and Org exist as columns but start hidden. Custom columns append after Added in `position` order.
- **Scope switch:** rendered in the toolbar only when the user has at least one org membership (from the existing `useBackendMe()` data). **All** (default) shows every row; **Personal** filters `visibility = private`; **Shared** filters `visibility = visible`. An optional second filter narrows Shared to the org that was active at creation (`organization_name`). Both are ordinary column filters through the same store, so they sort, group, save with views and are reachable by the AI. Users with no org see no switch and all rows.
- **Row cap** 25,000; page size 1,000; compact 40 px rows. Banner: "Loaded 25,000 of N contacts. Search applies to loaded contacts only." Search cannot fetch omitted contacts in this client-side design. Broad AI actions remain disabled at the cap; show an explicit explanation.
- **Custom field types in v1:** `text`, `number`, `date`, `checkbox`, `select`, `multi_select`, `url`. `person_ref` and `company_ref` wait for a picker (see Later).
- **Model:** `CONTACTS_VIEW_QUERY_MODEL` server env, defaulting to the chat BFF default `anthropic/claude-sonnet-4.5` via OpenRouter, provider sort `throughput`. Bake off cheaper tool-callers after Phase 5.
- **Conversation memory:** up to 10 complete user turns with their assistant/tool-result groups, bounded by bytes and tokens; reset when the route unmounts. Prune complete groups, never individual tool results.
- **Query log:** authenticated, idempotent per-turn receipt endpoint; the BFF supplies model timing and the browser supplies actual execution outcomes. See [Query log](#query-log).
- **Export CSV:** out of v1.

### Layout contract and reuse

1. `_authed.tsx` already mounts `WorkspaceShell`, which owns `Header`. Add `/contacts` (and its normalized trailing-slash form) to the shell's header visibility test. `ContactsViewPage` must **not** mount `Header`, Widgets, notifications, PersonSheet or another WorkspaceShell. Preserve their instances when moving between views.
2. Reuse the top navigation/chrome from `src/components/global/top-nav.tsx`. It currently derives its tab from `/network` search state. Introduce a small explicit standalone-route mode, or extract its presentational row, so `/contacts` has no falsely selected Discover tab and existing tab clicks navigate to `/network` with the chosen view. Keep the existing controls, spacing and interactions; no new Contacts `ActiveView` enum or TopNav tab is needed.
3. Match the `/network` outer gutters, top-row height, bottom inset, `--bg-page`, `--panel-surface`, 18 px panel radius, border and shadow. Use a one-column grid with rows `auto minmax(0,1fr)`; do not retain empty SideNav/right-rail tracks or placeholders. If using the shared three-column grid wrapper, the panel must span `1 / -1` and no side-panel components mount.
4. The panel is `min-h-0 min-w-0 flex flex-col overflow-hidden`. Toolbar and query dock are non-scrolling siblings of a `min-h-0 flex-1 overflow-auto` table scrollport. Sticky column headers stick inside that scrollport. Horizontal scroll moves columns, never the toolbar, app chrome or composer. Use shared spacing tokens; no viewport-sized fixed offsets inside cells.
5. Reuse `QueryInput` with `hideFilters`, `floatOverlay`, `collapsible`, `ariaLabel="Contacts table query"`, its voice behavior, loading hint, stop/retry hooks and draft lifecycle. Center a responsive dock with the same measured composer width as Discover at the same viewport, capped to panel width minus its inset. The table panel stays full width; the input does not stretch across the entire grid. Keep the response strip/approval card within that centered dock. Store the width rule in one shared token or small layout primitive if needed.
6. `floatOverlay` already portals a fixed visual to the body and measures a sentinel. Keep the sentinel in the centered dock, reserve its actual expanded height, and test its portal against modal/sheet z-index and focus behavior. Never position it relative to horizontal table scroll. The final row and focused cell must remain reachable above the expanded dock. Resizing, zoom and composer collapse must not cover cells.
7. Name opens the existing PersonSheet as an overlay. Field manager and confirmations use existing dialog/popover primitives. They do not add a permanent second or third panel. Show table-only errors inside the single panel; shared chrome remains usable.

### Visual acceptance

At 1440×900 and 1280×800, capture Discover and Contacts in the same session. The Contacts panel's left, right, top and bottom edges match the union of Discover's three panels within 2 CSS px; shared chrome stays at the same coordinates. The composer center matches the panel center within 2 CSS px. ## Navigation and palette command

### How existing navigation commands work

All palette commands are one array in `src/features/command-palette/constants/commands.tsx`, returned by `getCommands(navigate, queryClient, currentUser)`. Each entry is a `CommandDefinition` with `id`, `label`, `category` (`"Navigation" | "Actions" | "Tools"`), `icon`, `action`, and optional `hidden`, `shortcut` (display string) and `hotkey` (a `react-hotkeys-hook` combo). Three consumers read that array and need no changes:

- `command-palette.tsx` filters `category === "Navigation" && !hidden` into the **Navigation** group and calls `cmd.action()` on select.
- `hooks/use-command-hotkeys.ts` binds every command's `hotkey` with `useHotkeys`, enabled only when `hotkey` is set and the command is not hidden.
- `_authed.tsx` mounts the palette and `useCommandPaletteShortcut()` (⌘K) once for every protected route.

The three existing navigation commands navigate with `navigate({ to: "/" })` (Activity View), `navigate({ to: "/network" })` (Network View) and `navigate({ to: "/email-inbox" })` (Email Inbox). `navigate` is typed against `src/routeTree.gen.ts`, so the route file must exist before the command compiles.

### Steps for the AI agent

1. **Add the feature flag** in `src/env.ts`. In the client schema block add `VITE_CONTACTS_VIEW: tanstackAiChatFlagSchema` (the existing schema that parses the string `"true"` to a boolean) and in the `runtimeEnv` block add `VITE_CONTACTS_VIEW: import.meta.env.VITE_CONTACTS_VIEW`. In the server block add `CONTACTS_VIEW_QUERY_MODEL: z.string().min(1).optional()` with its `process.env` mirror. Add both keys to `.env.example`; configure staging when rollout is authorized. Add a server `CONTACTS_VIEW_ENABLED` gate as well: a hidden palette command is not API access control.

2. **Create the route file** `src/routes/_authed/contacts.tsx` (skeleton below). Run `pnpm dev` once so the router plugin regenerates `src/routeTree.gen.ts`; never edit that file by hand.

3. **Add the command** to `commands.tsx`, directly after the `network-view` entry so it sits between Network View and Email Inbox in the Navigation group:

### Route skeleton

```tsx src/routes/_authed/contacts.tsx
import { createFileRoute, redirect } from "@tanstack/react-router";
import { DefaultNotFound } from "@/components/global/default-not-found";
import Loader from "@/components/global/loader";
import { env } from "@/env";
import { contactFieldDefsQueryOptions } from "@/features/contacts-view/api/use-contact-field-defs";
import { contactViewsQueryOptions } from "@/features/contacts-view/api/use-contact-views";
import { contactsTableRowsQueryOptions } from "@/features/contacts-view/api/use-contacts-table-rows";
import { ContactsViewPage } from "@/features/contacts-view/components/contacts-view-page";

// `person` and `active-tab` must survive validation: PersonSheet is mounted
// in _authed.tsx and reads them from useSearch on every route.
type ContactsSearchParams = {
  view?: string;
  q?: string;
  person?: string;
  "active-tab"?: string;
};

// Interface sketch: use shared UUID schemas for view/person ids in production.
const str = (v: unknown) => (typeof v === "string" && v ? v : undefined);

export const Route = createFileRoute("/_authed/contacts")({
  beforeLoad: () => {
    if (!env.VITE_CONTACTS_VIEW) throw redirect({ to: "/" });
  },
  validateSearch: (search: Record<string, unknown>): ContactsSearchParams => ({
    view: str(search.view),
    q: typeof search.q === "string" ? search.q.slice(0, 200) : undefined,
    person: str(search.person),
    "active-tab": str(search["active-tab"]),
  }),
  loader: async ({ context: { queryClient } }) => {
    // Warm only the first page; render recoverable query errors inside the panel.
    // Pass authenticated user/environment keys from the route context in real code.
    await Promise.allSettled([
      queryClient.ensureQueryData(contactFieldDefsQueryOptions()),
      queryClient.ensureQueryData(contactViewsQueryOptions()),
      queryClient.ensureInfiniteQueryData(contactsTableRowsQueryOptions()),
    ]);
  },
  staleTime: 60 * 1000,
  component: ContactsViewPage,
  pendingComponent: () => <Loader />,
  notFoundComponent: DefaultNotFound,
});
```

`ContactsViewPage` consumes the existing `WorkspaceShell` and shared top navigation, then renders exactly one panel. See the [layout contract](#layout-contract-and-reuse); Header ownership stays in the shell.

## Rows endpoint

### Contract

`GET /v1/contacts/table` — the caller's live contacts as flat table rows, keyset-paged in large pages for full hydration. Lives in the `persons` feature next to `GET /v1/contacts` and is registered inside the existing `r.Route("/contacts", …)` block in `internal/features/persons/handler.go` as `r.Get("/table", …)`. Auth is the module-level `RequireWorkOS`; the owner is `pmw.OrbiterUserID(r)`, never a body or query field.

| Query param | Type | Notes |
| --- | --- | --- |
| `limit` | int | Default 500, max 1,000. Above `pagination.MaxLimit`, so the handler uses its own bound, not `Page.Normalize()`. |
| `cursor` | string | Opaque keyset cursor on `(created_at DESC, id DESC)`. Empty on the first call. |

There is no `sort` or `query` param: order is fixed for a stable keyset and every sort and filter happens in the browser (decision 2).

Success envelope is the standard `{data, error, meta}` via `pmw.OKMeta`, with `data` an array of rows and `meta` carrying `total`, `nextCursor` (empty string on the last page) and `fieldDefsVersion` (an owner-scoped monotonically increasing schema revision, including deletions; see the mutation contract).

### What the API returns today

```sql internal/features/persons/queries/listings.sql — new query
-- name: ListContactTableRowsByUser :many
-- Flat row projection for Contacts View. Fixed keyset on (created_at DESC, id DESC);
-- all sorting/filtering is client-side. Add the first-page upper bound
-- from the pagination contract when implementing the cursor.
SELECT
    c.id                        AS contact_id,
    c.person_id,
    c.created_at,
    c.updated_at,
    TRIM(CONCAT_WS(' ', mp.first_name, mp.middle_name, mp.last_name)) AS name,
    mp.first_name,
    mp.last_name,
    c.nickname,
    mp.avatar,
    EXISTS (SELECT 1 FROM users.users u WHERE u.person_id = mp.id) AS orbiter_user,
    mp.current_title,
    mc.id                       AS company_id,
    mc.name                     AS company_name,
    mc.logo                     AS company_logo,
    ploc.id                     AS location_id,
    ploc.formatted_location     AS location_formatted,
    pe.address                  AS primary_email,
    COALESCE(ec.email_count, 0)::int AS email_count,
    c.connected_at,
    c.last_activity_at,
    c.last_activity_kind,
    c.last_email_activity_id,
    c.last_calendar_event_id,
    c.total_email_activity,
    c.total_remote_events,
    il.total_emails,
    il.total_meetings,
    il.momentum,
    c.note,
    c.visibility,
    c.organization_id,
    org.name                    AS organization_name,
    c.custom_fields
FROM persons.contacts c
JOIN persons.persons mp ON mp.id = c.person_id
LEFT JOIN companies.companies mc ON mc.id = mp.current_company_id
LEFT JOIN locations.primary_locations ploc ON ploc.id = mp.primary_location_id
LEFT JOIN persons.contacts_interaction_log il ON il.contact_id = c.id AND il.user_id = c.user_id
LEFT JOIN organizations.organizations org ON org.id = c.organization_id
LEFT JOIN LATERAL (
    -- first email by creation; reuse the exact tables ListUserContactEmails joins
    SELECT ea.address
    FROM email_addresses.contact_emails ce
    JOIN email_addresses.email_addresses ea ON ea.id = ce.email_address_id
    WHERE ce.contact_id = c.id
    ORDER BY ce.created_at ASC, ce.id ASC
    LIMIT 1
) pe ON TRUE
LEFT JOIN LATERAL (
    SELECT COUNT(*) AS email_count
    FROM email_addresses.contact_emails ce
    WHERE ce.contact_id = c.id
) ec ON TRUE
WHERE c.user_id = sqlc.arg(user_id)
  AND c.merged_into_contact_id IS NULL
  AND (c.created_at, c.id) < (
        COALESCE(sqlc.narg(cursor_time)::timestamptz, 'infinity'::timestamptz),
        COALESCE(sqlc.narg(cursor_id)::uuid, 'ffffffff-ffff-ffff-ffff-ffffffffffff'::uuid))
ORDER BY c.created_at DESC, c.id DESC
LIMIT sqlc.arg(row_limit);
```

### Pagination and consistency requirements

- Query with `limit + 1`; return at most `limit`, and encode the last **returned** tuple only when the extra row exists. Validate timestamp and UUID together; malformed, overlong (over 1 KiB), wrong-version or partially populated cursors return 400. Do not widen the shared 200-row paginator for unrelated endpoints.
- Count and rows must use identical ownership, merge and person-join predicates. Add `CountContactTableRowsByUser`; run first-page count and rows in one short consistent read transaction. Check a partial index on `(user_id, created_at DESC, id DESC) WHERE merged_into_contact_id IS NULL` with `EXPLAIN (ANALYZE, BUFFERS)` before adding a duplicate index. Email lookup needs an index starting with `contact_id`.
- Carry the first page's upper tuple in subsequent opaque cursors, and bound every page by it. This makes inserts above that tuple appear on Refresh rather than midway through hydration. It is **not** an MVCC snapshot: deletes, merges, updates and backdated inserts can still change the data. Never hold a database transaction open across page requests. Document `total` as observed at hydration start, deduplicate by `contact_id`, and refresh on detected drift.
- Expose `fieldDefsVersion` from a per-user schema revision row, not `MAX(updated_at)`: deleting the newest or last definition must change the revision. If pages disagree, reload definitions and start a new hydration generation. Unknown keys are ignored until reconciled; never render a field using the wrong type.
- Joined organization names are attribution, not proof of current sharing access. Enforce the existing org-name visibility policy before exposing a name for a membership the caller has lost. Scope switch labels describe contact visibility; they do not promise that every current teammate can see the contact.
- Missing rollup row means nullable/unknown totals and momentum, not invented `cold` or zero. Keep `total_email_activity` distinct from rollup `total_emails`. Verify the producer's actual momentum vocabulary in Phase 0; the example values are not a backend enum. Deterministic primary email uses `(ce.created_at, ce.id)` ascending. It is a display choice, not an outreach deliverability decision.
- Merge policy must include custom fields: preserve winner values, copy loser-only keys, surface differing non-empty values for existing merge policy, and never transfer another owner's definitions. Extend contact-merge regression tests. Contact deletion removes values with the contact; field deletion strips values on both active and merged contacts owned by the caller.

`scope_id` has no foreign key because it is polymorphic. On every list/read/write, the service derives `scope_type='user'`, `scope_id=caller` and `created_by_id=caller`; reject attempts to supply a different scope. ### Value shapes

Values are keyed by definition **id** (stable, never renamed), not by `key`.

| `field_type` | JSON value | Validation |
| --- | --- | --- |
| `text` | string | max 2,000 chars, trimmed |
| `number` | number | finite; `config.precision` 0–4 |
| `date` | `"YYYY-MM-DD"` string | valid calendar date |
| `checkbox` | boolean | — |
| `select` | option id string | must be a live option id on the definition |
| `multi_select` | array of option id strings | each a live option id, max 25, deduplicated |
| `url` | string | parses as `http` or `https` |

Also bound labels to 60 characters, option labels to 60, options to 100, and every value map to 5 entries. Numeric precision is validated, never silently rounded; use decimal-aware comparison for allowed precision and reject unsafe numeric range. Empty text/URL and empty multi-select normalize to clearing; checkbox `false` and number `0` remain real values. Dates are date-only strings, never shifted by time zone. Option IDs are stable server-issued UUIDs. Reject duplicate option labels after trim/case normalization and unknown object keys.

### Mutation integrity

Implement these rules in the `persons` service/repository boundary, shared by manual and AI-driven writes:

- A user-scoped `contact_field_schema_state` row holds a monotonic `revision`. Definition create/update/archive/delete locks it for update and increments it in the same transaction. Value mutations lock it for share while validating definitions and updating rows. Lock schema first, then contacts in sorted id order, everywhere. This prevents a concurrent value writer from resurrecting a deleted field key.
- Validate the entire request before writing: 1–2,000 **unique** contact ids, 1–5 owned active field ids, all values valid, all contacts live and owned. A missing/foreign/merged id aborts the whole chunk with generic 404; there is no silent intersection or partial unauthorized success. An empty input is 400. Do not reveal which foreign id exists.
- Single-cell requests carry `expected_updated_at` from the row DTO; compare-and-set returns 409 `stale_contact` on conflict. Update the timestamp in the same transaction. Definition/view PATCH requests similarly carry their last version. Do not auto-overwrite a conflict; refetch and show the current value. Use the repository's timestamp precision consistently in wire and SQL.
- Bulk requests include `operation_id`, `chunk_id`, `expected_field_defs_version`, the frozen ids/values and per-contact expected revisions. Store an owner-scoped operation/chunk receipt with payload hash and result in the same transaction as the write. Same key and hash returns the original result; a changed payload returns 409. Lock/replay the receipt before checking stale row versions on retries. Retain receipts for at least seven days; clients never retry an expired operation silently.
- Each chunk is atomic. Several chunks are **not** one transaction. Process sequentially, record committed ids and counts after every chunk, stop on the first failure and show completed/failed/not-started counts. On uncertain transport outcome, retry the same chunk key or read the receipt; do not create a new operation. A conflict needs a new preview for unfinished rows. Cancellation stops future chunks and cannot undo committed chunks.
- Apply JSONB changes atomically in SQL; do not write back a whole JSON object fetched earlier. For a mixed map, remove null-valued keys and merge non-null entries once. Increment `updated_at` only on actual changes. Preserve unrelated custom keys. Run delete-key SQL for all owned contacts, including tombstones.
- Field option removal/reassignment is a transaction under the definition lock: validate replacement ids, rewrite scalar and array values (deduplicate arrays), then update options/revision. Archived options/fields are not offered for new writes. Concurrent limit checks (50 fields) and slug allocation use the scope lock/unique index; map collisions to domain errors.
- Hard field deletion shows the field manager's own destructive confirmation with affected count. Creating a field is additive; global table Undo does not delete it or erase values written later.
- `PATCH /v1/contacts/{contact_id}/nickname` is **new work**. `UpdateContactNickname` SQL exists but the inspected handler exposes no nickname route. Add owner checks, nullable/trimmed nickname validation (max 120 characters), revision handling, DTO, OpenAPI and tests. Extend the note route compatibly with optional revision preconditions for existing consumers; table edits always send one.

Use UUID operation ids and nonnegative chunk indexes. Field/view creation uses chunk zero with its same stable operation id. A concurrent request with the same receipt key waits for the first transaction and replays its result; no “in progress” success response. Result storage is private and bounded to the endpoint's 2,000-row maximum. Cleanup uses the existing scheduled maintenance path with the seven-day minimum retention; expiry never makes a known completed operation safe to replay under a new id.

- `PATCH /contacts/{id}/fields`: `{values, expected_updated_at, expected_field_defs_version, operation_id}`; return authoritative `{contact_id, custom_fields, updated_at, field_defs_version}` inside the standard envelope. Share validation with bulk.
- `POST /contacts/fields/bulk`: `{contact_ids, values, expected_updated_at: {contactId: timestamp}, expected_field_defs_version, operation_id, chunk_id}`. The revision map must match the exact deduplicated id set. Return `{operation_id, chunk_id, requested, updated, unchanged, rows}`; each row includes id, changed values and new revision. No missing-row successes. Bound actual body bytes to 512 KiB, reject before decode; field/view bodies to 64 KiB. Document these limits in OpenAPI.
- `GET /contacts/table/operations/{operation_id}/chunks/{chunk_id}`: owner-scoped receipt lookup for reconciling unknown transport outcomes, standard envelope; 404 means no committed receipt **yet**, not proof an in-flight request cannot still commit. Retry the identical request/key to serialize with an in-flight writer.
- Field/view POST takes `operation_id`; PATCH takes `expected_updated_at` in addition to changed properties. Service-returned DTOs include `updated_at`; frontend exposes that as `version` where the tool uses `expectedVersion`. Do not confuse a view's optimistic concurrency token with `state.version`, its JSON schema version. Field lists include the monotonic schema revision in meta; archive/delete/update all increment it.
- Implement owner-scoped list/view/definition DTOs and envelopes in the OpenAPI fragment and add root `paths` references. Static `/table`, `/fields`, `/views` routes must not fall through UUID contact parsing. Contract-test 400 validation, 401 auth, 404 ownership, 409 version/option/limit conflicts and 413 size bounds. No enum CHECK constraints or OpenAPI enums; Go owns enum validation under repository policy.

Collection operation receipts belong to the existing collection service if new support is needed. Inject/reuse its public boundary; Contacts must not write collection tables directly. Rollout is blocked until new-collection retry and membership deduplication have real integration evidence.

**Cache reconciliation:** cancel in-flight refetches before optimistic edits; patch every matching page of `InfiniteData`, preserving `pages` and `pageParams`. Track an edit token per contact/cell and roll back only that token's patch, never a whole stale query snapshot. Serialize writes to one contact so note/nickname/custom-cell edits cannot race locally. Replace with the server response on success and invalidate dependent contact list/person-sheet queries. Bulk writes patch only acknowledged chunks; refresh after partial/unknown outcomes. A reload from another tab may conflict and must not be silently lost.

### Filter, selection and undo semantics

- Column filters combine with AND. A column has one predicate: `add` upserts by column id, `replace` replaces all column predicates, `remove` takes ids only, and `clear` removes column filters. These do not clear quick search unless the command explicitly does so. Empty/missing input is rejected for operations that require values.
- Text `includes`/`equals`/`in` normalize case and surrounding whitespace; ids/options use exact identity. `in` means any listed value; on multi-select it means nonempty intersection. `not_in` means no intersection for nonempty values; use `is_empty` when emptiness is intended. Number comparisons are numeric; `between` is inclusive and ordered. `false` and `0` are not empty. Missing/null/empty string/empty array are empty. Other predicates exclude nulls.
- Date-only custom fields use calendar strings. Timestamp filtering uses the user's IANA time zone: `before D` is before local start of day D; `after D` is at/after start of the next day; `on_or_after D` is at/after start of D; `between [A,B]` is `[start(A), start(B+1))`. Add these distinct ops to the schema and test DST. “No interaction since D” includes null activity via a bounded `includeEmpty` flag on that date predicate; do not pretend `before` matches null.
- Sorts have an explicit null-last policy and contact-id tie-breaker. Group only supported categorical columns, at most two; grouping and collapse never alter matching counts or target ids. Count contacts, not groups. Numeric aggregation is opt-in sum; other columns show no fabricated aggregates. Header checkbox operates on matching contacts, not virtualized rows. Selection survives filtering; show “N selected, M hidden by filters.”
- Checkbox/Name stay visible, pinned start, and first in that order. Deduplicate show/hide/pin/order lists, reject contradictory lists and unknown ids, and append omitted columns in existing relative order. Do not store display widths, date formatting or labels as contact identity.
- The route owns selection mode `contacts-view`. Activate it on entry and restore the previous mode on exit only if still active. Add a minimal atomic `replaceNodesForMode` store action: existing `selectNodes` is additive and cannot implement a replacement safely. Row checkboxes are authoritative on this route; do not synchronize in both directions with effects. Map contacts to unique person ids for global handoff and report deduplication. Preserve other modes' selection.
- Undo is chronological, bounded to 50 entries and limited to view-state/selection changes. Store one before/after entry per completed AI turn (or manual gesture), excluding no-ops. Do not offer per-chip arbitrary undo when later changes depend on it. Field creation, saved-view writes, values and collection/outreach actions are not reversed by view Undo. Switching users or saved views clears Undo. Escape cancels editing, never silently undoes a database mutation.

### Editing and accessibility

Use a named table/grid with column headers, `aria-sort`, labeled row checkboxes and accessible filter/editor controls. For a virtual grid expose logical row count/index and maintain one roving focus cell; keyboard movement scrolls the destination into view before focusing it. Do not announce spacer rows as data. Enter/F2 starts an editor, Escape cancels, Tab commits once and moves to the next editable cell; IME composition must not submit. Sorting/filtering/grouping with an open editor commits valid edits or keeps focus with an error. Use local cell drafts, not a whole-table render on every keystroke. A validation/conflict error keeps the draft and identifies the cell. Announce result counts/loading/approval in a polite live region; errors use alerts. Test name-link clicks separately from checkbox clicks and field-editor events.

Use the existing focus-trapped sheet/dialog primitives. Closing PersonSheet preserves `view`, `q`, scroll anchor and focus; when its original row disappears, return focus to the table heading. Save field-manager forms only after their validation passes. Zero contacts, zero filtered matches, no custom definitions, stale definitions, offline, 401, 409, 429 and 5xx all need explicit recoverable UI states.

### Performance and verification procedure

- Measure a production frontend build, Chromium desktop at 1440×900, fixed fixture and documented hardware, three warm-up runs then 20 measured runs. Report p50/p95 and absolute maximum; do not call a subjective scroll impression a pass.
- At 20,000 contacts: filter/sort p95 at most 100 ms after input debounce; at most 200 mounted data/group rows; no main-thread task over 100 ms during a ten-second steady scroll. Repeat at the maximum 50 custom fields. Keep column definitions/cell callbacks stable and avoid rebuilding snapshots/facets per keystroke before reaching for workers or more virtualization.
- Rows endpoint p95 at most 300 ms per 1,000-row page over a seeded 10k-contact local database, excluding network transfer; log query count, plan and payload bytes. No per-row HTTP request or unbounded lateral scan. Hydration performance includes JSON decoding and cache allocation, not only DOM rendering.
- Browser suite covers the full matrix with a mock provider and real local Go/database path for writes. Provider-live tests are separately opt-in on synthetic data. Add a small Playwright setup only if the repo has no browser-test runner; do not label manual screenshots as automated tests.
- Backend: `make sqlc-generate`, targeted `go test ./internal/features/persons/...`, race tests for new concurrent service logic, migration Up/Down/Up on a disposable database, the repository lint target and `npx @redocly/cli lint api/openapi.yaml`. Verify actual endpoints against the OpenAPI envelope and root path references.
- Frontend: scoped `pnpm exec biome check` without `--write`, `pnpm exec tsc --noEmit`, `pnpm test`, `CI=true pnpm build`, then browser tests. Record existing baseline failures with unchanged evidence; they cannot mask a new failure.
- Documentation: `mintlify validate`, then `mintlify broken-links --check-anchors`; the installed CLI has no `--files` option, so separate findings in these two pages from existing site-wide link debt. Stop the preview for these checks because this CLI shares generated files, then restart it on its original port. Do not call disabled-OpenAPI validation a full-site pass.
