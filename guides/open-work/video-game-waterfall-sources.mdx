**Contract baseline: `games-v1`, September 8, 2026.** This locks the intended Go/GCP design, not a claim of implemented workers or enabled vendor access. Keep **six game entity families**. The game worker owns their creation/reuse through the finite queued plan; the movie pipeline supplies the existing game identity and credits. ## Decision by node type

| Type | Decision for the first Go build | Sources that can support it | Main relationship |
| --- | --- | --- | --- |
| `Video_Game` | Required canonical game; reuse an IMDb-created UUID and keep it hidden until game publication | Wikidata, reused IMDb identity, exact official game/store evidence; enabled catalog providers | Credits, companies, adaptations and game context |
| `Game_Series` | Include when a **video-game series** and membership are evidenced | Typed Wikidata P179; verified official series membership; enabled catalog series mapping | `IN_GAME_SERIES` |
| `Game_Platform` | Include exact supported platform identities | Typed Wikidata P400; explicit official/store platform evidence; enabled catalog platform records | `AVAILABLE_ON` after release evidence |
| `Game_Engine` | Include when exact game-engine use is evidenced; no blanket requirement for every game | Typed Wikidata P408, official developer/engine-maker evidence; enabled engine mapping | `USES_ENGINE` with version/use scope |
| `Game_Release` | Include **conditionally**, when a coherent platform release needs its own identity; retain sparse dates as facts | Qualified Wikidata dates; exact official releases; enabled catalog release records | `RELEASE_OF`, scoped `AVAILABLE_ON` |
| `Game_Award` | Include scoped nominations/results with known ceremony/category/nominee entry | The Game Awards, qualified Wikidata, other explicitly supported award-body pages | `HAS_AWARD`; named `WON_AWARD` / `NOMINATED_FOR` |

Support coverage is optional per game. Missing engine, series, release or award facts do not prevent a valid game publishing. An attempted **required** stage failure still blocks publication under the declared manifest; an optional unsupported provider cannot be silently marked successful. All support identities compete within the existing leaf budgets.

## Complete source inventory

This inventory covers every source class in the current game plan. “Can support” describes evidence capability; production access, parser verification and fact election are separate gates. No new subscription or global catalog import is required to implement the six contracts.

### Adapter mapping details

**Wikidata:** type-check the target of [P179](https://www.wikidata.org/wiki/Property:P179), [P400](https://www.wikidata.org/wiki/Property:P400) and [P408](https://www.wikidata.org/wiki/Property:P408). These properties span more than our game classes. P179 is not automatic franchise membership; P408 may describe another software-engine kind. [P577](https://www.wikidata.org/wiki/Property:P577) dates need their own platform/territory qualifiers; never multiply independent arrays into release combinations. P166/P1411 requires category, ceremony/year and recipient scope before `Game_Award` projection. P144/P4969 retains the existing normalized adaptation contract. A bounded inverse P406 lookup can support the music-to-game handoff after soundtrack and game identity resolve. Label resolution must not read `labels.en` alone: Valve Corporation ([Q193559](https://www.wikidata.org/wiki/Q193559)) and Linux ([Q388](https://www.wikidata.org/wiki/Q388)) carry 20 and 57 labels respectively but no English one, so a naive read drops developer and platform names silently rather than erroring. Fall back to `sitelinks.enwiki.title`, then to another available label with its language recorded; an unresolved label is a coverage reason, never an empty name.

**IGDB schema binding:** use `game_type`, `game_status`, `collections`; the older game `category`, `status`, `collection` fields are deprecated. Read typed collection membership, not every grouping. For `release_dates`, preserve `game`, `platform`, `release_region`, `date_format`, `date`, `status`; old `region`/`category` are deprecated. An ID there aliases a date assertion, not automatically a canonical release. Company flags distinguish `developer`, `publisher`, `porting`, `supporting`; inspect the role instead of assuming every involved company is the developer. `game_engines` supplies an engine candidate; a version needs its own evidence. The API documentation is reviewed; no authenticated response/entitlement is claimed. [Schema](https://api-docs.igdb.com/)

**MobyGames binding remains conditional:** verify fields and permitted retention for the enabled tier with a retained response before mapping. Group membership may describe an engine, theme or editorial grouping; classify it before accepting a series or engine relation. No generic group-to-series cast, assumed credits endpoint or fabricated provider release ID. A Wikidata Moby ID is still useful as an alias without buying access.

This is **not** strong-ID disagreement and must not block on conflict, nor merge. CS:GO additionally asserts a second app ID (`4465480`), so the Steam alias relation is many-to-many in both directions. Scope each alias by the observation and keep `P155`/`P156` succession as the ordering evidence. Verified on Wikidata September 9, 2026 |

## Frozen boundaries and maximum relationship value

- Use the six game types plus **existing** Person, Company, movie/theatre and music identities. Genres, themes, modes, ratings and artwork are scoped properties/media records; no new genre, character, award-category or storefront hubs in this build.
- `Game_Series` means a typed video-game series. Generic franchises, fictional universes, marketing collections and bundles stay source context until a separate compatible contract exists. Their labels alone cannot create `IN_GAME_SERIES` or `BASED_ON`.
- Remakes/remasters and substantive separately identified expansions may be distinct `Video_Game` identities. A port, SKU, cosmetic DLC or soundtrack app cannot automatically become another game. `EDITION_OF` and `EXPANSION_OF` need the exact typed relation; sequel/similarity links cannot stand in for either.
- Reuse company identity for a studio with development and publishing roles, while preserving separate scope records. Engine-owner, platform-maker, outsourcing, rights-holder and distribution assertions may be retained as typed pending facts; the current game-only edge endpoints do not authorize new predicates or ownership inferences.
- The useful paths are named people across games/movie/music; studios across scoped releases; titles across typed series/platform/engine contexts; and **actual** award recipients. Do not materialize inferred acquaintance edges or broaden discovery from those paths.

### Reuse each fetched source across allowed facts

Fetch an exact source object once per retained revision and extract all allowed claims for the already admitted game. The same [Xbox report](https://news.xbox.com/en-us/2024/05/16/hellblade-2-performance-capture-next-level-combat-design/) identifies Benoit Macon as combat director and Melina Juergens as Senua’s performer alongside engine-use evidence. These can feed separately resolved `WORKED_ON` claims from the same snapshot. The article author and studio job titles alone do not become game credits. Extra claims still compete within the fixed endpoint/relation manifest; they never admit more games or full person waterfalls.

## Queue and source capability lock

Persist an adapter capability record with source, version, enabled endpoint/page kinds, accepted subject types, field/edge allowlists, entitlement, retention/attribution policy, pagination/response limits and coverage scope. Pin that capability revision in the root manifest. Disabled or unverified capabilities yield a coverage reason without provider spend; do not silently fall back to an unrestricted scraper.

Every provider request and support lookup stays within the **same** 20-game / 60-new-leaf / 100-job / 100-network-attempt root limits. A support node is an identity-only leaf. Never enumerate games from a series/platform/engine, releases from another game, award archives or company catalogs from a descendant. A larger provider response is truncated deterministically; it cannot enlarge admission. Game cards and incident relationships remain hidden until game-owned publication succeeds; game-scoped release/award nodes and their incident edges inherit that readiness. All game-domain edges remain excluded from scoring.

The award seed's 200-entry parser ceiling is a defensive response bound, not permission to admit 200 candidates. The shared discovery limit of **50 candidates per page across at most 3 pages**, at most 20 admitted games and all lower remaining root limits still applies. Exact-target award lookups observe other entries without admitting them.

All adapters use the [same Universe failure/stage/attempt facilities](/guides/open-work/video-game-waterfall#shared-universe-error-logging-required). Capability/coverage reasons are not new `error_code` values. A 403, loading shell, partial page or wrong-year award body cannot masquerade as an empty successful result.

## Implementation acceptance

1. Replay all six typed examples with stable UUIDs; cross-source aliases and changed names do not allocate duplicates. A movie-created game keeps its UUID and receives game-owned publication only.
2. A generic franchise/group, Steam soundtrack app and middleware-only item produce zero wrongly typed game support nodes.
3. Release-date correction preserves its release UUID; unqualified dates and ambiguous remaster/platform scope remain facts pending resolution. Unknown territory is not worldwide and cannot join every region.
4. A nominated person becoming the winner updates the same award entry, replacing the current nominee projection while retaining history; same-game co-nominees remain separate.
5. Disabled IGDB/Moby capabilities spend nothing and do not claim complete coverage; supported free/official sources can still produce evidenced support types.
6. Series/platform/engine/award/identity leaves enqueue zero new roots. Duplicate events, retries and relation repair preserve budgets and do not reveal unpublished games.
7. A storefront ID shared by two successive base games resolves to two identities, scoped by observation — neither merged into one game nor blocked as a strong-ID conflict. A single game holding two storefront IDs resolves to one identity. Neither case allocates a duplicate or reveals an unpublished game.
