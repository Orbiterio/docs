## Decision by node type

| Type | Decision for the first Go build | Sources that can support it | Main relationship |
| --- | --- | --- | --- |
| `Video_Game` | Required canonical game; reuse an IMDb-created UUID and keep it hidden until game publication | Wikidata, reused IMDb identity, exact official game/store evidence; enabled catalog providers | Credits, companies, adaptations and game context |
| `Game_Series` | Include when a **video-game series** and membership are evidenced; accepted developer evidence must create/reuse Company endpoints and series development edges | Typed Wikidata P179/P178; verified official series/member development and membership; enabled catalog series mapping | `IN_GAME_SERIES`; series → `DEVELOPED_BY` → Company |
| `Game_Platform` | Include exact supported platform identities with a short description and optional verified official website; no standalone card | Typed Wikidata P400/target metadata/P856; exact official product/support pages; enabled catalog platform records | `AVAILABLE_ON` after release evidence |
| `Game_Engine` | Include when exact game-engine use is evidenced; short engine-family description required for public readiness; no standalone card | Typed Wikidata P408, official developer/engine-maker evidence; enabled engine mapping | `USES_ENGINE` with version/use scope |
| `Game_Release` | Include **conditionally**, when a coherent platform release needs its own identity; short description required for public readiness; retain sparse dates as facts | Qualified Wikidata dates; exact official releases; enabled catalog release records | `RELEASE_OF`, scoped `AVAILABLE_ON` |
| `Game_Award` | Locked scoped result with short description and card; reuses the associated game's published artwork; [node fields](/guides/ontology/nodes#game-award-properties) and [HAS_AWARD](/guides/ontology/edges#game-has-award) | The Game Awards, qualified Wikidata, other explicitly supported award-body pages | `HAS_AWARD`; named `WON_AWARD` / `NOMINATED_FOR` |

Support coverage is optional per game. Missing engine, series, release or award facts do not prevent a valid game publishing. An attempted **required** stage failure still blocks publication under the declared manifest; an optional unsupported provider cannot be silently marked successful. All support identities compete within the existing leaf budgets.

## Game platform parameters

**Locked September 9:** retain exact `name`, registered `platform_code` / `platform_kind`, canonical identity/source fields, plus a required short `description` for public readiness and optional verified `official_website`. Description: one factual sentence **≤127 Unicode code points**. No standalone card, tagline, image field or platform media job. [Authoritative Node Types contract](/guides/ontology/nodes#game-platform-properties) · [PlayStation 4 and Windows JSON](/guides/open-work/video-game-waterfall#game-platform-parameters).

Reuse the admitted platform's exact-item metadata, P856 candidates or an enabled exact-platform record. Verify the official product/family/support URL against the node's identity, including its final redirect target. The official [PlayStation 4 page](https://www.playstation.com/en-us/ps4/) and [Windows hub](https://www.microsoft.com/en-us/windows) were checked for these examples on September 9; the Windows node represents the OS family, not a new Windows 11 node. Example descriptions are editorial summaries of supported facts, not completed model calls. Keep website/description source evidence separate from the primary Wikidata identity source.

If needed, reserve one additional exact-platform official page at most, then queue a short description from retained facts using GLM 5.3 FLASH at low effort, at most two model attempts. All work deduplicates per canonical platform/root and consumes the original root limits and shared movie/music logging. No crawling or catalog discovery. Missing website is optional coverage; if no useful description can be produced, retain a still-supported prior value or keep that support identity/link pending internally while the independently valid game can publish.

## Game release description

**Creation added September 9:** reuse suitable supported text or queue one typed `game_release` / `release_description` job from retained elected release facts. Preserve exact platform/territory/edition correlations, date precision and release status. No browsing, release enumeration, extra identity or standalone card. [Authoritative Node Types requirement](/guides/ontology/nodes#game-release-description) · [Build sequence](/guides/open-work/video-game-waterfall#game-release-description).

## Game series card parameters

**Description fallback:** reject blank, name-only and generic type-only copy. Reuse useful elected series facts and official text; if needed, fetch at most one additional verified official series/about page, then queue a bounded description job producing one neutral sentence ≤127 characters. At most two model attempts share the existing root limits. No series/member crawling or invented details; insufficient evidence remains coverage/pending work. [Full quality, source and failure rules](/guides/open-work/video-game-waterfall#series-description-fallback).

**Agreed September 9, 2026:** `Game_Series` uses its short `description` for card text, with **no tagline**. Include `developers`, `official_website` and `image_url` when available. Every accepted series image is normalized and stored as a **400 × 267 px WebP (3:2)**, with a white canvas, 32 px padding and centered containment. These parameter decisions are reflected in [Graphs → Node Types](/guides/ontology/nodes#game-type-contract-v1); Go workers and the final card layout remain to be implemented.

**Required developer output:** accepted exact-series developer evidence, or an elected admitted member's developer credit plus its verified membership, must create/reuse the canonical Company identity and replay `Game_Series → DEVELOPED_BY → Company`. Queue missing Company identities through the shared non-enriching identity seam; do not merely store names. Before creating the edge, require a suitable evidence-grounded description or queue GLM 5.3 FLASH at low effort to produce one under the original budget. `developers` is the sorted, identity-deduplicated name projection of eligible associations, including for a single studio. Preserve direct-series/member scope, source IDs and publication dependencies. Names alone cannot authorize edges; no series enumeration, publisher-role inference, company enrichment or blanket member-game credits. Unresolved or over-budget associations retain explicit pending/deferred evidence. [Authoritative properties, creation contract and Zelda → Nintendo JSON](/guides/ontology/edges#developed-by).

#### Series image selection and fallbacks

Resolve artwork for the **already admitted series identity** in this order. Move to the next source only when the earlier one is absent, rejected or exhausted within the original root's remaining budget.

| Priority | Source and exact lookup | Acceptance / fallback rule |
| --- | --- | --- |
| 1 | The exact series Wikidata item: non-deprecated P154 logo; P18 only when explicitly suitable as series artwork | Prefer a current, preferred-rank logo compatible with the fixed white canvas. Resolve the named Commons file and retain its metadata/rights. For SVG, use a verified provider-supplied PNG rendition. A missing file, unsupported rendition or rejected asset advances to the next candidate |
| 2 | A verified official publisher/developer **series or brand hub**, from an existing verified URL or an approved exact-series resolver | Extract an explicitly series-associated logo/artwork from a supported page template or linked official media asset. Verify the series subject and asset association. Elden Ring's official Universe hub is the worked example. An individual game's cover or website is not automatically series evidence |
| 3 | An enabled catalog provider's exact, crosswalked series record, when that provider exposes approved series artwork | Require an explicit series-to-asset association and an enabled media policy. Do not substitute generic franchises, store collections, screenshots or the first member game's cover. Skip this source when unsupported or disabled |
| Exhausted | No acceptable series image within the finite plan | Omit `image_url`; record the coverage result or actual failure. Render the common 3:2 UI placeholder. Do not upload a placeholder as sourced artwork, block series identity/membership, or start another discovery pass |

Do not use IMDb artwork, search-result thumbnails, fan-made logos or generated branding. A game logo can qualify only when an independently verified official series source identifies that asset for the series, as in the Elden Ring hub. Human source research in this QA document is not permission for an unbounded production web crawl.

Admit **at most three ranked image candidates and one selected output per series**. Metadata resolution, candidate downloads and retries consume the existing root's network, byte and job budgets. The finite media job may retry a transient failure under the shared policy; terminal rejection can advance to the next already admitted candidate. Budget exhaustion stops the attempt. Shared Universe logging must retain root/run/stage/attempt, source and rejection/failure evidence; missing coverage must not be reported as a successful upload. This leaf job cannot enumerate series members or enqueue another waterfall.

#### Series image output and shared storage

**Pixel rounding:** keep a 3:2 UI frame and store a 400 px-wide raster with height `round(400 × 2 / 3) = 267`. Output validation requires exactly 400 × 267; the one-third-pixel rounding is expected.

**Stored output:** exactly **400 × 267 pixels**, WebP, white (`#FFFFFF`) opaque canvas, **32 px padding on each side** and centered proportional containment within the remaining 336 × 203 area. Generate the canvas deterministically from the accepted real source artwork; do not generate or redraw a logo. Prefer source renditions large enough for the fitted logo and record observed dimensions; enlarging a small source does not create additional detail. Composite source transparency onto the white canvas. Do not crop, distort or recolor the artwork. The card displays the complete asset in its 3:2 frame without adding another layer of padding; 400 px is the stored width, not a required UI width.

**Implementation requirement:** add a versioned `series-3x2-v1` normalization option inside the existing shared Go image package. The current `ConvertPoster` path preserves the input aspect ratio and caps width at 500 px, so it does **not** yet implement this 400 × 267 contract. The series option needs its own target canvas dimensions while preserving the current avatar and movie-poster behavior. Use the existing shared decoder/encoder, configured GCS media bucket, deterministic `ObjectKey` helper, upload client, media ledger, retries, shared failure/stage logging and CDN/media renderer. This is a shared transform extension, not a separate uploader or service.

Scope the deterministic object-key namespace to the canonical series identity and normalization version; retain the exact source-URL hash through the shared key helper. This prevents an older original-aspect asset from satisfying the new normalization receipt. Retain source page, exact fetched rendition, rights/attribution, source dimensions, transform version/parameters, output dimensions/MIME, storage key and processing receipt in the shared media/evidence records. Set `image_url` only to the serving URL returned for a successfully uploaded **400 × 267 WebP**. A rejected or missing asset cannot produce a ready receipt. Replays reuse the same successful variant; changing source or transform version requires a new matching receipt.

The current shared decoder supports PNG/JPEG/GIF/WebP, not SVG. Use a verified provider-supplied PNG rendition for SVG logos; do not pass the SVG original to the shared decoder or build a private conversion path. Fetch and decode must still pass during ingestion; a successful source HEAD check alone is not an ingestion receipt. Series image processing stays within its already admitted root and cannot trigger another waterfall.

**Consistency rule:** every successfully ingested `Game_Series` asset has the same 3:2 dimensions, background and padding **in the stored file**. The UI displays the complete normalized asset and uses the same 3:2 frame for the missing-image placeholder. Individual `Video_Game` cards keep their separately locked 2:3 portrait contract. This decision does not add a tagline or change storage services.

### Adapter mapping details

**Wikidata:** type-check the target of [P179](https://www.wikidata.org/wiki/Property:P179), [P400](https://www.wikidata.org/wiki/Property:P400) and [P408](https://www.wikidata.org/wiki/Property:P408). These properties span more than our game classes. P179 is not automatic franchise membership; P408 may describe another software-engine kind. [P577](https://www.wikidata.org/wiki/Property:P577) dates need their own platform/territory qualifiers; never multiply independent arrays into release combinations. P166/P1411 requires category, ceremony/year and recipient scope before `Game_Award` projection. P144/P4969 retains the existing normalized adaptation contract. A bounded inverse P406 lookup can support the music-to-game handoff after soundtrack and game identity resolve. Label resolution must not read `labels.en` alone: Valve Corporation ([Q193559](https://www.wikidata.org/wiki/Q193559)) and Linux ([Q388](https://www.wikidata.org/wiki/Q388)) carry 20 and 57 labels respectively but no English one, so a naive read drops developer and platform names silently rather than erroring. Fall back to `sitelinks.enwiki.title`, then to another available label with its language recorded; an unresolved label is a coverage reason, never an empty name.

**IGDB schema binding:** use `game_type`, `game_status`, `collections`; the older game `category`, `status`, `collection` fields are deprecated. Read typed collection membership, not every grouping. For `release_dates`, preserve `game`, `platform`, `release_region`, `date_format`, `date`, `status`; old `region`/`category` are deprecated. An ID there aliases a date assertion, not automatically a canonical release. Company flags distinguish `developer`, `publisher`, `porting`, `supporting`; inspect the role instead of assuming every involved company is the developer. `game_engines` supplies an engine candidate; a version needs its own evidence. The API documentation is reviewed; no authenticated response/entitlement is claimed. [Schema](https://api-docs.igdb.com/)

**MobyGames binding remains conditional:** verify fields and permitted retention for the enabled tier with a retained response before mapping. Group membership may describe an engine, theme or editorial grouping; classify it before accepting a series or engine relation. No generic group-to-series cast, assumed credits endpoint or fabricated provider release ID. A Wikidata Moby ID is still useful as an alias without buying access.

## Frozen boundaries and maximum relationship value

- Use the six game types plus **existing** Person, Company, movie/theatre and music identities. Genres, themes, modes, ratings and artwork are scoped properties/media records; no new genre, character, award-category or storefront hubs in this build.
- `Game_Series` means a typed video-game series. Generic franchises, fictional universes, marketing collections and bundles stay source context until a separate compatible contract exists. Their labels alone cannot create `IN_GAME_SERIES` or `BASED_ON`.
- Remakes/remasters and substantive separately identified expansions may be distinct `Video_Game` identities. A port, SKU, cosmetic DLC or soundtrack app cannot automatically become another game. `EDITION_OF` and `EXPANSION_OF` need the exact typed relation; sequel/similarity links cannot stand in for either.
- Reuse company identity for a studio with development and publishing roles, while preserving separate scope records. Elected series developer evidence requires Company identity creation/reuse and the locked series `DEVELOPED_BY` variant. Engine-owner, platform-maker, outsourcing, rights-holder and distribution assertions remain typed pending facts unless independently supported by an approved endpoint contract.
- The useful paths are named people across games/movie/music; studios across scoped releases; titles across typed series/platform/engine contexts; and **actual** award recipients. Do not materialize inferred acquaintance edges or broaden discovery from those paths.

### Reuse each fetched source across allowed facts

Fetch an exact source object once per retained revision and extract all allowed claims for the already admitted game. The same [Xbox report](https://news.xbox.com/en-us/2024/05/16/hellblade-2-performance-capture-next-level-combat-design/) identifies Benoit Macon as combat director and Melina Juergens as Senua’s performer alongside engine-use evidence. These can feed separately resolved `WORKED_ON` claims from the same snapshot. The article author and studio job titles alone do not become game credits. Extra claims still compete within the fixed endpoint/relation manifest; they never admit more games or full person waterfalls.

## Queue and source capability lock

Persist an adapter capability record with source, version, enabled endpoint/page kinds, accepted subject types, field/edge allowlists, entitlement, retention/attribution policy, pagination/response limits and coverage scope. Pin that capability revision in the root manifest. Disabled or unverified capabilities yield a coverage reason without provider spend; do not silently fall back to an unrestricted scraper.

Every provider request and support lookup stays within the **same** 20-game / 60-new-leaf / 100-job / 100-network-attempt root limits. Support writers receive no discovery or enqueue capability. A predeclared `series_evidence` stage may extract direct developer claims from the one admitted series record; only the original coordinator can reserve the resulting Company endpoints and freeze their identity/replay jobs. This fixed branch cannot enumerate games from a series/platform/engine, releases from another game, award archives or company catalogs. A larger provider response is truncated deterministically; it cannot enlarge admission. Game cards and incident relationships remain hidden until game-owned publication succeeds; game-scoped release/award nodes inherit that readiness, and member-supported series developer projections filter unpublished member support. All game-domain edges remain excluded from scoring.

The award seed's 200-entry parser ceiling is a defensive response bound, not permission to admit 200 candidates. The shared discovery limit of **50 candidates per page across at most 3 pages**, at most 20 admitted games and all lower remaining root limits still applies. Exact-target award lookups observe other entries without admitting them.

All adapters use the [same Universe failure/stage/attempt facilities](/guides/open-work/video-game-waterfall#shared-universe-error-logging-required). Capability/coverage reasons are not new `error_code` values. A 403, loading shell, partial page or wrong-year award body cannot masquerade as an empty successful result.

## Implementation acceptance

1. Replay all six typed examples with stable UUIDs; cross-source aliases and changed names do not allocate duplicates. A movie-created game keeps its UUID and receives game-owned publication only.
2. A generic franchise/group, Steam soundtrack app and middleware-only item produce zero wrongly typed game support nodes.
3. Release-date correction preserves its release UUID; unqualified dates and ambiguous remaster/platform scope remain facts pending resolution. Unknown territory is not worldwide and cannot join every region.
4. A nominated person becoming the winner updates the same award entry, replacing the current nominee projection while retaining history; same-game co-nominees remain separate.
5. Disabled IGDB/Moby capabilities spend nothing and do not claim complete coverage; supported free/official sources can still produce evidenced support types.
6. Series/platform/engine/award/identity leaves enqueue zero new roots. Duplicate events, retries and relation repair preserve budgets and do not reveal unpublished games.
7. A storefront ID shared by two successive base games resolves to two identities, scoped by observation — neither merged into one game nor blocked as a strong-ID conflict. A single game holding two storefront IDs resolves to one identity. Neither case allocates a duplicate or reveals an unpublished game.
8. With six elected Counter-Strike series developer claims and available budgets, resolve six canonical Company endpoints and write six series `DEVELOPED_BY` edges, creating only missing companies. Every edge must have a validated non-empty description; absent suitable text, queue GLM 5.3 FLASH at low effort before the write. Description failure leaves that relation pending, without a blank completed edge or additional budget. Replay creates zero duplicates and zero company waterfall/catalog jobs; it does not copy six credits onto Counter-Strike 2. Name-only, publisher-only, wrong-member and conflicting-identity candidates produce no unsupported edge.
9. Budget exhaustion retains pending Company/edge work without a success receipt. Last-support withdrawal retires the series edge and projected name, not the Company; partial snapshots preserve surviving support. Member-supported public edges and `developers` entries cannot reveal an unpublished game's credits.
