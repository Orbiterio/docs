<Warning>
  **Smoke-test finding, 2026-09-06: the DM API cannot see X's new encrypted chats.** In late 2025 X replaced Direct Messages with **Chat**, which is end-to-end encrypted for new conversations. `GET /2/dm_events` returns only legacy, unencrypted DMs. A conversation that starts today, or an old one a user "upgrades", is invisible to the API. X staff on the developer forum say API support for encrypted Chat is being explored; an XChat webhook exists but delivers encrypted payloads and the decryption SDK (`chat-xdk`) was unreleased as of June 2026. Verified live both ways: @Mark_L_Pederson's three legacy conversations from the last 30 days came back and were logged, while the new DM sent to @Orbiter_io during the test never appeared (HTTP 200, `result_count` 0). **Decide whether to build against a shrinking legacy set or wait for X before Charles writes a line of Go.** Details under [Smoke test](#smoke-test-with-marks-account).
</Warning>

## What this delivers

When a user connects X to Orbiter **with DM consent**, we pull every direct-message event X will give us (the last 30 days, across 1-to-1 and group conversations) and log one row per event in a new `x_dm_activity` table, then keep it current on a schedule. Each row carries what the X API returns for the event (text, conversation, sender, participants, attachments) plus the Orbiter fields that make it behave like `email_activity`: `user_id`, `my_person_id`, `activity_type_id`, `card_descriptor`, `activity_timestamp`, and an explicit `direction`.

Downstream, DM rows are just another activity source: the interaction-log job counts them next to email and calendar, and the same resolver CRON that turns `x_follower` rows into people and KNOWS edges can resolve DM counterparties. Nothing here touches the graph.

<Warning>
  **X only serves the last 30 days of DM events.** There is no historical backfill through the API. A user who connects today gets their DMs from the last 30 days and nothing older, and a sync that lapses for more than 30 days loses the gap permanently. The Nylas email import has no such limit, so this is the biggest behavioural difference from email.
</Warning>

    - Anyone who connected before `dm.read` was added must consent again. `x_oauth_token.scope` records what was granted, so the sync can skip rows without `dm.read` and the app can prompt for re-consent.
  </Step>
  <Step title="Exchange the code and store the token">
    Unchanged from the parent page: the callback calls `twitter-api-oauth-exchange` (13390), which exchanges the code at `/2/oauth2/token`, looks the account up at `/2/users/me`, and upserts `x_oauth_token` keyed by `x_user_id`.   </Step>
  <Step title="First import">
    On a successful exchange, queue the proposed `twitter-api-sync-dms` for the user. It pages `GET /2/dm_events` newest-first at 100 events per request and upserts one `x_dm_activity` row per event until X returns no `next_token` or the 15-request window is spent. A run row records `next_token` so a large inbox resumes on the next window.
  </Step>
  <Step title="Keep it current">
    A scheduled task re-runs the sync per connected account. Because X has no `since_id` on the DM lookup, each poll re-reads the newest events and **stops at the first event id already logged**. That bounds both the requests and the pay-per-use cost to genuinely new events plus one page of overlap.   </Step>
  <Step title="Resolve counterparties later">
    <Warning>
      **The sync does not resolve, enrich, or write graph data.** It writes `x_dm_activity` rows with the sender's X id and handle and leaves `my_person_id` at 0. The same scheduled CRON described in [Resolving Followers to Edges in User Graph](/guides/open-work/x-followers-capture#resolving-followers-to-edges-in-user-graph) picks up unresolved DM counterparties by `sender_profile_url`, resolves them, and back-fills `my_person_id`. Only then do the KNOWS pairs get fanned out, the way `known/ingest/_fanout_email_pairs` (12781) does for email.
    </Warning>
  </Step>
</Steps>

## How email does it today

The DM design mirrors the email path, so here is the chain it copies, with what each step becomes for DMs.

| Email today | Where | X DM equivalent |
| --- | --- | --- |
| Nylas `message.created` webhook fires per message | `mvp/nylas-webhook/message-created` (180) | No webhook in phase 1. A scheduled poll of `GET /2/dm_events`. X does sell a `dm.received` webhook event; see cost notes. |
| Dedupe on `(grant_id, message_id)` before logging | `mvp/activity/message-created-parse` (1913) | Dedupe on `(user_id, dm_event_id)`, enforced by a unique index |
| Direction: `from.email == grant.email_account` means sent | `parse-from` (2126) / `parse-to` | `sender_id == connected x_user_id` means sent |
| One `email_activity` row **per participant** with `activity_type_id` 1 to 4 (`email_from`, `email_to`, `email_cc`, `email_bcc`) | `mvp/activity/log-participant-activity` (12773) | One row **per event** with two new `activity_type` rows, `x_dm_from` and `x_dm_to`. Group DMs keep `participant_ids` on the row instead of fanning out. |
| Counterparty resolved at write time by email address into `my_person_id` | `mvp/identity/check-identity-email-to` inside 12773 | No email to key on. Store `sender_x_user_id` and `sender_profile_url`; `my_person_id` is filled later by the resolver CRON. |
| `card_descriptor` text like "from Emery Wells" | 12773 | "DM from @handle", "DM to @handle", "Group DM (4)" |
| `data_source_id` 14 (NylasEmail), master person source 47 / 48 | `data_source` (161) | New `data_source` row "X DM Sync". Rows 7 (Twitter) and 41 (Twitter Resolve) exist but mean profile enrichment, not activity. |
| KNOWS fan-out per sender/recipient pair | `known/ingest/_fanout_email_pairs` (12781) | Same call, made by the resolver CRON once `my_person_id` is known, never by the sync |
| Interaction-log counts read `email_activity` by `my_person_id` and `direction` | [Contacts Interaction Log](/guides/open-work/contacts-interaction-log) | Add `x_dm_activity` as a fourth activity source; `direction` is a first-class column from day one |

`email_activity` (597) columns for reference: `user_id`, `my_person_id`, `activity_type_id`, `card_descriptor`, `activity_timestamp`, `subject`, `grant_id`, `thread_id`, `message_id`, `snippet`, `unread`, `interlocutor_email`, `participant_count`, `data_source_id`, `temp_email_body`, `clean_message`. The DM table keeps every one that has an X analogue and drops `subject`, `unread` (X does not expose read state), and `interlocutor_email`.

## X API: the DM lookup

Verified against docs.x.com on 2026-09-06.

| | |
| --- | --- |
| Endpoint | `GET https://api.x.com/2/dm_events` (all conversations the user is in). Also `GET /2/dm_conversations/with/:participant_id/dm_events` for one 1-to-1 thread and `GET /2/dm_conversations/:dm_conversation_id/dm_events` for one group. |
| Auth | OAuth 2.0 user context (PKCE). App-only bearer is rejected. |
| Scopes | `dm.read`, `tweet.read`, `users.read`; add `offline.access` for the refresh token |
| Window | Events from up to **30 days** ago. Newest first. No `since_id` or `start_time`. |
| Paging | `max_results` 1 to 100 (default 100); `pagination_token` from `meta.next_token` |
| `event_types` | `MessageCreate`, `ParticipantsJoin`, `ParticipantsLeave`; omit the parameter to get all three |
| `dm_event.fields` | `id`, `text`, `event_type`, `created_at`, `dm_conversation_id`, `sender_id`, `participant_ids`, `referenced_tweets`, `attachments` |
| `expansions` | `sender_id`, `participant_ids` (user objects in `includes.users`), `attachments.media_keys` (`includes.media`), `referenced_tweets.id` (`includes.tweets`) |
| Rate limit | **15 requests per 15 minutes per user** on every DM lookup endpoint. At 100 events per request that is 1,500 events per window per user. Confirmed in the response headers: `x-rate-limit-limit: 15`. |
| Encrypted Chat | **Not returned.** Only legacy unencrypted DMs come back. See the warning at the top and the smoke-test notes. |
| Field names | The current reference lists `referenced_posts` and `entities` in `dm_event.fields`; the harness still sends `referenced_tweets` and X accepts it with HTTP 200. Use `referenced_posts` in the Go build. |

**Example request (curl)**

```bash
curl "https://api.x.com/2/dm_events?max_results=100&dm_event.fields=id,text,event_type,created_at,dm_conversation_id,sender_id,participant_ids,referenced_tweets,attachments&expansions=sender_id,participant_ids,referenced_tweets.id,attachments.media_keys&user.fields=id,username,name,profile_image_url,verified,protected&media.fields=media_key,type,url,preview_image_url&tweet.fields=id,text,author_id,created_at" \
  -H "Authorization: Bearer $X_USER_ACCESS_TOKEN"
```

Subsequent pages repeat the request with `pagination_token` set to the previous `meta.next_token`, until a response comes back with no `meta.next_token`.

Three shape facts the capture confirmed:

1. **1-to-1 conversation ids are the two user ids joined by a hyphen** (`16826747-1250774754799149056`). The sync derives the counterparty by removing the connected account's id and the hyphen, and that produced the right `counterpart_x_user_id` on all three rows. Group ids are a single snowflake; `participant_ids` is only needed for groups.
2. **Optional fields are omitted, not nulled.** `participant_ids`, `attachments` and `referenced_tweets` are absent from the event object when empty, even though they were requested in `dm_event.fields`. Read them with a default.
3. **`includes.users` covers senders only.** For a message the connected account *sent*, the recipient is not in `includes.users` (the third event above: sender is Mark, the counterpart `18799825` has no user object), so the sync wrote `card_descriptor = "DM to 18799825"`. The Go build needs a `GET /2/users/:id` lookup, or a cache keyed by X id, to fill the handle for sent messages. Received messages carry the sender's user object.

## Reference table: x_dm_activity (789)

Built in Xano as the reference schema Charles mirrors in AlloyDB (DDL in the [build plan](#suggested-build-plan-for-charles)). Empty until the smoke test writes to it. One row per DM event per Orbiter user. Two users in the same group conversation each get their own row for the same event, which is why the unique key includes `user_id`.

<Warning>
  X ids (users, events, conversations) are 64-bit snowflakes and exceed the safe integer range. Store every X id as **text**, never int, the same rule as `x_follower`.
</Warning>

| Column | Type | Source | Notes |
| --- | --- | --- | --- |
| <code style={{color: "#16a34a"}}>id</code> | int | GCP | Primary key |
| <code style={{color: "#16a34a"}}>created_at</code> | timestamp | GCP | Row created |
| <code style={{color: "#16a34a"}}>updated_at</code> | timestamp | GCP | Row last written |
| <code style={{color: "#16a34a"}}>user_id</code> | int | Orbiter | The Orbiter user whose DM this is. Same meaning as `email_activity.user_id`. Required. |

| <code style={{color: "#16a34a"}}>activity_type_id</code> | int | Orbiter | New `activity_type` rows `x_dm_from` (received) and `x_dm_to` (sent). Ids assigned when the rows are inserted; 11 and 14 are gaps in the table and must not be reused. |

Indexes, created on 789:

- unique on `(user_id, dm_event_id)`, which makes the upsert idempotent and is the stop condition for incremental polls
- btree on `(user_id, activity_timestamp)` for the interaction-log reader
- btree on `dm_conversation_id` for thread views
- btree on `my_person_id` for the resolver sweep of unresolved rows

## Reference function: twitter-api-sync-dms (13402)

Built in Xano as the reference implementation Charles ports to Go. It is a leaf function that reads the token row in its own stack and makes no nested `function.run`, so the CLI runner can execute it end to end. It writes 789 and 790 and nothing else. Source is in the [accordion below](#reference-source-twitter-api-sync-dms-13402).

**Inputs**

| Input | Type | Notes |
| --- | --- | --- |
| `user_id` | int | Required. The Orbiter user the rows belong to. Mark is 12. |
| `x_user_id` | text | Optional. Picks a specific user-context token row; defaults to the newest. |
| `mode` | text | `initial` pages until X runs out of the 30-day window. `incremental` (default) stops after the first page that contained an already-logged event. |
| `sync_run_id` | int | Optional. Resume a paused run from its stored `next_token`. |
| `max_pages` | int | Default 15, the per-window budget. |
| `max_results` | int | Default 100. |
| `activity_type_from`, `activity_type_to` | int | Default 0 until the `x_dm_from` / `x_dm_to` rows exist in `activity_type`. |
| `data_source_id` | int | Default 0 until the "X DM Sync" row exists in `data_source`. |

**What it does**

1. Loads the `x_oauth_token` row (`grant_type = user`). Throws `XScopeError` when `scope` lacks `dm.read`, and `XTokenError` when the row is missing or expires within 5 minutes (run `twitter-api-token` first; there is no nested refresh by design).
2. Confirms the token at `/2/users/me` and takes the account id and handle from it.
3. Creates an `x_dm_sync_run` row with `status = running`, or resumes the one in `sync_run_id`.
4. Pages `GET /2/dm_events` with the field and expansion lists above, accumulating `includes.users` for handle lookups. The first event of a fresh run becomes `newest_event_id`.
5. Per event: `direction` is `sent` when `sender_id` is the connected account and the type is `MessageCreate`; a hyphen in `dm_conversation_id` marks a 1-to-1 thread, and the counterpart is the id left after removing the account id and the hyphen; `participant_count` is 2 for 1-to-1, else the length of `participant_ids` when present; `card_descriptor` is "DM from @handle", "DM to @handle" or "Group DM (n)"; `snippet` is the first 160 characters. Then a query on `(user_id, dm_event_id)` decides between `db.add` and `db.edit`. An edit in `incremental` mode sets the stop flag.
6. After every page it checkpoints counts, `next_token` and `newest_event_id` on the run row, so a crash loses at most one page.
7. On HTTP 429 it stops and leaves the run `paused_rate_limit` with `next_token` for resume. Any other non-200 marks the run `failed` with the body in `error_message` and throws. A clean finish sets `complete`.

**What is deliberately missing.** No schedule, no `log_crash` write (the enum has no X phase yet), no resolver call, no graph write, no `activity_type` or `data_source` rows. Those are Charles's to add in Go per the build plan; the Xano function stays a reference and a smoke-test tool.

## Rate limits, cost, and cadence

{/* TODO(Mark): confirm the Orbiter app's plan and the DM read price in the developer portal before choosing the cadence. */}

- **Rate limit.** 15 requests per 15 minutes per user on `GET /2/dm_events`. A first import of a heavy inbox (1,500 events per window) finishes in one window; the resume task covers anything larger.
- **Pricing is pay-per-use, not tiered.** As of 2026-09-06, docs.x.com describes a single pay-per-use plan with no subscriptions or tiers. DM event **reads bill at $0.010 per resource**, DM creates at $0.015 per request, and the `dm.received` webhook event at $0.010 per event delivered. The older Basic and Pro tiers referenced on the parent page no longer appear there.
- **Per-resource pricing punishes naive polling.** Because there is no `since_id`, every poll re-reads the newest page and pays for every event on it, new or not. Hourly polls at 100 events per page could cost up to $1.00 per poll per user. Keep incremental polls at `max_results = 20`, stop at the first known event, and start with a daily cadence (worst case about $6 per user per month). Tune from the run rows.
- **The webhook is the email-shaped answer.** A `dm.received` webhook only bills for new events and removes the 30-day gap risk. It is not scoped here because it needs an Account Activity subscription per user and a public receiver. Revisit once the poll has run for a few weeks.
- Rate limits are per connected user, so many users syncing at once do not contend with each other. Cap concurrent runs on the resume task anyway.

## Suggested build plan for Charles

The short answer to "a cron every 15 minutes that updates all users who have authorized DMs": **tick every 15 minutes, but sync each account only when it is due.** The X rate limit would allow a 15-minute sweep, but X bills every event a request returns, and there is no `since_id`, so each poll costs at least one event. A sweep of every account every 15 minutes is a floor of about $29 per connected user per month before a single new message. Sync on connect, then at a per-account cadence that starts at every 4 hours, and let the 15-minute tick do dispatch and retries only.

| Poll cadence per account | Polls per month | Floor cost per user per month at $0.010 per event | Verdict |
| --- | --- | --- | --- |
| Every 15 minutes | 2,880 | $28.80 | No. Real-time DMs are not a product requirement, and the webhook does this for $0.010 per new event. |
| Hourly | 720 | $7.20 | Only for accounts the product flags as active. |
| Every 4 hours | 180 | $1.80 | Default. |
| Daily | 30 | $0.30 | Fallback for dormant accounts, and the reconciliation cadence once the webhook exists. |

New events cost $0.010 each on top of the floor at any cadence, and the first import of an account costs its 30-day DM count times $0.010. TODO(Mark): confirm the per-event price on the app's plan in the developer portal before Charles hard-codes the defaults.

  </Step>
  <Step title="dm-sync-worker: Cloud Run service behind the queue">

  </Step>
  <Step title="Connect-time initial run">
    The OAuth callback stores the token and enqueues one `initial` task immediately, not on the next tick, so the user sees DMs within a minute. An `initial` run that pauses on 429 resumes on the next tick with the same run id.
  </Step>
  <Step title="Resolver hand-off">

````xanoscript
// v1.0 (2026-09-06): smoke-test harness for X (Twitter) API v2 GET /2/dm_events, the endpoint behind the proposed x_dm_activity logger (docs: Open Work > X Followers Capture > Log X DMs). Reads the user-context token in this stack only and makes no nested function.run call, so it can be executed from the CLI/MCP runner (which cannot resolve nested calls, see docs trap 21): if the x_oauth_token row expires within 5 minutes it throws XTokenError asking for twitter-api-token (token_type user) to be run first, then the row is re-read here and the Authorization header is built here. Requires the row's scope to include dm.read (with tweet.read and users.read); throws XScopeError otherwise so a missing consent reads as a clear message instead of an X 403. Confirms the token via /2/users/me, then pages GET /2/dm_events (newest first, up to 100 events per page, only the last 30 days are available) with dm_event.fields plus expansions for sender and participant users, media, and referenced posts. On HTTP 429 it stops and returns what it has with rate_limited = true. Writes nothing.
function "twitter-api-dm-events" {
  input {
    // Optional numeric X user id to pick a specific user-context row in x_oauth_token. Defaults to the most recently updated user row.
    text x_user_id? filters=trim
  
    // How many pages (up to 100 events each) to fetch in this call. The endpoint allows 15 requests per 15 minutes per user.
    int max_pages?=1 filters=min:1|max:15
  
    // Events per page, 1 to 100.
    int max_results?=100 filters=min:1|max:100
  
    // next_token from a previous call, to continue where it left off.
    text pagination_token? filters=trim
  
    // Optional event type filter (MessageCreate, ParticipantsJoin or ParticipantsLeave). Leave empty to return all three.
    text event_types? filters=trim
  }

  stack {
    // Read the token in this stack: a specific account, or the newest user-context row
    conditional {
      if ($input.x_user_id != "") {
        db.query x_oauth_token {
          where = ($db.x_oauth_token.grant_type == "user") && ($db.x_oauth_token.x_user_id == $input.x_user_id)
          return = {type: "single"}
        } as $token_row
      }
    
      else {
        db.query x_oauth_token {
          where = $db.x_oauth_token.grant_type == "user"
          sort = {updated_at: "desc"}
          return = {type: "single"}
        } as $token_row
      }
    }
  
    conditional {
      if ($token_row == null) {
        throw {
          name = "XTokenError"
          value = "No user-context X token in x_oauth_token. Authorize with scopes dm.read tweet.read users.read offline.access, then run twitter-api-oauth-exchange."
        }
      }
    }
  
    // No nested refresh here (runner limitation): refuse a token that expires within 5 minutes and say what to run
    var $refresh_threshold {
      value = now|add_secs_to_timestamp:300
    }
  
    var $token_stale {
      value = ($token_row.expires_at == null) || ($token_row.expires_at < $refresh_threshold)
    }
  
    conditional {
      if ($token_stale) {
        var $stale_err {
          value = "Stored X token for @" ~ $token_row.username ~ " expires at " ~ $token_row.expires_at ~ ". Run twitter-api-token with token_type=user to refresh it, then re-run this harness."
        }
      
        throw {
          name = "XTokenError"
          value = $stale_err
        }
      }
    }
  
    // The DM endpoints need dm.read on the grant; fail early with a readable message
    var $scope {
      value = $token_row.scope
    }
  
    var $has_dm_scope {
      value = $scope|contains:"dm.read"
    }
  
    conditional {
      if ($has_dm_scope == false) {
        var $scope_err {
          value = "Stored X token for @" ~ $token_row.username ~ " was granted without dm.read (scope: '" ~ $scope ~ "'). Re-authorize with dm.read tweet.read users.read offline.access and re-run twitter-api-oauth-exchange."
        }
      
        throw {
          name = "XScopeError"
          value = $scope_err
        }
      }
    }
  
    var $token_source {
      value = "x_oauth_token:" ~ $token_row.id
    }
  
    var $auth_header {
      value = "Authorization: Bearer " ~ $token_row.access_token
    }
  
    // Confirm the token works and identify the connected account
    api.request {
      url = "https://api.x.com/2/users/me?user.fields=id,username,name,public_metrics"
      method = "GET"
      headers = []|push:$auth_header
      timeout = 30
    } as $me_call
  
    precondition ($me_call.response.result != false) {
      error = "X /2/users/me did not respond (timeout)"
    }
  
    var $me_status {
      value = $me_call.response.status
    }
  
    var $me_body {
      value = $me_call.response.result
    }
  
    conditional {
      if ($me_status != 200) {
        var $me_err {
          value = "X /2/users/me failed (HTTP " ~ $me_status ~ ") using " ~ $token_source ~ ": " ~ ($me_body|json_encode)
        }
      
        throw {
          name = "XApiError"
          value = $me_err
        }
      }
    }
  
    var $account {
      value = $me_body|get:"data":null
    }
  
    // Field lists for the DM lookup
    var $dm_fields {
      value = "id,text,event_type,created_at,dm_conversation_id,sender_id,participant_ids,referenced_tweets,attachments"
    }
  
    var $expansions {
      value = "sender_id,participant_ids,referenced_tweets.id,attachments.media_keys"
    }
  
    var $user_fields {
      value = "id,username,name,profile_image_url,verified,protected"
    }
  
    var $media_fields {
      value = "media_key,type,url,preview_image_url"
    }
  
    var $tweet_fields {
      value = "id,text,author_id,created_at"
    }

      value = "https://api.x.com/2/dm_events?max_results=" ~ $input.max_results ~ "&dm_event.fields=" ~ $dm_fields ~ "&expansions=" ~ $expansions ~ "&user.fields=" ~ $user_fields ~ "&media.fields=" ~ $media_fields ~ "&tweet.fields=" ~ $tweet_fields
    }
  
    // Only send event_types when asked; omitting it returns all three types
    conditional {
      if ($input.event_types != "") {
        var.update $base_url {
          value = $base_url ~ "&event_types=" ~ $input.event_types
        }
      }
    }

    var $events {
      value = []
    }
  
    var $users {
      value = []
    }
  
    var $media {
      value = []
    }
  
    var $tweets {
      value = []
    }
  
    var $next_token {
      value = $input.pagination_token
    }
  
    var $pages {
      value = 0
    }
  
    var $keep_going {
      value = true
    }
  
    var $rate_limited {
      value = false
    }
  
    var $last_status {
      value = 0
    }
  
    var $last_body {
      value = null
    }
  
    while ($keep_going) {
      each {
        var $page_url {
          value = $base_url
        }
      
        conditional {
          if ($next_token != "") {
            var.update $page_url {
              value = $base_url ~ "&pagination_token=" ~ $next_token
            }
          }
        }
      
        // Fetch one page of DM events
        api.request {
          url = $page_url
          method = "GET"
          headers = []|push:$auth_header
          timeout = 60
        } as $page_call
      
        precondition ($page_call.response.result != false) {
          error = "X dm_events request did not respond (timeout)"
        }
      
        var $page_status {
          value = $page_call.response.status
        }

          value = $page_call.response.result
        }

          value = $page_status
        }

          if ($page_status == 429) {

            var.update $rate_limited {
              value = true
            }
          
            var.update $last_body {
              value = $page_body
            }
          
            var.update $keep_going {
              value = false
            }
          }

            var $page_err {
              value = "X dm_events request failed (HTTP " ~ $page_status ~ ") after " ~ $pages ~ " page(s): " ~ ($page_body|json_encode)
            }
          
            throw {
              name = "XApiError"
              value = $page_err
            }
          }
        
          else {
            var $page_data {
              value = $page_body|get:"data":null
            }
          
            conditional {
              if ($page_data != null) {
                array.merge $events {
                  value = $page_data
                }
              }
            }
          
            var $inc_users {
              value = $page_body|get:"includes.users":null
            }
          
            conditional {
              if ($inc_users != null) {
                array.merge $users {
                  value = $inc_users
                }
              }
            }
          
            var $inc_media {
              value = $page_body|get:"includes.media":null
            }
          
            conditional {
              if ($inc_media != null) {
                array.merge $media {
                  value = $inc_media
                }
              }
            }
          
            var $inc_tweets {
              value = $page_body|get:"includes.tweets":null
            }
          
            conditional {
              if ($inc_tweets != null) {
                array.merge $tweets {
                  value = $inc_tweets
                }
              }
            }
          
            var.update $pages {
              value = $pages + 1
            }
          
            var.update $next_token {
              value = $page_body|get:"meta.next_token":""
            }
          
            conditional {
              if (($next_token == "") || ($pages >= $input.max_pages)) {
                var.update $keep_going {
                  value = false
                }
              }
            }
          }
        }
      }
    }
  
    var $events_returned {
      value = $events|count
    }
  }

  response = {
    account        : $account
    scope          : $scope
    token_source   : $token_source
    events_returned: $events_returned
````

## Open questions

0. **Build now, or wait for X?** With new conversations encrypted and invisible to `GET /2/dm_events`, a poll-based import captures only legacy threads that stay unencrypted, a set that shrinks every time a user upgrades a conversation. The alternatives are to wait for X's encrypted Chat API, or to scope the XChat webhook plus `chat-xdk` decryption once X ships it, which would also replace the polling design and its per-event floor cost. This decision comes before every other item on this page.
1. **Message bodies are third-party personal data.** Email stores `clean_message`, so parity says store `text`. DMs are more private than email in most users' minds. Decide whether to store full text, snippet only, or full text with a shorter retention than `x_follower` rows, and what happens on disconnect.
2. **`user_id` versus `entity_id`.** Tables 789 and 790 use `user_id` to match `email_activity`; the parent page adds `entity_id` to `x_oauth_token` for the same Orbiter user. Pick one name before the Go tables are created.
3. **Which activity types.** Two rows (`x_dm_from`, `x_dm_to`) mirror `email_from` / `email_to`. Group DMs could justify a third (`x_dm_group`) if the interaction-log job wants to discount them the way `direct_emails` discounts cc-only mail.
4. **Group DM participants.** X returns `participant_ids` only on join and leave events. To know a group's members at message time the sync must replay the group's join and leave events or call the conversation endpoint. Decide whether group membership matters for counts.
5. **Polling versus webhook.** Per-resource pricing makes the `dm.received` webhook the cheaper path once volume grows, but it needs a public receiver and per-user subscriptions. Phase 1 polls; confirm the crossover point from the run rows.
6. **Multiple X accounts per Orbiter user.** Same question as the parent page. If allowed, the sync runs once per token row and `x_user_id` on the activity row tells them apart.
7. **Protected and deleted counterparties.** A sender who protects their account after the fact still shows in `includes.users` with `protected = true`; a deleted account may drop out of `includes` entirely. Store `sender_username` at capture time so the row still reads.
