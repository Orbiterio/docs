## What this delivers

When a user connects X to Orbiter with DM consent, log one row per captured API event and connected account. The production key is `(user_id, x_user_id, source, dm_conversation_id, dm_event_id)`. Legacy message rows can carry text; Phase 1 chat rows carry metadata only. Keep capture separate from eligibility for contact counts: encrypted events whose meaning is unverified, membership changes, and unresolved groups must not silently become direct messages.

**Log first, attach known people, resolve the rest on a CRON.** For a direct conversation, look up the counterparty's X identity in the Universe and attach their `entity_id` when already known. Here, **`entity_id` is the person node's UUID**. A missing match or unavailable lookup never blocks capture: save the row with `entity_id = NULL`. The CRON resolves missing people, adds and enriches them in the Universe, adds them to the user's contacts, and backfills their event rows. It also adds already-known people who are missing from that user's contacts. See [Identity and contact resolution](#identity-and-contact-resolution).

Extend the interaction-log job with explicit X counters and timestamps keyed by `(user_id, entity_id)`. The existing in-app `chat_interactions` field belongs to Stream and must keep that meaning. Capture workers only look up existing identities; the CRON owns person and contact creation.

## Webhook identity and delivery

**Use webhooks as fetch notifications in Phase 1.** X's [real-time example](https://docs.x.com/xchat/real-time-events) exposes `event_uuid`, conversation, and sender, but does not expose the history event's `id` or `created_at`. Its signed message id is available after decryption. Therefore a delivery UUID cannot safely fill `dm_event_id`, and receipt time cannot stand in for message time. The proposed flow is:

```text
X webhook → verify + route → durable inbox → coalesce conversation fetch
                                             ↓
history API / initial import / reconciliation → canonical writer → activity
                                                                  ↓
                                                          resolver → rollups
```

- Register with `POST /2/webhooks` using the required app authorization; manage private Activity subscriptions using user authorization and an explicit `webhook_id`. Capture the actual create response and routing envelope before implementation; do not infer the owner from `sender_id`.
- Implement both CRC and POST signature verification. Compare the expected `x-twitter-webhooks-signature` in constant time over the original request bytes. CRC proves endpoint ownership; it does not authenticate deliveries. See X's [webhook quickstart](https://docs.x.com/x-api/webhooks/quickstart).
- Dedupe the durable inbox on `(user_id, x_user_id, event_uuid)`. A shared delivery can legitimately belong to more than one authorized account. Store allowlisted metadata, not `encoded_event`, tokens, signatures, or the full request body.
- Acknowledge within X's [10-second delivery requirement](https://docs.x.com/x-api/webhooks/introduction) after the inbox commit. A database failure gets a retryable response. A poller drains pending inbox rows, so a process crash between the commit and external queue publication cannot strand them.
- Coalesce into the conversation sync scope transactionally with marking the inbox item processed. Increment that scope's pending generation. A worker only clears the generation it acquired; notifications arriving mid-fetch remain due. An inbox item's `processed` status means “fetch scheduled,” not “activity captured.”
- An unmappable delivery produces a bounded, redacted diagnostic and leaves reconciliation responsible for discovery. Do not create an activity row with an invented account, id, or timestamp. Remove stale subscriptions on disconnect; report provisioning and removal failures separately from capture status.

This design adds a history read after a delivery. Measure the resulting latency and cost. A direct webhook writer is a later optimization only if a verified clear-text identifier can correlate with history without decrypting on the server.

## Pagination, completeness, and recovery

Maintain durable state per `(user_id, x_user_id, source, scope_key)`: empty `scope_key` means legacy events or chat conversation discovery; a chat conversation id means that conversation's event scan. Run rows describe attempts; state rows describe unfinished work across attempts.

1. **Discovery.** Persist each list page's conversation ids and next cursor in one transaction. Use a discovery generation to track the set being imported. List order may change during a walk, so periodically restart discovery and upsert ids. An exhausted list covers that scan; it does not prove future conversations cannot appear.
2. **Event pages.** Commit normalized rows, retryable item failures, the page cursor, and counters atomically. Save the request fingerprint with opaque cursors. A timeout before commit retries the same page. If a cursor expires, restart that scope with overlap and idempotent writes; keep the last completed boundary.
3. **Stopping.** Initial imports exhaust every discovered conversation's event pages. A known event is not an initial-import stopping condition. Incremental scans process the whole page and stop only after crossing a previously completed boundary with the configured overlap. Seeing one known event can otherwise skip older missing rows. Compare timestamps with deterministic id tie-breaks; never order numeric ids lexicographically.
4. **Empty or repeated pages.** No `next_token` means the API interval is exhausted. An empty page with a continuation token, a repeated cursor, or an HTTP 200 body with unresolved errors pauses that scope as `partial`; record the reason and schedule a bounded retry. Do not hot-loop or claim complete coverage. A persistently inconsistent API needs an explicit, visible coverage exception.
5. **Budgets and concurrency.** Lease one worker per scope with expiry and a fencing version. Reject a stale worker's commit after its lease has been replaced. Share request budgets across scopes for the same X account/app/endpoint. On 429, save the cursor and resume after the reset with jitter; on transient errors, back off; on a failed reauthorization requirement, pause the connection. A page, time, or spend cap produces a resumable pause.
6. **Reconciliation.** Prioritize notified conversations and run daily discovery plus a rotating sweep of every known conversation. Keep recent incremental work separate from older import backlogs. Expose `last_complete_at`, oldest pending work, unresolved coverage gaps, and the legacy retention deadline. Completion applies to a stated source/scope and coverage interval, not “all history forever.”

Start the pilot with a configurable 24-hour incremental overlap and a target seven-day full conversation sweep. These are proposed operating targets; large accounts may require more budget or a visibly longer sweep. Never claim the target was met merely because a worker exited successfully.

## Attribution, counting, and deletion

**Capture is broader than a direct-message count.** Add `count_eligible` with a default of false. Set it true only for a verified message event with valid timestamp/direction, a known direct counterpart, and a resolved contact owned by the same user. A history response's `is_trusted` is not proof of decrypted message semantics. Label unclassified encrypted rows `ChatEvent` until a fixture or documented contract establishes the countable kind; key changes, joins/leaves, edits, reactions, and deletion events must not inflate counts.

For direct conversations, prefer explicit participant metadata. If parsing a captured two-id conversation format, require exactly two ids, require that one equals the connected account, and select the other. Normalize only verified direct-id formats; preserve opaque group ids, including `g`-prefixed ids supported by the [Chat events endpoint](https://docs.x.com/x-api/chat/get-chat-conversation-events). Never derive membership or participant count from an arbitrary id string.

Resolve `counterpart_x_user_id` in both directions. Store `counterpart_profile_url` separately from `sender_profile_url`; handles are mutable hints and numeric X identity is the durable key. Cache handle lookups across runs, batch at most 100 distinct missing ids per request, and retain unresolved rows when accounts are deleted or unavailable. Groups remain captured but excluded from per-contact attribution in Phase 1. Message requests with unknown acceptance status remain ineligible; do not equate unsolicited contact with an established relationship.

### Identity and contact resolution

| DM field | Meaning |
| --- | --- |
| `user_id` | Orbiter user who owns this private activity row |
| `x_user_id` | Connected X account whose history was captured |
| `counterpart_x_user_id` | Numeric X account id of the person the user sent to or received from |
| `entity_id` | That person's node UUID in the Universe; `NULL` until resolved |

`entity_id` is the same person node UUID used elsewhere in Orbiter. It is not the owner's id, an X id, or the prototype's integer `my_person_id`. Contact membership is specific to `(user_id, entity_id)`: one person can already exist in the Universe while still needing to be added to this user's contacts.

1. **Capture everything available in the connected account's authorized event stream.** Persist the scoped event even when its counterparty is unresolved. For a verified direct counterpart, perform a cached, bounded Universe lookup. Match by numeric X id when available; otherwise use the normalized handle/profile URL and verify the account identity before attaching a person. Handles can change or be reassigned. Store an existing canonical person node UUID as `entity_id`; a miss, ambiguity, or lookup failure leaves it `NULL`. No person creation or enrichment runs in the capture request.
2. **Resolve missing identities on the CRON.** Group work by distinct counterparty, rather than paying to resolve every message. Recheck the Universe immediately before creation so another import or worker's match is reused. The existing `temp/resolve-x-to-linkedin` (13399) is reference logic for finding identity evidence; its `resolved` flag alone is not an identity-confidence guarantee. Accept corroborated matches, then use the normal deduplicated person-creation path and save the resulting person node UUID. Follow canonical merge redirects. Unavailable, ambiguous, or non-person accounts stay logged without inventing a person. See the [non-LinkedIn resolution scope](/guides/open-work/enrich-via-non-linkedin-scope) for why a bare X URL must not go directly into the legacy create path.
3. **Enrich and add contacts.** Enqueue or reuse enrichment for newly resolved people, then upsert contact membership for each affected user by `(user_id, entity_id)`. Reuse existing enrichment when sufficient. This step also handles rows whose `entity_id` was attached during capture but whose user contact does not yet exist. Keep enrichment and contact-creation checkpoints independently retryable so an optional enrichment failure cannot permanently strand an identified person. Use the shared durable resolver job state for attempts, retry times, and unresolved reasons; processing the same event again must not create another person, enrichment job, or user contact.
4. **Backfill and update interactions.** Attach `entity_id` to all matching unresolved direct rows in the authorized user's scope, including older events and both directions. Recheck contact membership and message eligibility before enabling counts; dirty the affected contact and original month. Keep every activity row after resolution. Jobs must recheck connection revocation before writing private rows or adding contacts, so disconnect cannot be undone by a late resolver.

The CRON has two work sets: unresolved counterpart identities, and resolved identities with missing user contacts. Do not equate a non-null `entity_id` with completed processing. Use bounded batches and persisted backoff for repeated failures. Shared person creation/enrichment is deduplicated by canonical identity; user contact creation is deduplicated separately by `(user_id, entity_id)`.

Only public profile identity and enrichment belong in the Universe. DM content, timestamps, conversation ids, and the fact that two people exchanged DMs stay in the user's private activity and relationship scope. Adding someone to contacts does not itself assert reciprocal KNOWS evidence.

### Interaction rollups and deletion

The [interaction-log consumer](/guides/open-work/contacts-interaction-log) needs a coordinated migration to `(user_id, entity_id)` attribution before enabling X rollups. Any adapter for its legacy `my_person_id` contact lookup belongs at that consumer boundary; it must not reinterpret the person node UUID as an integer contact id.

| Proposed field | Meaning over eligible, non-deleted direct rows |
| --- | --- |
| `total_x_dms`, `to_x_dms`, `from_x_dms` | All, sent, received; total equals sent plus received |
| `total_x_dm_threads` | Distinct `(x_user_id, dm_conversation_id)` across both transports, so an upgraded conversation remains one thread |
| `last_x_dm_at`, `last_to_x_dm_at`, `last_from_x_dm_at` | Event time overall and by direction |
| First/last interaction and monthly buckets | Include eligible X event times; keep Stream's `chat_interactions` separate |

Count a source-scoped event once per connected account. If a later fixture proves the same message appears in both transports, add an explicit identity mapping before combining their counts; do not dedupe by similar text or timestamps. Internal conversations between two X accounts owned by the same Orbiter user are excluded from contact counts. Derive relationship evidence from eligible rows under the existing private relationship policy; one incoming event does not automatically assert a reciprocal relationship.

Changes to resolution, eligibility, or deletion must dirty the affected contact and month using ingestion/change time, including when the event is old. On unchanged replays preserve `entity_id`, capture-time metadata, and future plaintext state; do not overwrite resolved values with defaults. Advance `updated_at` on meaningful changes, not every read.

**Phase 1 includes a deletion path.** DM metadata reveals who talks to whom and is private user data. Allowlist `raw` fields; legacy `text`/`snippet` must not also survive inside `raw`, logs, or cached payloads. Define retention for activity, inbox diagnostics, exports, and backups before rollout. Default disconnect behavior: disable DM capture and invalidate the connection generation; remove its subscriptions; cancel pending work; delete account-scoped activity and inbox data; recompute affected rollups and remove only the corresponding relationship evidence. Recheck the generation inside the write transaction so late workers cannot restore deleted rows. Preserve unrelated follower access if the user disables only DMs. Provider deletions or expiry are applied when observable; disappearance from the legacy 30-day lookup is not a deletion signal.

## Release checks

| Scenario | Required result |
| --- | --- |
| Same event delivered twice, fetched twice, or fetched during webhook processing | One scoped activity row; resolved fields preserved |
| Two Orbiter owners or two connected X accounts see matching event ids | Independent rows and correct owner checks |
| Crash during page commit; expired lease; cursor reset | Atomic page recovery; stale worker cannot advance state |
| Notification arrives during a conversation fetch | New generation remains pending and is fetched |
| Conversation appears mid-discovery; page 2 contains history; 29th conversation is nonempty | All are eventually captured; no offset or empty-streak skip |
| Empty page with next cursor; HTTP 200 plus errors; 429; exhausted budget | Visible resumable partial/pause, no false completion |
| Sent/received direct pair; group; unknown kind; message request | Correct counterpart; only verified eligible direct messages count |
| Universe lookup unavailable during capture | Event saved with null `entity_id`; CRON retries resolution |
| Existing Universe person with no contact for this user | Person node UUID attached; CRON creates the missing user contact |
| Many events/users reference one new person; jobs overlap or retry | One canonical person and deduplicated enrichment work; one contact per `(user_id, entity_id)`; historical rows backfilled |
| Handle changes, is reassigned, or resolves ambiguously | Numeric X identity verified; no speculative person attachment |
| Old event resolves after import; eligible event is deleted | Original contact/month rollup recomputed correctly |
| Invalid signature; revoked connection; disconnect while worker runs | No unauthorized write or data resurrection |
| Two concurrent OAuth refreshes across follower and DM jobs | One rotation persists; no stale pair overwrites it |
| Seven-day pilot | Compare reported coverage and latency with fixtures; reconcile estimated spend to console billing; exercise subscription removal and recovery |

## Source 1: legacy DMs (GET /2/dm_events)

Verified against docs.x.com and live on 2026-09-06.

| | |
| --- | --- |
| Endpoint | `GET https://api.x.com/2/dm_events` (all legacy conversations the user is in). Also `GET /2/dm_conversations/with/:participant_id/dm_events` for one 1-to-1 thread and `GET /2/dm_conversations/:dm_conversation_id/dm_events` for one group. |
| Auth | OAuth 2.0 user context. App-only bearer is rejected. |
| Scopes | `dm.read`, `tweet.read`, `users.read`; add `offline.access` for the refresh token |
| Window | Events from up to **30 days** ago. Newest first. No `since_id` or `start_time`. |
| Paging | `max_results` 1 to 100 (default 100); `pagination_token` from `meta.next_token` |
| `event_types` | `MessageCreate`, `ParticipantsJoin`, `ParticipantsLeave`; omit the parameter to get all three |
| `dm_event.fields` | `id`, `text`, `event_type`, `created_at`, `dm_conversation_id`, `sender_id`, `participant_ids`, `referenced_posts` (the harness still sends the older `referenced_tweets`, which X accepts), `attachments`, `entities` |
| `expansions` | `sender_id`, `participant_ids` (user objects in `includes.users`), `attachments.media_keys`, `referenced_tweets.id` |
| Rate limit | **15 requests per 15 minutes per user** on every DM lookup endpoint; `x-rate-limit-limit: 15` observed |
| Encrypted Chat | **Never returned.** New conversations, and old ones a user upgrades, are invisible here. Use Source 2. |

<Warning>
  **X only serves the last 30 days of legacy DM events.** There is no historical backfill through this API, and a sync that lapses for more than 30 days loses the gap permanently. The Nylas email import has no such limit.
</Warning>


## Source 2: encrypted chats (the X Chat API)

X ships a separate **X Chat API** plus a **Chat XDK**. The metadata endpoints and response shapes below were checked against docs.x.com, the `xdevplatform/chat-xdk` Go example, and live calls on 2026-09-06.

The server reads metadata with the user's OAuth token and does not decrypt message bodies. The current build needs no user PINs or private keys; see X's [private-key guidance](https://docs.x.com/xchat/handling-private-keys).

Bot accounts (`POST /2/bots`) only see messages sent to the bot, so they do not apply.

**Endpoints and authorization** — history reads use the user's token; webhook registration and Activity subscriptions have distinct authorization requirements described above.

## Cost, rate limits, and cadence

The [pricing page](https://docs.x.com/x-api/getting-started/pricing), checked 2026-09-06, lists DM Event reads and User reads at \$0.010 per resource, `chat.received` at \$0.010 per delivered event, and `chat.sent`/`chat.conversation_join` as not billed. It also documents **deduplication within each UTC day as a soft guarantee**. Repeated reads of the same event are therefore not a guaranteed charge on every poll. The old \$1.80/month four-hour “floor” was incorrect. Chat history/list pricing and any cross-delivery/read billing overlap still need confirmation in this app's console.

Use three separate budget categories: first import, ongoing reads (including user lookups), and billable deliveries. As an illustration, reading one unchanged legacy event on each of 30 UTC days costs approximately \$0.30 if daily deduplication holds; this excludes new events and all other resources. Model a conservative no-dedup case too. Cache handles: one request returning 100 users is 100 resources, not one. Do not size production around an unverified promotional allowance.

Keep the four-hour legacy cadence as a pilot freshness choice, not a pricing theorem. Chat notifications trigger coalesced fetches; daily discovery and the rotating sweep consume separate read budgets. A “3,000 events/day” limit could permit \$30/day at \$0.010 per resource before other costs, so define caps in dollars as well as requests/resources. Reserve the maximum estimated batch cost before dispatch and reconcile actual units afterward. Unknown unit prices block broad rollout, not fixture-based development.

The reference observed 15 legacy-event, 50 conversation-list, and 30 conversation-event requests per 15 minutes per user. Treat these as starting limits; respect returned headers and any shared app-level limits. Concurrent conversation workers consume the same account's endpoint budget. An application kill switch must stop polling **and remove billable subscriptions**; acknowledging or discarding already-delivered webhooks does not prevent provider charges. Use the console's spending limit as a second bound, and expose gaps caused by budget pauses.

**Lessons that go straight into the Go build**

- **Consent page rejects `dm.read` unless the app's permission level includes Direct Messages.** X shows only "Something went wrong". The level lives under the app's Settings in the developer console and does not rotate keys. Raised for the Orbiter app on 2026-09-06.
- **Client ID, callback and permission all live on one app.** A link built with one app's Client ID against another app's callback produced a code the second app could not exchange, with the same "Value passed for the authorization code was invalid" error as an expired code.
- **Authorization codes die in 30 seconds and are single-use.** Hand-pasting failed three times; a one-shot local listener that exchanged the code 2 seconds after the redirect worked first time. The Go callback must exchange in the request that receives it.
- **The console can mint a user token for the app owner.** Keys & Tokens → OAuth 2.0 Keys generates an access and refresh token for the owning account with chosen scopes; seeding the refresh token through `twitter-api-oauth-exchange` (13390) stores the rotated pair. Internal accounts only.
- **Xano CLI runner quirks.** `xano function run --json -` (stdin) delivers an empty input; use `-d key=value` or inline `--json`. Nested `function.run` calls fail in the runner, which is why all four functions read the token row themselves. `function create` drops `?=0` defaults on optional ints.
- **X Chat and legacy DMs disagree on id spelling and paging** (see Source 2). Normalize verified direct-id formats; preserve group ids. The reference stopped on empty pages, but production records contradictory continuation metadata as incomplete.

````xanoscript
                var.update $keep_going {
                  value = false
                }
              }
            }
          }
        }
      }
    }
  
    // Close the run
    var $final_status {
      value = "complete"
    }
  
    conditional {
      if ($rate_limited) {
        var.update $final_status {
          value = "paused_rate_limit"
        }
      }
    
      elseif (($next_token != "") && ($stop_incremental == false)) {
        var.update $final_status {
          value = "paused_rate_limit"
        }
      }
    }
  
    conditional {
      if ($final_status == "complete") {
        db.edit x_dm_sync_run {
          field_name = "id"
          field_value = $run_id
          data = {
            status         : "complete"
            events_seen    : $events_seen
            events_new     : $events_new
            pages_fetched  : $pages
            next_token     : ""
            newest_event_id: $newest_event_id
            finished_at    : now
            updated_at     : now
          }
        } as $run_done
      }
    
      else {
        db.edit x_dm_sync_run {
          field_name = "id"
          field_value = $run_id
          data = {
            status         : "paused_rate_limit"
            events_seen    : $events_seen
            events_new     : $events_new
            pages_fetched  : $pages
            next_token     : $next_token
            newest_event_id: $newest_event_id
            updated_at     : now
          }
        } as $run_paused
      }
    }
  }

  response = {
    sync_run_id    : $run_id
    mode           : $input.mode
    status         : $final_status
    account_id     : $account_id
    username       : $account_username
    events_seen    : $events_seen
    events_new     : $events_new
    events_updated : $events_updated
    pages_fetched  : $pages
    next_token     : $next_token
    newest_event_id: $newest_event_id
    rate_limited   : $rate_limited
    users_seen     : $users
  }
}
````

````xanoscript
// v1.0 (2026-09-06): read-only smoke-test harness for the X Chat API (encrypted chats), docs: Open Work > X Followers Capture > Log X DMs. Calls GET /2/chat/conversations/{conversation_id}/events with the stored user-context token and returns the raw response: message events arrive as ciphertext next to sender_id and created_at in the clear, plus meta.conversation_key_events and meta.next_token. Optional path input overrides the request path for probing other Chat endpoints. Reads the token in this stack (no nested function.run, so the CLI runner can execute it); requires dm.read on the row. Writes nothing and never decrypts.
function "twitter-api-chat-events" {
  input {
    // Optional numeric X user id to pick a specific user-context row in x_oauth_token. Defaults to the most recently updated user row.
    text x_user_id? filters=trim
  
    // Chat conversation id (1-to-1 ids are the two user ids joined by a hyphen). Defaults to Mark <-> Orbiter_io.
    text conversation_id? filters=trim
  
    // Events per page, 1 to 100.
    int max_results?=100 filters=min:1|max:100
  
    // next_token from a previous call.
    text pagination_token? filters=trim
  
    // Optional request path override (must start with /2/), for probing other Chat endpoints. When set, conversation_id and max_results are ignored.
    text path? filters=trim
  }

  stack {
    conditional {
      if ($input.x_user_id != "") {
        db.query x_oauth_token {
          where = ($db.x_oauth_token.grant_type == "user") && ($db.x_oauth_token.x_user_id == $input.x_user_id)
          return = {type: "single"}
        } as $token_row
      }
    
      else {
        db.query x_oauth_token {
          where = $db.x_oauth_token.grant_type == "user"
          sort = {updated_at: "desc"}
          return = {type: "single"}
        } as $token_row
      }
    }
  
    conditional {
      if ($token_row == null) {
        throw {
          name = "XTokenError"
          value = "No user-context X token in x_oauth_token. Authorize with scopes dm.read tweet.read users.read offline.access, then run twitter-api-oauth-exchange."
        }
      }
    }
  
    var $scope {
      value = $token_row.scope
    }
  
    var $has_dm_scope {
      value = $scope|contains:"dm.read"
    }
  
    conditional {
      if ($has_dm_scope == false) {
        var $scope_err {
          value = "Stored X token for @" ~ $token_row.username ~ " was granted without dm.read (scope: '" ~ $scope ~ "')."
        }
      
        throw {
          name = "XScopeError"
          value = $scope_err
        }
      }
    }
  
    var $refresh_threshold {
      value = now|add_secs_to_timestamp:300
    }
  
    var $token_stale {
      value = ($token_row.expires_at == null) || ($token_row.expires_at < $refresh_threshold)
    }
  
    conditional {
      if ($token_stale) {
        var $stale_err {
          value = "Stored X token for @" ~ $token_row.username ~ " expires at " ~ $token_row.expires_at ~ ". Run twitter-api-token with token_type=user to refresh it, then re-run this harness."
        }
      
        throw {
          name = "XTokenError"
          value = $stale_err
        }
      }
    }
  
    var $auth_header {
      value = "Authorization: Bearer " ~ $token_row.access_token
    }
  
    var $conversation_id {
      value = $input.conversation_id
    }
  
    conditional {
      if ($conversation_id == "") {
        var.update $conversation_id {
          value = "16826747-1594015572706181121"
        }
      }
    }
  
    // Build the URL: events for one conversation, or an arbitrary Chat path for probing
    var $url {
      value = "https://api.x.com/2/chat/conversations/" ~ $conversation_id ~ "/events?max_results=" ~ $input.max_results
    }
  
    conditional {
      if ($input.path != "") {
        var.update $url {
          value = "https://api.x.com" ~ $input.path
        }
      }
    }
  
    conditional {
      if ($input.pagination_token != "") {
        var.update $url {
          value = $url ~ "&pagination_token=" ~ $input.pagination_token
        }
      }
    }
  
    api.request {
      url = $url
      method = "GET"
      headers = []|push:$auth_header
      timeout = 60
    } as $call
  
    precondition ($call.response.result != false) {
      error = "X Chat API request did not respond (timeout)"
    }
  
    var $status {
      value = $call.response.status
    }
  
    var $body {
      value = $call.response.result
    }
  
    var $headers {
      value = $call.response.headers
    }
  
    var $token_source {
      value = "x_oauth_token:" ~ $token_row.id ~ " @" ~ $token_row.username
    }
  }

  response = {
    token_source   : $token_source
    conversation_id: $conversation_id
    url            : $url
    status         : $status
    body           : $body
    headers        : $headers
  }
}
````

````xanoscript
// v1.1 (2026-09-06): last_body and last_headers now returned for every page status, for diagnostics. v1.0 (2026-09-06): smoke-test harness for X (Twitter) API v2 GET /2/dm_events, the endpoint behind the proposed x_dm_activity logger (docs: Open Work > X Followers Capture > Log X DMs). Reads the user-context token in this stack only and makes no nested function.run call, so it can be executed from the CLI/MCP runner (which cannot resolve nested calls, see docs trap 21): if the x_oauth_token row expires within 5 minutes it throws XTokenError asking for twitter-api-token (token_type user) to be run first, then the row is re-read here and the Authorization header is built here. Requires the row's scope to include dm.read (with tweet.read and users.read); throws XScopeError otherwise so a missing consent reads as a clear message instead of an X 403. Confirms the token via /2/users/me, then pages GET /2/dm_events (newest first, up to 100 events per page, only the last 30 days are available) with dm_event.fields plus expansions for sender and participant users, media, and referenced posts. On HTTP 429 it stops and returns what it has with rate_limited = true. Writes nothing.
function "twitter-api-dm-events" {
  input {
    // Optional numeric X user id to pick a specific user-context row in x_oauth_token. Defaults to the most recently updated user row.
    text x_user_id? filters=trim
  
    // How many pages (up to 100 events each) to fetch in this call. The endpoint allows 15 requests per 15 minutes per user.
    int max_pages?=1 filters=min:1|max:15
  
    // Events per page, 1 to 100.
    int max_results?=100 filters=min:1|max:100
  
    // next_token from a previous call, to continue where it left off.
    text pagination_token? filters=trim
  
    // Optional event type filter (MessageCreate, ParticipantsJoin or ParticipantsLeave). Leave empty to return all three.
    text event_types? filters=trim
  }

  stack {
    // Read the token in this stack: a specific account, or the newest user-context row
    conditional {
      if ($input.x_user_id != "") {
        db.query x_oauth_token {
          where = ($db.x_oauth_token.grant_type == "user") && ($db.x_oauth_token.x_user_id == $input.x_user_id)
          return = {type: "single"}
        } as $token_row
      }
    
      else {
        db.query x_oauth_token {
          where = $db.x_oauth_token.grant_type == "user"
          sort = {updated_at: "desc"}
          return = {type: "single"}
        } as $token_row
      }
    }
  
    conditional {
      if ($token_row == null) {
        throw {
          name = "XTokenError"
          value = "No user-context X token in x_oauth_token. Authorize with scopes dm.read tweet.read users.read offline.access, then run twitter-api-oauth-exchange."
        }
      }
    }
  
    // No nested refresh here (runner limitation): refuse a token that expires within 5 minutes and say what to run
    var $refresh_threshold {
      value = now|add_secs_to_timestamp:300
    }
  
    var $token_stale {
      value = ($token_row.expires_at == null) || ($token_row.expires_at < $refresh_threshold)
    }
  
    conditional {
      if ($token_stale) {
        var $stale_err {
          value = "Stored X token for @" ~ $token_row.username ~ " expires at " ~ $token_row.expires_at ~ ". Run twitter-api-token with token_type=user to refresh it, then re-run this harness."
        }
      
        throw {
          name = "XTokenError"
          value = $stale_err
        }
      }
    }
  
    // The DM endpoints need dm.read on the grant; fail early with a readable message
    var $scope {
      value = $token_row.scope
    }
  
    var $has_dm_scope {
      value = $scope|contains:"dm.read"
    }
  
    conditional {
      if ($has_dm_scope == false) {
        var $scope_err {
          value = "Stored X token for @" ~ $token_row.username ~ " was granted without dm.read (scope: '" ~ $scope ~ "'). Re-authorize with dm.read tweet.read users.read offline.access and re-run twitter-api-oauth-exchange."
        }
      
        throw {
          name = "XScopeError"
          value = $scope_err
        }
      }
    }
  
    var $token_source {
      value = "x_oauth_token:" ~ $token_row.id
    }
  
    var $auth_header {
      value = "Authorization: Bearer " ~ $token_row.access_token
    }
  
    // Confirm the token works and identify the connected account
    api.request {
      url = "https://api.x.com/2/users/me?user.fields=id,username,name,public_metrics"
      method = "GET"
      headers = []|push:$auth_header
      timeout = 30
    } as $me_call
  
    precondition ($me_call.response.result != false) {
      error = "X /2/users/me did not respond (timeout)"
    }
  
    var $me_status {
      value = $me_call.response.status
    }
  
    var $me_body {
      value = $me_call.response.result
    }
  
    conditional {
      if ($me_status != 200) {
        var $me_err {
          value = "X /2/users/me failed (HTTP " ~ $me_status ~ ") using " ~ $token_source ~ ": " ~ ($me_body|json_encode)
        }
      
        throw {
          name = "XApiError"
          value = $me_err
        }
      }
    }
  
    var $account {
      value = $me_body|get:"data":null
    }
  
    // Field lists for the DM lookup
    var $dm_fields {
      value = "id,text,event_type,created_at,dm_conversation_id,sender_id,participant_ids,referenced_tweets,attachments"
    }
  
    var $expansions {
      value = "sender_id,participant_ids,referenced_tweets.id,attachments.media_keys"
    }
  
    var $user_fields {
      value = "id,username,name,profile_image_url,verified,protected"
    }
  
    var $media_fields {
      value = "media_key,type,url,preview_image_url"
    }
  
    var $tweet_fields {
      value = "id,text,author_id,created_at"
    }
  
    var $base_url {
      value = "https://api.x.com/2/dm_events?max_results=" ~ $input.max_results ~ "&dm_event.fields=" ~ $dm_fields ~ "&expansions=" ~ $expansions ~ "&user.fields=" ~ $user_fields ~ "&media.fields=" ~ $media_fields ~ "&tweet.fields=" ~ $tweet_fields
    }
  
    // Only send event_types when asked; omitting it returns all three types
    conditional {
      if ($input.event_types != "") {
        var.update $base_url {
          value = $base_url ~ "&event_types=" ~ $input.event_types
        }
      }
    }
  
    // Page through DM events
    var $events {
      value = []
    }
  
    var $users {
      value = []
    }
  
    var $media {
      value = []
    }
  
    var $tweets {
      value = []
    }
  
    var $next_token {
      value = $input.pagination_token
    }
  
    var $pages {
      value = 0
    }
  
    var $keep_going {
      value = true
    }
  
    var $rate_limited {
      value = false
    }
  
    var $last_status {
      value = 0
    }
  
    var $last_body {
      value = null
    }
  
    var $last_headers {
      value = null
    }
  
    while ($keep_going) {
      each {
        var $page_url {
          value = $base_url
        }
      
        conditional {
          if ($next_token != "") {
            var.update $page_url {
              value = $base_url ~ "&pagination_token=" ~ $next_token
            }
          }
        }
      
        // Fetch one page of DM events
        api.request {
          url = $page_url
          method = "GET"
          headers = []|push:$auth_header
          timeout = 60
        } as $page_call
      
        precondition ($page_call.response.result != false) {
          error = "X dm_events request did not respond (timeout)"
        }
      
        var $page_status {
          value = $page_call.response.status
        }
      
        var $page_body {
          value = $page_call.response.result
        }
      
        var.update $last_status {
          value = $page_status
        }
      
        // Keep the raw body and headers of the last page for diagnostics (v1.1)
        var.update $last_body {
          value = $page_body
        }
      
        var.update $last_headers {
          value = $page_call.response.headers
        }
      
        conditional {
          if ($page_status == 429) {
            // Per-user window exhausted: stop and hand back what we have plus the resume token
            var.update $rate_limited {
              value = true
            }
          
            var.update $keep_going {
              value = false
            }
          }
        
          elseif ($page_status != 200) {
            var $page_err {
              value = "X dm_events request failed (HTTP " ~ $page_status ~ ") after " ~ $pages ~ " page(s): " ~ ($page_body|json_encode)
            }
          
            throw {
              name = "XApiError"
              value = $page_err
            }
          }
        
          else {
            var $page_data {
              value = $page_body|get:"data":null
            }
          
            conditional {
              if ($page_data != null) {
                array.merge $events {
                  value = $page_data
                }
              }
            }
          
            var $inc_users {
              value = $page_body|get:"includes.users":null
            }
          
            conditional {
              if ($inc_users != null) {
                array.merge $users {
                  value = $inc_users
                }
              }
            }
          
            var $inc_media {
              value = $page_body|get:"includes.media":null
            }
          
            conditional {
              if ($inc_media != null) {
                array.merge $media {
                  value = $inc_media
                }
              }
            }
          
            var $inc_tweets {
              value = $page_body|get:"includes.tweets":null
            }
          
            conditional {
              if ($inc_tweets != null) {
                array.merge $tweets {
                  value = $inc_tweets
                }
              }
            }
          
            var.update $pages {
              value = $pages + 1
            }
          
            var.update $next_token {
              value = $page_body|get:"meta.next_token":""
            }
          
            conditional {
              if (($next_token == "") || ($pages >= $input.max_pages)) {
                var.update $keep_going {
                  value = false
                }
              }
            }
          }
        }
      }
    }
  
    var $events_returned {
      value = $events|count
    }
  }

  response = {
    account        : $account
    scope          : $scope
    token_source   : $token_source
    events_returned: $events_returned
    events         : $events
    users          : $users
    media          : $media
    tweets         : $tweets
    pages_fetched  : $pages
    next_token     : $next_token
    rate_limited   : $rate_limited
    last_status    : $last_status
    last_body      : $last_body
    last_headers   : $last_headers
  }
}
````
