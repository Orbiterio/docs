<Warning>
  **Charles, read this first.** In late 2025 X replaced Direct Messages with end-to-end encrypted **Chat**. That splits the feature into two sources that land in one table:

  1. **Legacy DMs** through `GET /2/dm_events`: conversations that were never upgraded to encryption. Full text, last 30 days only. Proven: 3 of Mark's conversations logged.
  2. **Encrypted chats** through the **X Chat API**: every new conversation. The API gives the user's own token each event's id, sender, timestamp and conversation in the clear, and the body only as ciphertext that decrypts on the user's device. Proven: a full walk of Mark's 499-conversation list logged 78 chat events across 16 conversations, back to November 2025, as metadata rows.

  **Decision taken for this spec: Phase 1 logs encrypted chats as metadata-only rows (`text` empty) and never holds user keys or PINs server-side. Knowing that a conversation is happening, with whom, in which direction and how recently is the value for Orbiter's interaction log and KNOWS edges. Phase 2, message text through on-device decryption in the Orbiter client, is scoped as the last step of the build plan.** The ordered task list is in [Build plan](#build-plan-for-charles); everything you need to reproduce the live results is in [Smoke-test record](#smoke-test-record).
</Warning>

## What this delivers

When a user connects X to Orbiter with DM consent, we log one `x_dm_activity` row per message event, from both sources, keyed by `(user_id, dm_event_id)`. Every row carries the Orbiter fields that make it behave like `email_activity` (`user_id`, `my_person_id`, `activity_type_id`, `card_descriptor`, `activity_timestamp`, `direction`) plus the X identifiers (event, conversation, sender, counterpart) and a `source` of `legacy_dm` or `xchat`. Legacy rows also carry `text`; chat rows never do.

Downstream nothing changes: the interaction-log job counts DM rows next to email and calendar, and the resolver CRON from the parent page turns `sender_profile_url` into `my_person_id` and KNOWS edges. The loggers never touch the graph.

Work top to bottom. Each step names its acceptance check.

<Steps>
  <Step title="1. Read the two source sections and the smoke-test record">
    [Source 1: legacy DMs](#source-1-legacy-dms-get-2dm_events) and [Source 2: encrypted chats](#source-2-encrypted-chats-the-x-chat-api) carry the exact endpoints, real captured responses, rate limits and the shape quirks that cost us time. The [smoke-test record](#smoke-test-record) has the token, consent and CLI lessons. Nothing there is speculative; every number was observed on 2026-09-06.
  </Step>
  <Step title="2. AlloyDB tables">
    Run the [copy-paste migration](#copy-paste-migration-alloydb). It mirrors Xano 789 and 790 including the three chat columns. Extend the token table (the Go equivalent of `x_oauth_token`) with `user_id`, `scope`, `dm_enabled`, `next_sync_at`, `sync_cadence_minutes` (default 240) and `needs_reconsent`. Keep every X id as `text`; they are 64-bit snowflakes. **Check:** the DDL applies cleanly and a row with `source = 'xchat'` and empty `text` inserts.
  </Step>
  <Step title="3. OAuth consent in Go">
    Scopes `tweet.read users.read follows.read dm.read offline.access`, PKCE with S256 in production (`plain` with verifier `challenge` was only for the Xano exchange function). The callback handler must exchange the code **in the request that receives it**: codes are single-use and die in 30 seconds. Store access and refresh tokens encrypted; X rotates the refresh token on every refresh, so write the new pair back before anything else. **Check:** a consent from a second account lands a token row with `dm.read` in `scope` without any manual step. Prerequisite in the X developer console: the app's permission level must be *Read and write and Direct message* and the callback must be registered on that same app.
  </Step>
  <Step title="4. Encrypted chats: webhook receiver and subscriptions">
    At connect time create Activity API subscriptions for the user: `POST /2/activity/subscriptions` with `{"event_type": "chat.received", "filter": {"user_id": "<x_user_id>"}}` and the same for `chat.sent` (free) and `chat.conversation_join` (free). Run a Cloud Run receiver that answers the CRC challenge (HMAC-SHA256 of the token with the consumer secret) and, on delivery, writes one metadata row: `source = 'xchat'`, `event_uuid` from the envelope, `conversation_id` (hyphen form), `sender_id`, `conversation_key_version`, `direction` from sender versus connected account, `card_descriptor` from a cached handle. Dedupe on `event_uuid`, never decrypt `encoded_event`. **Check:** send one chat to a subscribed account and see the row within a minute. Each `chat.received` costs $0.010.
  </Step>
  <Step title="5. Encrypted chats: initial import and reconciliation">
    Port `twitter-api-sync-chats` (13404): `GET /2/chat/conversations?max_results=50` newest first, then `GET /2/chat/conversations/{id}/events?max_results=100` per conversation, one `GET /2/users?ids=` batch for handles, upsert on `(user_id, dm_event_id)`. Budget per user: 50 list and 30 events requests per 15 minutes, so a first import of a busy account spans several windows; checkpoint per conversation and resume with `skip_conversations`, and refresh the token before every batch (a 2-hour token expires mid-walk; the Xano reference refuses a token inside its 5-minute margin and lost one batch that way). Stop paging a conversation on the first already-logged event (incremental) or on an empty page (X can answer `has_more: true` and then return an empty page). **Stop the walk after 28 consecutive conversations with zero events**: the list is ordered by last activity, encrypted Chat began in November 2025, and everything older can only have legacy events. Mark's list has 499 conversations; the first 84 held every chat event and the next 56 held none. Run the reconciliation daily per account over the newest conversations only. **Check:** re-running the import inserts zero rows.
  </Step>
  <Step title="6. Legacy DMs: dispatcher and worker">
    Port `twitter-api-sync-dms` (13402) for the pre-Chat conversations. Cloud Scheduler ticks every 15 minutes and a dispatcher enqueues only accounts whose `next_sync_at` has passed (default cadence every 4 hours, see [Cost, rate limits, and cadence](#cost-rate-limits-and-cadence)); a worker pages `GET /2/dm_events` newest first, stops at the first known event, fills sent-message counterpart handles with a `GET /2/users?ids=` batch, and sets `next_sync_at`. 15 requests per 15 minutes per user; on 429 read `x-rate-limit-reset`. **Check:** the cadence table's floor cost holds in the run rows for a week.
  </Step>
  <Step title="7. Resolver hand-off">
    Never resolve counterparties in the loggers. The resolver CRON from the parent page sweeps rows with `my_person_id = 0` by `sender_profile_url`, or `counterpart_x_user_id` for sent 1-to-1 rows, back-fills `my_person_id`, and only then fans out KNOWS pairs as `known/ingest/_fanout_email_pairs` does for email. Chat rows resolve exactly like legacy rows; they only lack text.
  </Step>
  <Step title="8. Cost guards, observability, tests, rollout">
    Per-account daily cap on events read (start at 3,000) and a global monthly budget behind a kill switch. One structured log line per run from the run row; metrics for accounts due, runs completed, 429s, reconsents needed, webhook deliveries and estimated spend. Unit tests for direction, counterpart from the hyphenated id, `card_descriptor` and colon-to-hyphen normalisation, driven by the recorded fixtures on this page; an idempotency test that runs a fixture twice. Feature flag per user; internal accounts first; a week of spend data; then everyone. **Phase 1 ships here.**
  </Step>
  <Step title="9. Phase 2, later: message text through on-device decryption (Option B)">
    Phase 1 already tells Orbiter that a conversation is happening, with whom, in which direction and how recently. Phase 2 adds the words, and it can only happen on the user's device, because that is where X keeps the keys. **This does not wait for an iOS app.** X's own desktop web client decrypts chats in the browser with the WASM build of the Chat XDK, and the Orbiter web app can do the same. Scope, in order:

    1. **Client integration, web first.** Embed `@xdevplatform/chat-xdk` (WASM, see X's "Building UI apps with WASM" guide) in the Orbiter web app; add the native binding when the iOS app exists. The client calls `unlock(pin)` once per device, keeps the key material in the XDK's own storage, and never sends the PIN or keys anywhere. Trade-offs by platform:

       | | Web app (WASM) | iOS app (native binding) |
       | --- | --- | --- |
       | Ships | First; no new app needed | Later, with the mobile build |
       | When text syncs | Only while an Orbiter tab is open | Background refresh keeps up with new chats |
       | Key storage | Browser profile; PIN re-entry after a cleared profile or a new browser | Keychain-backed; PIN prompt recurs rarely |
       | Coverage | Chats that arrived before the tab opened are fetched on open, so nothing is missed, only delayed | Near real-time |
    2. **PIN prompt.** A one-time screen that asks for the user's XChat PIN with a plain explanation of what it unlocks and that it stays on the device. Users who decline stay on Phase 1; the metadata rows are unaffected.
    3. **Decrypt and post.** On open, and while the app is in the foreground, the client fetches `GET /2/chat/conversations/{id}/events` for conversations with rows whose `text` is empty, runs `decrypt_events()`, and posts `{dm_event_id, text}` pairs to a new ingest endpoint that fills `text` and `snippet` on the existing row. Nothing new is inserted; Phase 1 rows are the anchor. Webhook events keep arriving as metadata and get their text the next time a client opens.
    4. **Ingest endpoint.** Authenticated, per-user, idempotent on `dm_event_id`, rejects rows that do not belong to the caller's `user_id`. Rate-limit and size-cap the payload.
    5. **Privacy and retention.** Explicit consent copy for storing plaintext of end-to-end encrypted chats, a retention window shorter than legacy DM text, deletion on disconnect, and a per-user switch to stop text sync while keeping metadata. Legal review before rollout.
    6. **Acceptance.** A row logged by Phase 1 gains `text` within one client session; a user who never enters a PIN keeps working with metadata only; revoking the switch clears stored text for that user.

    Do not start Phase 2 until Phase 1 has run for real users and the product has decided it needs the words. Everything above the metadata layer is reversible; a store of decrypted private messages is not.
  </Step>
</Steps>

## How email does it today

The DM design mirrors the email path. What each step becomes for X:

| Email today | Where | X equivalent |
| --- | --- | --- |
| Nylas `message.created` webhook fires per message | `mvp/nylas-webhook/message-created` (180) | `chat.received` Activity webhook for encrypted chats. A scheduled poll of `GET /2/dm_events` for legacy DMs, which have no usable webhook for us. |
| Dedupe on `(grant_id, message_id)` before logging | `mvp/activity/message-created-parse` (1913) | Dedupe on `(user_id, dm_event_id)`, enforced by a unique index; webhook deliveries also dedupe on `event_uuid` |
| Direction: `from.email == grant.email_account` means sent | `parse-from` (2126) / `parse-to` | `sender_id == connected x_user_id` means sent |
| One `email_activity` row **per participant** with `activity_type_id` 1 to 4 (`email_from`, `email_to`, `email_cc`, `email_bcc`) | `mvp/activity/log-participant-activity` (12773) | One row **per event** with two new `activity_type` rows, `x_dm_from` and `x_dm_to`. Group chats keep `participant_ids` on the row instead of fanning out. |
| Counterparty resolved at write time by email address into `my_person_id` | `mvp/identity/check-identity-email-to` inside 12773 | No email to key on. Store `sender_x_user_id` and `sender_profile_url`; `my_person_id` is filled later by the resolver CRON. |
| `card_descriptor` text like "from Emery Wells" | 12773 | "DM from @handle", "DM to @handle", "Group DM (4)" |
| `data_source_id` 14 (NylasEmail), master person source 47 / 48 | `data_source` (161) | New `data_source` row "X DM Sync". Rows 7 (Twitter) and 41 (Twitter Resolve) mean profile enrichment, not activity. |
| KNOWS fan-out per sender/recipient pair | `known/ingest/_fanout_email_pairs` (12781) | Same call, made by the resolver CRON once `my_person_id` is known, never by the loggers |
| Interaction-log counts read `email_activity` by `my_person_id` and `direction` | [Contacts Interaction Log](/guides/open-work/contacts-interaction-log) | Add `x_dm_activity` as a fourth activity source; `direction` is a first-class column from day one |

`email_activity` (597) columns for reference: `user_id`, `my_person_id`, `activity_type_id`, `card_descriptor`, `activity_timestamp`, `subject`, `grant_id`, `thread_id`, `message_id`, `snippet`, `unread`, `interlocutor_email`, `participant_count`, `data_source_id`, `temp_email_body`, `clean_message`. The DM table keeps every one that has an X analogue and drops `subject`, `unread` (X does not expose read state) and `interlocutor_email`.

## Source 1: legacy DMs (GET /2/dm_events)

Verified against docs.x.com and live on 2026-09-06.

| | |
| --- | --- |
| Endpoint | `GET https://api.x.com/2/dm_events` (all legacy conversations the user is in). Also `GET /2/dm_conversations/with/:participant_id/dm_events` for one 1-to-1 thread and `GET /2/dm_conversations/:dm_conversation_id/dm_events` for one group. |
| Auth | OAuth 2.0 user context. App-only bearer is rejected. |
| Scopes | `dm.read`, `tweet.read`, `users.read`; add `offline.access` for the refresh token |
| Window | Events from up to **30 days** ago. Newest first. No `since_id` or `start_time`. |
| Paging | `max_results` 1 to 100 (default 100); `pagination_token` from `meta.next_token` |
| `event_types` | `MessageCreate`, `ParticipantsJoin`, `ParticipantsLeave`; omit the parameter to get all three |
| `dm_event.fields` | `id`, `text`, `event_type`, `created_at`, `dm_conversation_id`, `sender_id`, `participant_ids`, `referenced_posts` (the harness still sends the older `referenced_tweets`, which X accepts), `attachments`, `entities` |
| `expansions` | `sender_id`, `participant_ids` (user objects in `includes.users`), `attachments.media_keys`, `referenced_tweets.id` |
| Rate limit | **15 requests per 15 minutes per user** on every DM lookup endpoint; `x-rate-limit-limit: 15` observed |
| Encrypted Chat | **Never returned.** New conversations, and old ones a user upgrades, are invisible here. Use Source 2. |

<Warning>
  **X only serves the last 30 days of legacy DM events.** There is no historical backfill through this API, and a sync that lapses for more than 30 days loses the gap permanently. The Nylas email import has no such limit.
</Warning>

## Source 2: encrypted chats (the X Chat API)

X ships a separate **X Chat API** plus a **Chat XDK** (Rust core; Go, Python, TypeScript/WASM, .NET and JVM bindings; Go package `github.com/xdevplatform/chat-xdk/go/chatxdk`, cgo over prebuilt static libraries). Verified against docs.x.com, the `xdevplatform/chat-xdk` Go example, and live calls on 2026-09-06.

**The rule that shapes everything:** each user's private keys live on their device, backed up in a PIN-protected store; X's guidance says "Servers must not hold user private keys" and "Never share [encryption PINs and private keys] with third parties, never put them on your servers." So a server can read **metadata** with the user's OAuth token, and **text** only if decryption happens in the Orbiter client on the user's device.

| Option | What we get | Where keys live | Verdict |
| --- | --- | --- | --- |
| **A. Server-side metadata** | Every chat event's timestamp, conversation, sender, direction, counterpart, group flag. No text. | Nowhere; nothing is decrypted. | **This spec.** Proven with 13404. Exactly what the interaction-log job counts. |
| **B. On-device text** | Full text, decrypted in the Orbiter web or mobile app with the WASM or native XDK after the user enters their XChat PIN there; the client posts decrypted events to an ingest endpoint that fills `text` on the Phase 1 rows. | On the user's device only. | **Phase 2**, step 9 of the build plan. Sync runs only while the client is open, and storing plaintext of end-to-end encrypted messages is a deliberate privacy decision. |
| **C. Server-side text with the user's PIN** | Full text on the server. | On Orbiter's servers. | **Do not build.** Contradicts X's developer guidance and the encryption promise users were given. |

Bot accounts (`POST /2/bots`) only see messages sent to the bot, so they do not apply.

**Endpoints used, all with the user's token**

| | Path | Notes |
| --- | --- | --- |
| Conversation list | `GET /2/chat/conversations?max_results=50` | Newest first. Items are `{id, type, participant_ids, is_muted}`; `participant_ids` excludes the caller. `meta.next_token` pages; `meta.has_message_requests` flags pending requests. **50 requests per 15 minutes per user.** |
| Conversation events | `GET /2/chat/conversations/{id}/events?max_results=100` | Newest first. `id`, `sender_id`, `created_at`, `is_trusted` and `conversation_id` in the clear; `encoded_event` is the ciphertext; `message_event_signature` carries the sender's signing key. `meta.conversation_key_events` are ciphertext key changes. **30 requests per 15 minutes per user.** |
| Handles | `GET /2/users?ids=<up to 100>&user.fields=username,name` | One batch per run resolves every participant and sender. |
| Real-time | `POST /2/activity/subscriptions` with `event_type` `chat.received`, `chat.sent` or `chat.conversation_join` and `filter.user_id` | Webhook payload: `conversation_id`, `sender_id`, `conversation_key_version` in the clear, `encoded_event` ciphertext, `event_uuid` for dedupe. CRC: HMAC-SHA256 of the token with the consumer secret. `chat.received` $0.010 per event; the other two not billed. |

Shape facts the capture confirmed:

1. **Ids come back in two spellings.** The list uses hyphens (`14382995-16826747`); the events use colons (`14382995:16826747`). Store the hyphen form so legacy and chat rows share one `dm_conversation_id`.
2. **`participant_ids` on the list excludes the caller**, so a direct conversation has exactly one participant and the counterpart needs no derivation.
3. **Paging can lie once.** The first events page said `has_more: true` with 6 events; the next two pages were empty. Stop on an empty page as well as on a missing `next_token`.
4. **Nothing in the metadata is sensitive to store**, but `encoded_event`, `conversation_token` and `message_event_signature` are bulky and useless without keys; the writer strips them before saving `raw`.
5. **Handles need one extra call.** Neither endpoint expands users; a single `GET /2/users?ids=` batch per run covers senders and counterparts. One of Mark's 140 walked conversations resolved to no user at all (deleted or suspended account); its rows keep the raw id.
6. **Chat history is not capped at 30 days.** The oldest event logged is from 2025-11-15, the month X switched DMs to Chat. The 30-day window belongs to the legacy DM endpoint only.
7. **Legacy-only threads return zero chat events.** Of the newest 140 conversations, 16 had chat events and 124 had none; the two sources do not overlap, so both loggers are needed and neither double-counts.

- **Pricing is pay-per-use.** docs.x.com lists DM event reads at $0.010 per resource, DM creates at $0.015 per request, the `chat.received` webhook at $0.010 per event, and `chat.sent`, `chat.conversation_join`, `dm.sent` and `dm.read` webhook events as not billed. No tiers.

**Lessons that go straight into the Go build**

- **Consent page rejects `dm.read` unless the app's permission level includes Direct Messages.** X shows only "Something went wrong". The level lives under the app's Settings in the developer console and does not rotate keys. Raised for the Orbiter app on 2026-09-06.
- **Client ID, callback and permission all live on one app.** A link built with one app's Client ID against another app's callback produced a code the second app could not exchange, with the same "Value passed for the authorization code was invalid" error as an expired code.
- **Authorization codes die in 30 seconds and are single-use.** Hand-pasting failed three times; a one-shot local listener that exchanged the code 2 seconds after the redirect worked first time. The Go callback must exchange in the request that receives it.
- **The console can mint a user token for the app owner.** Keys & Tokens → OAuth 2.0 Keys generates an access and refresh token for the owning account with chosen scopes; seeding the refresh token through `twitter-api-oauth-exchange` (13390) stores the rotated pair. Internal accounts only.
- **Xano CLI runner quirks.** `xano function run --json -` (stdin) delivers an empty input; use `-d key=value` or inline `--json`. Nested `function.run` calls fail in the runner, which is why all four functions read the token row themselves. `function create` drops `?=0` defaults on optional ints.
- **X Chat and legacy DMs disagree on id spelling and paging** (see Source 2). Normalise to hyphens and stop on empty pages.

      value = []
    }
  
    var $tweets {
      value = []
    }
  
    var $next_token {
      value = $input.pagination_token
    }
  
    var $pages {
      value = 0
    }
  
    var $keep_going {
      value = true
    }
  
    var $rate_limited {
      value = false
    }
  
    var $last_status {
      value = 0
    }
  
    var $last_body {
      value = null
    }
  
    var $last_headers {
      value = null
    }
  
    while ($keep_going) {
      each {
        var $page_url {
          value = $base_url
        }
      
        conditional {
          if ($next_token != "") {
            var.update $page_url {
              value = $base_url ~ "&pagination_token=" ~ $next_token
            }
          }
        }
      
        // Fetch one page of DM events
        api.request {
          url = $page_url
          method = "GET"
          headers = []|push:$auth_header
          timeout = 60
        } as $page_call
      
        precondition ($page_call.response.result != false) {
          error = "X dm_events request did not respond (timeout)"
        }
      
        var $page_status {
          value = $page_call.response.status
        }
      
        var $page_body {
          value = $page_call.response.result
        }
      
        var.update $last_status {
          value = $page_status
        }
      
        // Keep the raw body and headers of the last page for diagnostics (v1.1)
        var.update $last_body {
          value = $page_body
        }
      
        var.update $last_headers {
          value = $page_call.response.headers
        }
      
        conditional {
          if ($page_status == 429) {
            // Per-user window exhausted: stop and hand back what we have plus the resume token
            var.update $rate_limited {
              value = true
            }
          
            var.update $keep_going {
              value = false
            }
          }
        
          elseif ($page_status != 200) {
            var $page_err {
              value = "X dm_events request failed (HTTP " ~ $page_status ~ ") after " ~ $pages ~ " page(s): " ~ ($page_body|json_encode)
            }
          
            throw {
              name = "XApiError"
              value = $page_err
            }
          }
        
          else {
            var $page_data {
              value = $page_body|get:"data":null
            }
          
            conditional {
              if ($page_data != null) {
                array.merge $events {
                  value = $page_data
                }
              }
            }
          
            var $inc_users {
              value = $page_body|get:"includes.users":null
            }
          
            conditional {
              if ($inc_users != null) {
                array.merge $users {
                  value = $inc_users
                }
              }
            }
          
            var $inc_media {
              value = $page_body|get:"includes.media":null
            }
          
            conditional {
              if ($inc_media != null) {
                array.merge $media {
                  value = $inc_media
                }
              }
            }
          
            var $inc_tweets {
              value = $page_body|get:"includes.tweets":null
            }
          
            conditional {
              if ($inc_tweets != null) {
                array.merge $tweets {
                  value = $inc_tweets
                }
              }
            }
          
            var.update $pages {
              value = $pages + 1
            }
          
            var.update $next_token {
              value = $page_body|get:"meta.next_token":""
            }
          
            conditional {
              if (($next_token == "") || ($pages >= $input.max_pages)) {
                var.update $keep_going {
                  value = false
                }
              }
            }
          }
        }
      }
    }
  
    var $events_returned {
      value = $events|count
    }
  }

  response = {
    account        : $account
    scope          : $scope
    token_source   : $token_source
    events_returned: $events_returned
    events         : $events
    users          : $users
    media          : $media
    tweets         : $tweets
    pages_fetched  : $pages
    next_token     : $next_token
    rate_limited   : $rate_limited
    last_status    : $last_status
    last_body      : $last_body
    last_headers   : $last_headers
  }
}

## Open questions

1. **When to start Phase 2.** Message text for encrypted chats is scoped as step 9 of the build plan (Option B, on-device decryption) and needs the user's XChat PIN entered in the Orbiter client. Decide the trigger: a product need for the words, or a share of connected users on encrypted-only conversations.
2. **Retention of legacy text.** Email stores `clean_message`, so parity says store `text` for legacy DMs. Decide the retention and what happens on disconnect.
3. **`user_id` versus `entity_id`.** Tables 789 and 790 use `user_id` to match `email_activity`; the parent page adds `entity_id` to `x_oauth_token` for the same Orbiter user. Pick one name before the Go tables are created.
4. **Activity types.** `x_dm_from` and `x_dm_to` mirror email. Group chats could take a third (`x_dm_group`) if the interaction-log job wants to discount them the way `direct_emails` discounts cc-only mail.
5. **Message requests.** The conversation list flags `has_message_requests`; whether those conversations are included in the list, and whether they should count, needs one probe.
6. **Multiple X accounts per Orbiter user.** If allowed, the loggers run once per token row and `x_user_id` tells rows apart.
7. **Deleted or protected counterparties.** Store `sender_username` at capture time so the row still reads if the user lookup later fails.
