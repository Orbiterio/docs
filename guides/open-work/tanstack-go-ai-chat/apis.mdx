Proposed Go routes follow orbiter-backend conventions: `/v1/` prefix, `{data, error, meta}` envelope, `RequireWorkOS` auth, owner from session. The `suggestions` and `relationships` features already exist on `main` — request/result endpoints extend `suggestions` (`suggestions.suggestion_request`, Xano name kept) and `relationships`; the remaining surface is a proposed `copilot` feature for threads/messages. See [table mapping](/guides/open-work/tanstack-go-ai-chat).

**Canonical AlloyDB request table:** `suggestions.suggestion_request`. All Go request reads and writes below use this existing table.

<Info>
**Name collision:** Xano "outcomes" (suggestion requests/results) is not the Go `outcomes` feature (`outcomes.investment_theses` = investor profiles). Chat outcome endpoints are proposed under `/v1/copilot/outcomes/*` to keep them out of that feature.
</Info>

## Current Phase I authority

[Build Plan — Outcome Chat](/guides/open-work/tanstack-go-ai-chat/build-plan-outcome-chat#api-contracts) defines the complete current request/response, auth, retry, transaction and acceptance contracts. The Xano tables below are a historical inventory, not DTO templates. Go runs only in `orbiter-backend`; `orbiter-frontend` owns React UI and the TypeScript TanStack AI server, classification, tools, SSE and OpenUI validation. Backend access is through authenticated HTTP APIs.

Phase I uses `copilot_mode=outcome`, null beneficiary, null-class initial drafts and explicit user SUBMIT. It has four copilot tables (conversations/runs/messages/mutations), the existing `suggestions.suggestion_request`, and no generation/result writes. See the [refreshed table baseline](/guides/open-work/tanstack-go-ai-chat#phase-i-build-authority).

## Threads — shared transport

The historical Xano thread endpoints serve every surface. Their `thread_id` carries a surface prefix (`meeting_prep:<key>`, `leverage_loops:<request_id>`, `outcomes:<request_id>`) that the handler parses to route messages into the right transcript table. The current Go Phase I routes use structured IDs and only the outcome surface.

| Endpoint | What it does | Tables | Status |
| --- | --- | --- | --- |
| `POST /threads/ensure` | Find-or-create a `conversation` row by surface + thread key | `conversation` R/W | Implemented |
| `GET /threads` | List the user's threads | `conversation` R | Shell |
| `GET /threads/{thread_id}/messages` | Hydrate messages — resolves surface from `thread_id`, queries the matching transcript table | `conversation` + `copilot_chat_messages` / `leverage_loop_conversations` / `outcome_conversations` R | Implemented |
| `POST /threads/{thread_id}/messages` | Append messages; dedupes on (request, role, content) before insert; creates the surface conversation if missing | `conversation` R/W + transcript tables R/W | Implemented |

| `DELETE /threads/{thread_id}` | Delete/archive a thread | `conversation` W | Shell |

### Current Phase I Go thread routes

All IDs are scoped to the authenticated local user and exact nullable organization. Only `surface=outcome` is accepted. Signed TypeScript harness writes are required for run acquisition/checkpoint/finish; no client-authored assistant history.

| Route | Current contract |
| --- | --- |
| `POST /v1/copilot/threads/ensure` | Idempotent live-owner/org/surface/key ensure; no prefix parsing |
| `GET /v1/copilot/threads` | Owner-scoped cursor history, explicit archived filter |
| `GET /v1/copilot/threads/{id}/messages` | All pages at one transcript version; SDK IDs/parts, question and UI-library metadata |
| `POST /v1/copilot/threads/{id}/messages` | Lease/revision-guarded assistant checkpoints, preserving committed tool pairs |
| `PATCH /v1/copilot/threads/{id}` | Rename/archive/restore; reject live active run |
| `DELETE /v1/copilot/threads/{id}` | Idempotent soft archive; no row deletion |
| `POST /v1/copilot/threads/{id}/runs` | Accept fresh structured input or reload an original accepted retry input; return accepted turn index, inherited model/policy metadata and lease/effect state to harness only |
| `PATCH /v1/copilot/threads/{id}/runs/{run_id}` | Pin model metadata with `configure_execution`, renew or terminalize; fenced, idempotent writes |

The [model bake-off contract](/guides/open-work/tanstack-go-ai-chat/build-plan-outcome-chat#gemma-to-second-model-bake-off) defines the signed execution snapshot. Model calls and Gemma-to-continuation switching stay in TypeScript; Go stores the selection and accepted turn index.

See the build plan for exact payloads and errors. The TypeScript route uses Go acquisition responses for retry metadata; no new public run-detail endpoint is assumed.

### Current Phase I harness and Go split

The four registered model tools run as TypeScript `.server()` implementations in `orbiter-frontend`. The Go request row is authoritative; transcript tool results mirror committed state. No model tool can submit.

| Tool / action | Current behavior |
| --- | --- |
| `resolve_outcome` | Bounded TypeScript classifier call or accepted routing choice; commit route through Go context API |
| `update_context` | One consolidated, evidence-backed context effect per accepted turn; Go derives discrete count/slot/skip choices from accepted metadata |
| `re_route` | Explicit user correction; one reset effect per turn, followed by context extraction into the new schema |
| `handoff_to_akira` | Go atomically persists terminal exit and run; no external handoff |
| `submitOutcome` / internal `submit_outcome_request` | Trusted user-action handler only; omitted from `chat({tools})` and OpenUI runtime actions |
| Intake conversation | Existing TypeScript `chat()` route streams restricted OpenUI Lang; Go owns checkpoints and state |

| Go route | Current contract |
| --- | --- |
| `GET /v1/copilot/outcomes/classes` | Optional `registry_version`; immutable supported registry, explicit unavailable-version failure |
| `POST /v1/copilot/outcomes/drafts` | First accepted input binds one null-class request to the conversation before classification |
| `PATCH /v1/copilot/outcomes/drafts/{id}/context` | Atomic typed domain change + tool checkpoint + logical-turn receipt; no arbitrary JSON state replacement |
| `POST /v1/copilot/outcomes/dispatch` | Explicit user click, reviewed version, scope/readiness/no-active-run checks; frozen snapshot/receipt, status submitted |
| `GET /v1/copilot/outcomes/requests` | Owner/org-scoped bound outcome requests; no beneficiary/multi-mode result feed |
| `GET /v1/copilot/outcomes/requests/{id}` | Authoritative RequestView and public receipt for resume/review |

These six outcome routes plus the eight thread routes are the **14 Phase I Go routes**. There are no Go classify/interview/clarification endpoints. Public API details, exact receipt JSON and SQL acceptance checks live in the build plan, not a second contract on this page.

### Later-phase API candidates

Result nodes/actions/trajectories, beneficiary outcomes, files, contact actions and pitch profiles remain outside this build. Pitch profiles belong to `files`; future result reads use the existing suggestions tables. Their old Xano contracts may inform later designs but must not be copied into the current Phase I routes. Existing button-only `loop` behavior and tables remain unchanged.

## Notes

- Historical Xano interview endpoints call OpenRouter directly. The replacement AI orchestration runs in TypeScript inside `orbiter-frontend`; Go provides domain APIs and persistence only.
- Xano shell DTOs are not the Phase I contract: input ownership, retry, accepted answers, counts, receipts and submission were redesigned in the build plan.
- Context changes atomically write the request, assistant checkpoint and operation receipt in Go. The TypeScript harness awaits commit before emitting success.
- Browser completion means an actual authenticated chat → review → SUBMIT → reload journey and an independent assertion on the same `suggestions.suggestion_request` row.
