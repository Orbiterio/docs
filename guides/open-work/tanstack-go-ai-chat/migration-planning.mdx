## `outcomes`

One `suggestion_request` row carries the whole lifecycle (`copilot_mode = "outcome"`); `status` walks `draft` → `processing` → `suggestion` → `archived`.

### How Xano works now

| Step | Endpoint | What it does | Writes |
| --- | --- | --- | --- |
| Classify | `POST /outcomes/classify` | Pure JS keyword rules → `class_slug` + confidence. No LLM, no persistence | — |
| Clarify | `POST /outcomes/clarifications` | Clarification options for ambiguous prompts *(shell)* | — |
| Draft | `POST /outcomes/drafts` *(shell)* | Create/update request row: `class_slug`, `request_context` = prompt, `status=draft`, `llm_summary_context` = `{source, thread_id, run_id, draft}` | `suggestion_request` add/edit |
| Interview | `POST /outcomes/interview`, `/find-talent/interview` | Stateless LLM turn: rebuild transcript from client messages → per-class system prompt → OpenRouter → parsed JSON contract back | — |
| Context patch | `PATCH /outcomes/drafts/{id}/context` *(shell)* | Persist title / running summary / `request_context` (`context_version` guard) | `suggestion_request` edit |
| Submit metadata | `PATCH /outcomes/drafts/{id}/submit-metadata` | Persist `number_of_results` + `deliver_format` (enum-gated: `suggestions`/`csv`/`pdf`/`create collection`) | `suggestion_request` edit |
| Dispatch | `POST /outcomes/dispatch` | Guard owner + mode + not-archived. `draft` → `processing`, overwrites `llm_summary_context` with the dispatch blob (`approval_id`, `dispatch_mode`, `selected_result_ids`, `query`, `class_override`, `requested_n`, `constraints`, `tool_calls`, `previous_context`). Already `processing`/`suggestion` → no-op | `suggestion_request` edit |
| Files | `POST /outcomes/files` *(shell)* | Attach file/deck content to a draft | `suggestion_request_file` |
| Pitch profiles | `GET/PATCH/POST /outcomes/pitch-profiles/*` *(shells)* | Read/update profile fields, summarize after edits, latest | `files.pitch_profiles` |
| Transcript | `POST /threads/{id}/messages` | Appends each turn to the surface transcript table with (request, role, content) dedupe | `outcome_conversations` |
| Results | `GET /outcomes/requests`, `results`, `results/{id}/nodes|actions|trajectories` *(shells)* | Read request list + result cards | — |

### The interview contract (worth preserving verbatim)

Each turn returns one strict JSON object — `ready`, `summary`, `next_question`, `options[] {label,value}`, `allow_freetext`, `multi_select`, `missing_fields`, `awaiting_result_count`, `section`, `field`, `context`. Class-specific prompts key off `class_slug` (`find_investors`, `find_talent`, `find_customers`, `find_partners`, `find_advisors`, `find_journalists`, `find_cofounder`, `find_collaborators`, `find_speakers`, `find_warm_intros`, `find_co_investors`, `find_event_attendees`, `research_person`, `summarize_meeting`).

**Result-count gate** — when info is sufficient but count is unasked, the model must ask "How many matches do you want?" (options 20 / 100 / as-many) and set `awaiting_result_count`; once answered, `ready=true`.

Model today: `anthropic/claude-sonnet-4.6`, temp 0.2, max_tokens ~750, `data_collection: deny`.

### How we should implement it

| Area | Xano now | Go proposal |
| --- | --- | --- |
| Request row | `suggestion_request` | `suggestions.suggestion_request` — `copilot_mode = "outcome"` |
| Draft endpoints | `POST /outcomes/drafts` | `POST /v1/copilot/outcomes/drafts` — same upsert-by-`request_id` semantics |
| Interview | Stateless turn, client re-sends messages each call | Keep stateless turn contract, but read transcript from `copilot.messages` server-side when `conversation_id` given — client doesn't have to replay history |
| Prompts | Inline JS string-building per class in the endpoint | `assets/prompts/outcome-interview-*.md` per class + shared contract block; env-overridable paths per repo LLM-prompt policy |
| LLM call | `api.request` → OpenRouter inline | Platform LLM client (`internal/clients`); model pinned via config, not literal |
| Classifier | JS keyword rules in endpoint | `classify.go` in the feature — pure Go table of rules, unit-testable, no LLM |
| Idempotency | `thread_id`/`run_id`/`turn_id` stored inside `llm_summary_context` — not enforced | Real dedupe: `(conversation_id, run_id, turn_id)` unique on `copilot.messages`; `context_version`/`transcript_version` optimistic checks already in contract |
| Dispatch | Overwrites `llm_summary_context` with dispatch blob; status `draft`→`processing`; nothing consumes it yet | **Phase I:** update the `suggestion_request` row (persist the dispatch context) and flip status to `submitted` — no consumer yet. **Phase II:** add the API that sends the JSON payload to Universe; generated results return via `POST /v1/ingest/suggestions` |
| Transcripts | `outcome_conversations` keyed by `suggestion_request_id` | `copilot.messages` via `conversation_id` — conversation row carries `surface` + `request_id` link |
| Guards | Xano `precondition` errors (`notfound`, `accessdenied`, `badrequest`, `inputerror`) | Direct map to `apperror.NotFound`/`Forbidden`/`Validation` |

### Listing outcomes — drafts & archived

**Xano now:** `GET /outcomes/requests` is a contract shell. Inputs: `status`, `request_id`, `contact_id`, `limit`, `cursor`. The contract's own description says it returns "active/archived Outcome requests **and contact-card dedupe records**" — so the list doubles as the "does this contact already have a request?" check for contact cards.

**Go proposal — mirror the merged `GET /v1/leverage-loops` shape** (`listLeverageLoops`, already on `main`):

| Param | Behavior |
| --- | --- |
| `status` | One of `draft`, `submitted`, `processing`, `suggestion`, `archived`. **Empty excludes archived** — the default list is drafts + live outcomes |
| `query` | Case-insensitive substring on `request_panel_title` |
| `limit`, `cursor` | Keyset pagination — activity cursor `(updated_at, id)` via the feature's existing `cursor.go`; `pmw.Paged` meta |
| `contact_id` / `person_id` | Filter by beneficiary (leverage_outcome only) |
| `request_id` | Single-request lookup shortcut — or just `GET /v1/copilot/outcomes/requests/{id}` |

Response items embed the resolved person + non-archived suggestion children (same shape as the leverage-loops list item). The dedupe concern is served by `status != archived` filtering rather than a separate record type.

<Note>
Go added a `submitted` status Xano didn't have (`draft | submitted | processing | suggestion | archived` vs Xano's `draft | processing | suggestion | archived`) — it sits between draft and processing. Map Xano `processing` → `submitted`+`processing` when reading old rows.
</Note>

### Chat harness — TanStack AI + OpenUI

**The interview/classify loop does not live in Go.** It runs in the TanStack Start server route using `@tanstack/ai` + `@tanstack/ai-openrouter` (`openRouterText`, the stable `/v1/chat/completions` path). Every message is a fresh `chat()` call; the route handler picks the model adapter per request from conversation state. Go owns persistence, dispatch, and results — the harness calls thin Go endpoints through tools.

**Tools carry the structured state** (the Xano strict-JSON contract is retired):

| Tool | Replaces | Behavior |
| --- | --- | --- |
| `resolve_outcome` | `POST /outcomes/classify` | Intake model classifies against the canonical registry; writes `{outcome_type, summary, confidence}` — read newest-first |
| `update_context` | `PATCH .../context` + `submit-metadata` | Fills the null-initialized slot schema for the resolved class, turn by turn |
| `submit_outcome_request` | `POST /outcomes/dispatch` | Calls the Go submit endpoint — Phase I: persist + `status=submitted`; Phase II: also ships the payload to Universe |
| `re_route` | — | Working-model route correction; same schema, newest-first read means a fix takes effect next request |
| `handoff_to_akira` | — | Out-of-scope requests exit the harness |
| `draft_intro` | — | Server tool calling Sonnet internally; visible model stays fast, intro voice stays premium |

Route state lives in the message history as tool results — so **persistence middleware is mandatory**: `defineAIPersistence` loads the thread server-side (client-sent history can't be trusted — a forged `submit_outcome_request` result would skip phases), and threads map onto `copilot.conversations`/`copilot.messages`. Re-derive current route state into turn context each request so compaction can't summarize it away.

**Rendering: OpenUI replaces Crayon** (`@crayonai/react-core` is the legacy-era Thesys SDK — OpenUI is the actively developed successor). The model streams **OpenUI Lang** restricted to registered components; `@openuidev/react-lang`'s Renderer parses progressively. Structured fields (`ready`, `missing_fields`, `awaiting_result_count`, `class`) move to tool calls — the fence-stripping/brace-matching parse layer from Xano disappears entirely. `find_talent`'s dedicated skill becomes a dedicated prompt + component set, same mechanism.

**Model routing** (from the routing design doc — pending evals):

| Tier | Model | Notes |
| --- | --- | --- |
| Intake | `google/gemma-4-31b-it` on Cerebras **or** single-model DeepSeek V4.1 Flash | Decided by TTFT test (~1s threshold); single model wins on cache continuity + no voice seam |
| Working | `deepseek-v4.1-flash` (GLM 5.3 Flash as control) | Tool-call accuracy unproven — measured on 50 working-phase transcripts before commit |
| Drafting | Sonnet via `draft_intro` server tool | Internal call; swappable without touching the harness |

Two-turn intake cap: no route by turn two → submit `confidence: low` and let the general path handle it (replaces Xano's silent `find_investors` default — the `ask_back` sentinel is the explicit version of this).

### Decisions

- **Dispatch consumer (decided 9/14)** — the Universe suggestion engine consumes dispatched requests, and results return through `POST /v1/ingest/suggestions`. The engine isn't built yet, so it's phased: **Phase I** — dispatch only persists context and flips status to `submitted` (this is why the Go enum has `submitted` where Xano had `processing`); **Phase II** — add the endpoint that ships the JSON payload to Universe.
- **Classify (decided 9/14)** — **LLM classify**, not the Xano keyword ruleset. `POST /v1/copilot/outcomes/classify` makes one call against the canonical class enum above: `model: "google/gemma-4-31b-it"`, `provider: {"only": ["Cerebras"]}` via OpenRouter. Returns `{class_slug, confidence, ambiguous, reasoning}`; `ambiguous` lets the UI show a class picker before the interview starts. Stays stateless like Xano, but `request_id` is real — when supplied, `class_slug` persists on `suggestions.suggestion_request` and is correctable later.
- **`serendipity` mode (decided 9/14)** — stays in `suggestion_request.copilot_mode` alongside `outcome` and `leverage_outcome`, but has **no chat**: serendipity requests are initiated by agents autonomously, not through the interview/dispatch flow. No chat endpoints or prompts for it in this pass — the mode exists so agent-created requests have somewhere to land.
- **Delivery formats (decided 9/14)** — **removed entirely.** Suggestions always come back to the UI; alternate formats (CSV, collection, PDF) are chosen from the suggestion's context menu and become **Phase III APIs** — out of this spec's scope. `deliver_format` is not needed in backend tables (the column exists on `main` from `suggestions_001_init` — treat as unused, drop or ignore). Submit-metadata persists only `number_of_results` + constraints.
- **Pitch profiles (decided 9/14)** — owned by the `files` feature, not `copilot`. The `outcomes/pitch-profiles/*` contracts become `files` routes (e.g. `GET /v1/pitch-profiles/latest`, `PATCH /v1/pitch-profiles/{id}`, `POST /v1/pitch-profiles/{id}/summarize`); the chat UI calls them directly and the interview flow references `pitch_profile_request_id` in context only. No `/v1/copilot/outcomes/pitch-profiles/*` proxy — the domain logic already lives in `files/pitchprofile`.
- **Chat loop location (decided 9/14)** — the interview/classify loop runs in the **TanStack AI server route** (`chat()` + tools), not in Go. `outcomes/classify`, `outcomes/interview`, `outcomes/find-talent/interview`, `outcomes/clarifications` have no Go endpoint equivalent — they become harness tools (`resolve_outcome`, `update_context`, `re_route`, `handoff_to_akira`). Go owns `suggestion_request` persistence, `submitted` transitions, the class registry, and result reads.
- **OpenUI replaces Crayon (decided 9/14)** — chat rendering migrates from `@crayonai/react-core` to OpenUI (`@openuidev/react-lang` + registered components). The model emits OpenUI Lang; structured contract fields move to tool calls. The Xano JSON-contract parse layer is retired.

- **Harness wiring (decided 9/14)** — **keep `useChat` + OpenUI Renderer** over the AG-UI bridge. The generated system prompt goes into `chat()`; text parts pass through `@openuidev/react-lang`'s Renderer. The harness's state model is tool results in message history, so it needs what only `useChat` keeps: persistence middleware, resumable streams, tool-call lifecycle states, per-request adapter switching. The glue is ours to write — including a strict-mode check, since the OpenUI parser silently drops invalid lines.

## `leverage_outcomes`

The only difference between an `outcome` and a `leverage_outcome` is that a `leverage_outcome` is **for a specific person**:

- `outcome` — "I want to hire a chief of staff"
- `leverage_outcome` — "I want to help Katelyn hire a chief of staff"

A `leverage_outcome` carries a contact ID for the person the outcome is for. In Xano that's `suggestion_request.master_person_id` (`draft.for_master_person_id`); in Go it's `suggestions.suggestion_request.person_id` / `contact_id`.

<Note>
Xano's `POST /leverage-loops/interview` is the `leverage_outcome` flow — the endpoint name predates the rename. In the Go model, `leverage_outcome` is an outcome request with a beneficiary person, not a separate pipeline.
</Note>

### How Xano works now

Same `suggestion_request` row, `copilot_mode = "loop"`. Fewer steps than outcomes — no clarify, files, or pitch-profile endpoints.

| Step | Endpoint | What it does | Writes |
| --- | --- | --- | --- |
| Classify | `POST /leverage-loops/classify` *(shell)* | Loop intent classification with `target_master_person_id` context | — |
| Draft | `POST /leverage-loops/drafts` | Create/update request row: `class_slug` (default `get_advice`), `request_context` = prompt, `master_person_id` = `draft.for_master_person_id` **(the beneficiary — the person being helped)**, `status=draft` | `suggestion_request` add/edit |
| Interview | `POST /leverage-loops/interview` | Stateless LLM turn — richer context inputs than outcomes: `for_master_person_id`, `target_name`, `target_yaml_context`, `target_company_yaml_context`, `target_relationship_summary`, `self_yaml_context`, `self_company_yaml_context`, `current_summary` | — |
| Context patch | `PATCH /leverage-loops/drafts/{id}/context` | Same as outcomes: title / summary / context | `suggestion_request` edit |
| Dispatch | `POST /leverage-loops/dispatch` | Same guards (owner, `copilot_mode="loop"`, not archived); `draft` → `processing`, dispatch blob into `llm_summary_context` | `suggestion_request` edit |
| Transcript | `POST /threads/{id}/messages` | Per-turn append with dedupe | `leverage_loop_conversations` |
| Results | `GET /leverage-loops/requests`, `results/{id}/actions`, `results/{id}/trajectories` *(shells)* | Read request list + loop result cards | — |

### The leverage interview contract

Same strict JSON turn shape as outcomes, plus `structured_fields` — extracted snake_case values populated when `ready=true`. The system prompt injects the beneficiary context blocks — `[YOU]` (the helper), `[YOUR COMPANY]`, `[HELPING TARGET]` (name + `master_person_id` + YAML), `[TARGET COMPANY]`, `[YOUR RELATIONSHIP WITH TARGET]` — and writes every summary as "Helping {target}…". This is where `how_i_know` relationship data shows up inside the outcome flow.

Result-count gate options here are 20 / 100 / 500. Class list adds `get_advice` (the default) to the shared set.

### How we should implement it

| Area | Xano now | Go proposal |
| --- | --- | --- |
| Request row | `suggestion_request.master_person_id` = beneficiary | `suggestions.suggestion_request.person_id`/`contact_id` = beneficiary; `copilot_mode = "leverage_outcome"` (rename `loop`) |
| Draft endpoint | `POST /leverage-loops/drafts` — beneficiary via `draft.for_master_person_id` | Same `POST /v1/copilot/outcomes/drafts` as outcomes — beneficiary in the body decides mode |
| Interview context | Client passes self/target/company YAML + relationship summary per call | Server assembles it: `persons`/`companies` YAML builders + `relationships.relationships.relationship_summary` by (`user_id`, `person_id`) — no client-supplied context |
| Prompts | Inline JS per class | `assets/prompts/leverage-outcome-interview-*.md` |
| Results | `leverage_loop_conversations` transcript + result shells | `copilot.messages`; `suggestions.leverage_loop_*` tables already exist on `main` |

### Decisions

- **Result tables (decided 9/14)** — `leverage_outcome` shares the **unified `suggestion*` set** (`suggestion`, `suggestion_node`, `suggestion_trajectory`, `suggestion_action_group`, `suggestion_action`). Its results are outcome cards arriving via the same ingest path; `person_id` on the request row distinguishes them. The `leverage_loop_*` family stays scoped to the button-only leverage loop surface it was built for.
- **Suggestion views (decided 9/14)** — the UI has three suggestion views: **Leverage Loops**, **Outcomes**, **Serendipity**. Filter semantics: Leverage Loops view shows `leverage_loop` **and** `leverage_outcome` results (anything for-a-specific-person); Outcomes shows `outcome` only; Serendipity shows `serendipity` only. List endpoints need a mode filter that accepts multi-value buckets — `copilot_mode IN (leverage_loop, leverage_outcome)` for the leverage view, not just single-mode equality.
- **Endpoint paths (decided 9/14)** — the `leverage_outcome` chat flow folds into **`/v1/copilot/outcomes/*`**: a leverage_outcome is an outcome request + beneficiary `person_id` in the draft body, so the URL says the same. `/v1/leverage-loops/*` stays exclusively the button-only leverage loop surface already live on `main`. "Leverage Loops" as a *view* is a list filter (`copilot_mode IN (leverage_loop, leverage_outcome)`), not a routing concern.
