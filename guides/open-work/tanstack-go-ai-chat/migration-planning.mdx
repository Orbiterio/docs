## Current Phase I decisions

| Topic | Decision |
| --- | --- |
| Runtime | Go only in `orbiter-backend`; React and TypeScript TanStack Start in `orbiter-frontend` |
| AI loop | TypeScript `chat()` and `.server()` tools, including the bounded classifier; no Go LLM endpoints |
| Model routing | Gemma for the configured opening user turns, then a second OpenRouter model; policy pinned per conversation and execution metadata per turn |
| State authority | Go `suggestions.suggestion_request` and versioned intake; transcript/tool results are evidence and projections |
| Persistence | Four new copilot tables: conversations, runs, messages, mutations; atomic Go checkpoints and effect receipts |
| Draft | Created once on first accepted input, before classification, with null class and null beneficiary |
| Classifier | LLM call in TypeScript or deterministic accepted routing choice; Go validates registry membership and commits route |
| Routing cap | At most two unresolved routing turns; fallback to `plan_outcome` still needs real goal, slots, result count and user SUBMIT |
| Answers | Structured option/multi-select/free-text/skip metadata; Go-derived discrete values, source evidence for extraction |
| Retry | Go reloads original accepted input; logical-turn effects are not repeated under fresh run/tool IDs |
| Handoff | Durable exit message and completed run committed with state; no external agent contact |
| Submit | Dedicated authenticated user-action handler, never a model tool; reviewed version frozen in receipt/snapshot; status submitted |
| Phase I endpoint | Same approved request ID and receipt restored after refresh; no Universe/queue/results work |
| Registry/library versions | Separate pinned contracts; explicit lookup and historical rendering; no silent reinterpretation |
| Auth | Existing frontend GCP auth/refresh cookie path; Go verifies WorkOS bearer and current local account/org membership |
| OpenUI | Restricted intake library; headless parser on the TypeScript server; strict final syntax/tree policy |
| Unsent edits | Bounded session-local presentation cache; never authoritative intake or a new server table |
| Verification | Agent operates the real browser flow and independently checks the final database record; every acceptance row has evidence |

### Chat harness — TanStack AI + OpenUI

Keep the existing `/api/tanstack-ai-chat` TypeScript server route, `useChat`, and OpenUI Renderer. The route loads Go-authoritative history, performs model/tool orchestration, commits changes through signed Go APIs, and streams output. A TypeScript backend client calls Go over HTTP; no Go runs inside the frontend.

Use the installed APIs documented in the build plan: `systemPrompts`, UIMessage text `parts[].content`, and `lang-core@0.2.4` `generatePrompt` / `PromptSpec`. `defineAIPersistence` is not an installed core export. Do not attach a competing transcript saver. Checkpoint recovery is the Phase I promise; exact stream replay requires a separately specified chunk log. A completed stream alone cannot enable an unsaved question or SUBMIT.

Generate prompt spec and parser schema from the same small versioned component library. Keep OpenUI runtime queries/actions disabled and validate the final source/tree explicitly. `onStateUpdate` is unsent presentation state; explicit accepted answers and the user-controlled SUBMIT action have separate contracts.

### Model selection and later work

Start intake on an exact configured Gemma model, then switch to a continuation candidate via OpenRouter after the configured number of accepted user turns. The TypeScript server owns routing; Go stores `copilot.runs.execution_metadata` and returns the accepted turn index. Retries preserve the selected model, conversation policy and original turn. See the [model bake-off contract](/guides/open-work/tanstack-go-ai-chat/build-plan-outcome-chat#gemma-to-second-model-bake-off).

Exact model IDs, the opening-turn threshold and the winning continuation candidate remain to be selected. Compare candidates with repeated OpenUI multiple-choice/multi-select/free-text/skip flows through explicit Submit and independent SQL verification. Both models perform Phase I intake; working-phase agents, `draft_intro`, code mode, Gateway, memory and agent orchestration remain deferred.

Phase II can add Universe dispatch and generation; Phase III may add alternate delivery formats and result actions. `deliver_format` remains in the existing table and is untouched. No destructive migration, mode rename, or legacy-row reinterpretation is part of Phase I.

## Deferred surfaces

`leverage_outcomes`, `how_i_know` and `meeting_prep` need later build plans. Existing `loop` is the button-only mode and must not be bulk-renamed. Future beneficiary outcomes may share outcome APIs only through an explicit contract extension; Phase I rejects non-null `person_id`. Serendipity remains agent-created and has no chat in this build. Relationship/meeting AI orchestration will also stay in TypeScript; Go supplies context/domain APIs.

### Historical `leverage_outcomes` source flow

The only difference between an `outcome` and a `leverage_outcome` is that a `leverage_outcome` is **for a specific person**:

- `outcome` — "I want to hire a chief of staff"
- `leverage_outcome` — "I want to help Katelyn hire a chief of staff"

A `leverage_outcome` carries a contact ID for the person the outcome is for. In Xano that's `suggestion_request.master_person_id` (`draft.for_master_person_id`); in Go it's `suggestions.suggestion_request.person_id` / `contact_id`.

<Note>
Xano's `POST /leverage-loops/interview` is the `leverage_outcome` flow — the endpoint name predates the rename. In the Go model, `leverage_outcome` is an outcome request with a beneficiary person, not a separate pipeline.
</Note>

#### Historical interview contract

Same strict JSON turn shape as outcomes, plus `structured_fields` — extracted snake_case values populated when `ready=true`. The system prompt injects the beneficiary context blocks — `[YOU]` (the helper), `[YOUR COMPANY]`, `[HELPING TARGET]` (name + `master_person_id` + YAML), `[TARGET COMPANY]`, `[YOUR RELATIONSHIP WITH TARGET]` — and writes every summary as "Helping {target}…". This is where `how_i_know` relationship data shows up inside the outcome flow.

Result-count gate options here are 20 / 100 / 500. Class list adds `get_advice` (the default) to the shared set.


Future result views may combine beneficiary outcome and button-only loop results, but their mode names and filters require a separate compatibility decision. Phase I lists only its bound `outcome` drafts/submitted requests; it does not hydrate result children, pitch profiles, files or beneficiary context.
