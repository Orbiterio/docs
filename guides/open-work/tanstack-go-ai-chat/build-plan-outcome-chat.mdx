| Build now | Do not build in this phase |

| Outcome thread creation, history, resume, rename, archive | Meeting prep, How I Know, beneficiary interviews, agent-created serendipity |

- All Phase I conversational turns use the configured intake model. Resolving a class does **not** enter the working phase or switch to a working model.
- `deliver_format` remains untouched. Alternate delivery formats belong to later context-menu APIs.
- A rendered component, model claim, tool result, or two-turn cap can never authorize submission.

## State contract

### One source of truth

Go's `Request` row and `intake_context` are authoritative for class, slot values, result-count choice, readiness, and status. The transcript is durable conversational evidence, not an authorization store. Tool results echo committed state for the model; never reconstruct submission authorization exclusively from them.

The browser receives `RequestView` after every committed mutation and on reload. The model cannot set `ready`, `status`, ownership, approval, version counters, or timestamps.

### State machine

| State | Entry condition | Permitted next action |
| --- | --- | --- |
| `unrouted` | Draft created; `class_slug=null` | Classify the user's goal |
| `clarifying` | Classifier returns `ask_back` | Ask one clarification; do not store `ask_back` as a class |
| `collecting` | Real class selected; required slots unresolved | Ask next required question or accept a user correction |
| `awaiting_result_count` | Required slots resolved; count mode is `unasked` | Ask 20 / 100 / as-many question |
| `ready` | Required slots resolved, count answered, nonempty summary | Show review and enable user SUBMIT when no run is active |
| `submitted` | Explicit submit command passes Go validation | Freeze intake; show receipt and “Submitted; generation is not started in this phase” |
| `handed_off` | Unsupported request; user offered an exit | Persist a visible exit message; no external handoff call and no submission |

`phase` is computed from committed state, not a second mutable status column. `Request.status` remains `draft` until the explicit submit operation. Archiving a thread only hides the thread; it does not mutate the request or delete a transcript.

### Two-turn routing cap

A routing turn is one newly accepted user message while the class is unresolved. Retries, tool calls, and assistant messages do not increment it. Permit at most two classifier attempts per unresolved route:

1. First ambiguous result: keep `class_slug=null`, persist `routing_attempts=1` and the clarification, ask it. Each clarification option's `value` is a routing class slug.
2. If the next user turn is a selection of one of those persisted options, route to that slug with `confidence=1`, `routing_source=user_selection`, and **no classifier call**. Otherwise call the classifier with `routing_attempt=2`; the prompt instructs it to be decisive on attempt 2.
3. Second ambiguous result: select existing `plan_outcome` with `confidence=0` and `routing_source=cap_fallback`; disclose that it is a general plan and collect its generic slots.
4. The result-count gate and explicit SUBMIT still apply. Unknown facts remain unknown. A message with no usable goal requires a goal answer; the cap does not make it ready.

`routing_source` is null before routing, then `classifier`, `user_selection`, `cap_fallback`, or `user_correction` after `re_route`. `routing_attempts` counts unique committed unresolved-routing decisions, including a validated option selection; it does not count provider retries or later corrections. On a retry of an already-recorded input turn, reuse its saved route/clarification rather than increasing the counter or calling the classifier again. This cap bounds classification, not the entire interview.

### Slot and count representation

All live-class slot values are trimmed strings or null. Keep monetary amounts, currencies, timelines, and location qualifiers as stated by the user; this intake build does not normalize money or resolve location IDs.

```json IntakeContext v1 example
{
  "schema_version": 1,
  "registry_version": "outcome-intake-v1",
  "routing_attempts": 1,
  "routing_turn_ids": ["user-costa-rica-1"],
  "routing_source": "classifier",
  "clarification": {"question": null, "options": []},
  "confidence": 0.97,
  "summary": "Buy a vacation house in Costa Rica within six months.",
  "slots": {
    "transaction_type": {"status": "filled", "value": "buy"},
    "location": {"status": "filled", "value": "Costa Rica"},
    "budget_range": {"status": "filled", "value": "USD 600,000–800,000"},
    "property_type": {"status": "filled", "value": "House"},
    "timeline": {"status": "filled", "value": "Within six months"},
    "financing": {"status": "filled", "value": "Cash"},
    "use": {"status": "filled", "value": "Vacation home"}
  },
  "result_count": {"mode": "exact", "value": 20},
  "handed_off": false
}
```

- Slot status: `empty`, `filled`, or `skipped`. `empty`/`skipped` require `value=null`; `filled` requires 1–2,000 characters. Unknown keys are invalid. “I don't know,” “no preference,” and “skip” may explicitly mark a slot skipped; the model may not silently skip one.
- Required slots are resolved by `filled`, or by an explicit user `skipped` only when the registry's `CanSkip` is true. The generic `goal` and real-estate `transaction_type` are non-skippable. A greeting is not a goal; a generic fallback with an empty/skipped goal cannot become ready. `missing_fields` contains unresolved required keys in registry order; `skipped_fields` is shown in the review and retained at submission.
- Count: `{mode:"unasked", value:null}`, `{mode:"exact", value:1..200}`, or `{mode:"all", value:null}`. Reject all other combinations. Go derives `number_of_results`: exact value, otherwise null. **Null alone never means the question was answered.** “All” is a preference, not a promise of unlimited results.
- `confidence` is always a number from 0 through 1, or null before classification. Do not mix numeric scores with `"high"`/`"low"` strings.
- Go records at most two unique accepted user-message IDs in `routing_turn_ids`; `routing_attempts` is their count. Persist the latest classifier question/options in `clarification` for reload, and clear them after routing or handoff. A repeated classification for an already-recorded turn reuses its receipt; it is not a new attempt.
- `request_context` holds the original accepted ask and is not overwritten by running summaries. `intake_context.summary` holds the current 1–4,000-character summary.
- Re-routing resets the slot set and count to `unasked`, clears any clarification/question binding, sets `routing_source=user_correction`, invalidates readiness, and increments the version. Preserve the original ask/transcript, not arbitrary old slots. Set the new goal-form summary from the explicit correction and re-extract applicable facts into the new schema. Changing `transaction_type` within real estate similarly clears price, financing, and result-count answers before re-extraction, since purchase totals, sale prices, and rent are not interchangeable.

**Readiness formula:** `status=draft`, dispatchable class, nonempty original goal and summary, no unresolved required slots, count mode not `unasked`, and `handed_off=false`. Go re-evaluates this under the submission lock.

## Data model

### Request columns and additive migration

The inspected request table already has UUID `id`, nullable `user_id`, nullable `organization_id`, `copilot_mode`, `status`, nullable `class_slug`, nullable beneficiary `person_id`, title fields, nullable TEXT `request_context`, nullable INT `number_of_results`, JSONB `llm_summary_context` (default `[]`), nullable `deliver_format`, BOOLEAN `modified`, and timestamps.

- For this surface, owner and org come from authenticated scope; `person_id` is null. Do not confuse WorkOS IDs with local UUIDs.
- Titles are TEXT NOT NULL DEFAULT `''`; cap each at 500 characters. `modified` becomes true on post-create changes; `updated_at` gets the database time.
- Do not overwrite legacy `llm_summary_context` to store an approval ID. The new receipt stores the approved snapshot separately.
- Add these fields in the next **suggestions-owned** migration, not an unreviewed ALTER hidden in `copilot_001_init`. Do not use `IF NOT EXISTS` to conceal an incompatible existing column.

### Conversations and messages

Create the next `copilot` migration after the request migration. These are proposed tables, not claims about the deployed database. All SQL row IDs use `ids.NewUUIDv7()`; SDK message and run IDs remain opaque strings.

Enums and JSON shapes are Go service validators, not SQL enum types or enum CHECK constraints. This phase accepts only `surface=outcome`, conversation `person_id=null`, UI roles `user|assistant`, and message status `streaming|complete|interrupted|error`. The frontend's existing `surface="outcomes"` maps explicitly to Go `"outcome"`; do not change other legacy surfaces globally.

`copilot.runs` provides a durable single-writer lease; an in-memory mutex is insufficient across frontend/server replicas. `copilot.mutations` stores retry receipts for draft creation, context changes, and submit. Do not store credentials in either table.

### Ownership and transaction boundary

All chat reads/writes require the caller's local user ID **and** exact organization scope (`IS NOT DISTINCT FROM` for null). A null org is a separate personal scope, never a wildcard. For non-null orgs, verify current membership; a still-valid token does not prove current membership. Once bound, the conversation and request must have the same user and org. Org changes do not move a draft between tenants.

Thread history is private to its creator. Organization-shared result visibility is the separate suggestion-feed contract, not permission to read another member's intake transcript. Missing, foreign-user, and foreign-org resources all return 404 on these new routes.

Expose a **new** `suggestionspub` contract; it did not exist in the inspected tree. These are interface signatures to implement alongside typed DTOs, not a claim that these methods already exist:

```go RequestStore contract
 type RequestStore interface {
  WithTx(tx pgx.Tx) RequestStore
  CreateDraft(ctx context.Context, in CreateDraftParams) (SuggestionRequest, error)
  PatchContext(ctx context.Context, in PatchContextParams) (SuggestionRequest, error) // context_version guard
  Submit(ctx context.Context, in SubmitParams) (SuggestionRequest, error)             // owner + state guard, approval replay
  Get(ctx context.Context, scope RequestScope, id uuid.UUID) (SuggestionRequest, error)
  List(ctx context.Context, in ListParams) (RequestPage, error)
 }
```

`RequestScope` contains local `UserID` and nullable `OrganizationID`; every Params type embeds it. `WithTx` binds the owning service/repository to the supplied transaction without committing it. `copilot` opens the transaction, locks the conversation, then calls the transaction-bound suggestions service. Suggestions SQL stays in `suggestions`; copilot SQL stays in `copilot`. Never open independent nested transactions and call the result atomic. Composition-root code only wires services.

Global lock order: conversation → active run → request → message/receipt. Every mutating route follows that order. Do not hold a database transaction open during an LLM/network call.

Audit **all existing request writers**, not just these new routes. Legacy leverage-loop update/delete/dispatch handlers must reject this versioned outcome mode before mutation. Otherwise an alternate endpoint could bypass the new readiness, receipt, and submitted-immutability checks. Add regression tests for those paths without changing their behavior for legacy `loop` requests.

## Class registry

The suggestions-owned registry supplies validation and deterministic readiness through `suggestionspub`. A read-only Go endpoint exports it to the harness so prompt generation, tools, and frontend types do not maintain three independent lists. Use version `outcome-intake-v1`; pin a draft to its registry version and fail visibly if that version is unavailable.

```go Registry entry
 type ClassEntry struct {
  Slug        string     // canonical class_slug
  Label       string     // display label
  PromptAsset string     // frontend prompt asset key for the class question set
  Slots       []SlotSpec // required intake slots
  Live        bool       // has a dedicated question set this build (else generic fallback)
 }
```

`SlotSpec` contains `Key`, `Label`, `Question` (strings), `Required`, `CanSkip` (booleans), and nullable `RequiredIf:{key,equals}`. A slot is required when `Required=true` or its single `RequiredIf` equality matches a filled slot; this is declarative registry data, not an expression to evaluate from model output. All values use the slot representation above. The 25 dispatchable slugs and the `ask_back` sentinel are listed in the classifier prompt below. Validate exact membership on both draft changes and submit; `ask_back` is never a request class.

| Class | Required slots in question order | Optional or conditional slots |
| --- | --- | --- |
| `purchase_real_estate` | `transaction_type`, `location`, `budget_range`, `property_type`, `timeline` | `financing` required only for `transaction_type=buy`; `use` optional |
| `find_investors` | `stage`, `sector`, `check_size`, `raise_amount` | `geography` |
| `find_talent` | `role`, `seniority`, `location`, `skills` | `comp_range` |
| `find_customers` | `icp_industry`, `company_size`, `geography`, `buyer_role` | None |
| Every other dispatchable class | `goal`, `target_description`, `constraints` | None |

`CanSkip=false` for generic `goal` and real-estate `transaction_type`; all other slots permit an explicit skip. `transaction_type` is a canonical string `buy`, `sell`, or `lease`, extracted from the goal when clear. For financing use `Required=false`, `RequiredIf:{key:"transaction_type",equals:"buy"}`; otherwise it remains empty and is neither asked nor included in `missing_fields`. All other `RequiredIf` values are null. A class change initializes every registered slot to `{status:"empty",value:null}` before extracting known facts.

Use these default English questions in deterministic fallbacks; localize the copy without changing keys or option values:

| Slot group | Questions, in the same order as above |
| --- | --- |
| Real estate | “Are you buying, selling, or taking a long-term lease?”; “Where is the property, or where are you looking?”; “What price or rent range and currency should I use? For rent, include the payment period.”; “What kind of property is involved?”; “When do you want to complete the transaction?”; **buy only** → “Will you use cash or financing?” |
| Investors | “What stage is your company at?”; “What sector are you in?”; “What check size and currency are you targeting?”; “How much are you raising, and in what currency?” |
| Talent | “What role are you hiring for?”; “What seniority do you need?”; “Where can this person work, including remote options?”; “Which skills are essential?” |
| Customers | “Which industries fit your ideal customer?”; “What company size are you targeting?”; “Which geographies matter?”; “Who is the buyer or decision-maker?” |
| Generic | “What result do you want?”; “Who or what would help you get there?”; “What constraints or timing should I consider?” |

Do not re-ask facts already supplied. Optional slots do not block ready and are not automatically asked after required slots. Offer **Other** and free text, plus an explicit **Skip for now** when appropriate. If the user skips, preserve that uncertainty in the review.

## API contracts

### Transport, authentication, and errors

All Go routes are under `/v1/copilot`. Use per-feature `api/copilot.openapi.yaml` with unique operation IDs and root `$ref`s. Use OpenAPI 3.1 nullable types and the repository's Go enum validators, not OpenAPI enums or `oneof` tags.

Every route uses `RequireWorkOS`; extract the local user with `pmw.OrbiterUserID(r)` and optional local org with `pmw.OrbiterOrgIDOrNil(r)`. Reuse current-account/membership checks through public feature interfaces. Never accept `user_id`, `organization_id`, WorkOS IDs, or bearer tokens in JSON bodies.

**Trusted writes:** POST messages, run start/update, draft creation, context patch, and dispatch additionally require a verified **harness signature** from the TanStack server. A WorkOS bearer alone is insufficient. Otherwise a user could insert assistant/tool-result parts and make forged history appear server-authored.

Proposed signature contract to implement on both servers:

- A secret-manager-provisioned `COPILOT_HARNESS_SIGNING_KEY` of at least 32 random bytes, server-only on both services; never in a `VITE_` env or a prompt.
- Headers `X-Copilot-Timestamp` (Unix seconds) and `X-Copilot-Signature` (hex HMAC-SHA256). Signed UTF-8 input is timestamp, uppercase method, exact escaped path including query, hex SHA256 of raw body bytes, and hex SHA256 of the WorkOS bearer token, separated by newline characters with no final newline.
- Go verifies the MAC in constant time, accepts at most 60 seconds of clock skew, verifies WorkOS independently, and uses durable operation/message receipts to handle replays. Sign the bytes actually sent; do not reserialize before hashing.
- The BFF strips inbound signature headers and signs only validated operations through typed helpers. No arbitrary signed-path proxy. Missing key fails closed. Deployment must provision this prerequisite; do not invent a working credential or weaken auth to get tests passing.

Cookie-authenticated frontend mutations require same-origin checks and the existing CSRF protection. Go endpoints do not use CORS as an authorization boundary.

**Success envelope:** `{data, error:null, meta:{requestId}}`. Most examples below show only `data` or only the request body, explicitly labeled. Cursor lists put `{items,total,next_cursor}` inside `data` using `pmw.OK`; do not confuse `pmw.Paged`'s page-number metadata with cursor pagination.

```json Full error envelope — version conflict
{
  "data": null,
  "error": {
    "code": "CONFLICT",
    "message": "Draft changed; reload before applying this edit.",
    "details": [
      {"field": "reason", "issue": "version_conflict"},
      {"field": "context_version", "issue": "4"}
    ]
  },
  "meta": {"requestId": "req-example"}
}
```

Use `apperror.Error.Fields` for these details; its existing middleware formats them as `{field,issue}` pairs. No new top-level `version_conflict` error code. Reason values below live in a detail whose field is `reason`.

| HTTP / code | Conditions |
| --- | --- |
| 400 `VALIDATION_FAILED` | Malformed IDs/JSON, unknown fields, invalid class/slot/count, invalid cursor, unsupported surface |
| 401 `UNAUTHORIZED` | Missing/expired WorkOS token or missing local user claim |
| 403 `FORBIDDEN` | Invalid harness signature; revoked organization membership before resource lookup |
| 404 `NOT_FOUND` | Missing resource or wrong user/org scope |
| 409 `CONFLICT` | `version_conflict`, `idempotency_conflict`, `run_in_progress`, `lease_expired`, `thread_archived`, `stale_question`, `retry_not_latest`, `not_ready`, `already_submitted`, `invalid_state` |
| 500 `INTERNAL` | Unexpected infrastructure failure; safe message, no raw provider/SQL output |

Reject unknown JSON fields. Bound ordinary JSON writes to 64 KiB, message checkpoints to 256 KiB, user text to 8,000 characters, IDs to 128 ASCII characters, and checkpoint batches to 20 messages. Enforce limits before allocating/decoding; oversized bodies use `VALIDATION_FAILED`. Use database UTC timestamps, RFC3339 on the wire. All nullable response fields remain present. `next_cursor` is the empty string on the last page. Resource IDs are UUID strings; SDK IDs and other opaque identifiers are case-sensitive, untrimmed, and URL-encoded as individual path segments. Never concatenate an unescaped SDK run ID into a route.

### Shared response types

Stored status is `active|complete|failed|cancelled`; a read projects an expired active lease as `failed` without writing. `latest_run` is the newest attempt, even if it failed before a request was bound, so a refreshed client can find the input to retry. New writes normalize expired state under the lock before checking `run_in_progress`.

This is the compact, server-constructed projection used as the model tool output and as JSON text inside its persisted tool-result part. The Go HTTP response still returns the full RequestView to the harness/UI; do not store that whole object repeatedly inside every model tool result. Failed tools use SDK error state and a safe error code, not a successful result with invented ready fields.

### Thread ensure, list, rename, archive

`POST /threads/ensure` requires `surface="outcome"` and `surface_key` (a client-generated UUID string retained across retry); optional `title` is null or 1–500 characters. Do not accept client-supplied `surface_ref_id` or `person_id`. Ensure finds by exact user/org/surface/key. Under a uniqueness race, read and return the winner. No metadata changes on replay.

```json Thread ensure request
{"surface":"outcome","surface_key":"01994430-1000-7000-8000-000000000001","title":null}
```

Return 201 `{conversation,created:true}` on creation or 200 `{conversation,created:false}` on replay. An archived match returns 409 `thread_archived`; never silently create a second thread or unarchive it. Resume known threads through history; a new **+** gets a new key.

`GET /threads`: `surface` only accepts `outcome`; `archived` defaults false; `limit` defaults 20, range 1–50; cursor orders `(updated_at DESC,id DESC)`. Return `{items:[Conversation],total,next_cursor}`. Cursor encodes filter/scope fingerprint and the last tuple; reject reuse with a different filter or scope. Activity ordering is not a snapshot: de-duplicate IDs in the client and reload the first page after mutations.

`PATCH /threads/{id}` accepts nonempty subsets of `{title,archived}`. Null title clears it; omitted means unchanged; `archived` must be a boolean. `true` sets `archived_at` once, false restores it. Reject during an active run. Return 200 `Conversation`.

`DELETE /threads/{id}` applies the same archive operation; repeat archive succeeds. Return 200 with `data:null`, never 204. Request status is unaffected.

### Run start and recovery

`POST /threads/{id}/runs` is harness-only. After auth/scope checks, it locks the conversation and checks existing run/message identities. An identical completed run returns its replay before any new-turn status guard. For a new attempt, normalize any expired run under the global lock order, reject an archived/handed-off/non-draft request, validate answer metadata, then insert the run and persist the new **user** message before any LLM call. A not-yet-bound conversation is allowed; a bound request in `submitted`, `processing`, `suggestion`, or `archived` is not.

```json Start-run request
{
  "run_id": "run-costa-rica-1",
  "message": {
    "id": "user-costa-rica-1",
    "role": "user",
    "parts": [{"type":"text","content":"I want to buy a house in Costa Rica"}]
  },
  "retry_of_run_id": null,
  "answer_to": null,
  "selected_option": null
}
```

Only one user text part is allowed from the browser in this phase. Persist its SDK ID as `message_id`; never accept browser tool/system/assistant parts. `turn_id` is that original user message's ID for all attempts and assistant messages responding to it. A fresh run cannot reuse an existing user-message ID except through the explicit retry contract. Assign sequence numbers while holding the conversation lock and increment `transcript_version` once per committed change.

Persist `{retry_of_run_id,answer_to,selected_option}` in `runs.input_metadata`. The semantic input hash covers normalized `message`, `answer_to`, and `selected_option`, not only visible text. Same run ID with changed answer metadata, retry parent, or normalized text conflicts. A retry must copy the original normalized text and answer metadata; do not reconstruct them from current UI state.

Return 201 `{run_id,lease_token,lease_expires_at,transcript_version,accepted_message_id}`. Leases last 60 seconds, renewed every 20 seconds. A second active caller, including the same run ID, gets 409 `run_in_progress`; a duplicate must not start another model call. A completed identical run returns 200 `{run_id,status:"complete",replayed:true}` for hydration, not a new lease. Same ID with different canonical input → `idempotency_conflict`.

On disconnect/provider failure, persist the latest checkpoint and mark the run `cancelled`/`failed` with its assistant message `interrupted`/`error`. If the process dies, the next acquisition marks the expired run failed and unfinished messages interrupted under the same lock. A late writer carrying its old lease token is rejected, even if it still has a valid WorkOS session.

Explicit retry uses a **new** run ID and `retry_of_run_id` pointing to the **latest** failed/cancelled attempt of the latest accepted user turn. Reject retry of an older turn after newer input has been accepted (`retry_not_latest`). Normalize an expired active retry parent to failed first. The semantic input hash and answer metadata must match the accepted parent; the already-consumed question is not revalidated as a fresh answer. Reuse the immutable user message without appending it or consuming another routing attempt. Assistant messages in the retry get fresh SDK IDs; older terminal messages are immutable. Rebuild from committed Request state and completed tool pairs. This is regeneration, not byte-for-byte SSE resumption.

`PATCH /threads/{id}/runs/{run_id}` accepts `{lease_token,action}` where action is `renew`, `complete`, `fail`, or `cancel`. After auth/scope and stored-token checks, identical terminal retries return 200 without an active/expiry requirement; a different terminal action conflicts. Only a currently active, unexpired lease may renew or transition. Map complete/fail/cancel to complete/failed/cancelled. Fail/cancel atomically marks unfinished messages error/interrupted. Completion requires at least one terminal assistant response or trusted fallback and no streaming messages. Return 200 `{run_id,status,lease_expires_at}`. Never mark a run complete before its transcript saves succeed.

A shared `expireRunIfNeeded` operation runs under the conversation lock before start, archive, or submit checks. It fences the expired run and terminalizes unfinished messages; lease expiry must not leave SUBMIT or archive permanently blocked until another chat message is sent. Cleanup after an aborted browser request uses a separate bounded five-second server context, not the already-aborted provider signal.

### Message read and checkpoint

`GET /threads/{id}/messages`: `limit` default 50/max 200, ascending `sequence` cursor. Return `{items:[PersistedMessage],total,next_cursor,transcript_version,high_water_sequence,latest_run}`. On the first page fix a high-water sequence and transcript version in the cursor; if revisions change during pagination, return `CONFLICT` and restart. Load **all** pages before constructing model history.

`PersistedMessage` contains `message_id`, `sequence`, `revision`, `status`, `role`, `parts`, nullable `question_context`, `run_id`, `turn_id`, `created_at`, `updated_at`. Hydrate SDK `UIMessage.id` from `message_id`, not the database row's UUID. User message content is immutable; a streaming assistant message keeps its identity while its revision advances.

TanStack `UIMessage` has no `role:"tool"`. Tool results are parts on an assistant message. `TextPart` uses **`content`**, not `text`; a tool result references `toolCallId`, not a tool name:

```json Assistant message example
  "id": "assistant-costa-rica-1",
  "role": "assistant",
```

`POST /threads/{id}/messages` accepts `{run_id,lease_token,expected_transcript_version,messages}`. Each message includes `message_id`, `expected_revision` (0 for insert), `revision` (next integer), `status`, `role`, `parts`, `question_context` (object or null), and `turn_id`. This endpoint inserts/updates assistant messages only; user input is written only by run start.

- Validate the whole batch before writing; duplicate IDs are a 400. In-progress tool-call arguments may be incomplete strings; require valid schema-matching JSON at `input-complete` and before executing a tool, not on every streaming prefix. Completed results must pair with the matching call ID/name in that run.
- Preserve previously committed complete tool-call/result pairs unchanged in every later assistant revision. Only the transactional context endpoint may introduce a successful state-changing tool result; plain text checkpoints cannot replace it, erase it, or claim a new mutation succeeded. Define and test a shared `OutcomeToolResult` serializer for the Go-constructed result and the SDK mirror.
- Lock and check scope/lease. A terminal message is immutable. A streaming assistant message may be replaced only by its owning active run, with the next revision; prefix checkpoints are not additional messages.
- Check an all-identical replay before enforcing expected transcript/message versions; return its existing IDs/versions without writes. Otherwise enforce `expected_transcript_version` plus every expected message revision atomically. Canonical content includes `question_context`. Same ID/revision with different content → `idempotency_conflict`; a stale version → `version_conflict`. Never silently `DO NOTHING` on changed content.
- Allocate consecutive sequence values for new IDs in batch order; retain sequences on updates. Commit the whole batch and transcript-version increment together.
- Return 200 `{stored_count,updated_count,replayed_count,transcript_version,last_message_id}`; obtain the real existing final ID on replay. If every item is identical, return success without touching timestamps or versions.

### Question identity and option selections

Persist nullable `question_context` on the terminal assistant message: `{question_id,context_version,field,text,options,multi_select,allow_freetext,can_skip}`. `field` is `class_slug`, `result_count`, or a current registry slot. Go validates the field against the current phase (the next missing required slot, routing clarification, or unanswered result count) and creates `question_id="q:" + hex_sha256(JSON([conversation_id,message_id,context_version,field]))`; IDs claimed by model text are not authoritative. The BFF validates presentation props, and Go stamps the committed question metadata. At most one question is actionable per assistant turn.

Each option is `{label,value}` with a distinct value. Routing options mirror the persisted classifier clarification and use registry slugs. Result-count values are exactly `20`, `100`, and `all` as strings; slot option values are bounded answer strings. Other/free-text and skip are trusted shell controls, not extra classifier classes. `can_skip` is false for routing, result count, and non-skippable slots.

Every question-control answer supplies `answer_to:{message_id,question_id,context_version}`. A routing-option click also supplies `selected_option:{question_id,value}`; otherwise `selected_option=null`. Validate under the run-start lock **before** accepting the input: the referenced message is the latest terminal question, version matches the current draft, no newer user message has consumed it, and the selected value exists. A selection must match both question IDs and `field=class_slug`; non-null `selected_option` without `answer_to` is invalid. New unbound free-text goals/corrections use both fields null.

```json Routing option answer
{
  "answer_to": {
    "message_id": "assistant-clarify-1",
    "question_id": "q:54f263a8554482133053064007bf4d881c6bcc3645374612de787e76a5a1df01",
    "context_version": 1
  },
  "selected_option": {
    "question_id": "q:54f263a8554482133053064007bf4d881c6bcc3645374612de787e76a5a1df01",
    "value": "find_talent"
  }
}
```

The example's hash is illustrative; use the actual stored ID. For a valid routing click, Go derives the accepted user text and initial goal summary from the stored option label, not browser-supplied text or the bare slug. Record both the chosen value and label in the run metadata. It is explicit user intent (`confidence=1`), not a model's confidence estimate. Required slot answers still need extraction and review; a class selection is not readiness. A stale or reused question returns 409 `stale_question` without a new run/message. Explicit retry uses the original accepted metadata rather than trying to consume the old question again.

The trusted shell renders controls from stored `question_context`, including after reload or a presentation fallback. While streaming, controls are disabled; activate them only after the terminal checkpoint and run completion. An advisory model `SubmitReadyCard` is not a question context or approval.

### Draft creation and binding

`POST /outcomes/drafts` is harness-only and requires an active run. Create on the **first accepted user message**, before classification, with `class_slug=null` so even an ambiguous conversation has a request ID. `operation_id` is stable for the conversation's draft creation.

```jsonc Create-draft request
{
  "conversation_id": "01994430-1000-7000-8000-000000000002", // required; binds copilot.conversations.surface_ref_id
  "run_id": "run-costa-rica-1",
  "lease_token": "01994430-1000-7000-8000-000000000003",
  "operation_id": "draft-create",
  "class_slug": null,
  "person_id": null, // beneficiary support is deferred; non-null is rejected in Phase I
  "request_context": "I want to buy a house in Costa Rica",
  "request_panel_title": "New outcome"
}
```

The JSONC annotations above are explanatory; actual HTTP requests are JSON without comments. Source the original ask from the accepted user message, not model-generated prose. `person_id` may be omitted or null only. In this phase `class_slug` must be null on creation; route changes initialize the real class and its slots atomically afterward. Do not expose an uninitialized pre-seeded-class path.

One transaction: scope/lease checks → replay receipt lookup → create draft via `suggestionspub` → bind conversation's `surface_ref_id` → save receipt. Initial `context_version=0`, routing attempts 0, confidence null, empty summary/slots, count `unasked`, `handed_off=false`. Set `copilot_mode=outcome`; no class is silently defaulted to investors.

Return 201 `{request:RequestView,created:true}` or 200 identical receipt replay. A conversation can never be rebound to a new request; create a new thread for a new outcome. Different payload with the same operation ID → 409. Injected failures must leave neither a half-created draft nor a dangling binding.

### Context mutations

`PATCH /outcomes/drafts/{id}/context` takes `conversation_id`, `run_id`, `lease_token`, `operation_id`, `context_version`, and a discriminated `change` object. Classify/slot/handoff operations are signed server operations; clients cannot PATCH arbitrary `intake_context` or set readiness.

| `change.kind` | Allowed fields and semantics |
| --- | --- |
| `route` | Either `{routing_source:"classifier",classification}` with the validated six-field classifier result, or `{routing_source:"user_selection"}` with no model-generated class/summary. For user selection, Go derives the choice from this run's accepted option metadata. `cap_fallback` is computed only in Go. An `ask_back` result leaves class null and stores the clarification; a real class initializes all slots. Record the original input turn so retries cannot consume another attempt. |
| `slots` | `slots` map of registered slot updates, optional `summary`, optional title fields, optional `result_count`. Merge by slot key, never replace the whole slot map. Omitted means unchanged; null is allowed only where explicitly defined. |
| `reroute` | `class_slug` (real class), `reason` (1–500 characters), `confidence`, nonempty goal-form `summary`; requires an existing class and explicit user correction evidence in persisted history. Reset slots/count as specified above; set `routing_source=user_correction`. |
| `handoff` | `reason`, `summary`; set `handed_off=true`, keep request status draft, revoke readiness. No external Akira call. |

```jsonc Re-route change object
{
  "kind": "reroute",
  "class_slug": "find_job", // only via re_route
  "reason": "The user is looking for employment, not hiring.",
  "confidence": 0.98,
  "summary": "Find a chief-of-staff job"
}
```

Also require `checkpoint: {expected_transcript_version, message_id, expected_revision, parts, tool_call_id}`. The signed harness supplies the current assistant parts including the complete tool call, but not a claimed result for this call. Go validates the call ID/name and declared input schema, then checks the mapping to `change`: `resolve_outcome` has empty model arguments while its result comes from the bounded classifier or accepted selection; the other tools map their validated arguments to slots/reroute/handoff changes. These are not a byte-equality comparison between `{}` and classifier output. Apply the request change, construct its successful `OutcomeToolResult`, and append the paired result part to that checkpoint. An existing completed result for this call must match a replay receipt, not be overwritten.

The copilot coordinator commits the request update, assistant checkpoint, and operation receipt in **one transaction** through the transaction-bound suggestions service. It increments the assistant revision and transcript version with the checkpoint, using the same sequence/revision rules as POST messages. The model never supplies its own successful result. Serialize text checkpoints and tool commits so they consume the latest returned transcript/message revisions.

Use `operation_id="route:" + hex_sha256(JSON([input_message_id]))` for unresolved routing, `draft-create` for binding, and `"tool:" + hex_sha256(JSON([run_id,tool_call_id]))` for other tool mutations. Submit receipts use `"submit:" + approval_id`. Hash arrays with no whitespace, UTF-8, no Unicode normalization, and lowercase hex; the prefix plus 64 hex characters fits the 128-character ID limit even when both SDK IDs are maximal length. On regeneration of a turn already in `routing_turn_ids`, do not register `resolve_outcome`; use the committed route/clarification and start a fresh presentation message. Network retries retain the original operation ID/body and do not fabricate a new tool call.

Guards for a new mutation: correct binding/scope/lease; request status draft and not handed off; compatible registry version; `context_version` equals stored; change validates against the class. `route` requires an unresolved class; `slots` and `reroute` require a real class; only `handoff` can end either route state. Keep allowed transitions in Go rather than relying on which tools the model happens to call. On success increment `context_version` once, set `modified=true`, update timestamps, compute `RequestView`, and return `{request:RequestView,transcript_version,message_revision}`. A no-op user-confirmed update may still increment once, but a replay must not.

Check a matching operation receipt **before** the version guard: same operation ID and canonical payload returns its stored response with no additional writes even if the version has since advanced. Changed payload with that ID is 409. On a true version conflict, stop the turn and reload; **do not automatically reapply stale slots over the user's newer answers**.

Canonical payload hashing is performed in Go only: decode validated typed DTOs, reject duplicate JSON keys and trailing JSON values, preserve field presence wherever omission means unchanged, and normalize defaults only where omission and null are explicitly equivalent. Then deterministically encode the typed operation. Preserve array order, normalize equivalent numeric spellings through typed numeric fields, and exclude transport timestamp/signature, trace IDs, lease token, and attached checkpoint. Compare same-operation replays against the stored digest before any write. A retry may return historical receipt versions; the harness reloads current RequestView/message versions before its next mutation rather than overwriting its local state with stale receipt data. Do not put data in a receipt before all operation writes commit.

### Explicit submission

`POST /outcomes/dispatch` is called by a dedicated authenticated frontend submit action, not by a model-visible tool. The internal server helper may retain the name `submit_outcome_request`, but it is **not in `chat({tools})`**.

```json Submit request
{
  "conversation_id": "01994430-1000-7000-8000-000000000002",
  "request_id": "01994430-1000-7000-8000-000000000004",
  "approval_id": "01994430-1000-7000-8000-000000000005",
  "expected_context_version": 4
}
```

The browser creates and retains `approval_id` for that click until success is known. It is an **idempotency key**, not proof of authorization. Authorization is the authenticated, CSRF-checked submit action; readiness and the approved version are checked again in Go. Do not accept `approved:true`, raw `constraints`, arbitrary `tool_calls`, or replacement slot values on dispatch.

Under the conversation/request locks:

1. Verify user/org scope and request binding; reject archived thread or non-outcome mode.
2. If an identical submission receipt exists for this approval ID and version, return the original receipt. Different body with the same approval ID → `idempotency_conflict`; a different approval ID after submission → `already_submitted`.
3. For a new submit, normalize any expired run first, then require no live active run, `status=draft`, matching context version, and server-computed ready. A stale version requires the user to review the updated summary and click again with a new approval ID.
4. Copy the authoritative approved snapshot into `submission_receipt`, set status submitted, `modified=true`, and update the timestamp. Persist the operation receipt in the same transaction. Never overwrite the original ask or legacy `llm_summary_context`.
5. Return 200 `SubmissionReceipt`. Do not publish an event, call Universe, create suggestion children, mark processing, or call the existing loop dispatch method.

Identical replay returns the original submitted receipt even if a later phase has moved the request to processing. Obtain current status through GET; do not misreport a replay as a second dispatch. Scope checks still apply after membership revocation. Two concurrent clicks must yield one transition, with the second receiving replay or conflict according to its approval ID.

### Request resume and list

`GET /outcomes/requests/{id}` returns `RequestView` after owner/org/bound-thread checks. It does not hydrate result children. A legacy request without this chat's versioned intake state is not automatically resumable; return 409 `invalid_state` rather than constructing invented slots.

`GET /outcomes/requests`: fixed `copilot_mode=outcome` and only requests bound to this chat's conversations. Optional `status` accepts known request statuses; empty excludes archived requests. `query` is trimmed title substring (max 200 characters; SQL parameters, escape LIKE wildcards). `limit` defaults 20/max 50. Use `(updated_at DESC,id DESC)` cursor with scope/filter fingerprint and return `{items:[RequestView],total,next_cursor}`. A thread archive hides it from the default chat list; restore through the thread history's archived filter.

Do not implement multi-mode result feeds, beneficiary filters, or serendipity through this endpoint in Phase I. Index the actual owner/org/mode/order query after checking its execution plan; the old user/mode/status index does not automatically cover every new filter/order combination.

## Classifier system prompt

**This is the copy-ready prompt**, proposed for the frontend asset `src/features/tanstack-ai-chat/prompts/outcome-classifier.md`. It is not installed or deployed by this documentation change. The classifier is a separate bounded, non-streaming structured-output call inside the server implementation of `resolve_outcome`; Go performs no LLM call.

The server passes a user-role JSON payload containing only `original_goal`, persisted `user_messages` in order, `routing_attempt` (`1` or `2`, from `routing_attempts + 1`), and `current_class_slug` (always null in Phase I; reserved so a later re-route validator can reuse this prompt unchanged). No client-supplied system messages, route state, credentials, or external YAML. The quoted user material is data, not instructions. Use temperature 0, a 600-output-token cap, a 15-second timeout, and a strict local output validator. Retry once on invalid structure; after a second failure show a recoverable error, not a fabricated class or an auto-submit.


### Per-turn execution

1. Authenticate and validate the newest user input. Start the Go run, durably accepting the input and acquiring its lease before calling the provider.
2. Create/bind the draft on the first user turn; otherwise GET its authoritative `RequestView`. Load all transcript pages at a consistent version. Rebuild provider messages from trusted UI parts using the installed SDK converter. The accepted user message is already in that history: do not append it again. Preserve completed tool pairs even in an interrupted assistant message; exclude only interrupted text and unmatched/incomplete calls. The RequestView remains authoritative when replayed transcript content is older.
3. Load the pinned registry. Compose server prompts from base voice, intake rules, generated OpenUI library instructions, and current Go state. Runtime credentials and lease tokens stay in server closures, not prompts/tools' model-visible input schemas.
4. Select the configured intake adapter once for this request. Call `chat()` with `.server()` tools and OpenUI text output. Remove the legacy `outputSchema: turnResultSchema` **only for this Go outcome path**, not for existing other surfaces.
5. Persist each successful tool mutation and its checkpoint before exposing its successful result to the stream. During visible text streaming, flush accumulated text at the earlier of 1 second or 2 KiB, with at most one checkpoint in flight and another on terminal events. Coalesce pending text while a save is in flight; these are target intervals, not a data-loss bound during a storage outage. Renew the lease every 20 seconds; abort on renewal failure.
6. Validate the completed OpenUI response. Save the final assistant message, then complete the run, then allow SUBMIT. Invalidate request/history queries after commit.
7. On cancellation/error, save the last valid checkpoint and fail/cancel the run. If cleanup cannot complete, lease expiry provides recovery. Keep the original error visible; never show a successful submit or a silent blank turn.

**Recovery promise:** accepted user messages and committed tool mutations survive refresh. At most the last uncheckpointed text tail can be lost. This phase restores checkpoints and permits explicit regeneration; it does not promise exact token replay or resumable SSE without an event log and deployment support.

### Server tools

Model-visible input schemas are strict and deliberately exclude request IDs, user/org scope, lease tokens, approval IDs, context versions, and operation IDs. The server injects those from its active run and latest committed response. Serialize mutations in one run; do not let parallel tool calls race the same context version. Bound a turn to six tool executions, four intake-model steps, and 60 seconds total including classifier retries. On a limit, preserve committed state and return a recoverable error. Do not recursively call the intake model from inside a tool; only `resolve_outcome` makes the bounded classifier sub-call.

| Tool | Model input | Server behavior |
| --- | --- | --- |
| `resolve_outcome` | `{}` | For an accepted routing-option click, PATCH `change:{kind:"route",routing_source:"user_selection"}` and let Go derive the choice — no classifier call. Otherwise make the bounded classifier call and PATCH `change:{kind:"route",routing_source:"classifier",classification}`. Return Go's OutcomeToolResult. No third automatic unresolved classifier call and no reclassification of a committed retry turn. |
| `update_context` | `{slots?,summary?,request_panel_title?,request_header_title?,result_count?}` | At least one field required. Validate slot keys/types and support in accepted user messages, then PATCH `kind=slots`. Return OutcomeToolResult; a skip of a non-skippable field fails in Go. |

| `handoff_to_akira` | `{reason,summary}` | Persist `kind=handoff`, return a visible exit state. This phase does not claim Akira received anything. |

`submit_outcome_request` is a user-action server helper only. `draft_intro`, general network tools, arbitrary SQL/HTTP, and memory mutation tools are not registered here.

## Acceptance tests

### Golden end-to-end journey

1. Click **+**; ensure creates one empty outcome conversation. Refresh/retry of the same key creates no duplicate.
2. Send “I want to buy a house in Costa Rica.” The user message and null-class draft persist before classification. Classifier selects `purchase_real_estate`; confirmation is visible; transaction type, location, and property type are extracted without asking again.
3. Answer “USD 600,000–800,000; a vacation house; within six months; cash.” Extract the remaining required slots and optional use; do not ask each already answered question again.
4. Answer **20 great matches**. RequestView reports ready and version N; the trusted review includes the exact count and supplied details.
5. Click **SUBMIT**. Go accepts expected version N, saves one immutable receipt, and marks submitted. There is no Universe call, event publication, or generation billing.
6. Refresh. History and the submitted receipt are restored; further intake mutations are rejected. Both the user and reviewer can verify the actual request row, not just a success-looking component.
