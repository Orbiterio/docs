## Deltas vs. earlier drafts of this plan

These corrections come from reconciling this page against the merged table designs — apply them, don't resurrect the old shapes:

1. **`copilot.conversations` carries `surface` + `surface_key` + `surface_ref_id`**, not a `mode` column. The Xano `meeting_prep:<id>` / `outcomes:<id>` / `leverage_loops:<id>` prefix-parsed `thread_id` is decomposed into structured fields; the Go side never parses prefixes.
2. **`suggestion_request` needs `context_version` and `intake_context`** — the optimistic-check counter and the slot-schema JSONB the PATCH context contract requires. Verified absent from the merged `suggestions_001_init`/`002_ingest` DDL — `copilot_001_init` adds both (recheck the working branch anyway; if equivalents landed meanwhile, use those names).
3. **`copilot_mode` values are `outcome | leverage_outcome | leverage_loop | serendipity`** — Xano's `loop` is renamed `leverage_outcome`; `leverage_loop` stays for the button-only surface; `serendipity` has no chat.
4. **`status` adds `submitted`** between `draft` and `processing`: `draft | submitted | processing | suggestion | archived`. Xano's `processing` maps onto `submitted`+`processing` when reading old rows.
5. **`copilot.messages` stores `parts` jsonb** (the full TanStack AI parts array — text, tool-call, tool-result parts), not Xano's `content`/`template_name`/`template_props` triple.
6. **Idempotency is enforced, not stored-and-hoped:** unique `(conversation_id, run_id, turn_id)` on `copilot.messages`; `(request_id, approval_id)` semantics on dispatch.
7. **`suggestion_request` is the ingest parent row — one table, two names by layer.** `suggestions_002_ingest` states it outright: "The guide's `request_suggestion` IS `suggestion_request` (`user_id` = `requested_by`, `copilot_mode` = `suggestion_type`, `person_id` = `beneficiary`)". AlloyDB has **only** `suggestions.suggestion_request` — the chat draft row and the delivery parent are the same row, and `suggestion_batch.suggestion_request_id` references it. `request_suggestion`/`request_suggestion_id` remains the correct name on the **wire** (v2 ingest envelope, OpenAPI `SuggestionBatch`) — keep using it there; don't create a second table and don't rename anything. The [Suggestion Delivery and Tables](/guides/open-work/suggestion-delivery-and-tables) DDL block showing a `request_suggestion` table is the doc-side alias, not a second physical table.

## Data model

### Existing — `suggestions.suggestion_request`

Already on `main` — verified against `suggestions_001_init` + `suggestions_002_ingest` merged DDL below. The chat surface uses these columns; writes to `suggestions.*` go through `suggestionspub` — `copilot` never touches the schema directly.

| Column | Type (as merged) | Chat use |
| --- | --- | --- |
| `id` | uuid PK (uuidv7 via `ids.NewUUIDv7()`) | `request_id` on the wire |
| `user_id` | uuid → `users.users`, `ON DELETE SET NULL` | Owner; session-derived, never client-supplied. Ingest reads it as `requested_by` |
| `organization_id` | uuid → `organizations.organizations`, `SET NULL` (added by `002`) | Caller's active org; nullable — don't block draft creation if unresolvable |
| `copilot_mode` | text NOT NULL | `outcome` default; `leverage_outcome` when `person_id` set. Ingest reads it as `suggestion_type` |
| `status` | text NOT NULL DEFAULT `'draft'` | `draft` → `submitted` on dispatch |
| `class_slug` | text NULL | Written by drafts/classify; `ValidClassSlug()`-validated |
| `person_id` | uuid → `persons.persons`, `SET NULL` | Beneficiary — set ⇒ `leverage_outcome`. Ingest reads it as `beneficiary_contact_id` |
| `request_panel_title` | text NOT NULL DEFAULT `''` | List title; `update_context` may revise |
| `request_header_title` | text NOT NULL DEFAULT `''` | Card header; set at draft create, revised on patch |
| `request_context` | **text** NULL | The user's canonical ask — prompt text + running summary as **text**. Slots can't live here; that's what `intake_context` is for |
| `llm_summary_context` | jsonb NOT NULL DEFAULT `'[]'` | Dispatch blob written at submit; see dispatch spec |
| `number_of_results` | int NULL | Result-count gate answer. Existing DTO validators cap at `1–200`; `20` / `100` / `null` = "as many as you can find" |
| `deliver_format` | text NULL | **Unused — never write it** |
| `modified` | **boolean** NOT NULL DEFAULT `FALSE` | A "modified since create" **flag**, not a timestamp — set `TRUE` on any post-create write |
| `created_at` / `updated_at` | timestamptz NOT NULL DEFAULT `now()` | Standard |

Existing index `suggestion_request_user_mode_status_idx (user_id, copilot_mode, status, updated_at DESC)` already covers the requests-list query — no new index needed there.

**Delta to add in `copilot_001_init` (verify against live migration first):**

```sql
ALTER TABLE suggestions.suggestion_request
  ADD COLUMN IF NOT EXISTS context_version integer NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS intake_context  jsonb   NOT NULL DEFAULT '{}';
```

- `context_version` — optimistic concurrency counter for `PATCH …/context`; increments on every accepted patch.
- `intake_context` — the resolved class's slot schema as filled so far: `{"slots": {"<slot_key>": {"value": <any>, "status": "empty|asked|filled"}}, "awaiting_result_count": bool, "confidence": "low|medium|high|null"}`.

### New — `copilot` schema (`copilot_001_init`)

```sql
CREATE SCHEMA copilot;

CREATE TABLE copilot.conversations (
  id             uuid PRIMARY KEY,                       -- ids.NewUUIDv7()
  user_id        uuid NOT NULL REFERENCES users.users(id) ON DELETE CASCADE,
  surface        text NOT NULL,                          -- outcome | leverage_loop | meeting_prep
  surface_key    text NOT NULL,                          -- caller's thread key; client-minted uuid per new thread
  surface_ref_id uuid,                                   -- typed link: suggestion_request.id when surface='outcome'
  person_id      uuid,                                   -- optional person context (beneficiary / attendee)
  title          text,
  archived_at    timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT copilot_conversations_key_uq UNIQUE (user_id, surface, surface_key)
);
CREATE INDEX copilot_conversations_user_idx
  ON copilot.conversations (user_id, updated_at DESC, id DESC);
CREATE INDEX copilot_conversations_ref_idx
  ON copilot.conversations (surface, surface_ref_id)
  WHERE surface_ref_id IS NOT NULL;

CREATE TABLE copilot.messages (
  id              uuid PRIMARY KEY,                      -- ids.NewUUIDv7()
  conversation_id uuid NOT NULL REFERENCES copilot.conversations(id) ON DELETE CASCADE,
  role            text NOT NULL,                         -- user | assistant | tool
  parts           jsonb NOT NULL,                        -- full TanStack AI parts array for the message
  run_id          text,                                  -- harness run; idempotent-retry key
  turn_id         text,                                  -- per-turn id; idempotent-retry key
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX copilot_messages_conv_idx
  ON copilot.messages (conversation_id, created_at, id);
CREATE UNIQUE INDEX copilot_messages_turn_uq
  ON copilot.messages (conversation_id, run_id, turn_id)
  WHERE run_id IS NOT NULL AND turn_id IS NOT NULL;
```

Rules the SQL can't express (enforce in Go): `surface`/`role` membership via `ValidX()`; `surface_ref_id` semantics per surface (`outcome` → `suggestion_request.id`, `leverage_loop` → its request id, `meeting_prep` → the meeting context id); `parts` is always a JSON **array** of part objects. `NULLS NOT DISTINCT` is not needed — `surface_key` is `NOT NULL`.

### `POST /v1/copilot/threads/ensure`

Find-or-create a conversation. Lookup order: `(user_id, surface, surface_key)` when `surface_key` sent; else `(user_id, surface, surface_ref_id)` when `surface_ref_id` sent; else create with a caller-supplied or server-minted `surface_key`.

```json Request
{
  "surface": "outcome",
  "surface_key": "9f1c2a44-…-client-uuid",
  "surface_ref_id": null,
  "person_id": null,
  "title": null
}
```

```json 200 data
{
  "conversation": {
    "id": "uuid", "surface": "outcome", "surface_key": "…",
    "surface_ref_id": null, "person_id": null, "title": null,
    "archived_at": null, "created_at": "…", "updated_at": "…"
  },
  "created": true
}
```

| Error | When |
| --- | --- |
| 400 `validation` | `surface` not in `ValidSurface()`; neither `surface_key` nor `surface_ref_id` on create path |
| 403 `forbidden` | `surface_ref_id`/`person_id` resolves to a row owned by someone else |
| 409 `conflict` | `surface_key` collision returning an `archived_at`-set row (treat as validation if simpler — pick one, document it) |

### `POST /v1/copilot/threads/{id}/messages`

The persistence middleware's write path. Max 50 messages per call.

```json Request
{
  "run_id": "run-…",
  "messages": [
    { "turn_id": "t-1", "role": "user",      "parts": [ {"type": "text", "text": "I want to buy a house in Costa Rica"} ] },
    { "turn_id": "t-2", "role": "assistant",  "parts": [ {"type": "tool-call", "name": "resolve_outcome", …}, {"type": "text", "text": "…"} ] },
    { "turn_id": "t-3", "role": "tool",       "parts": [ {"type": "tool-result", "name": "resolve_outcome", "result": {…}} ] }
  ]
}
```

Insert each row `ON CONFLICT (conversation_id, run_id, turn_id) DO NOTHING`. Role validated against `user|assistant|tool`; `parts` must be a JSON array. Touch `conversations.updated_at = now()` in the same transaction.

```json 200 data
{ "stored_count": 2, "duplicated_count": 1, "last_message_id": "uuid" }
```

A retried call with identical keys returns 200 with `stored_count: 0` and the original `last_message_id` — never 409.

### `POST /v1/copilot/outcomes/drafts`

Creates the `suggestion_request` draft. Called by the harness after `resolve_outcome` (or lazily inside `update_context` when no `request_id` exists yet).

```json Request
{
  "conversation_id": "uuid",          // optional; binds copilot.conversations.surface_ref_id
  "class_slug": "purchase_real_estate",
  "person_id": null,                  // beneficiary uuid — presence ⇒ leverage_outcome
  "request_context": "I want to buy a house in Costa Rica",
  "request_panel_title": "Buy a house in Costa Rica"
}
```

Writes: `copilot_mode = person_id ? "leverage_outcome" : "outcome"`, `status = 'draft'`, `class_slug` (validated — `ask_back` rejected here), `context_version = 0`, `intake_context` initialized to the class's null slot schema, `organization_id` from the caller's active org (nullable — don't block draft creation when org can't be resolved). If `conversation_id` is present: verify it exists, is owned, `surface = 'outcome'`; then set its `surface_ref_id = request.id` in the same transaction.

```json 201 data
{
  "request": {
    "id": "uuid", "status": "draft", "copilot_mode": "outcome",
    "class_slug": "purchase_real_estate", "person_id": null,
    "request_panel_title": "…", "request_context": "…",
    "intake_context": {"slots": {…}, "awaiting_result_count": false, "confidence": null},
    "context_version": 0, "number_of_results": null,
    "created_at": "…", "updated_at": "…"
```

| Error | When |
| --- | --- |
| 400 `validation` | bad `class_slug` (details carry the registry list); `class_slug = "ask_back"`; `person_id` malformed |
| 404 `notfound` | `conversation_id` missing/not-owned |
| 409 `conflict` | conversation already bound to a different live (`status != archived`) request |

### `PATCH /v1/copilot/outcomes/drafts/{id}/context`

The `update_context` tool's write. Partial update — absent fields unchanged.

```json Request
{
  "context_version": 3,
  "request_panel_title": "Costa Rica house",
  "request_context": "…running summary…",
  "intake_context": {"slots": {"location": {"value": "Costa Rica", "status": "filled"}, …}, "awaiting_result_count": true, "confidence": "high"},
  "number_of_results": 20,
```

```json 200 data
{ "request_id": "uuid", "context_version": 4, "updated_at": "…" }
```

### `POST /v1/copilot/outcomes/dispatch`

The `submit_outcome_request` tool's write. Phase I: persist + flip status — **no downstream call**.

```json Request
{
  "request_id": "uuid",
  "approval_id": "client-minted-uuid",
  "dispatch_mode": "submit",
  "constraints": {},
  "tool_calls": []
}
```

Guards (single transaction): owner → 404; `copilot_mode IN ('outcome','leverage_outcome')` → else 409 `invalid_mode`; `status`:

| Stored status | Same `approval_id` recorded | Different/missing `approval_id` |
| --- | --- | --- |
| `draft` | n/a → submit | submit |
| `submitted` | 200 replay (idempotent) | 409 `already_submitted` |
| `processing`/`suggestion` | 200 replay | 409 `already_submitted` |
| `archived` | 409 `invalid_state` | 409 `invalid_state` |

On submit: `llm_summary_context` = dispatch blob `{"approval_id", "dispatch_mode", "requested_n": number_of_results, "constraints", "tool_calls", "submitted_at", "intake_summary": <final request_context>}`, `status = 'submitted'`, `modified = TRUE`, `updated_at = now()`. Phase II note: the Universe-bound envelope field is `request_suggestion_id` (the v2 wire name) — the payload ships `{request_suggestion_id: request.id, …}` even though the column is `suggestion_request`.

```json 200 data
{ "request_id": "uuid", "status": "submitted", "submitted_at": "…", "dispatch_started": false }
```

`dispatch_started` is always `false` in Phase I — it's the Phase II seam.

Needed for draft resume + the three suggestion views.

Query (list): `status?` — **empty excludes `archived`**; `modes?` — comma list, e.g. `leverage_loop,leverage_outcome` for the Leverage Loops view, `outcome` for Outcomes, `serendipity` for Serendipity; `query?` — case-insensitive substring on `request_panel_title`; `person_id?` — beneficiary filter; `limit`, `cursor` — keyset `(updated_at DESC, id DESC)`. ## Harness — orbiter-frontend

The existing `src/features/tanstack-ai-chat/` feature + `POST /api/tanstack-ai-chat` route is the base (it already has `chat()` + `openRouterText`, runtime-context plumbing, otel middleware, a typed tool registry, and tests). This build retargets it: Xano client → Go backend client, `orbiter_*` multi-action tools → the five named tools below, adds persistence middleware, route-state derivation, and OpenUI rendering. New route path: **`POST /api/chat`** (the old route can stay until cutover).

### `POST /api/chat` route

```text Request → response
body: TanStack AI chat params (threadId, runId, messages[], forwardedProps)
response: SSE via toServerSentEventsResponse(stream)
auth: getAuth() WorkOS session; 401 without it
```

Per request:

1. Load thread history **server-side** via the persistence store (below) — client-sent history is ignored except the newest user message.
2. Derive route state (below) from the loaded history.
3. Pick the adapter: `openRouterText(modelId)` where `modelId` = intake model before a route exists, working model after `resolve_outcome`/`re_route`. **Switch between requests only — never mid-loop.**
4. Build system prompts: `BASE_VOICE` + `INTAKE` + generated OpenUI component prompt + injected `ROUTE_STATE` block.
5. `chat({adapter, messages, systemPrompts, tools, stream: true, context, middleware: [otel, persistence]})`.

New envs: `ORBITER_BACKEND_URL` (required), `INTAKE_MODEL`, `WORKING_MODEL` (defaults per eval outcome). Existing: `OPENROUTER_API_KEY`, `TANSTACK_AI_CHAT_MODEL` fallback.

### `backendFetch` — server→Go client

`src/features/tanstack-ai-chat/server/backend-client.server.ts` — same shape as `TanstackAiXanoServerClient` but: base `env.ORBITER_BACKEND_URL`, `Authorization: Bearer <workos token>` (Go verifies via `RequireWorkOS`), envelope unwrap `{data,error,meta}`, zod-validate `data`, throw typed `toolFailed` on `error.code`. Map Go error codes → tool-visible errors (`version_conflict`, `already_submitted`, `invalid_state`, `notfound`, `validation`).

### Tools — `.server()` implementations

| Tool | Input (zod) | Server call | Output |
| --- | --- | --- | --- |
| `resolve_outcome` | `{prompt: string, context?: object}` | **none — in-route LLM classify** against the registry (intake model, one sub-call) | `{class_slug, confidence: number, ambiguous: bool, summary: string}` |
| `update_context` | `{request_id?: uuid, class_slug?: string, slots: object, number_of_results?: int, request_panel_title?: string, request_context?: string}` | `POST drafts` when `request_id` absent → `PATCH drafts/{id}/context` (sends current `context_version` from route state; retries once on 409 by re-reading) | `{request_id, context_version}` |
| `submit_outcome_request` | `{request_id: uuid, approval_id: uuid}` | `POST /v1/copilot/outcomes/dispatch` | `{request_id, status: "submitted"}` |
| `re_route` | `{class_slug: string, reason: string}` | `PATCH …/context` with `{class_slug}` | `{class_slug}` |
| `handoff_to_akira` | `{reason: string, summary: string}` | none — terminal signal | `{handed_off: true}` |

`draft_intro` (Sonnet) is **not** in this build — working-phase only.

### Route state — newest-first derivation

After loading history, scan parts newest→oldest for `tool-result` parts named `resolve_outcome`, `re_route`, `submit_outcome_request`. First hit wins per key:

```ts
type RouteState = {
  class_slug: string | null;      // re_route beats resolve_outcome when newer
  confidence: "low" | "medium" | "high" | null;
  request_id: string | null;      // from update_context/submit results
  status: "draft" | "submitted" | null;
};
```

Inject as a system block every request (`ROUTE_STATE: class_slug=… confidence=… request_id=… status=…`) so compaction can never summarize it away. A forged client-sent `submit_outcome_request` result can never survive — history is server-loaded.

### Persistence middleware — `defineAIPersistence`

Store interface over the Go thread endpoints:

| Hook | Implementation |
| --- | --- |
| `ensure/load` | `POST threads/ensure` (client supplies `surface` + `surface_key`) → `GET threads/{id}/messages` |
| `save` | `POST threads/{id}/messages` — `{run_id, messages:[{turn_id, role, parts}]}` batched after each turn completes |

Refresh mid-turn loses nothing; retried saves dedupe on the unique key.

### Prompts — `src/features/tanstack-ai-chat/prompts/`

Versioned in-repo. `base-voice.md` (Chief of Staff persona) + `intake.md` must encode, at minimum:

- The 26-slug registry verbatim (class names + one-line labels) and the `ask_back` sentinel rule.
- **Confirm-after-routing:** a turn that calls `resolve_outcome` must also speak a one-sentence goal confirmation — routing turns never end silent.
- Per-class question sets for the four live classes; generic fallback for the rest.
- Slot discipline: ask for missing required slots only; `update_context` on every turn that learns something; never invent values.
- **Result-count gate:** once required slots are filled and count unasked → ask "How many matches do you want?" with options `20 great matches` / `100 broader` / `as many as you can find`; answers map to `number_of_results` = `20` / `100` / `null` (uncapped); set `awaiting_result_count` in `intake_context` until answered; `ready` only after it's answered.
- **Two-turn cap:** no route after two intake turns → `submit_outcome_request` with `confidence: low`.
- OpenUI output rules: emit only registered components; one question component per turn; text outside components allowed only as a one-line lead-in.

### OpenUI components + client

Register exactly these (generated system prompt via `@openuidev/lang-core`):

| Component | Props | Use |
| --- | --- | --- |
| `question` | `text`, `options[]?`, `allow_freetext` | Primary ask each turn |
| `option-list` | `options[]` (3–5) + `other: bool` | Single-select answers |
| `multi-select` | `options[]` | Multi-pick slots |
| `free-text` | `prompt` | Open-ended slot |
| `summary-card` | `title`, `rows[]` | Recap before ready |
| `submit-ready-card` | `title`, `cta_label` | Ready state → enables SUBMIT |

Client (`use-tanstack-ai-chat.ts` + outcome surface): `useChat` → text parts through `@openuidev/react-lang` Renderer; **strict-mode parse check** — any line that fails Lang parse surfaces as an error card, never dropped silently (the OpenUI parser's default is to skip). Option selections post back as user messages. `+` button → `POST threads/ensure` (new `surface_key`) → new thread. **SUBMIT** enabled only when `submit-ready-card` rendered (or `confidence: low` cap hit) → mints `approval_id`, sends the submit message that triggers `submit_outcome_request` → on `status=submitted` hands the thread to the results view (view itself out of scope).

## The scripted flow (what "done" looks like)

1. `+` → `threads/ensure` (`surface:"outcome"`, fresh `surface_key`) → `201/200 {conversation, created:true}`
2. User: *"I want to buy a house in Costa Rica"* → `chat()` turn 1 → model calls `resolve_outcome` → `{class_slug:"purchase_real_estate", confidence:high}` + speaks confirmation → `update_context` → `POST drafts` (creates row, binds `surface_ref_id`) → `PATCH context` (`slots.location` filled)
3. Turns 2–N: questions via OpenUI `question`/`option-list` components; `update_context` patches each turn
4. Slots filled → count gate question → `number_of_results` patched
5. `submit-ready-card` → SUBMIT enabled
6. SUBMIT → `submit_outcome_request` → `POST dispatch` → `status=submitted`, `request_id` returned
7. Every turn persisted to `copilot.messages` with `run_id`/`turn_id` keys
