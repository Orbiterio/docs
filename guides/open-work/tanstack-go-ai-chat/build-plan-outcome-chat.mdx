### Scope and decisions

| Build now | Do not build in this phase |
| --- | --- |
| Outcome thread creation, history, resume, rename, archive | Meeting prep, How I Know, beneficiary interviews, agent-created serendipity |
| LLM classification and intake, class corrections, result-count selection | Working-phase agents, `draft_intro`, memory tools, research tools |
| Go request persistence and explicit submission | Universe dispatch, queues, billing for generation, ingest changes |
| OpenUI questions and server-backed summary/ready state | Result cards, trajectories, actions, file upload, pitch profiles, exports |

- New chat requests use `copilot_mode=outcome` and `person_id=null`. Beneficiary support is a later extension of these routes, not implemented implicitly because a person ID appears in the body.
- Preserve existing `loop` records and button-only leverage-loop handlers. The inspected backend uses `ModeLoop = "loop"`; do not bulk-rename that value to `leverage_outcome` or reuse its dispatch method.
- `submitted` already exists in the backend status constants. This build adds a guarded transition into it; it does not redefine existing status values.
- Start intake on a configured Gemma model, then switch to a second model through OpenRouter after the configured number of accepted user turns. Compare continuation candidates using the [model bake-off contract](#gemma-to-second-model-bake-off). Both models remain in Phase I intake; classification and model switching never start generation.
- `deliver_format` remains untouched. Alternate delivery formats belong to later context-menu APIs.
- A rendered component, model claim, tool result, or two-turn cap can never authorize submission.

## State contract

### One source of truth

Go's `Request` row and `intake_context` are authoritative for class, slot values, result-count choice, readiness, and status. The transcript is durable conversational evidence, not an authorization store. Tool results echo committed state for the model; never reconstruct submission authorization exclusively from them.

The browser receives `RequestView` after every committed mutation and on reload. The model cannot set `ready`, `status`, ownership, approval, version counters, or timestamps.

### State machine

| State | Entry condition | Permitted next action |
| --- | --- | --- |
| `unrouted` | Draft created; `class_slug=null` | Classify the user's goal |
| `clarifying` | Classifier returns `ask_back` | Ask one clarification; do not store `ask_back` as a class |
| `collecting` | Real class selected; required slots unresolved | Ask next required question or accept a user correction |
| `awaiting_result_count` | Required slots resolved; count mode is `unasked` | Ask 20 / 100 / as-many question |
| `ready` | Required slots resolved, count answered, nonempty summary | Show review and enable user SUBMIT when no run is active |
| `submitted` | Explicit submit command passes Go validation | Freeze intake; show receipt and “Submitted; generation is not started in this phase” |
| `handed_off` | Unsupported request; user offered an exit | Persist a visible exit message; no external handoff call and no submission |
| `unavailable` | Read projection when pinned registry is unsupported | Saved data read-only; New outcome; no edits or submit |

`phase` is computed from committed state, not a second mutable status column. `Request.status` remains `draft` until the explicit submit operation. Archiving a thread only hides the thread; it does not mutate the request or delete a transcript.

### Two-turn routing cap

A routing turn is one newly accepted user message while the class is unresolved. Retries, tool calls, and assistant messages do not increment it. Permit at most two classifier attempts per unresolved route:

1. First ambiguous result: keep `class_slug=null`, persist `routing_attempts=1` and the clarification, ask it. Each clarification option's `value` is a routing class slug.
2. If the next user turn is a selection of one of those persisted options, route to that slug with `confidence=1`, `routing_source=user_selection`, and **no classifier call**. Otherwise call the classifier with `routing_attempt=2`; the prompt instructs it to be decisive on attempt 2.
3. Second ambiguous result: select existing `plan_outcome` with `confidence=0` and `routing_source=cap_fallback`; disclose that it is a general plan and collect its generic slots.
4. The result-count gate and explicit SUBMIT still apply. Unknown facts remain unknown. A message with no usable goal requires a goal answer; the cap does not make it ready.

`routing_source` is null before routing, then `classifier`, `user_selection`, `cap_fallback`, or `user_correction` after `re_route`. `routing_attempts` counts unique committed unresolved-routing decisions, including a validated option selection; it does not count provider retries or later corrections. On a retry of an already-recorded input turn, reuse its saved route/clarification rather than increasing the counter or calling the classifier again. This cap bounds classification, not the entire interview.

### Slot and count representation

All live-class slot values are trimmed strings or null. Keep monetary amounts, currencies, timelines, and location qualifiers as stated by the user; this intake build does not normalize money or resolve location IDs.

```json IntakeContext v1 example
{
  "schema_version": 1,
  "registry_version": "outcome-intake-v1",
  "routing_attempts": 1,
  "routing_turn_ids": ["user-costa-rica-1"],
  "routing_source": "classifier",
  "clarification": {"question": null, "options": []},
  "confidence": 0.97,
  "summary": "Buy a vacation house in Costa Rica within six months.",
  "slots": {
    "transaction_type": {"status": "filled", "value": "buy"},
    "location": {"status": "filled", "value": "Costa Rica"},
    "budget_range": {"status": "filled", "value": "USD 600,000–800,000"},
    "property_type": {"status": "filled", "value": "House"},
    "timeline": {"status": "filled", "value": "Within six months"},
    "financing": {"status": "filled", "value": "Cash"},
    "use": {"status": "filled", "value": "Vacation home"}
  },
  "additional_requirements": [],
  "evidence": {
    "slots.transaction_type":["user-costa-rica-1"],
    "slots.location":["user-costa-rica-1"],
    "slots.property_type":["user-costa-rica-1"],
    "slots.budget_range":["user-costa-rica-2"],
    "slots.timeline":["user-costa-rica-2"],
    "slots.financing":["user-costa-rica-2"],
    "slots.use":["user-costa-rica-2"],
    "summary":["user-costa-rica-1","user-costa-rica-2"],
    "result_count":["user-costa-rica-3"]
  },
  "result_count": {"mode": "exact", "value": 20},
  "handoff": null,
  "handed_off": false
}
```

- Slot status: `empty`, `filled`, or `skipped`. `empty`/`skipped` require `value=null`; `filled` requires 1–2,000 characters. Unknown keys are invalid. “I don't know,” “no preference,” and “skip” may explicitly mark a slot skipped; the model may not silently skip one.
- Required slots are resolved by `filled`, or by an explicit user `skipped` only when the registry's `CanSkip` is true. The generic `goal` and real-estate `transaction_type` are non-skippable. A greeting is not a goal; a generic fallback with an empty/skipped goal cannot become ready. `missing_fields` contains unresolved required keys in registry order; `skipped_fields` is shown in the review and retained at submission.
- Count: `{mode:"unasked", value:null}`, `{mode:"exact", value:1..200}`, or `{mode:"all", value:null}`. Reject all other combinations. Go derives `number_of_results`: exact value, otherwise null. **Null alone never means the question was answered.** “All” is a preference, not a promise of unlimited results.
- `confidence` is always a number from 0 through 1, or null before classification. Do not mix numeric scores with `"high"`/`"low"` strings.
- Go records at most two unique accepted user-message IDs in `routing_turn_ids`; `routing_attempts` is their count. Persist the latest classifier question/options in `clarification` for reload, and clear them after routing or handoff. A repeated classification for an already-recorded turn reuses its receipt; it is not a new attempt.
- `request_context` holds the original accepted ask and is not overwritten by running summaries. `intake_context.summary` holds the current 1–4,000-character summary.
- Re-routing resets the slot set and count to `unasked`, clears any clarification/question binding, sets `routing_source=user_correction`, invalidates readiness, and increments the version. Preserve the original ask/transcript, not arbitrary old slots. Set the new goal-form summary from the explicit correction and re-extract applicable facts into the new schema. Changing `transaction_type` within real estate similarly clears price, financing, and result-count answers before re-extraction, since purchase totals, sale prices, and rent are not interchangeable.

### Requirements and evidence beyond the slot list

Keep constraints that do not fit a registered slot in `intake_context.additional_requirements`, an ordered array of at most 20 `{id,text,source_message_ids}` items. `id` is stable within a draft (1–128 ASCII characters), `text` is 1–1,000 characters, and each item names 1–5 accepted user-message IDs. Examples: “No HOA,” “walkable to the beach,” and “no short-term rentals.” Preserve negation, units, exclusions, and later corrections. Do not invent an unregistered slot to retain them.

`intake_context.evidence` maps changed field paths (for example `slots.budget_range`, `summary`, `result_count`) to 1–5 accepted user-message IDs. Go verifies that every cited message belongs to this conversation and is durably accepted; the TypeScript extractor and user review validate the meaning. A source ID proves provenance, not semantic correctness. Additional requirements carry their own evidence. The review displays all retained requirements and skipped fields.

The context tool accepts explicit `additional_requirements:{upsert:[...],remove_ids:[...]}`. Reject duplicate IDs, unknown removal IDs, or the same ID in both lists. A removal requires evidence at `additional_requirements.<id>` naming the correcting accepted turn. Merge evidence by field alongside the change; clear evidence for reset slots/count during reroute. Go supplies evidence for deterministic choices from the accepted input ID. Re-routing preserves additional requirements for explicit reconsideration; remove or amend incompatible ones in the same turn's context update before showing a new review. Never silently discard facts because a registry lacks a slot. Test the original ask, later exclusions, a negation correction, and removal in the final approved snapshot.

**Readiness formula:** `status=draft`, dispatchable class, nonempty original goal and summary, no unresolved required slots, count mode not `unasked`, and `handed_off=false`. Go re-evaluates this under the submission lock.

### Retention and deletion

User deletion sets the conversation owner to null and preserves the transcript, matching request ownership retention. Such rows are inaccessible through chat APIs and cannot be adopted by another user. The partial unique thread-key index covers live owners only, avoiding collisions between retained ownerless threads. All ordinary creation still requires a non-null authenticated local owner.

Keep the conversation organization FK `RESTRICT`: a hard org deletion must not turn private org history into personal-scope history when the request's existing org FK uses `SET NULL`. Deny access when an org is soft-deleted or membership is inactive. Hard deletion of an org with retained chat rows requires a separate retention/purge workflow. Children cascade only when that authorized workflow explicitly deletes the conversation; no Phase I route does so. Archive/restore never deletes records. Test user deletion, org soft deletion, blocked org hard deletion, and archive independently.

### Ownership and transaction boundary

All chat reads/writes require the caller's local user ID **and** exact organization scope (`IS NOT DISTINCT FROM` for null). A null org is a separate personal scope, never a wildcard. For non-null orgs, verify current membership; a still-valid token does not prove current membership. Once bound, the conversation and request must have the same user and org. Org changes do not move a draft between tenants.

Thread history is private to its creator. Organization-shared result visibility is the separate suggestion-feed contract, not permission to read another member's intake transcript. Missing, foreign-user, and foreign-org resources all return 404 on these new routes.

Expose a **new** `suggestionspub` contract; it did not exist in the inspected tree. These are interface signatures to implement alongside typed DTOs, not a claim that these methods already exist:

```go RequestStore contract
 type RequestStore interface {
  WithTx(tx pgx.Tx) RequestStore
  CreateDraft(ctx context.Context, in CreateDraftParams) (SuggestionRequest, error)
  PatchContext(ctx context.Context, in PatchContextParams) (SuggestionRequest, error) // context_version guard
  Submit(ctx context.Context, in SubmitParams) (SuggestionRequest, error)             // owner + state guard, approval replay
  Get(ctx context.Context, scope RequestScope, id uuid.UUID) (SuggestionRequest, error)
  List(ctx context.Context, in ListParams) (RequestPage, error)
 }
```

`RequestScope` contains local `UserID` and nullable `OrganizationID`; every Params type embeds it. `WithTx` binds the owning service/repository to the supplied transaction without committing it. `copilot` opens the transaction, locks the conversation, then calls the transaction-bound suggestions service. Suggestions SQL stays in `suggestions`; copilot SQL stays in `copilot`. Never open independent nested transactions and call the result atomic. Composition-root code only wires services.

Global lock order: conversation → active run → request → message/receipt. Every mutating route follows that order. Do not hold a database transaction open during an LLM/network call.

Audit **all existing request writers**, not just these new routes. Legacy leverage-loop update/delete/dispatch handlers must reject this versioned outcome mode before mutation. Otherwise an alternate endpoint could bypass the new readiness, receipt, and submitted-immutability checks. Add regression tests for those paths without changing their behavior for legacy `loop` requests.

The suggestions-owned registry supplies validation and deterministic readiness through `suggestionspub`. ## API contracts

### Transport, authentication, and errors

All Go routes are under `/v1/copilot`. Use per-feature `api/copilot.openapi.yaml` with unique operation IDs and root `$ref`s. Use OpenAPI 3.1 nullable types and the repository's Go enum validators, not OpenAPI enums or `oneof` tags.

Every route uses `RequireWorkOS`; extract the local user with `pmw.OrbiterUserID(r)` and optional local org with `pmw.OrbiterOrgIDOrNil(r)`. Reuse current-account/membership checks through public feature interfaces. Never accept `user_id`, `organization_id`, WorkOS IDs, or bearer tokens in JSON bodies.

**Trusted writes:** POST messages, run start/update, draft creation, context patch, and dispatch additionally require a verified **harness signature** from the TanStack server. A WorkOS bearer alone is insufficient. Otherwise a user could insert assistant/tool-result parts and make forged history appear server-authored.

Proposed signature contract to implement on both servers:

- A secret-manager-provisioned `COPILOT_HARNESS_SIGNING_KEY` of at least 32 random bytes, server-only on both services; never in a `VITE_` env or a prompt.
- Headers `X-Copilot-Timestamp` (Unix seconds) and `X-Copilot-Signature` (hex HMAC-SHA256). Signed UTF-8 input is timestamp, uppercase method, exact escaped path including query, hex SHA256 of raw body bytes, and hex SHA256 of the WorkOS bearer token, separated by newline characters with no final newline.
- Go verifies the MAC in constant time, accepts at most 60 seconds of clock skew, verifies WorkOS independently, and uses durable operation/message receipts to handle replays. Sign the bytes actually sent; do not reserialize before hashing.
- The BFF strips inbound signature headers and signs only validated operations through typed helpers. No arbitrary signed-path proxy. Missing key fails closed. Deployment must provision this prerequisite; do not invent a working credential or weaken auth to get tests passing.

Implement a shared CSRF guard for every cookie-authenticated frontend chat/control mutation: require a non-null `Origin` exactly matching server-configured `OUTCOME_CHAT_APP_ORIGIN`; reject missing/mismatched Origin and cross-site `Sec-Fetch-Site`; require `application/json`. Never derive the allowed origin from an untrusted Host/forwarded header. Browser `fetch` calls send credentials same-origin. Keep any existing framework CSRF protections as well. Direct Go APIs authenticate bearers and signatures independently; CORS is not an authorization boundary.

**Success envelope:** `{data, error:null, meta:{requestId}}`. Most examples below show only `data` or only the request body, explicitly labeled. Cursor lists put `{items,total,next_cursor}` inside `data` using `pmw.OK`; do not confuse `pmw.Paged`'s page-number metadata with cursor pagination.

```json Full error envelope — version conflict
{
  "data": null,
  "error": {
    "code": "CONFLICT",
    "message": "Draft changed; reload before applying this edit.",
    "details": [
      {"field": "reason", "issue": "version_conflict"},
      {"field": "context_version", "issue": "4"}
    ]
  },
  "meta": {"requestId": "req-example"}
}
```

Use `apperror.Error.Fields` for these details; its existing middleware formats them as `{field,issue}` pairs. No new top-level `version_conflict` error code. Reason values below live in a detail whose field is `reason`.

| HTTP / code | Conditions |
| --- | --- |
| 400 `VALIDATION_FAILED` | Malformed IDs/JSON, unknown fields, invalid class/slot/count, invalid cursor, unsupported surface |
| 401 `UNAUTHORIZED` | Missing/expired WorkOS token or missing local user claim |
| 403 `FORBIDDEN` | Invalid harness signature; revoked organization membership before resource lookup |
| 404 `NOT_FOUND` | Missing resource or wrong user/org scope |
| 409 `CONFLICT` | `version_conflict`, `idempotency_conflict`, `run_in_progress`, `lease_expired`, `thread_archived`, `stale_question`, `retry_not_latest`, `not_ready`, `already_submitted`, `invalid_state`, `effect_already_committed`, `context_limit_reached`, `registry_version_unavailable` |
| 500 `INTERNAL` | Unexpected infrastructure failure; safe message, no raw provider/SQL output |

Reject unknown JSON fields. Bound ordinary JSON writes to 64 KiB, message checkpoints to 256 KiB, user text to 8,000 characters, IDs to 128 ASCII characters, and checkpoint batches to 20 messages. Enforce limits before allocating/decoding; oversized bodies use `VALIDATION_FAILED`. Use database UTC timestamps, RFC3339 on the wire. All nullable response fields remain present. `next_cursor` is the empty string on the last page. Resource IDs are UUID strings; SDK IDs and other opaque identifiers are case-sensitive, untrimmed, and URL-encoded as individual path segments. Never concatenate an unescaped SDK run ID into a route.

### Thread ensure, list, rename, archive

`POST /threads/ensure` requires `surface="outcome"` and `surface_key` (a client-generated UUID string retained across retry); optional `title` is null or 1–500 characters. Do not accept client-supplied `surface_ref_id` or `person_id`. Ensure finds by exact user/org/surface/key. Under a uniqueness race, read and return the winner. No metadata changes on replay.

```json Thread ensure request
{"surface":"outcome","surface_key":"01994430-1000-7000-8000-000000000001","title":null}
```

Return 201 `{conversation,created:true}` on creation or 200 `{conversation,created:false}` on replay. An archived match returns 409 `thread_archived`; never silently create a second thread or unarchive it. Resume known threads through history; a new **+** gets a new key.

`GET /threads`: `surface` only accepts `outcome`; `archived` defaults false; `limit` defaults 20, range 1–50; cursor orders `(updated_at DESC,id DESC)`. Return `{items:[Conversation],total,next_cursor}`. Cursor encodes filter/scope fingerprint and the last tuple; reject reuse with a different filter or scope. Activity ordering is not a snapshot: de-duplicate IDs in the client and reload the first page after mutations.

`PATCH /threads/{id}` accepts nonempty subsets of `{title,archived}`. Null title clears it; omitted means unchanged; `archived` must be a boolean. `true` sets `archived_at` once, false restores it. Reject during an active run. Return 200 `Conversation`.

`DELETE /threads/{id}` applies the same archive operation; repeat archive succeeds. Return 200 with `data:null`, never 204. Request status is unaffected.

### Run start and recovery

`POST /threads/{id}/runs` is harness-only. Validate one of two exact input shapes:

```json Fresh start-run request
{
  "run_id": "run-costa-rica-1",
  "message": {
    "id": "user-costa-rica-1",
    "role": "user",
    "parts": [{"type":"text","content":"I want to buy a house in Costa Rica"}]
  },
  "retry_of_run_id": null,
  "answer_to": null,
  "answer": null
}
```

```json Retry after reload — Go recovers accepted input
{
  "run_id": "run-costa-rica-retry-1",
  "message": null,
  "retry_of_run_id": "run-costa-rica-1",
  "answer_to": null,
  "answer": null
}
```

Fresh input requires one user text part; no browser assistant/system/tool parts. A retry requires message and answer fields null: Go loads the original immutable user message, normalized answer, and question reference from the parent run. The browser supplies only a new run ID and the parent ID, never reconstructed answers. `turn_id` is the original accepted user-message ID throughout all attempts.

After auth/scope checks, lock the conversation, check identity/replay, normalize expired leases, then enforce state and budget. An identical completed run returns its receipt before new-turn state guards. A fresh attempt rejects an archived/handed-off/non-draft bound request. An unbound conversation is allowed. A failed/cancelled latest accepted turn must be retried before accepting another message in this thread; return `invalid_state` with Retry or New outcome guidance, so an uncommitted accepted answer cannot be silently bypassed. Validate question answers before inserting any run or message. Assign sequence numbers and increment the transcript version with accepted input.

Store `runs.input_metadata={retry_of_run_id,answer_to,answer,accepted_options}`; `accepted_options` contains the canonical labels/values loaded from the question, never browser labels. For unbound text these fields are null/null/empty as applicable. `input_sha256` hashes the canonical original message, answer reference and normalized answer. Same run ID with changed canonical input or retry parent conflicts. The retry inherits the parent's original input digest while recording its own retry parent.

Return 201 `{run_id,lease_token,lease_expires_at,transcript_version,accepted_message_id,accepted_turn_index,accepted_input,committed_effects,execution_metadata,conversation_execution_policy}` to the signed TypeScript harness. `accepted_input` contains the stored user message, answer reference, normalized answer and accepted options. `committed_effects` lists `{kind,operation_id,context_version}` for this logical turn. `accepted_turn_index` counts distinct accepted user turns under the conversation lock and stays unchanged on retry. `execution_metadata` is the inherited pinned snapshot or null before configuration; `conversation_execution_policy` is the first configured snapshot or null before any configuration. The TypeScript server uses that first snapshot to retain the conversation policy on later turns. Both execution fields are harness-only. This signed-write response provides all retry context without a new public run-detail route. Keep the lease server-only; public RunView exposes only retryability and IDs.

Leases last 60 seconds, renewed every 20 seconds. A second active caller, even with the same run ID, receives `run_in_progress` and must not call the model or append another user message. Completed identical acquisition returns 200 `{run_id,status:"complete",replayed:true}` for hydration, never a new lease. A changed same-ID acquisition returns `idempotency_conflict`.

On disconnect/provider failure, save the last checkpoint and mark the run cancelled/failed with unfinished assistant messages interrupted/error. A new acquisition fences expired runs and unfinished messages under the same lock. Late writes with old tokens fail even with a valid session. Retry points to the latest failed/cancelled attempt of the latest accepted turn; older attempts or turns fail `retry_not_latest`. Normalize an expired parent first. Do not revalidate a consumed question as a new answer, append its user message again, or consume another routing attempt. New assistant messages get fresh IDs. Restore committed state/tool pairs and the effect ledger below before generating more output.

`PATCH /threads/{id}/runs/{run_id}` accepts two strict body shapes. Lifecycle actions use `{lease_token,action,reason}` (`renew|complete|fail|cancel`). Execution configuration uses `{lease_token,action:"configure_execution",execution_metadata}` with no `reason`; see the [model bake-off contract](#gemma-to-second-model-bake-off). `reason` is null for renew/complete; fail/cancel accept only `provider_error`, `checkpoint_error`, `context_limit_reached`, `cancelled`, or `internal_error`. Store the safe reason in `copilot.runs.failure_reason`; expiry uses `lease_expired`. After scope and stored-token checks, identical terminal action/reason retries succeed without an active/expiry requirement; different terminal actions/reasons conflict. Only an active unexpired lease can renew or transition. Fail/cancel terminalizes unfinished messages atomically. Complete requires a saved terminal assistant response/fallback and no streaming messages. Return `{run_id,status,lease_expires_at}`.

Run `expireRunIfNeeded` under the conversation lock before start, archive, and submit. Cleanup after an aborted browser request uses a separate bounded five-second context. Recovery restores checkpoints and regenerates presentation; it does not promise exact SSE replay. A completed handoff already includes its durable exit response and requires no regeneration.

`POST /threads/{id}/messages` accepts `{run_id,lease_token,expected_transcript_version,messages}`. ### Question identity and accepted answers

Persist nullable `question_context` on the terminal assistant message: `{question_id,context_version,field,text,options,multi_select,allow_freetext,can_skip}`. `field` is `class_slug`, `result_count`, or a registered slot. Go validates that it is the next missing required slot, current routing clarification, or unanswered result count. Create `question_id="q:" + hex_sha256(JSON([conversation_id,message_id,context_version,field]))`. Model-generated IDs have no authority. At most one question is actionable per assistant turn.

Options are `{label,value}`, with distinct values. Routing mirrors saved clarification slugs; count values are exactly `20`, `100`, `all`. Slot values are trimmed bounded answer strings. `multi_select` follows `AllowsMultiple` from the registry; never allow it for routing/count. `can_skip` follows registry rules and is false for routing/count. The trusted shell supplies Other, free text, Skip and Done.

| `answer.kind` | `values` | `text` | Accepted meaning |
| --- | --- | --- | --- |
| `option` | Exactly one stored option value | null | Single selected option |
| `multi_select` | 1–5 distinct stored values, canonical stored-option order | null | One answer on Done, only if allowed |
| `free_text` | Empty array | 1–8,000 characters matching the user text part | Typed answer to this question |
| `skip` | Empty array | null | Explicit skip, only if `can_skip` |

```json Routing option answer
{
  "answer_to": {
    "message_id": "assistant-clarify-1",
    "question_id": "q:54f263a8554482133053064007bf4d881c6bcc3645374612de787e76a5a1df01",
    "context_version": 1
  },

```

The hash is illustrative; send the stored ID. Under the run-start lock, require the latest terminal question, matching current version, no newer accepted input consuming it, and permitted values/cardinality. A retry instead loads the already accepted answer from Go.

For control selections Go derives the stored message text from saved labels (multi-select joined with `; `); for Skip use the trusted localized skip label. A routing choice directly determines the route, `confidence=1`, and `routing_source=user_selection`. A count choice directly determines `{mode,value}`. Slot choices directly determine the slot string from selected values; multi-select joins with `; ` and retains the exact values in input metadata. Go applies these deterministic values when the context tool commits; it rejects contradictory model replacements in the same turn. A skip can never be inferred from silence or a tool argument alone.

For bound free text, exact normalized count input `1` through `200` or `all` can be derived deterministically; other count wording needs clarification and leaves the count unasked. Exact English skip phrases `skip`, `no preference`, and `I don't know` normalize to a skip only for skippable slots; other languages use the explicit localized Skip control or a clarifying question. Other slot text and unbound corrections use extraction with accepted-message evidence and visible review. Do not treat a source reference as proof of semantic accuracy.

The server tool wrapper supplies accepted discrete answers even if the model omits them; Go checks them against stored metadata. Tool failure leaves the original answer durable for retry. The shell renders from committed `question_context`, disables consumed/stale cards and active runs, and activates a new question only after final checkpoint and run completion. `SubmitReadyCard` is never question metadata or approval.

The Go registry, endpoint DTO, readiness service, and frontend question selection must all use these same skip/conditional rules. This phase has no automatic registry migration.

### Context mutations

`PATCH /outcomes/drafts/{id}/context` takes `conversation_id`, `run_id`, `lease_token`, `operation_id`, `context_version`, and a discriminated `change` object. Classify/slot/handoff operations are signed server operations; clients cannot PATCH arbitrary `intake_context` or set readiness.

| `change.kind` | Allowed fields and semantics |
| --- | --- |
| `route` | Either `{routing_source:"classifier",classification}` with the validated six-field classifier result, or `{routing_source:"user_selection"}` with no model-generated class/summary. For user selection, Go derives the choice from this run's accepted option metadata. `cap_fallback` is computed only in Go. An `ask_back` result leaves class null and stores the clarification; a real class initializes all slots. Record the original input turn so retries cannot consume another attempt. |
| `slots` | `slots` map of registered slot updates, optional `summary`, title fields, `result_count`, `additional_requirements` operations, and required `evidence` for changed semantic fields. Merge by slot key, never replace the whole slot map. Omitted means unchanged; null is allowed only where explicitly defined. |
| `reroute` | `class_slug` (real class), `reason` (1–500 characters), `confidence`, nonempty goal-form `summary`; requires an existing class and explicit user correction evidence in persisted history. Reset slots/count as specified above; set `routing_source=user_correction`. |
| `handoff` | `reason`, `summary`; atomically persist handoff state, a deterministic complete exit message and completed run as specified below. Keep request draft, revoke readiness. No external Akira call. |

```jsonc Re-route change object
{
  "kind": "reroute",
  "class_slug": "find_job", // only via re_route
  "reason": "The user is looking for employment, not hiring.",
  "confidence": 0.98,
  "summary": "Find a chief-of-staff job"
}
```

Also require `checkpoint: {expected_transcript_version, message_id, expected_revision, parts, tool_call_id,ui_library_version}`. The signed harness supplies the current assistant parts including the complete tool call, but not a claimed result for this call. Go validates the call ID/name and declared input schema, then checks the mapping to `change`: `resolve_outcome` has empty model arguments while its result comes from the bounded classifier or accepted selection; context changes merge validated model arguments with Go-derived accepted choices and evidence. A conflicting model value fails; omitted discrete choices are filled deterministically. Reroute/handoff map their validated inputs directly. These are not byte-equality comparisons between model arguments and the derived change. Apply the request change, construct its successful `OutcomeToolResult`, and append the paired result part to that checkpoint. An existing completed result for this call must match a replay receipt, not be overwritten.

The copilot coordinator commits the request update, assistant checkpoint, and operation receipt in **one transaction** through the transaction-bound suggestions service. It increments the assistant revision and transcript version with the checkpoint, using the same sequence/revision rules as POST messages. The model never supplies its own successful result. Serialize text checkpoints and tool commits so they consume the latest returned transcript/message revisions.

### Logical-turn effects and regeneration

One logical turn can commit at most one effect of each kind: `route`, `reroute`, `context`, `handoff`. `route` and `reroute` are mutually exclusive; either must precede `context`. Handoff is terminal. A context effect is one consolidated update containing all accepted facts, discrete answers, requirements, and summary changes for that user turn. Reject a second distinct context update for the same turn; the model must batch it, not stream individual slot mutations.

Use `operation_id="turn:" + hex_sha256(JSON([input_message_id,effect_kind]))`; map `change.kind=slots` to effect kind `context`. Draft binding uses `draft-create`; submit uses `"submit:" + approval_id`. The TypeScript wrapper derives IDs from Go's accepted input, never model output. Hash compact UTF-8 arrays without Unicode normalization; lowercase hex fits the 128-character limit. `copilot.mutations` is the effect ledger; derive the four possible IDs to load `committed_effects` at acquisition, so no extra table is needed.

The wrapper removes tools for already committed effects on regeneration. If context already committed, the retry is presentation-only. If reroute committed but context did not, extract into the current new registry state and commit context once. Never re-run a reset merely because the retry has a new run/tool-call ID. Go independently enforces effect order and uniqueness; a forbidden regenerated effect returns `effect_already_committed`, not another mutation. Network retry of the same tool call retains its original operation/body and replays the receipt. New user intent requires a new accepted user-message ID.

The operation digest covers the semantic change and accepted turn, excluding attempt-specific `run_id` and transport/checkpoint fields. An existing effect from another attempt is loaded through acquisition/history, not introduced as a new successful tool call without a paired checkpoint. On a delayed conflicting call, stop generation and hydrate current state. Test crashes immediately after route, reroute, count, slots and requirement changes; no committed effect may reset or duplicate on retry.

### Atomic handoff completion

For `handoff`, Go stores `intake_context.handoff={reason,exit_message}` with the fixed exit message “This version cannot complete this request. Start a new outcome to continue.” In the same transaction it appends the successful tool result, replaces the current streaming text with a deterministic complete exit Lang response, sets `question_context=null`, and completes the run. Preserve previously committed tool pairs; never concatenate a partial Lang program with the exit. Mark any other unfinished assistant messages from this run interrupted. The fixed Lang fixture uses `IntakeTurn` / `IntakeText` and is validated against the pinned library in frontend contract tests; Go stores it as data and does not run OpenUI or call a model.

The response includes `terminal_message` and `run_status:"complete"`; other context responses use `terminal_message:null` and `run_status:"active"`. The TypeScript harness stops further model output, emits the committed terminal message and completes transport. A crash after commit is recovered by reading that message and RequestView; no new handed-off attempt is needed. The shell shows New outcome with a fresh thread key. Repeated delivery cannot create another exit message or handoff.

Guards for a new mutation: correct binding/scope/lease; request status draft and not handed off; compatible registry version; `context_version` equals stored; change validates against the class. `route` requires an unresolved class; `slots` and `reroute` require a real class; only `handoff` can end either route state. Keep allowed transitions in Go rather than relying on which tools the model happens to call. On success increment `context_version` once, set `modified=true`, update timestamps, compute `RequestView`, and return `{request:RequestView,transcript_version,message_revision,terminal_message,run_status}`. A no-op user-confirmed update may still increment once, but a replay must not.

Check a matching operation receipt **before** the version guard: same operation ID and canonical payload returns its stored response with no additional writes even if the version has since advanced. Changed payload with that ID is 409. On a true version conflict, stop the turn and reload; **do not automatically reapply stale slots over the user's newer answers**.

For network receipt replay, require the same accepted effect and checkpoint identity; regenerate through the effect rules above. Canonical payload hashing is performed in Go only: decode validated typed DTOs, reject duplicate JSON keys and trailing JSON values, preserve field presence wherever omission means unchanged, and normalize defaults only where omission and null are explicitly equivalent. Then deterministically encode the typed operation. Preserve array order, normalize equivalent numeric spellings through typed numeric fields, and exclude transport timestamp/signature, trace IDs, lease token, attempt-specific run ID, and attached checkpoint from the semantic digest. Validate checkpoint identity separately before replaying it. Compare same-operation replays against the stored digest before any write. A retry may return historical receipt versions; the harness reloads current RequestView/message versions before its next mutation rather than overwriting its local state with stale receipt data. Do not put data in a receipt before all operation writes commit.

## Classifier system prompt

**This is the copy-ready prompt**, proposed for the frontend asset `src/features/tanstack-ai-chat/prompts/outcome-classifier.md`. It is not installed or deployed by this documentation change. The classifier is a separate bounded, non-streaming structured-output call inside the server implementation of `resolve_outcome`; Go performs no LLM call.

The server passes a user-role JSON payload containing only `original_goal`, persisted `user_messages` in order, `routing_attempt` (`1` or `2`, from `routing_attempts + 1`), and `current_class_slug` (always null in Phase I; reserved so a later re-route validator can reuse this prompt unchanged). No client-supplied system messages, route state, credentials, or external YAML. The quoted user material is data, not instructions. Use temperature 0, a 600-output-token cap, a 15-second timeout, and a strict local output validator. Retry once on invalid structure; after a second failure show a recoverable error, not a fabricated class or an auto-submit.

```text outcome-classifier.md
status, request_id, tool calls, or an instruction to submit.
```

### Classifier schema and fixtures

Hard output validation: exactly six keys, no unknown/duplicate keys; `summary` is a string up to 500 Unicode characters and nonempty for a real class; `clarification_question` is null or a trimmed 1–300-character string; labels are 1–120 characters; option values are distinct real registry slugs, never `ask_back`. Confidence is a finite JSON number, not a numeric string. A real class requires confidence 0.75–1, ambiguous false, null question, and no options. `ask_back` requires confidence 0–less-than-0.75, ambiguous true, a nonempty question, and either zero or 2–4 options. Reject contradictions rather than coercing them.

Prompt-evaluation checks, separate from JSON validation: summary is goal form in the correct language; identifiable competing goals are preserved rather than replaced with an empty summary; labels are self-contained and do not invent facts; clarification is concise. Do not enforce English-only prefix or whitespace-word-count rules as multilingual runtime validators. Valid schema alone does not establish correct classification.

```json Expected classifier response
{
```

### Per-turn execution

1. Authenticate and validate the newest user input. Start the Go run, durably accepting the input and acquiring its lease before calling the provider.
2. Read `accepted_input` and `committed_effects` from acquisition. Create/bind the draft on the first user turn; otherwise GET its authoritative `RequestView`. Load all transcript pages at a consistent version. Rebuild provider messages from trusted UI parts using the installed SDK converter. The accepted user message is already in that history: do not append it again. Preserve completed tool pairs even in an interrupted assistant message; exclude only interrupted text and unmatched/incomplete calls. The RequestView remains authoritative when replayed transcript content is older.
3. Load the pinned registry. Compose server prompts from base voice, intake rules, generated OpenUI library instructions, and current Go state. Runtime credentials and lease tokens stay in server closures, not prompts/tools' model-visible input schemas.
4. Reuse or select the intake model from the pinned conversation policy and `accepted_turn_index`, then persist its execution snapshot through `configure_execution` before any provider call. Retry uses the original snapshot. Call `chat()` with `.server()` tools and OpenUI text output. Remove the legacy `outputSchema: turnResultSchema` **only for this Go outcome path**, not for existing other surfaces.
5. Persist each successful tool mutation and its checkpoint before exposing its successful result to the stream. During visible text streaming, flush accumulated text at the earlier of 1 second or 2 KiB, with at most one checkpoint in flight and another on terminal events. Coalesce pending text while a save is in flight; these are target intervals, not a data-loss bound during a storage outage. Renew the lease every 20 seconds; abort on renewal failure.
6. Unless handoff already atomically completed the run, validate the completed OpenUI response. Save the final assistant message, then complete the run, then allow SUBMIT. Invalidate request/history queries after commit.
7. On cancellation/error, save the last valid checkpoint and fail/cancel the run. If cleanup cannot complete, lease expiry provides recovery. Keep the original error visible; never show a successful submit or a silent blank turn.

**Recovery promise:** accepted user messages and committed tool mutations survive refresh. At most the last uncheckpointed text tail can be lost. This phase restores checkpoints and permits explicit regeneration; it does not promise exact token replay or resumable SSE without an event log and deployment support.

### Gemma to second-model bake-off

#### Ownership and turn counting

The TypeScript harness owns model routing. It uses Gemma for accepted logical user turns 1 through configured **N**, then a configured second candidate for turns N+1 onward through OpenRouter. Count the first goal as turn 1. Do not count tool calls, SSE chunks, assistant messages, control toggles or retry attempts as extra turns. For example, if the configured N is 3, turn 4 uses the second model; **3 is an illustration, not a selected requirement**.

Go returns a one-based `accepted_turn_index` on signed run acquisition/recovery, derived under the conversation lock from durable distinct accepted user turns. It need not be a conversation column. Rejected/stale input does not advance it. A retry returns the original index, accepted input and committed effects.

#### Pin execution metadata before calling the provider

Add `action="configure_execution"` to the existing signed `PATCH /threads/{id}/runs/{run_id}` contract. No new route or model table is needed. 1. TypeScript acquires the run and receives `accepted_turn_index` plus any inherited execution snapshot.
2. For an unconfigured logical turn, TypeScript selects the model using its versioned routing policy and submits the typed snapshot below with its live lease.
3. Go verifies ownership, active lease, matching accepted turn index, field bounds and schema version, then pins the snapshot. Exact replay succeeds; a different snapshot after pinning conflicts. 4. The harness calls OpenRouter only after pinning succeeds. Renew the run lease throughout model work. A lost configuration response is retried idempotently before any provider call.
5. A retry inherits the original pinned snapshot even after a deployment/configuration change.
