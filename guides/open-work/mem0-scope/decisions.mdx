Every decision made during the Mem0 Scope 2.0 work, in the order it was made. A decision is added here when an open question on one of the scope pages is answered. Anything not listed here is still open.

## Decided

| # | Area | Decision | Decided |
| --- | --- | --- | --- |
| 1 | Base memories | **Scope key is `entity:{entity_id}`.** One pattern for people and companies. The `#13148` prototype's `master_person:{master_person_id}` key is retired; no shared memories are deployed, so there is nothing to migrate. | Mark, 2026-09-21 |
| 2 | Base memories | **Company edges: every outbound edge, plus an inbound allow-list.** A person's one-hop edges are bounded; a large company has an inbound edge from every employee, alum, and member in Universe. Companies take every edge that starts at the company (`RAISED`, `SPECIALIZES_IN`, `LOCATED_IN`, `SPONSORS`, `PRODUCES`, `DONOR_TO`, and the rest), plus inbound edges only from types that describe the company itself: `FOUNDED`, `INVESTED_IN`, `BOARD_MEMBER_OF`, `ADVISOR_TO`, and `WORKS_AT` limited to current leadership (`is_current` with C-level or founder seniority). People keep the full one-hop rule. | Mark, 2026-09-21 |
| 3 | Base memories | **The check is a claim stamp on the entity row.** `UPDATE … SET base_memories_at = now() WHERE id = {entity_id} AND base_memories_at IS NULL`. One row affected: this worker writes the base memories. Zero rows: they exist or another worker has claimed them, so skip without calling mem0. This closes the race where two users add the same new entity at the same moment, and it removes a mem0 read from every later add. The mem0 "any memories?" read stays as the repair check: [Dream State](/guides/open-work/mem0-scope/dream-state) finds stamped entities whose memory count is short and finishes them. | Mark, 2026-09-21 |
| 4 | Base memories | **Dream State owns the refresh, nightly, for changed entities only.** Re-enrichment adds awards, ends roles, and rewrites descriptions after the base memories exist. The nightly cron selects entities that are in at least one user's contacts and whose Universe publish time is newer than their `base_memories_at` stamp, and refreshes only those. Nothing is added to Universe's edge writers, and Universe stays unaware of mem0. Worst-case staleness is one day. | Mark, 2026-09-21 |
| 5 | Base memories | **Refresh is a diff on `edge_uuid`.** Dream State reads the entity's base memories, adds edges that are missing, updates text that changed, and deletes edges that are gone. A typical re-enrichment touches a few edges, so it is a few calls and memory IDs stay stable. Wipe-and-rewrite is rejected: two calls per memory every time, and it races mem0's asynchronous filtered delete. | Mark, 2026-09-21 |
| 6 | Base memories | **Every award edge is written; volume is handled at retrieval.** 83 of Ryan's 135 base memories are awards. The rule stays one memory per edge, with no edge-type exceptions in the writer. `edge_type` is in every memory's metadata, so retrieval can leave out `NOMINATED_FOR` by default or cap awards to the most recent. Nothing is lost and the choice is reversible. | Mark, 2026-09-21 |
| 7 | Base memories | **Keep one memory per accepted edge; retries deduplicate by canonical edge identity.** Use `entity_id` plus `edge_uuid`, not memory text. The Buried DFCC and IGN nominations are distinct awards and both are written. Universe removes redundant pure-founder employment upstream; a separately supported operating role can coexist with `FOUNDED`. The memory writer formats the accepted edges without merging their facts. | Mark, 2026-09-21 |
| 8 | Dates | **Backdate events from 1970 onward. Never backdate evergreen facts.** Backdating is for events that age: a role that started, an award that was won, a film credit. For those, pass mem0’s `timestamp` when the start date is 1970 or later and omit it for anything earlier, because the field takes Unix epoch seconds and older dates go negative. Evergreen facts such as a birthdate, a location, or an expertise are never backdated, whatever the year: dating a birthdate memory 1966 would tell mem0 it is sixty years stale. A birthdate keeps its full date in the text and metadata, plus `month_day` (for example `"11-20"`) so "whose birthday is this month?" is a metadata filter. The real dates are always in the memory text and metadata, so nothing depends on `timestamp` alone. The 1970 cutoff is defensive: whether mem0 accepts a negative value is untested. Check it alongside Q13 and drop the cutoff if it does. | Mark, 2026-09-21 |
| 9 | Base memories | **A base memory is identified by `edge_uuid` in metadata. `run_id` is not used.** The key is `entity_id` plus `edge_uuid`, and `entity_id` plus `base_type = identity` for the identity memory. Checked against the mem0 docs on 2026-09-21: metadata filters work on both get-all and search (top-level keys; `eq`, `ne`, `contains`), and mem0 defines `run_id` as a short-lived session to be cleaned up later, so a hash per memory would create one run per base memory. `run_id` stays free for real sessions such as a chat thread or a meeting-prep flow. The live email writer's `run_id = hash` convention is re-examined when email memories are re-scoped. | Mark, 2026-09-21 |
| 10 | Base memories | **Company leadership is `founder`, `c_suite`, and `president`.** These are the `seniority_level` values on an inbound `WORKS_AT` edge that qualify for a company's base memories. Universe keeps past roles on a separate `WORKED_AT` edge, so `WORKS_AT` is current by construction. `INVESTMENT_PARTNER_AT` and `OFFICER_OF` join the inbound allow-list from decision 2, because for a VC firm or a nonprofit those are the leadership edges. The full inbound allow-list is now `FOUNDED`, `INVESTED_IN`, `BOARD_MEMBER_OF`, `ADVISOR_TO`, `INVESTMENT_PARTNER_AT`, `OFFICER_OF`, and leadership `WORKS_AT`. | Mark, 2026-09-21 |
| 11 | Base memories | **Investment edges are capped at the 50 most recent per edge type.** A VC firm has an `INVESTED_IN`, `LEAD_INVESTED_IN`, or `FOLLOW_ON_INVESTED_IN` edge per deal, which can run to thousands for one firm. Each of those edge types is capped at its 50 most recent deals. Everything else about the firm is written in full. The complete portfolio stays in the graph, which is the right tool for it. This is the one volume cap in the writer: awards (decision 6) are not capped, because they top out in the low hundreds. | Mark, 2026-09-21 |
| 12 | JEV | **The first JEV pilot is the email pre-filter, in shadow.** JEV's `extract` / `skip` / `unknown` verdict is recorded next to the `cheap_prefilter` LLM stage that `#13149` already runs, and replaces nothing yet. Email is the only deployed writer, the existing pre-filter gives a ready comparison on real threads, and a pre-filter is where the savings are: every thread JEV confidently skips is an extractor call not paid for. Promotion follows the `jev-classifier` skill: labeled examples, a held-out set, and a threshold measured for this surface. The candidate gate (seam B) waits until seam A has results. | Mark, 2026-09-21 |
| 13 | Contact creation | **The user's short bio is linked, not repeated.** The contact creation memory carries the user's WorkOS ID, record ID, entity ID, and name. The short bio lives once, in the user's own identity base memory, and is reached through `user_entity_id`. Repeating it would put the same paragraph in every contact creation memory (2,000 copies after one LinkedIn import), every search about the user would match all of them, and every copy would go stale when the bio is re-enriched. | Mark, 2026-09-21 |
| 14 | Contact creation | **A user's own base memories are created at sign-up, with contact add as the safety net.** They are written when the user's entity is resolved during onboarding, so they exist before the first contact is added. Every contact add also runs the claim-stamp check (decision 3) for the user's entity: one database statement that does nothing when the memories exist, and repairs the case where sign-up seeding failed or the user predates this rule. | Mark, 2026-09-21 |
| 15 | Contact creation | **One contact creation memory per user and contact, ever.** It records the moment the contact came into existence for that user, so it is written exactly once. A contact that turns up again through a second path (imported last month, put into a collection today) does not get another one. If the second event is worth remembering it is its own entry point with its own wording, not a second "added to Orbiter" memory. | Mark, 2026-09-21 |
| 16 | Contact creation | **The contact creation sentence is also the `KNOWS` edge's `origination`.** The same template output is written to the contact creation memory and to `KNOWS.origination` in the same job, so "how do I know Ryan?" reads the same from the graph and from mem0, and graph traversals can show it without a mem0 call. The existing [KNOWS edge](/guides/open-work/edge-sync/knows-edge) docs stay correct. | Mark, 2026-09-21 |
| 17 | User memories | **The inviter is recorded when the invitation names one.** The user created memory carries `invited_by_name` and `invited_by_entity_id`, and the sentence says it: "through an invitation from the organization Maximum Effort, sent by Ryan Reynolds". The source is `organization_invitations.invited_by_user_id`, then that user's `person_id`. The column is empty when the inviter's account was deleted or the invitation was created in the WorkOS dashboard, and then the fields are left out. | Mark, 2026-09-21 |
| 18 | User memories | **One user created memory per user, ever.** It records the moment the user came into existence and how, and that never changes. A user who joins an org later, by accepting an invitation while signed in, gets a separate memory from its own entry point ("joined the organization"), written to the same private scope with the same org and inviter fields. `joined_via` always means how the user first arrived. Same reasoning as decision 15. | Mark, 2026-09-21 |
| 19 | Base memories | **A brand-new entity gets its identity memory at once and its edge memories when the first enrichment package lands.** Adding an entity Universe has never seen creates a shell with no edges while enrichment runs in a worker. The identity memory is written immediately when there is a description to write. The edge memories are written when the entity's first enrichment package is applied, which is the moment the backend's sync worker applies the first projection. That is the one event-driven trigger, first package only. Every later change goes through the nightly Dream State diff (decision 4), which also stays the backstop if the trigger is missed. | Mark, 2026-09-21 |

## Open questions

Staged here with a recommendation each. When one is answered it moves up into the table above.

| # | Area | Question | Recommendation |
| --- | --- | --- | --- |
| Q13 | Mem0 API | **Add response.** The current v3 reference shows `event_id` and `status: PENDING` for an add. The old spec assumed `infer=false` answers synchronously with a memory ID. | **Verify, do not decide.** Send one `infer=false` add to the dev project and record the real response. Send a second add with a negative `timestamp` (a pre-1970 date) to settle the decision 8 cutoff. The refresh diff (Q5) needs memory IDs, so this has to be known before it is built. |
| Q22 | Base memories | **New entities: event trigger, or Dream State?** Decision 19 writes a brand-new entity's edge memories from an event, when its first enrichment package lands. Mark's later note: base memories can be added and updated by the Dream State cron. | **Let Dream State own it, with an hourly sweep for recently added entities.** One owner and no event plumbing: the nightly run stays as it is, and a light hourly pass looks only at entities claimed in the last 48 hours whose edge count is ahead of their memory count. A newly added contact fills in within about an hour of enrichment finishing, instead of up to a day. If accepted, this replaces the trigger in decision 19. |
| Q23 | Dream State | **Supersede, never delete.** When the reconciliation pass retires a private memory, is it deleted or kept? | **Kept and marked.** `status = superseded`, `valid_to`, and `superseded_by` in metadata, with every read filtering on `status = active`. History stays answerable and a bad verdict can be undone. It means every writer stamps `status = active` from the first memory written, because mem0 metadata filters only match keys that are present. Base memories stay the exception: the graph holds their history, so the refresh diff deletes. |
| Q24 | Dream State | **Who makes the reconciliation verdict?** `same`, `supersedes`, `generalize`, `stale`, `unrelated`, `unknown` over a pair of memories. | **JEV for the verdict, code for dates, a generative model only to write a `generalize` memory.** The verdict is a bounded choice over supplied text. Which of two dated facts is newer is arithmetic, which JEV is documented as weak at. Shadow first, with labeled pairs and a held-out set, per the `jev-classifier` skill. |
