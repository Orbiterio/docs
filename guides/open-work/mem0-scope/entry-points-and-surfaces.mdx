This page lists every place a memory is created in Orbiter, one entry point at a time. Email memories are the only writer deployed today ([mem0 Functions](/guides/open-work/mem0/functions), `#13149`), and they can change. Everything else is scoped here from a blank page, starting with the rules that are not up for debate: user memories, base memories, and the contact creation memory.

## How each entry point is documented

| Question | What the section answers |
| --- | --- |
| **When** | The trigger: the event that causes a memory to be written |
| **Where** | The surface in the app, or the background job, where that event happens |
| **How** | The writer and its write policy: always write, or JEV-gated |
| **What** | The memories themselves, with a copy-and-paste example |

## Write policy: when JEV decides

Every entry point declares one write policy. Use JEV wherever the question is "is this worth remembering?" and the answer is a bounded choice over text Orbiter already has.

| Policy | Meaning | Fits |
| --- | --- | --- |
| **Always write** | Deterministic. No classifier, no LLM | System events and base memories. Anything the user explicitly tells Orbiter to keep |
| **JEV-gated** | The source is mostly noise, so a classifier decides what becomes a memory | Streams Orbiter reads on the user's behalf: email, calendar, chat turns, meeting transcripts |

JEV has two possible seats in a gated writer:

| Seam | Decision | Sits where | Labels |
| --- | --- | --- | --- |
| **A. Source pre-filter** | Is this thread, event, or transcript worth running the extractor on? | The `cheap_prefilter` LLM stage that `#13149` runs today | `extract` · `skip` · `unknown` |
| **B. Candidate gate** | Is this extracted candidate worth saving? | After the extractor, before the mem0 write | `save` · `duplicate` · `not_memory` · `unknown` |

Rules carried over from the `jev-classifier` skill and the [Akira JEV pilots](/guides/open-work/roadmap/akira/jev):

- **JEV judges supplied text.** It does not extract facts, write memory text, resolve identity, or compare and calculate dates. Extraction stays with the generative extractor. Dates stay in code.
- **Closed vocabulary with an explicit `unknown`.** `unknown`, low confidence, a malformed answer, or a timeout falls back to the surface's existing path. A failure is never a silent drop and never an automatic save.
- **State is data.** Email bodies, transcripts, and existing memories go in `state`. The instructions tell the model to ignore any instruction found inside them.
- **Shadow first.** Record JEV's verdict next to the current path, then promote on measured results. Thresholds are set per surface from labeled examples. The 0.70, 0.75, and 0.90 values used elsewhere in Orbiter are local settings, not defaults.
- **Validate before acting.** Expected answer keys, `type: choice`, a label from that question's criteria, finite confidence and probabilities.
- **Transport.** `POST https://openrouter.ai/api/alpha/decisions`, model `typesafe/jev-1.13`, server-side only. Reuse the existing clients: backend `internal/clients/openrouter/decisions.go` (`DecisionsClient.Decide`), frontend `jev-classifier.server.ts`.

## 0. User memories

<Note>
  **Set by Mark, 2026-09-21.** Written when a user is created. Always write: no classifier, no LLM. This runs before anything else on this page, because every later memory links back to the user.
</Note>

### The rule

When a user is created, write the user's own memories:

1. **The user's base memories.** A user is a person in Universe with an entity ID, so the user gets base memories by the same rule as [entry point 1](#1-base-memories): one identity memory (entity ID, name, short bio) and one memory per Universe edge. They live in the shared scope, `entity:{user_entity_id}`, like any other person's.
2. **One user created memory.** A private memory that records who the user is inside Orbiter and how the user got here: WorkOS ID, `users.users` record ID, entity ID, name, when the user joined, and whether the user signed up directly or was invited by an org. For an invite it names the org and carries the org's entity ID, which links it to the org's base memories.

An org is a company in Universe. When a user joins through an org's invitation, the same base memory check runs for the org's entity, so `entity:{org_entity_id}` exists for the link to land on.

### How a user joins

| `joined_via` | Sign-up path | How the memory says it | Source fields |
| --- | --- | --- | --- |
| `direct` | The user signs up on their own | "signing up directly" | None |
| `org_invite` | An org invites the user by email, and the user signs up through that invitation | "through an invitation from the organization Maximum Effort" | The `org_` and `invited_` fields in the table below |

### When, where, and how

| | |
| --- | --- |
| **When** | When the user's entity ID is stamped, which is after sign-up. See the finding below. The user's edge memories follow when the first enrichment package lands ([decision 19](/guides/open-work/mem0-scope/decisions)). Every contact add re-runs the base memory check for the user's entity as a safety net ([decision 14](/guides/open-work/mem0-scope/decisions)) |
| **Where** | Sign-up and onboarding, by either path. No surface the user sees |
| **How** | A background job. Always write. Base memories use the entry point 1 writer unchanged, for the user and for an inviting org |
| **Writes to** | Base memories: `entity:{user_entity_id}`, shared. User created memory: `user_id = {user WorkOS ID}`, private |
| **Links** | `user_entity_id` to the user's base memories. `org_entity_id` to the inviting org's base memories, when there is one |

Account identifiers stay out of the shared scope. The WorkOS ID, the `users.users` record ID, and the org record ID are written only to the private user created memory. The shared identity memory carries the entity ID alone, because anyone who has this person as a contact reads that scope.

### The org invite flow, as built

Traced on 2026-09-21 through `orbiter-frontend` (`src/routes/invite.tsx`, `accept-invitation.tsx`) and `orbiter-backend` on `main` (`users/service_auth.go`, `users/workos_invited.go`, `organizations/service_invitation_webhooks.go`).

<Steps>
  <Step title="An org member sends the invitation">
    The backend writes an `organizations.organization_invitations` row: `organization_id`, `email`, `role`, `status = pending`, `invited_by_user_id`. WorkOS sends the email and mints a user shell with no password, plus a pending membership.
  </Step>
  <Step title="The invitee opens the link">
    The email lands on `/invite?invitation_token=…`. A signed-out invitee is sent to sign-up, and the token survives the detour in session storage.
  </Step>
  <Step title="Sign-up claims the shell">
    `SignUp` sees the token, checks that the invitation is pending and was issued to the same email, and claims the WorkOS shell instead of creating a user (`createOrClaimUser`). It then writes the `users.users` row: a new `id`, the `workos_id`, and `onboarding_status = account_verification_required`.
  </Step>
  <Step title="Authenticating accepts the invitation">
    Sign-up authenticates with the token, which is what turns the pending membership active in WorkOS. Every invited user has two orgs, a personal one and the inviting one, so sign-in finishes through the select-organization step.
  </Step>
  <Step title="Webhooks settle the local rows">
    `invitation.accepted` sets `status = accepted`, `accepted_at`, and `accepted_user_id` on the invitation row. `organization_membership.created` writes the `organization_memberships` row.
  </Step>
  <Step title="Account verification stamps the entity ID">
    After the user passes account verification, `CompletePersonSetup` resolves the user to a person and stamps `users.users.person_id`. This is the first moment all three user IDs exist.
  </Step>
</Steps>

<Warning>
  **Three findings that shape this entry point.**

  1. **The user's entity ID does not exist at sign-up.** Every new user starts at `account_verification_required`, and `person_id` is stamped later by `CompletePersonSetup`. That call is the trigger for this entry point, not the creation of the `users.users` row. `joined_at` still comes from `users.users.created_at`.
  2. **How the user joined is not stored on the user.** Nothing on `users.users` says direct or invited. It is derived: an accepted `organization_invitations` row whose `accepted_user_id` is this user means `org_invite`, and no such row means `direct`. The webhook can arrive before the local user row exists, which leaves `accepted_user_id` empty, so the writer falls back to matching the invitation on the user's email.
  3. **An org does not always have an entity.** `organizations.organizations.company_id` is the org's company entity ID, and it can be empty. Then the memory still names the org, but there is no `org_entity_id` and no link.
</Warning>

### What each field gets

| Memory field | Direct sign-up | Org invite | Source in the backend |
| --- | --- | --- | --- |
| `user_id` (the scope) and `workos_id` | The WorkOS user created at sign-up | The WorkOS shell minted at invite time, claimed at sign-up | `users.users.workos_id` |
| `user_record_id` | Set | Set | `users.users.id` |
| `user_entity_id` | Set | Set | `users.users.person_id`, stamped by `CompletePersonSetup` |
| `user_name` | Set | Set | First and last name from the sign-up form |
| `joined_at` and mem0 `timestamp` | Set | Set | `users.users.created_at` |
| `joined_via` | `direct` | `org_invite` | Derived from `organization_invitations` (finding 2) |
| `org_record_id` | Absent | Set | `organization_invitations.organization_id` |
| `org_name` | Absent | Set | `organizations.organizations.name` |
| `org_entity_id` | Absent | Set when the org has one | `organizations.organizations.company_id` |
| `org_role` | Absent | `owner`, `admin`, or `member` | `organization_invitations.role` |
| `invited_at` | Absent | Set | `organization_invitations.created_at` |
| `invitation_accepted_at` | Absent | Set | `organization_invitations.accepted_at` |
| `invited_by_name`, `invited_by_entity_id` | Absent | Set when the inviter is known ([decision 17](/guides/open-work/mem0-scope/decisions)) | `organization_invitations.invited_by_user_id`, then that user's `person_id` |

The user's personal org (`is_personal = true`) never appears in these fields. Every user has one, and it says nothing about how the user arrived.

## 1. Base memories

<Note>
  **Non-negotiable (Mark, 2026-09-21).** Every entity in any user's contacts has base memories. This entry point is not gated by a classifier and is not optional per surface.
</Note>

### The rule

When a person or company is added to a user's contacts by entity ID, check whether that entity ID has any memories yet. If it has none, create its base memories from Universe enrichment data:

1. **One identity memory.** Entity ID, name, and the short bio (person) or description (company).
2. **One memory per Universe edge.** The edge `description`, plus every temporal or date property the edge carries.

A person takes every one-hop edge. A company takes every edge that starts at the company, plus inbound edges from a short allow-list: `FOUNDED`, `INVESTED_IN`, `BOARD_MEMBER_OF`, `ADVISOR_TO`, `INVESTMENT_PARTNER_AT`, `OFFICER_OF`, and `WORKS_AT` where the seniority is `founder`, `c_suite`, or `president`. A company's investment edges are capped at the 50 most recent per edge type. The reasons are decisions 2, 10, and 11 on [Mem0 Decisions](/guides/open-work/mem0-scope/decisions).

Base memories are created once per entity, not once per user. The second user who adds Ryan Reynolds finds his base memories already there and creates nothing.

### When, where, and how

| | |
| --- | --- |
| **When** | A contact is created or attached with a resolved entity ID, and that entity has no base memories yet |
| **Where** | Every path that puts an entity in a user's contacts: Add Contact, LinkedIn import, vCard and Nylas contact imports, contacts discovered from email and calendar history, Orbiter connect. Confirm this list when the add paths are walked through |
| **How** | A background job, off the add-contact request, so adding a contact stays fast. Always write: no classifier, no LLM |
| **Reads** | Universe only: the entity's enrichment record and its one-hop edges. Never user data, never user-graph edges such as `KNOWS` |
| **Writes to** | The entity's shared scope in mem0, `user_id = "entity:{entity_id}"`. A user's private memories about the same contact live in that user's own scope and never in this one |

<Steps>
  <Step title="Contact added">
    The add path resolves the entity ID and enqueues a base-memory job for it.
  </Step>
  <Step title="Claim the entity">
    One atomic statement on the entity's row. One row affected means this worker writes the base memories. Zero rows means they exist or another worker has claimed them: stop, without calling mem0.

    ```sql
    UPDATE persons.persons
    SET    base_memories_at = now()
    WHERE  id = '0a499029-8797-4511-9a43-424f5a600c2e'
      AND  base_memories_at IS NULL;
    ```

    The mem0 read below is the repair check, not the gate. Dream State uses it to find a claimed entity whose memories never finished writing.

    ```json
    POST https://api.mem0.ai/v3/memories/?page=1&page_size=1
    Authorization: Token {MEM0_API_KEY}

    {
      "filters": { "user_id": "entity:0a499029-8797-4511-9a43-424f5a600c2e" }
    }
    ```
  </Step>
  <Step title="Write the identity memory">
    Entity ID, name, short bio or description, from the enrichment record.
  </Step>
  <Step title="Write one memory per edge">
    Read the entity's one-hop Universe edges. For each edge that has a `description`, write one memory: the description plus the edge's temporal data. Edges without a description are skipped.

    An entity Universe has never seen has no edges yet, because enrichment is still running in a worker. For that entity this step runs when its first enrichment package is applied, not at add time ([decision 19](/guides/open-work/mem0-scope/decisions)).
  </Step>
</Steps>

### The Cypher read

Every base memory comes from one read-only Cypher call against the Universe graph: the entity, and its one-hop edges that have a `description`. The identity memory uses the node's own fields (`name`, plus `short_biography` for a person or `description` for a company). The reads below document the original local snapshot taken on 2026-09-21 with `GRAPH.RO_QUERY`, which rejects writes. They are not a replay of the revised descriptions. The formatter contract now also requires the typed fields listed below; expand the consumer projection before implementing it.

<CodeGroup>
```cypher Person
CYPHER id='0a499029-8797-4511-9a43-424f5a600c2e'
MATCH (p:Person) WHERE p.entity_id = $id
OPTIONAL MATCH (p)-[r]-(x)
WHERE r.description IS NOT NULL
RETURN toJSON({
  entity_id: p.entity_id, name: p.name,
  edge_type: type(r), outbound: ID(startNode(r)) = ID(p), edge_uuid: r.uuid,
  description: replace(r.description, '\n', ' '),
  valid_from: r.valid_from, valid_to: r.valid_to, year: r.year, announced_date: r.announced_date,
  title: r.title,
  other_name: x.name, other_entity_id: x.entity_id, other_labels: labels(x)
}) AS row
ORDER BY type(r), r.valid_from DESC
```

```cypher Company
CYPHER d='parallel.ai'
       lead=['founder','c_suite','president']
       inbound=['FOUNDED','INVESTED_IN','BOARD_MEMBER_OF','ADVISOR_TO','INVESTMENT_PARTNER_AT','OFFICER_OF']
MATCH (c:Company) WHERE c.company_domain = $d
OPTIONAL MATCH (c)-[r]-(x)
WHERE r.description IS NOT NULL
  AND ( ID(startNode(r)) = ID(c)
        OR type(r) IN $inbound
        OR (type(r) = 'WORKS_AT' AND r.seniority_level IN $lead) )
RETURN toJSON({
  entity_id: c.entity_id, name: c.name, company_domain: c.company_domain,
  company_description: replace(c.description, '\n', ' '),
  edge_type: type(r), outbound: ID(startNode(r)) = ID(c), edge_uuid: r.uuid,
  description: replace(r.description, '\n', ' '),
  valid_from: r.valid_from, valid_to: r.valid_to, year: r.year, announced_date: r.announced_date,
  title: r.title, seniority: r.seniority_level,
  other_name: x.name, other_entity_id: x.entity_id, other_labels: labels(x)
}) AS row
ORDER BY type(r), r.valid_from DESC
```
</CodeGroup>

- **Do not trust `toJSON` with free text.** FalkorDB's `toJSON` does not escape double quotes inside a string. Frame.io's Series C description contains "camera to cloud", which broke the row. The writer should return plain columns and let its client library decode them. The reads above are shown with `toJSON` for readability only.
- **The company read is decision 2 and decision 10 in code.** Every outbound edge, inbound edges from the allow-list, and `WORKS_AT` only for `founder`, `c_suite`, and `president`. The investment cap of 50 (decision 11) is applied by the writer after the read.
- **Preserve typed dates and evidence.** The revised projection must also carry `release_year`, `acquired_date`, `date_basis`, `date_precision`, roles, amounts, currency and description provenance where available. Role intervals, release years, award years, funding announcements and acquisition closing dates have different meanings; see [the formatter contract](#how-the-memory-text-is-built).
- **Checked on real companies.** Figma returns 17 edges: 7 `RAISED`, 5 `SPECIALIZES_IN`, 1 inbound `FOUNDED`, and 4 inbound leadership `WORKS_AT`. With the identity memory, that snapshot yields 18 candidates; it is not proof of a Mem0 write.

### How the memory text is built

The shared LLM writer owns the edge description upstream. The base-memory writer remains a deterministic formatter, with no additional model call or JEV admission gate:

1. Start with the accepted edge `description`; trim and collapse whitespace. The verified examples above already contain their supported roles and dates.
2. Preserve the edge's date meaning and precision. Never use an award date as a film's release date, or an employment departure as a founding end date.
3. Add a temporal clause only when it contributes a supported date not already expressed at the same precision and with the same meaning. Matching a year alone is insufficient: “2014” does not express “February 2014”. Do not append a second copy of a date already in the description.
4. Carry the original date and supporting fields as metadata, including `valid_from`, `valid_to`, `year`, `release_year`, `announced_date`, `acquired_date`, `date_basis`, `date_precision`, `is_current`, roles, amounts and currency where present. Preserve edge identity and description provenance; absent values stay absent.
5. Backdate event-like memories only when a supported date is available and is 1970 or later. For year/month precision, the draft `timestamp` examples use the start of that period in UTC; the original value remains in metadata. A normalized timestamp is not evidence of an exact day. Evergreen specialties and undated investments get no invented event timestamp.
6. Keep one memory per accepted edge. Make retries idempotent by canonical source/edge identity, never by prose alone. Separate awards can legitimately have similar descriptions.

| Relationship | Date contract |
| --- | --- |
| `WORKED_ON` | `release_year` / `year`, with `date_basis: title_release_year`; no award-derived interval |
| `WON_AWARD` / `NOMINATED_FOR` | The award event's own year; preserve ceremony, category, title and outcome identity |
| `FOUNDED` | Supported founding start at its source precision; no employment end date |
| `WORKS_AT` / `WORKED_AT` / `ATTENDED` | Supported start/end dates and current status; do not collapse a month/date interval to a bare year |
| `RAISED` | `announced_date`; retain round, amount, lead and participants |
| `ACQUIRED_BY` | `acquired_date`, `date_basis`, `date_precision`, amount and currency; distinguish announcement from closing |
| Unknown or evergreen | No invented date; retain the accepted relationship |

## 2. Contact creation memory

<Note>
  **Set by Mark, 2026-09-21.** Written any time a user adds a contact. Always write: no classifier, no LLM.
</Note>

### The rule

Any time a user adds a contact, write one memory that records the event: who added whom, when, and how. It is the first private memory in that user's relationship with the contact, and it links to the base memories of both sides, the contact's and the user's own.

The user is an entity too. A user has an entity ID in Universe like any other person, so the user has base memories under `entity:{user_entity_id}`, created at sign-up by [entry point 0](#0-user-memories). Adding a contact therefore makes sure two sets of base memories exist: the contact's and the user's.

### What it carries

| Field | Where it lives | Notes |
| --- | --- | --- |
| User's WorkOS ID | `user_id` (the private scope) and `metadata.workos_id` | The privacy boundary, as in the live email writer |
| User's record ID | `metadata.user_record_id` | The `users.users` row ID |
| User's entity ID | `metadata.user_entity_id` | The link to the user's base memories, `entity:{user_entity_id}` |
| User's name | Memory text and `metadata.user_name` | |
| User's short bio | The user's identity base memory, reached through `user_entity_id` | Linked, not repeated in every contact creation memory. Staged as a question on [Mem0 Decisions](/guides/open-work/mem0-scope/decisions#open-questions) |
| Contact's entity ID | `metadata.contact_entity_id` | The link to the contact's base memories, `entity:{contact_entity_id}` |
| Contact's name and type | Memory text, `metadata.contact_name`, `metadata.contact_entity_type` | Person or company |
| Contact added to Orbiter timestamp | Memory text, `metadata.added_at`, and mem0's `timestamp` | When the contact was created for this user |
| How it was added | Memory text in natural language, `metadata.added_via`, and the source fields below | |

### How a contact gets added

Every add path writes the same memory. Only the "how" sentence and its source fields change. The sentence names the contact instead of using a pronoun, because a contact's pronouns are not known.

| `added_via` | Add path | How the memory says it | Source fields |
| --- | --- | --- | --- |
| `manual` | The user adds the person or company by hand in the app | "manually in the app" | None |
| `import` | An import: LinkedIn, vCard, Nylas contacts | 'through the LinkedIn import "Connections.csv", run on 2026-09-21' | `import_type`, `import_name`, `import_date` |
| `email_history` | Found in the user's historical email | "Orbiter found Ryan Reynolds in Mark Pederson's past email, where their first exchange was on 2024-03-11" | `first_seen_at` |
| `calendar_history` | Found in the user's historical calendar events | The same sentence, with the first meeting date | `first_seen_at` |
| `email_webhook` | A new email arrives from or to someone who is not yet a contact | "when a new email with Ryan Reynolds arrived" | `source_date` |
| `calendar_webhook` | A new calendar event includes someone who is not yet a contact | 'when the calendar event "Wrexham sponsorship sync" on 2026-09-24 included Ryan Reynolds' | `source_title`, `source_date` |
| `collection` | The user puts a person or company into a collection | 'by putting Ryan Reynolds into the collection "Sports team owners"' | `collection_id`, `collection_name` |

### When, where, and how

| | |
| --- | --- |
| **When** | A contact is created for a user, person or company. Once per user and contact pair |
| **Where** | Every add path in the table above. A bulk import writes one memory per contact it creates |
| **How** | The same background job as base memories. Always write. The text comes from a template per `added_via`, not from a model |
| **Writes to** | The user's private scope, `user_id = {user WorkOS ID}`. Never the shared `entity:` scope: who added whom is private to that user |
| **Links** | `contact_entity_id` and `user_entity_id`. Both are entity IDs, so this memory does not wait for either set of base memories to be written first |
